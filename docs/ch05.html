옵션과 세트: 변형이 폭발하는 메뉴

4장까지 만든 v3은 "주문 한 건에 메뉴가 몇 개"를 잘 담았습니다. 그런데 동백커피는 손님이 메뉴에 덧붙이는 주문과 묶음 상품을 팔기 시작합니다. 이 장은 교재에서 처음으로 새 요구사항이 들어와 기존 설계를 깨는 장입니다. 4장이 "곧 깨질 것"이라고 예고한 C3이 실제로 깨지고, 2장이 '가정 3'으로 표시하고 4장이 D3로 적어 둔 빚을 갚습니다. 끝에서 스키마는 v4가 됩니다.

서연

키오스크를 열어 보니 손님 절반이 메뉴에 한마디씩 붙여요. "샷 추가요", "시럽 빼 주세요", "얼음 적게요", "휘핑크림 올려 주세요", "우유 추가요." 샷이랑 휘핑이랑 우유는 500원씩 받고, 시럽 빼기랑 얼음 적게는 돈을 안 받아요. 얼음 많이도 있는데 이것도 안 받고요.

지호

메뉴마다 다르기도 해요. 아메리카노에는 우유 추가가 없고, 휘핑은 카페라떼에만 올려요. 치즈케이크에는 붙일 게 아무것도 없고요. 그리고 어제 한 주문에 카페라떼 두 잔이 들어왔는데, 한 잔은 샷을 두 번 넣고 한 잔은 그냥 달라고 했어요. 같은 라떼인데 주문서에 라인을 둘로 적어야 하더라고요.

서연

아, 그리고 음료랑 케이크를 묶은 세트도 팔고 싶어요. 음료 하나에 케이크 하나, 케이크는 치즈케이크나 티라미수 중에 고르게요. 세트 가격은 따로 정할게요.

이번 요구를 문장으로 고치면

  1. 메뉴에는 손님이 덧붙이거나 바꾸는 선택지가 붙는다(샷 추가, 시럽 빼기, 얼음 적게·많이, 휘핑크림, 우유 추가).
  2. 선택지마다 가격이 있고, 0원인 것도 있다.
  3. 메뉴마다 고를 수 있는 선택지가 다르다.
  4. 같은 메뉴라도 선택지가 다르면 주문에서 다른 라인이다.
  5. 음료와 케이크를 묶은 세트가 있다. 자리(음료 1, 케이크 1)마다 고를 수 있는 후보가 정해져 있고, 세트에는 세트 가격이 따로 있다.

이 장의 진행

  1. 페이지 2 — 카페 업무 용어(샷, 시럽, 세트 구성)부터 정리합니다. 코드는 그 뒤입니다.
  2. 페이지 3~4 — 손이 먼저 가는 두 해법(열 늘리기, 글자로 적기)이 왜 실패하는지 봅니다.
  3. 페이지 5~7 — 옵션 모델, 주문 라인 개편(D3), 선택 개수 규칙(C9).
  4. 페이지 8~9 — 세트 모델(C10). 페이지 10~11은 선택 페이지입니다(분류 트리, EAV).
  5. 페이지 12~13 — 스키마 v4 정리, 요약·퀴즈·직접 해보기.

한 가지는 이 장의 범위 밖입니다. 옵션 가격이나 메뉴 가격이 오르면 과거 주문 금액이 바뀌는 문제(D1)는 이 장에서도 그대로 남고 6장에서 다룹니다.

샷 추가는 "같은 아메리카노인데 샷이 더 들어간" 것이지 다른 메뉴가 아닙니다. 매출을 "아메리카노가 몇 잔 나갔나"로 셀 때 샷 추가 잔도 아메리카노입니다. 반면 세트는 메뉴 둘을 하나의 가격으로 묶은 상품입니다. 이 차이가 이 장의 모델을 가릅니다.

이름 붙이기

  • 옵션 — 손님이 메뉴에 덧붙이거나 바꾸는 선택지 하나(샷 추가, 얼음 적게). 메뉴를 바꾸지만 다른 메뉴로 만들지는 않습니다. 가격이 붙고, 0원일 수도 있습니다.
  • 옵션 그룹 — 같은 종류의 옵션을 모은 묶음(샷, 시럽, 얼음). 그룹마다 고를 수 있는 개수의 범위(최소~최대)가 있습니다. 얼음 그룹은 0~1이라 "적게"와 "많이"를 함께 고를 수 없습니다.
  • 세트 — 여러 메뉴를 묶어 하나의 가격으로 파는 상품. 옵션이 메뉴를 바꾼다면 세트는 메뉴를 묶는다.
  • 구성 슬롯 — 세트 안에서 채워야 하는 자리(음료 1, 디저트 1). 슬롯마다 들어갈 수 있는 후보 메뉴가 정해져 있습니다.

문제왜 생기는가
새 옵션마다 ALTER TABLE옵션이 늘 때마다 표의 구조를 바꿔야 합니다. 옵션 하나 추가가 배포가 됩니다(운영 중 구조 변경의 위험은 9장).
칸 대부분이 NULL치즈케이크 라인에도 휘핑 열이 있습니다. 그 NULL이 "해당 없음"인지 "안 했음"인지 "모름"인지 구별되지 않습니다(4장 NULL 페이지).
가격을 둘 곳이 없다옵션의 가격은 열 값이 아니라 열 자체의 속성입니다. 가격 열을 또 6개 더하거나 앱 코드에 상수로 박아야 합니다.
"메뉴마다 다르다"를 못 담는다모든 라인이 같은 열을 가지므로 "이 메뉴에서는 이 옵션이 안 된다"를 구조로 표현할 수 없습니다. 앱 코드가 떠안습니다.
옵션별 판매량"어느 옵션이 제일 많이 나갔나"를 옵션 6개의 열을 UNION(조회 결과를 위아래로 이어 붙이는 문법)으로 이어 붙여 세야 합니다.
D3은 그대로기본키 (order_id, menu_id)가 남아 있으니 같은 메뉴 두 라인은 여전히 안 됩니다.

두 시도의 공통점

둘 다 "종류가 늘어나는 것"을 구조(열)나 조합(행)에 새겨 넣었습니다. 종류는 계속 늘어나는 것이니 데이터(행)로 다뤄야 하고, "옵션이 무엇이 있는가"는 표 하나에 있어야 합니다. 그렇다고 한 칸에 옵션 목록을 적으면 될까요? 다음 페이지가 그 시도입니다.

-- 글자 칸에 대한 집계SELECT COUNT(*) FROM order_line WHERE options LIKE '%샷 추가%';   -- 3
SELECT COUNT(*) FROM order_line WHERE options LIKE '%얼음 적게%';  -- 2
SELECT COUNT(*) FROM order_line WHERE options LIKE '%샷%';         -- 4
  • LIKE는 글자가 패턴과 맞는지 묻는 연산자이고, %는 "아무 글자가 몇 개든"입니다. '%샷 추가%'는 "샷 추가"라는 글자가 어딘가에 들어 있는 값입니다.
  • 1행은 4가 아니라 3입니다. 301의 '샷추가x2'는 띄어쓰기가 달라서 패턴에 안 걸립니다. 2행도 304의 '얼음적게' 때문에 3이어야 할 값이 2입니다.
  • 3행은 4로 맞지만 옵션 이름에 '샷'이 들어간 다른 옵션(예: '더블샷 변경')이 생기는 순간 틀립니다. 패턴을 넓히면 오탐이 생기고 좁히면 누락이 생깁니다.
문제이유
1NF 위반한 칸에 값이 여럿입니다. 3장 1NF에서 본 "아메리카노 2, 치즈케이크 1"을 한 칸에 적은 메뉴 목록과 같은 모양이고, 같은 병이 납니다.
집계가 부정확하다위의 LIKE 결과처럼 DB가 "샷 추가"를 값으로 모르고 글자로만 봅니다. 조인도 GROUP BY도 못 씁니다.
표기 흔들림을 못 막는다'샷추가', '샷 추가', 'x2', '×2'가 다 들어갑니다. 글자 열의 표기 문제는 1장과 4장에서 본 그대로인데, CHECK로도 "이 목록의 이름만"을 표현할 수 없습니다.
가격을 못 계산한다옵션의 가격이 어디에도 없습니다. 글자를 쪼개 이름으로 가격표를 찾는 일이 앱의 몫이 됩니다. 옵션 이름을 바꾸면 모든 라인의 글자를 고쳐야 합니다(갱신 이상).
외래키를 걸 수 없다"없는 옵션은 못 고른다"(C5와 같은 규칙)를 선언할 수단이 없습니다. '샷 삼추가'도 저장됩니다.
C3이 더 애매해진다'샷 추가, 얼음 적게'와 '얼음 적게, 샷 추가'는 같은 조합인데 글자로는 다른 값입니다. 같은 조합 두 라인을 막지 못합니다.
더 깊이 — PostgreSQL 배열이나 JSONB에 넣으면 되지 않나

PostgreSQL에는 배열 타입(TEXT[])과 JSON 타입(JSONB)이 있어서 "목록을 한 칸에" 담는 것이 타입으로는 가능해집니다. 글자 조각을 LIKE로 긁는 것보다 낫고 인덱스도 걸 수 있습니다. 그러나 배열의 각 원소에는 외래키를 걸 수 없고, 옵션 가격 같은 속성을 원소에 붙일 자리가 없으며, 옵션별 집계는 여전히 풀어헤쳐야(UNNEST 등) 합니다. "옵션 이름이 오타인지 DB가 모른다"는 문제는 그대로입니다. 옵션이 자기만의 사실(가격, 그룹)을 가진 대상이면 엔터티이고, 엔터티는 표(행)로 두라는 것이 2장의 결론이었습니다.

이 모양은 Bill Karwin의 『SQL Antipatterns』가 Jaywalking이라 부르는 전형입니다(쉼표로 이은 목록을 한 칸에 저장).

그래서 결론은

옵션은 칸(열)에도, 글자에도, 메뉴 이름에도 넣지 않고 자기 표의 행으로 둡니다. 그리고 주문 라인에 붙는 옵션 여러 개는 별도 표의 여러 행으로 표현합니다. 다음 페이지부터 그 표를 만듭니다.

5장 · 페이지 5

옵션 그룹 · 옵션 · 메뉴-옵션그룹 — 구조부터

2장의 방법 그대로 요구사항의 동사에서 관계를 뽑습니다.

  • "그룹에는 옵션이 여럿 있다" → 옵션 그룹 1 : 옵션 N. 샷 그룹에 샷 추가, 얼음 그룹에 얼음 적게·얼음 많이.
  • "메뉴는 여러 그룹을 고를 수 있다, 그룹은 여러 메뉴에 쓰인다" → 메뉴 N : 옵션 그룹 M. 샷 그룹은 아메리카노에도 카페라떼에도 쓰입니다. N:M이니 2장처럼 연결 테이블이 필요합니다.

그림으로 그리고 각 표의 한 행이 무엇을 뜻하는지 정한 뒤에 코드를 봅니다.

표한 행이 뜻하는 것이 표만 가진 사실
option_group옵션 종류 하나(샷, 시럽, 얼음 …)고를 수 있는 개수의 범위(min_select~max_select). 범위는 그룹 전체의 성질이라 옵션이 아니라 그룹에 있다
option_item고를 수 있는 옵션 한 가지가격. 그룹에 속한다(group_id)
menu_option_group"이 메뉴에서 이 그룹을 고를 수 있다"는 사실 하나없음(연결 자체가 사실이다)
-- 스키마 v4 ①: 옵션 모델 (새 표 셋)-- 옵션 그룹 한 종류 (샷, 시럽, 얼음 ...)와 고를 수 있는 개수 범위
CREATE TABLE option_group (
    group_id    INTEGER PRIMARY KEY,
    name        TEXT    NOT NULL UNIQUE
                CHECK (name <> '' AND name = btrim(name)),
    min_select  INTEGER NOT NULL DEFAULT 0 CHECK (min_select >= 0),
    max_select  INTEGER NOT NULL CHECK (max_select >= 1),
    CHECK (max_select >= min_select)
);

-- 옵션 한 가지 (샷 추가, 얼음 적게 ...)와 그 가격. 0원 옵션은 0 으로 적는다
CREATE TABLE option_item (
    option_id  INTEGER PRIMARY KEY,
    group_id   INTEGER NOT NULL REFERENCES option_group (group_id),
    name       TEXT    NOT NULL
               CHECK (name <> '' AND name = btrim(name)),
    price      INTEGER NOT NULL CHECK (price >= 0),
    is_active  BOOLEAN NOT NULL DEFAULT TRUE,
    UNIQUE (group_id, name)
);

-- 이 메뉴에서 이 옵션 그룹을 고를 수 있다 (메뉴와 옵션 그룹의 N:M 연결)
CREATE TABLE menu_option_group (
    menu_id   INTEGER NOT NULL REFERENCES menu (menu_id),
    group_id  INTEGER NOT NULL REFERENCES option_group (group_id),
    PRIMARY KEY (menu_id, group_id)
);
  1. 2~9행 option_group. 4~5행의 name은 4장 menu.name과 같은 규칙(겹침 금지, 빈 글자·끝 공백 금지)입니다.
  2. 6~8행 개수 범위. 6행 min_select의 기본값 0은 "안 골라도 된다"이고, 7행 max_select >= 1은 고를 수 없는 그룹을 막습니다. 8행의 CHECK는 열 하나가 아니라 한 행의 두 열을 비교하는 표 수준 제약입니다(4장: CHECK는 한 행의 열은 자유롭게 볼 수 있다). 최소가 최대보다 큰 그룹을 DB가 거부합니다.
  3. 12~20행 option_item. 14행 group_id가 그룹을 가리키는 외래키(1:N의 N쪽), 17행이 가격입니다.
  4. 17행 price INTEGER NOT NULL CHECK (price >= 0) — 0을 허용하고 NULL은 허용하지 않습니다. 아래에서 이유를 설명합니다.
  5. 18행 is_active는 4장의 판매중지 플래그와 같은 역할입니다. 옵션도 지우지 않고 내립니다(페이지 6의 RESTRICT와 짝).
  6. 19행 UNIQUE (group_id, name)은 열 두 개를 묶은 유일성입니다. 같은 그룹 안에서만 이름이 겹치지 않으면 되고, 다른 그룹에 같은 이름이 있어도 됩니다.
  7. 23~27행 연결 테이블. 26행 기본키가 (menu_id, group_id)라서 같은 연결을 두 번 적을 수 없습니다(2장의 order_line과 같은 모양: 기본키 (order_id, menu_id)가 두 외래키의 조합).

0원 옵션은 0으로 저장합니다 — NULL이 아닙니다

4장 페이지 2가 남긴 약속을 갚습니다. 얼음 적게의 가격은 "공짜라는 사실"입니다. 이것을 NULL로 저장하면 "가격을 모른다"와 구별되지 않습니다.

-- 가정: 얼음 적게의 가격을 0 대신 NULL 로 저장했다면 (옵션이 두 개뿐이라고 하자)SELECT name, 5000 + price AS latte_price FROM option_item;
--   샷 추가     5500
--   얼음 적게   NULL     <- 공짜인지 가격을 모르는 것인지 알 수 없다

이 모델의 비용과 반대 의견

메뉴 세 개에 옵션 여섯 개뿐인 동백커피에는 표 셋이 과해 보일 수 있습니다. 조회할 때마다 조인이 둘 늘고, 옵션 하나를 추가하려고 INSERT 두세 번을 합니다. 옵션 그룹 없이 메뉴-옵션만 연결하는 더 단순한 모델(menu_option)도 가능합니다. 다만 그러면 "샷은 0~3번"이라는 그룹 전체의 규칙을 둘 곳이 없어서 옵션마다 같은 범위를 복사해 두게 되고, 이것이 같은 사실을 여러 곳에 적는 중복입니다. 표 수를 줄이는 것과 중복을 줄이는 것 중 이 교재는 후자를 택했습니다.

5장 · 페이지 6

주문 라인의 옵션 저장과 라인 기본키 개편 — D3을 갚는다

갚는 빚

2장 페이지 12가 "가정 3 — 한 주문에서 같은 메뉴는 한 라인이다"에 "5장에서 다시 본다"는 표시를 남겼고, 4장 페이지 10이 그 가정을 빚 D3로, C3을 "DB(5장에서 깨짐)"로 적었습니다. 이 페이지가 그 D3을 갚고 C3을 다시 정의합니다.

주문 라인은 이제 "카페라떼 한 잔 + 샷 추가 2번 + 얼음 적게"처럼 메뉴 하나에 옵션 여러 개가 붙는 것입니다. 옵션 여러 개는 별도 표의 여러 행이어야 하는데(페이지 4의 결론), 그 행들이 "어느 라인의 옵션인가"를 가리키려면 라인 하나를 가리킬 수 있는 키가 필요합니다. 그런데 v3의 라인 식별자 (order_id, menu_id)는 같은 메뉴 두 라인을 구별하지 못합니다. 후보는 셋입니다.

방법장점약점
키에 옵션을 넣는다
(order_id, menu_id, 옵션)		기존 모양을 유지옵션은 여러 행이라 열 하나로 키에 넣을 수 없다. 글자로 합치면 페이지 4의 문제가 그대로 돌아온다
라인 번호
(order_id, line_no)		주문서의 "몇 번째 라인"이라는 업무 의미가 있다. 이전이 쉽다(페이지 12)자식 표의 외래키가 열 두 개가 된다. 번호는 앱이 1부터 매긴다
대리키
line_id		자식 표의 외래키가 한 열. DB가 번호를 매긴다번호에 의미가 없다. 자식 표에서 그 라인이 어느 주문 소속인지 알려면 order_line을 조인해야 하고, 한 주문 안에서 번호가 1, 2, 3으로 이어지지 않는다

이 교재는 라인 번호를 택합니다. 이유는 업무 의미가 있고, 이미 자식 표들이 order_id를 들고 다니기 때문에 조인 경로가 눈에 잘 보이며, 기존 데이터에 번호만 붙이면 끝나기 때문입니다. 대리키가 틀린 답은 아닙니다. 2장의 자연키 대 대리키 논쟁이 여기서 한 번 더 일어나는 것이고, 접힌 상자에서 대리키 문법을 봅니다.

CREATE TABLE order_line (
    order_id  INTEGER NOT NULL REFERENCES orders (order_id),
    line_no   INTEGER NOT NULL CHECK (line_no >= 1),
    menu_id   INTEGER NOT NULL REFERENCES menu (menu_id) ON DELETE RESTRICT,
    quantity  INTEGER NOT NULL CHECK (quantity >= 1),
    PRIMARY KEY (order_id, line_no)
);

-- 라인에 붙은 옵션 한 가지와 그 횟수 (같은 옵션은 한 라인에 한 번만 적는다)
CREATE TABLE order_line_option (
    order_id    INTEGER NOT NULL,
    line_no     INTEGER NOT NULL,
    option_id   INTEGER NOT NULL REFERENCES option_item (option_id) ON DELETE RESTRICT,
    option_qty  INTEGER NOT NULL DEFAULT 1 CHECK (option_qty >= 1),
    PRIMARY KEY (order_id, line_no, option_id),
    FOREIGN KEY (order_id, line_no) REFERENCES order_line (order_id, line_no)
);

  2. 7행 기본키가 (order_id, menu_id)에서 (order_id, line_no)로 바뀐 것이 D3의 상환입니다. menu_id는 이제 키가 아니라 일반 열이라 같은 메뉴가 여러 라인에 나올 수 있습니다.
  3. 11~18행 order_line_option — 한 행은 "이 라인에 이 옵션을 이만큼". 옵션이 여럿이면 행이 여럿입니다.
  4. 12~13행 라인을 가리키는 order_id, line_no는 열 옆에 REFERENCES를 쓰지 않습니다. 열 둘을 한 덩어리로 가리켜야 해서 17행에서 따로 선언합니다.
  5. 14행 옵션 외래키도 5행의 메뉴 외래키처럼 ON DELETE RESTRICT를 명시합니다. 주문이 가리키는 옵션을 지울 수 없게 하는 C6의 확장입니다(지우고 싶으면 is_active로 내립니다).
  6. 15행 option_qty는 그 옵션을 몇 번 했는가입니다. 샷 추가 2번이 두 행이 아니라 한 행, 횟수 2입니다. 라인의 quantity(잔 수)와 다른 열입니다.
  7. 16행 기본키 (order_id, line_no, option_id) — 같은 옵션은 한 라인에 한 행만 들어갑니다. "같은 것은 합친다"는 C3의 정신이 옵션 안에서는 여전히 DB가 지킵니다.

line_no는 주문 라인 배열의 인덱스(lines[0], lines[1])와 닮았습니다. 다만 배열은 중간 원소를 지우면 뒤가 앞으로 당겨지지만, DB의 라인 번호는 당겨지지 않습니다. 행에는 순서가 없고 번호는 그냥 값입니다. 2번 라인을 지우면 1, 3번 라인이 남고 빈 번호는 그대로 둡니다. 라인 번호는 식별자이지 위치가 아닙니다.

라인 금액 계산 — 여기서 NULL이 다시 나옵니다

라인 금액은 quantity × (menu.price + 옵션 금액의 합)이고, 옵션 금액은 option_item.price × option_qty의 합입니다. 옵션이 없는 라인도 나와야 하므로 LEFT JOIN(4장: 짝이 없는 왼쪽 행도 남기고 오른쪽 열을 NULL로 채우는 조인)을 씁니다.

-- 주문 201 의 라인 금액 (현재 가격 기준)SELECT ol.order_id, ol.line_no,
       ol.quantity
         * (m.price + COALESCE(SUM(i.price * o.option_qty), 0)) AS line_amount
FROM   order_line AS ol
JOIN   menu AS m ON m.menu_id = ol.menu_id
LEFT JOIN order_line_option AS o
       ON o.order_id = ol.order_id AND o.line_no = ol.line_no
LEFT JOIN option_item AS i ON i.option_id = o.option_id
WHERE  ol.order_id = 201
GROUP BY ol.order_id, ol.line_no, ol.quantity, m.price
ORDER BY ol.line_no;
-- (201, 1, 6000)  (201, 2, 5000)  (201, 3, 6500)
  • 3행 COALESCE(값, 대체값)은 첫 번째로 NULL이 아닌 값을 돌려줍니다. 옵션이 없는 라인은 LEFT JOIN이 옵션 열을 NULL로 채우고, 그 NULL들의 SUM도 NULL이라 COALESCE(..., 0)이 없으면 m.price + NULL이 라인 전체 금액을 NULL로 만듭니다.
  • 실제로 COALESCE를 빼면 결과는 (201, 1, 6000), (201, 2, NULL), (201, 3, NULL)입니다. 옵션이 없는 두 라인의 금액이 사라집니다. 4장의 "NULL이 섞인 계산은 NULL"이 그대로 재현된 것입니다.
  • 이 NULL은 옵션 행이 아예 없어서 생기는 NULL이고, 옵션 행이 있는 0원 옵션(얼음 적게)은 price가 0이라 문제가 없습니다. 0과 NULL의 차이가 금액 계산에서 드러나는 장면입니다.
  • 10행 GROUP BY는 같은 라인의 행들을 한 덩어리로 묶어 SUM을 라인마다 계산하게 합니다. 묶는 열에 m.price를 넣은 이유는 묶는 열도 집계 함수도 아닌 열은 SELECT에 쓸 수 없기 때문입니다(빼면 오류). quantity는 PostgreSQL이 라인의 기본키로 묶으면 생략을 허용하지만, 다른 DB에서도 돌도록 적었습니다.

C3의 재정의

C3 — 새 문장

"한 주문에서 같은 (메뉴 + 옵션 조합)은 한 라인로 합친다." v1~v3의 C3은 "같은 메뉴는 한 라인"이었고 기본키 (order_id, menu_id)가 지켰습니다. 이제 규칙이 메뉴와 옵션 조합에 대한 것으로 바뀌었는데, 옵션 조합은 다른 표의 여러 행이므로 UNIQUE나 기본키 같은 선언으로는 표현할 수 없습니다. C3은 DB의 규칙에서 앱의 규칙이 되었습니다. 주문을 만드는 앱이 같은 조합을 미리 합쳐서(수량만 올려서) 저장합니다.

이 규칙이 깨지면(같은 조합 두 라인) 금액 합계는 맞지만 주문서가 지저분해지고 "한 라인이 몇 잔인가"가 흔들립니다. 그래서 4장의 C1처럼 점검 조회를 같이 둡니다(4장 페이지 9: LEFT JOIN ... IS NULL로 라인이 없는 주문을 찾는 조회).

더 깊이 — C3 위반을 찾는 점검 조회 
-- 같은 (메뉴 + 옵션 조합)인 라인이 둘 이상인 경우를 찾는다SELECT order_id, menu_id, sig, COUNT(*) AS lines
FROM  (SELECT ol.order_id, ol.line_no, ol.menu_id,
              COALESCE(string_agg(o.option_id || 'x' || o.option_qty, ','
                                  ORDER BY o.option_id), '') AS sig
       FROM   order_line AS ol
       LEFT JOIN order_line_option AS o
              ON o.order_id = ol.order_id AND o.line_no = ol.line_no
       GROUP BY ol.order_id, ol.line_no, ol.menu_id) AS t
GROUP BY order_id, menu_id, sig
HAVING COUNT(*) > 1;

안쪽 조회가 각 라인의 옵션 조합을 글자 하나로 만듭니다. string_agg(값, 구분자 ORDER BY ...)는 그룹의 값을 구분자로 이어 붙인 글자를 돌려주는 집계 함수이고, ||는 글자 잇기입니다. 옵션 번호 순으로 이으니 '샷 추가, 얼음 적게'와 '얼음 적게, 샷 추가'가 같은 글자(1x2,3x1)가 됩니다. 이 글자(sig)는 조회 안에서만 만들고 열로 저장하지 않습니다. 저장하면 옵션이 바뀔 때 어긋날 수 있는 파생값(3장)이기 때문입니다. 한계가 하나 있습니다. 세트 라인은 옵션이 없어도 고른 구성(order_line_pick)이 다를 수 있는데 이 조회는 구성을 보지 않아서, 구성이 다른 두 세트 라인을 잘못 중복으로 잡습니다. 세트 라인의 점검에는 구성도 조합에 넣어야 합니다.

더 깊이 — 대리키(IDENTITY)로 하면 이렇게 됩니다

INSERT에서 line_id를 적지 않으면 채워지고, 직접 값을 넣으려 하면 거부됩니다(GENERATED ALWAYS는 자동 값만 허용). 자식 표는 line_id 한 열로 라인을 가리키니 외래키가 단순해집니다. 이 교재가 라인 번호를 택한 것은 주문서의 라인이라는 업무 의미와 기존 데이터에 번호만 붙이면 되는 이전의 쉬움 때문이고, 대리키의 단순함이 더 값지다고 보는 팀도 많습니다. 번호를 DB가 매긴다는 것은 같은 주문 안에서도 번호가 1, 2, 3으로 이어지지 않는다는 뜻이기도 합니다. 라인이 "몇 번째인가"가 필요하면 별도 열이 또 필요합니다.

FOREIGN KEY (option_id, group_id)
    REFERENCES option_item (option_id, group_id)

이러면 (메뉴, 그룹)이 연결 표에 없거나 옵션이 그 그룹 소속이 아니면 DB가 거부합니다. 대가는 분명합니다. group_id는 option_id만 알면 정해지는 값(3장의 함수 종속)인데 다시 적는 것이라 정규화를 일부러 어기는 중복입니다. 외래키가 어긋남을 막아 주니 안전하지만, 열과 인덱스와 쓰기 코드가 늘고 이해하기 어려워집니다. 그리고 합계 범위(샷 3번 이하)는 여전히 못 막습니다. 이 교재는 얻는 것(조각 하나)보다 잃는 것(중복, 복잡성)이 크다고 보고 앱 검사로 두었습니다. "DB에 맡길 수 있는 만큼 맡긴다"는 4장의 입장은 비용을 함께 재는 입장이라는 사례입니다.

세트는 메뉴인가 — 주문 라인에서의 모양

서연이 "케이크 세트 주문이요"라고 받은 주문이 주문 라인에서 어떻게 보일지부터 정합니다. 후보는 셋입니다.

모델주문 라인의 모양장점약점
A. 세트도 menu의 한 행라인의 menu_id가 세트(케이크 세트)를 가리킨다. 구성은 별도 표라인 구조, 가격 계산, 이름 유일(C4), 삭제 방지(C6), 판매중지가 그대로 재사용된다메뉴판에 세트와 단품이 섞인다. 세트인지 아는 방법이 따로 필요하다
B. 별도 표 set_product라인에 set_id 열을 더하고 menu_id와 둘 중 하나만 채운다세트와 메뉴가 구조로 분리된다menu_id가 NOT NULL이 아니게 되고(4장 원칙 훼손: NOT NULL이 기본이고 NULL 허용은 이유를 댈 수 있는 열만), 둘 중 하나만 채우는 것을 CHECK로 따로 지켜야 한다. 가격 계산·이름 유일·삭제 방지가 두 갈래
C. 구성 메뉴 라인로 풀어 저장세트 라인 없이 음료 라인 + 케이크 라인기존 구조 그대로세트 가격(9500)을 어느 라인에 둘지 정해야 하고, "세트가 몇 개 팔렸나"를 알 수 없다
-- 모델 B 가 요구하는 제약 (설명용, v4 스키마 밖)CHECK ((menu_id IS NULL) <> (set_id IS NULL))   -- 정확히 하나만 NULL 이 아니다

이 CHECK는 동작합니다. 둘 다 NULL이거나 둘 다 채워진 라인을 거부합니다. 그러나 라인이 가리키는 대상이 두 표 중 하나가 되면 외래키도 두 개, 기본키·삭제 정책·가격 계산도 모두 두 갈래로 갈라집니다. 이 교재는 모델 A를 고릅니다.

모델 A에서 세트는 menu의 평범한 한 행입니다. menu 표의 열은 바뀌지 않습니다. 두 행이 추가됩니다.

모델 A의 한계와 결정

  • 세트인지 어떻게 아나 — 열을 두지 않습니다. is_set 열을 menu에 더할 수도 있지만, "구성 슬롯을 가진 메뉴가 세트"라는 사실은 슬롯 표(다음 페이지)에서 계산할 수 있는 값입니다. 저장하면 슬롯이 없는데 is_set = TRUE인 행이 생길 수 있는 어긋남이 생깁니다. 3장의 파생값 질문과 같은 결정입니다.
  • 세트 가격은 구성 메뉴 가격의 합과 다른 사실입니다. 아메리카노 4500 + 치즈케이크 6500 = 11000인데 세트는 9500입니다. 두 숫자는 값이 비슷해 보이지만 의미가 다른 사실(세트 가격은 "세트를 사면 얼마를 받기로 했는가")이라 중복이 아닙니다. 이 구분은 6장의 스냅샷에서 다시 중요해집니다.
  • 세트 안의 구성 메뉴에는 옵션을 붙일 수 없습니다. 옵션은 라인에 붙는데 세트 라인은 하나라서 "세트 음료에 샷 추가"가 어느 음료에 붙는지 표현할 자리가 없습니다. 필요하면 세트를 자식 라인로 풀어 저장하는 더 복잡한 모델이 필요합니다. 이 교재 범위 밖입니다.
  • 구성품별 집계는 두 곳을 합쳐야 합니다. "치즈케이크가 몇 개 팔렸나"는 order_line(단품 주문)과 다음 페이지의 order_line_pick(세트 안 선택)을 이어 붙여야 나옵니다.
  • 세트 구성에 따른 추가금은 없습니다. 카페라떼를 고르면 500원을 더 받는 식의 규칙은 이 모델에 없습니다. 필요하면 후보 표에 금액 열을 더합니다.

반대 의견 — "세트는 상품이고 메뉴는 품목이다"

규모가 큰 시스템은 판매 단위인 상품(product)과 만드는 단위인 품목(item)을 구분합니다. 세트는 상품이고 아메리카노는 품목이 되며, 같은 아메리카노도 단품 상품과 세트의 구성 품목으로 따로 나옵니다. 이 구분이 있으면 위의 "구성품별 집계가 두 곳" 문제가 줄지만 표와 조인이 늘어납니다. 동백커피의 지금 규모에서는 "세트도 메뉴"가 더 작은 설계이고, 구성품별 집계가 자주 필요해지면 그때 나눕니다.

옵션과 세트는 다른 것입니다

옵션은 라인 하나에 붙는 선택(라인은 여전히 메뉴 하나)이고, 세트는 라인 자체가 여러 메뉴의 묶음입니다. 그래서 옵션은 "라인에 붙는 행"(order_line_option)이고, 세트는 "라인이 자리마다 고른 것"(다음 페이지의 order_line_pick)입니다.

세트 구성 슬롯 — 자리와 후보 (C10)

C10은 "세트는 구성 슬롯을 모두 채워야 한다(음료 1 + 디저트 1, 디저트는 케이크류 중 택1)"입니다. 구성 요소는 셋입니다.

  • 슬롯 — 세트가 가진 자리. 케이크 세트는 음료, 디저트 두 자리.
  • 후보 — 슬롯마다 들어갈 수 있는 메뉴. 음료 슬롯은 아메리카노·카페라떼, 디저트 슬롯은 치즈케이크·티라미수.
  • 선택 — 세트 주문 라인이 슬롯마다 실제로 고른 메뉴.

"디저트는 케이크류 중 택1"은 이 교재의 v4에서는 후보 메뉴를 하나씩 열거해 표현합니다. 후보가 둘뿐이기 때문입니다. "케이크류"처럼 분류로 지정하는 방법은 페이지 10에서 설명합니다.

-- 스키마 v4 ③: 세트 구성 (새 표 셋)-- 세트의 구성 슬롯 (케이크 세트의 '음료', '디저트')
CREATE TABLE set_slot (
    slot_id      INTEGER PRIMARY KEY,
    set_menu_id  INTEGER NOT NULL REFERENCES menu (menu_id),
    name         TEXT    NOT NULL
                 CHECK (name <> '' AND name = btrim(name)),
    UNIQUE (set_menu_id, name)
);

-- 슬롯에 들어갈 수 있는 메뉴 (후보)
CREATE TABLE set_slot_menu (
    slot_id  INTEGER NOT NULL REFERENCES set_slot (slot_id),
    menu_id  INTEGER NOT NULL REFERENCES menu (menu_id),
    PRIMARY KEY (slot_id, menu_id)
);

-- 세트 라인이 슬롯마다 고른 메뉴
CREATE TABLE order_line_pick (
    order_id  INTEGER NOT NULL,
    line_no   INTEGER NOT NULL,
    slot_id   INTEGER NOT NULL,
    menu_id   INTEGER NOT NULL,
    PRIMARY KEY (order_id, line_no, slot_id),
    FOREIGN KEY (order_id, line_no) REFERENCES order_line (order_id, line_no),
    FOREIGN KEY (slot_id, menu_id)  REFERENCES set_slot_menu (slot_id, menu_id)

  2. 11~15행 set_slot_menu — 한 행은 "이 슬롯에 이 메뉴를 넣을 수 있다". 연결 테이블이고 14행 기본키가 (slot_id, menu_id)입니다. 이 기본키가 25행의 외래키가 가리킬 대상이 됩니다.
  3. 18~27행 order_line_pick — 한 행은 "이 세트 라인의 이 슬롯에 이 메뉴를 골랐다".
  4. 23행 기본키 (order_id, line_no, slot_id)로 한 라인의 한 슬롯에는 한 번만 고릅니다("택1"). 음료 슬롯에 음료 둘은 못 넣습니다.
  5. 24행 라인 번호로 order_line의 라인을 가리키는 복합 외래키입니다(페이지 6).
  6. 25~26행 (slot_id, menu_id)를 한 덩어리로 set_slot_menu에 대조합니다. 고른 메뉴가 그 슬롯의 후보여야만 저장됩니다. 음료 슬롯에 치즈케이크를 고르면 DB가 거부합니다. 26행 RESTRICT는 이미 주문에 쓰인 후보를 후보 표에서 지울 수 없게 합니다(C6의 확장).

FROM   order_line AS ol

C++ 비유와 그 한계

세트는 std::tuple<Drink, Dessert>와 닮았습니다. 칸 수와 각 칸의 타입이 정해져 있다는 점에서 그렇습니다. 그러나 C++의 튜플 구조는 컴파일할 때 고정이고 잘못된 타입은 컴파일러가 막아 줍니다. 슬롯은 데이터라서 서연이 새 세트를 만들면 슬롯 행이 늘어나고, "음료 자리에 디저트가 들어갔는가"는 컴파일러가 아니라 복합 외래키가 실행할 때 지킵니다. "모든 칸이 채워졌는가"는 튜플 생성자가 보장하지만 DB에서는 앱이 합니다.

그래서 나중에 무슨 문제가 되는가

슬롯 충족 검사도 C9처럼 주문을 저장하는 트랜잭션 안에서 해야 안전합니다. 8장에서 다시 본다 또 세트 라인의 quantity가 2이면 같은 구성의 두 세트를 뜻합니다. 구성이 다른 두 세트는 다른 라인로 저장합니다(옵션과 같은 C3의 논리).

  • 2장의 외래키는 "다른 표"를 가리켰지만 같은 표를 가리켜도 됩니다. 행을 만들 때는 부모가 먼저 있어야 하므로 최상위를 먼저 넣습니다.
  • 부모를 지우려 하면 자식이 있는 한 거부됩니다(기본 동작).

트리를 아래로 끝까지 따라가는 일(디저트 아래 모든 분류)이 자기 참조 표의 까다로운 부분입니다. 깊이를 미리 알 수 없어 JOIN을 몇 번 해야 하는지 정할 수 없기 때문입니다. SQL에는 이를 위한 재귀 조회 문법 WITH RECURSIVE가 있습니다.

-- 디저트(3번) 아래의 모든 분류, 자기 자신 포함WITH RECURSIVE sub AS (
    SELECT category_id
    FROM   menu_category
    WHERE  category_id = 3
  UNION ALL
    SELECT c.category_id
    FROM   menu_category AS c
    JOIN   sub AS s ON c.parent_id = s.category_id
)
SELECT category_id FROM sub ORDER BY category_id;   -- 3, 4, 5
  • 2~4행이 출발점(디저트 자신)이고, 6~8행이 반복 단계입니다. 지금까지 나온 결과(sub)의 자식을 찾아 결과에 더합니다.
  • 더 찾을 자식이 없을 때까지 반복하고 끝납니다. UNION ALL은 두 결과를 이어 붙입니다(중복을 지우지 않습니다).
  • 이 분류를 세트 슬롯에 쓰면 "디저트 슬롯의 후보는 분류 '케이크' 이하의 메뉴"로 바뀌고, 새 케이크를 menu에 더하기만 하면 모든 세트가 그 케이크를 후보로 받습니다. 후보 연결 표가 (slot_id, menu_id) 대신 (slot_id, category_id)가 됩니다.

자기 참조 표의 위험과 반대 의견

  • 순환을 DB가 막지 못합니다. 디저트의 부모를 케이크로 고쳐도(UPDATE menu_category SET parent_id = 4 WHERE category_id = 3) 저장됩니다. 이러면 위의 재귀 조회가 끝나지 않고 3, 4, 5를 반복합니다(UNION ALL은 중복을 지우지 않으므로). 순환 여부는 여러 행을 따라가야 알 수 있어 앱이 검사합니다. CHECK (parent_id <> category_id)는 자기 자신을 부모로 삼는 가장 작은 순환만 막습니다. PostgreSQL 14부터는 재귀 조회에 순환을 감지하는 CYCLE 절이 있습니다.
  • Bill Karwin의 『SQL Antipatterns』는 이 모양을 Naive Trees(순진한 트리)의 예로 듭니다. 재귀 조회를 지원하지 않던 시절에는 아래로 끝까지 따라가는 조회가 어려웠기 때문입니다. 지금의 PostgreSQL은 WITH RECURSIVE를 지원하므로 깊이가 얕은 분류에는 충분한 경우가 많습니다. 경로를 글자로 저장하는 방식, 중첩 집합, 클로저 테이블 같은 대안이 있으나 각각 쓰기나 갱신이 복잡해지는 대가가 있어 이름만 소개합니다.
  • 이 교재의 v4는 후보를 열거합니다. 후보가 둘뿐이고, 분류 트리 없이도 C10의 구조를 설명할 수 있어서입니다. 분류를 택한 설계라면 위처럼 바뀐다는 것이 이 페이지의 요점입니다.

선택 페이지입니다

건너뛰어도 페이지 12로 이어집니다. 이 페이지의 표는 스키마 v4에 포함되지 않는 설명용입니다.

동료가 이렇게 제안합니다. "옵션 표를 그룹, 항목, 연결로 셋이나 만들지 말고, 주문 라인 속성을 행으로 쌓는 표 하나면 되지 않을까요? 새 옵션도 열 추가 없이 INSERT 한 라인이면 돼요."

);

이 설계를 EAV(Entity-Attribute-Value)라고 부릅니다. 유연해 보이지만 무엇을 잃는지 봅니다.

잃는 것설명
타입값 열이 TEXT 하나라서 샷 횟수('2')와 '많이'가 같은 열에 들어갑니다. 횟수를 비교하려고 attr_value::INTEGER >= 2(::INTEGER는 글자를 정수로 바꾸는 형 변환)로 바꾸면 '많이'를 만나는 순간 조회 전체가 오류로 끝납니다(아래).
필수·제약"이 속성은 꼭 있어야 한다"(NOT NULL), "0 이상이다"(CHECK)를 속성마다 다르게 걸 수 없습니다. 열 하나에 모든 속성이 섞여 있어서입니다.
외래키"이 값은 옵션 표의 행이어야 한다"를 선언할 수 없습니다. 속성 이름 오타('extra_shoot')도 그냥 새 속성이 됩니다.
조회한 라인의 옵션을 가로로 보려면 속성마다 조인하거나 행을 열로 돌리는 조회를 씁니다. 속성이 늘면 조회도 늘어납니다.
가격옵션의 가격과 개수 범위를 둘 곳이 여전히 없습니다.
-- 타입을 잃으면 생기는 일SELECT order_id, line_no FROM line_attr
WHERE  attr_name = 'extra_shot' AND attr_value::INTEGER >= 2;
-- ERROR:  invalid input syntax for type integer: "많이"

'extra_shot'에 '많이'가 들어 있는 이상 이 조회는 실패합니다. 값 열이 글자라서 DB가 그 입력을 막아 주지 못했기 때문입니다. 속성 이름으로 거르니 괜찮지 않겠냐고 생각하기 쉽지만, 그 행이 없더라도 WHERE의 조건이 적힌 순서대로 평가된다는 보장이 없어서 다른 속성의 값('적게' 등)에 형 변환이 먼저 적용될 수 있습니다. 오류가 나는 원인이 데이터 한 칸이라 찾기도 어렵습니다.

그러면 v4의 option_item도 EAV 인가요 — 아닙니다

EAVv4의 옵션 모델
"어떤 옵션이 있는가"속성 이름이 데이터(글자)옵션이 행이고 기본키가 있다
선택의 기록이름 글자 + 값 글자option_id(외래키) + option_qty(INTEGER, >= 1)
옵션이 가진 사실둘 곳이 없다price, group_id, 범위가 열로 있고 타입·제약이 붙는다
없는 옵션 선택막을 수 없다외래키가 거부

요약: "무엇이 있는가"(옵션의 종류)는 행으로 두어 늘릴 수 있게 하고, "그것이 어떤 사실을 갖는가"(가격, 개수 범위)는 열로 남겨 타입과 제약을 붙입니다. 종류를 데이터로 풀되 구조까지 풀지는 않습니다.

EAV가 정당한 드문 경우

  • 속성의 종류가 사용자마다 달라 미리 열거할 수 없을 때: 사용자가 자기 필드를 마음대로 만드는 서비스(사용자 정의 필드)처럼 "어떤 속성이 있는지"가 개발 시점에 정해지지 않는 경우.
  • 값을 조건으로 조회·집계하지 않고 통째로 보여 주기만 하는 경우(상품 상세의 사양표 같은 것).
  • 속성 종류가 수천 가지이고 행마다 몇 개만 쓰는 제품 카탈로그.

PostgreSQL에서는 이런 경우 JSONB 열이 대안이 되기도 합니다(인덱스를 걸 수 있습니다). 다만 제약과 타입이 약하다는 점은 같습니다. 동백커피의 옵션은 종류가 열 가지 안팎으로 정해져 있고 가격·개수 규칙·집계가 필요한 경우라 이 조건에 해당하지 않습니다. 이 주제는 Bill Karwin의 『SQL Antipatterns』가 Entity-Attribute-Value라는 이름의 안티패턴으로 다룹니다.

v4 전체 DDL 한눈에 보기 (표 11개, 만드는 순서)

CREATE TABLE menu (
    menu_id    INTEGER PRIMARY KEY,
    name       TEXT    NOT NULL UNIQUE
               CHECK (name <> '' AND name = btrim(name)),
    price      INTEGER NOT NULL CHECK (price >= 0),
    is_active  BOOLEAN NOT NULL DEFAULT TRUE
);

-- 회원 한 명
CREATE TABLE member (
    member_id  INTEGER PRIMARY KEY,
    name       TEXT    NOT NULL,
    phone      TEXT    NOT NULL UNIQUE
               CHECK (phone ~ '^01[0-9]-[0-9]{3,4}-[0-9]{4}$')
);

-- 주문 한 건 (비회원 주문이면 member_id 는 NULL)
CREATE TABLE orders (
    order_id    INTEGER     PRIMARY KEY,
    member_id   INTEGER     REFERENCES member (member_id),
    ordered_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    barista     TEXT        NOT NULL,

);

    group_id    INTEGER PRIMARY KEY,

    max_select  INTEGER NOT NULL CHECK (max_select >= 1),

);

    group_id   INTEGER NOT NULL REFERENCES option_group (group_id),

    is_active  BOOLEAN NOT NULL DEFAULT TRUE,

    menu_id   INTEGER NOT NULL REFERENCES menu (menu_id),
    group_id  INTEGER NOT NULL REFERENCES option_group (group_id),
    PRIMARY KEY (menu_id, group_id)
);

-- 주문 안의 한 줄 (같은 메뉴여도 옵션이 다르면 다른 라인이다)
CREATE TABLE order_line (
    order_id  INTEGER NOT NULL REFERENCES orders (order_id),
    line_no   INTEGER NOT NULL CHECK (line_no >= 1),
    menu_id   INTEGER NOT NULL REFERENCES menu (menu_id) ON DELETE RESTRICT,
    quantity  INTEGER NOT NULL CHECK (quantity >= 1),
    PRIMARY KEY (order_id, line_no)

-- 라인에 붙은 옵션 한 가지와 그 횟수 (같은 옵션은 한 라인에 한 번만 적는다)
CREATE TABLE order_line_option (
    order_id    INTEGER NOT NULL,
    line_no     INTEGER NOT NULL,
    option_id   INTEGER NOT NULL REFERENCES option_item (option_id) ON DELETE RESTRICT,
    option_qty  INTEGER NOT NULL DEFAULT 1 CHECK (option_qty >= 1),
    PRIMARY KEY (order_id, line_no, option_id),
    FOREIGN KEY (order_id, line_no) REFERENCES order_line (order_id, line_no)
);

-- 세트의 구성 슬롯 (케이크 세트의 '음료', '디저트')

v3에서 v4로 — 이미 있는 데이터를 지키며

새 표 7개는 위의 DDL대로 CREATE TABLE하면 됩니다. 다만 order_line_option과 order_line_pick은 order_line의 새 기본키를 가리키므로 아래 이전이 끝난 뒤에 만듭니다(v3의 기본키 (order_id, menu_id) 위에는 (order_id, line_no)를 가리키는 외래키를 걸 수 없습니다). 문제는 이미 행이 들어 있는 order_line입니다. 기존 여섯 라인에 라인 번호를 붙이고 기본키를 바꿔야 합니다.

-- order_line 이전 (기존 데이터를 그대로 둔 채)BEGIN;
ALTER TABLE order_line ADD COLUMN line_no INTEGER;
UPDATE order_line AS ol
SET    line_no = t.rn
FROM  (SELECT order_id, menu_id,
              ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY menu_id) AS rn
       FROM   order_line) AS t
WHERE  ol.order_id = t.order_id AND ol.menu_id = t.menu_id;
ALTER TABLE order_line ALTER COLUMN line_no SET NOT NULL;
ALTER TABLE order_line ADD CHECK (line_no >= 1);
ALTER TABLE order_line DROP CONSTRAINT order_line_pkey;
ALTER TABLE order_line ADD PRIMARY KEY (order_id, line_no);
COMMIT;
  1. 1행 BEGIN과 13행 COMMIT이 한 트랜잭션의 시작과 끝입니다. PostgreSQL은 ALTER TABLE 같은 구조 변경도 트랜잭션 안에서 되돌릴 수 있어서, 중간에 실패하면 표가 반쯤 바뀐 채로 남지 않습니다(다른 DB에서는 구조 변경이 자동으로 확정되는 곳도 있습니다).
  2. 2행 새 열을 일단 NOT NULL 없이 더합니다. 기존 여섯 행에 넣을 값이 아직 없기 때문입니다(4장 페이지 4: 행이 있는 표에 NOT NULL 열을 더하려면 값이 필요).
  3. 3~8행 기존 행에 라인 번호를 채웁니다. UPDATE ... FROM은 다른 조회 결과를 붙여 그 값으로 갱신하는 문법입니다. 안쪽 조회(5~7행)의 ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY menu_id)는 주문(order_id)별로 나누어 menu_id 순서로 1, 2, 3…을 매기는 윈도 함수입니다. 주문 101이면 아메리카노(1번)가 1, 치즈케이크(3번)가 2가 됩니다.
  4. 9~10행 값이 다 채워졌으니 9행에서 NOT NULL을 겁니다. 10행은 line_no >= 1 검사를 더합니다.
  5. 11~12행 옛 기본키를 지우고 새 기본키를 만듭니다. order_line_pkey는 PostgreSQL이 기본키에 자동으로 붙인 이름(표이름_pkey)입니다. 이 라인이 D3의 상환이 기존 데이터 위에서 일어나는 지점입니다.

이 방식으로 바꾼 표는 line_no 열이 맨 끝에 놓여, 처음부터 v4로 만든 표와 열 순서만 다릅니다. 의미와 제약은 같습니다. 이 이전은 작은 표에서만 가벼운 방법입니다. 수백만 행이 있고 서비스가 켜져 있는 표에서는 UPDATE 한 번이 오래 걸려 그동안 다른 요청을 막을 수 있습니다. 안전한 순서(확장 → 이전 → 축소)는 9장의 몫입니다. 9장에서 다시 본다

핵심 요약

  1. 종류가 늘어나는 것은 열이나 글자 한 칸이나 메뉴 이름에 새기지 않고 행으로 둡니다. 옵션은 option_group · option_item · menu_option_group 세 표이고, 가격은 옵션 행에, 개수 범위는 그룹 행에 둡니다.
  2. 0원 옵션은 0으로 저장하고 NULL은 허용하지 않습니다. NULL은 "공짜"와 "모른다"를 구별하지 못하고 계산을 NULL로 만들거나 SUM에서 조용히 사라집니다.
  3. 같은 메뉴 두 라인 문제(D3)는 라인 번호로 풀었습니다(PK (order_id, line_no)). 그 대가로 C3(같은 메뉴+옵션 조합은 한 라인)는 선언할 수 없는 앱의 규칙이 되었습니다.
  4. C9(선택 개수)와 C10(슬롯 충족)은 규칙의 값과 모순 방지, 후보 대조까지는 DB가 하고, 합계·개수를 세는 검사는 앱과 트랜잭션이 합니다(C1과 같은 모양).
  5. 세트는 menu의 한 행이고 구성은 슬롯·후보·선택 세 표로 담습니다. 옵션은 메뉴를 바꾸고 세트는 묶습니다. 결과가 스키마 v4이고, D1(옵션·세트 가격까지)·D2·D4·D5는 남았습니다.

옵션 '얼음 적게'는 공짜입니다. option_item.price에는 무엇을 저장하는 것이 맞을까요?

  1. 0
  2. NULL (가격이 없으므로)
  3. 옵션 행을 만들지 않고 앱 코드에서 "얼음 적게는 0원"이라고 처리한다

4장 페이지 7에서 menu.price의 경계를 >= 0으로 잡은 이유도 같습니다. 경계값은 업무가 정합니다. 한 가지 더, 0원 옵션이 있는 라인도 옵션 행이 있으니 금액 계산이 안전하고, 문제가 되는 NULL은 "옵션 행이 아예 없는 라인"을 LEFT JOIN으로 센 경우의 SUM이라서 COALESCE로 0을 채워야 했습니다. 두 NULL은 원인이 다릅니다.

v4에서 한 주문에 카페라떼가 옵션 없이 두 라인 저장되어 있습니다(라인 번호 1, 2). 이것을 막는 것은 무엇일까요?

  1. 기본키 (order_id, line_no)가 같은 메뉴의 중복 라인을 막는다
  2. order_line에 같은 조합을 거부하는 CHECK를 걸면 된다
  3. DB가 막지 못한다. 주문을 만드는 앱이 같은 조합을 합쳐서 저장해야 한다

이것이 규칙이 DB에서 앱으로 옮겨 가는 전형적인 장면입니다. 설계를 바꾸면 DB가 지켜 주던 규칙이 조용히 사라질 수 있습니다. 그래서 스키마를 바꿀 때는 "이 변경으로 어떤 제약이 약해지는가"를 제약 표(C1~C17)와 대조해야 합니다. 한편 옵션 한 줄 안에서 같은 옵션을 두 행으로 넣는 것은 여전히 기본키 (order_id, line_no, option_id)가 막습니다.

2. "꼭 하나"는 min_select = 1, max_select = 1입니다. 이 교재가 만든 모델에서 min_select가 처음으로 0이 아닌 값을 갖는 그룹입니다. DB는 범위 값이 말이 되는지(최소 ≤ 최대)만 지킵니다. 온도를 안 고른 라인을 막는 것은 앱이고, "행이 없음"을 찾는 점검 조회(그룹 쪽에서 시작하는 LEFT JOIN)가 구멍을 찾습니다. C1과 같은 모양의 규칙입니다. 세트 안의 음료는 v4에서 옵션을 붙일 자리가 없으므로(페이지 8) 이 규칙은 단품 음료 라인에만 적용됩니다.
