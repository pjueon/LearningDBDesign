이 교재를 읽는 방법과 동백커피 이야기

이 교재는 SQL 문법 교재가 아닙니다. "요구사항이 바뀌어도 버티는 테이블 구조를 어떻게 고르는가"를 배우는 DB 설계 교재입니다. 문법은 설계를 읽고 쓰는 데 필요한 만큼만, 나오는 자리에서 설명합니다.

이 교재가 가정하는 독자

  • 프로그래밍 경험이 있습니다. 구조체·클래스·참조(포인터)를 압니다.
  • DB를 다뤄본 적이 거의 없고, SQL은 기초 문법을 한 번 훑어본 정도입니다.
  • 웹·네트워크 경험은 없어도 됩니다. 이 교재에는 나오지 않습니다.

이 교재의 진행

  1. 0~1장 — 표를 읽는 눈을 얻고, 엑셀 한 장짜리 설계가 왜 아픈지 겪습니다.
  2. 2~4장 — 테이블을 나누고, 정규화로 검증하고, 규칙을 DB에 맡깁니다.
  3. 5~6장 — 이미 만든 설계가 흔들리는 순간들을 겪고 고칩니다.
  4. 7~9장 — 규모, 동시성, 운영 중 변경 앞에서 설계가 버티는지 봅니다.
  5. 10장 — 정규화를 언제 깨고, 관계형 DB를 언제 쓰지 말지 판단합니다.

읽는 방법

  • 화면은 ← → 키나 아래 버튼으로 넘기고, 왼쪽 목차에서 원하는 화면으로 이동합니다. 어디까지 읽었는지는 이 브라우저에 저장됩니다.
  • 점선 밑줄이 그어진 테이블 같은 낱말은 마우스를 올리면 뜻이 나옵니다.
  • N장에서 다시 본다 딱지는 지금은 덮어 두고 뒤의 장에서 다시 꺼내는 이야기라는 표시입니다. 설계에 일부러 남겨 둔 약점(빚)도 이 딱지로 표시해 두었다가 그 장에서 갚습니다. 빚에는 D1~D5 번호를 붙여 4장에서 한데 모아 보여 드립니다.
  • 더 깊이 접힌 상자는 처음 읽을 때 건너뛰어도 됩니다.
  • 퀴즈는 선택지를 눌러 보세요. 맞고 틀린 이유가 해설로 나옵니다. 해설에 본문에 없는 이야기가 들어 있습니다.

코드는 PostgreSQL 기준으로 씁니다. SQL 키워드는 SELECT, CREATE TABLE처럼 대문자로, 테이블·열 이름은 menu, order_line처럼 소문자 영문으로 씁니다. SQL은 키워드의 대소문자를 구분하지 않지만, 이렇게 쓰면 무엇이 문법이고 무엇이 우리가 붙인 이름인지 한눈에 보입니다.

더 깊이 — 왜 PostgreSQL인가, SQLite로 공부해도 되나

SQL에는 국제 표준(ISO/ANSI)이 있지만 DB 제품마다 방언이 있습니다. CREATE TABLE, 기본키·외래키, JOIN, INSERT/UPDATE 같은 핵심은 거의 공통이고, 정규화나 ER 모델링 같은 개념은 제품과 무관합니다.

PostgreSQL을 고른 이유는 무료 오픈소스이고, 제약조건이 처음부터 제대로 강제되고, 뒤에서 쓸 기능(행 단위 잠금, 트랜잭션 안에서의 스키마 변경 등)이 잘 맞기 때문입니다.

SQLite로도 개념 공부는 됩니다. 다만 외래키 강제가 기본으로 꺼져 있고 타입이 느슨하며, 행 단위 잠금이 없어 8장의 동시성 사고를 재현하기 어렵습니다. 그래서 본문을 그대로 옮겨 실행하면 동작이 달라질 수 있습니다. 차이가 학습에 영향을 주는 곳은 "다른 DB에서는" 상자로 알려 드립니다. 이 교재는 브라우저에서 코드를 실행하지 않고 읽는 방식이라 제품 선택은 "본문의 SQL이 정확한가"에만 영향을 줍니다.

표(테이블)를 읽는 법

동백커피의 메뉴를 담은 테이블 menu를 봅시다. 앞으로 계속 나올 표입니다.

menu_idnameprice
1아메리카노4500
2카페라떼5000
3치즈케이크6500
  • 열(column)은 사실의 속성 하나입니다. menu_id는 메뉴를 구별하는 번호, name은 이름, price는 가격(원)입니다. 열마다 타입이 하나 정해져 있습니다. price는 정수이므로 "오천원" 같은 글자는 들어갈 수 없습니다.
  • 행(row)은 사실 하나입니다. 이 표에서 한 행은 "메뉴 한 종류"를 뜻합니다. 표를 처음 볼 때는 항상 "한 행이 무엇을 뜻하는가?"부터 물으세요. 그것이 표의 정체입니다.
  • 표에는 행 순서라는 개념이 없습니다. 위 표가 1, 2, 3 순으로 보이는 것은 우연이고, 순서가 필요하면 조회할 때 ORDER BY로 요청해야 합니다. 테이블을 구조체 배열로 보는 비유가 깨지는 곳이 여기입니다. 배열과 달리 행에는 첨자(위치)가 없어서 "세 번째 행"으로 가리킬 수 없고, 행은 열의 값으로 찾습니다.
비교엑셀 시트DB 테이블
셀의 값셀마다 숫자든 글자든 자유열마다 타입이 하나. 어기면 거부
행 순서위에서 아래가 의미를 가짐순서 개념 없음. 조회할 때 요청
규칙서식·색깔 정도. 값은 기본으로 막지 못함(유효성 검사를 따로 걸 수는 있음)제약조건으로 선언하면 DB가 막음
다른 표 참조사람이 VLOOKUP으로 이음키로 이어 붙임. 외래키가 존재를 보장
동시 사용파일 단위로 다룸. 여러 사람이 각자 고치면 덮어쓰기 위험여러 프로그램이 동시에 접근하도록 설계(동시에 몰릴 때의 어려움은 8장)

이 차이가 다음 1장의 출발점입니다. 엑셀 한 장으로 잘 돌아가던 장부가 질문과 변경이 늘면서 왜 어긋나기 시작하는지를 겪게 됩니다.

최소 SQL ① — 표를 만드는 문장을 읽는다

앞 화면의 menu 표를 DB에 만드는 문장입니다. 쓰는 법이 아니라 읽는 법을 익히세요. 이 교재에서 테이블의 모양은 대부분 이런 CREATE TABLE 문으로 보여 드립니다.

-- menu 테이블 만들기-- 메뉴 한 종류를 한 행으로 담는 표
CREATE TABLE menu (
    menu_id  INTEGER PRIMARY KEY,
    name     TEXT    NOT NULL,
    price    INTEGER NOT NULL
);
  1. 1행 --로 시작하는 줄은 주석입니다. DB는 무시하고 사람만 읽습니다.
  2. 2행 CREATE TABLE menu ( — "menu라는 이름의 테이블을 만든다"입니다. 괄호 안에 열을 쉼표로 나열하고, 6행의 );로 닫습니다.
  3. 3행 menu_id INTEGER PRIMARY KEY — 열 이름 menu_id, 타입 INTEGER(정수), 그리고 이 열이 기본키라는 선언입니다. 기본키 열은 행마다 값이 달라야 하고 비어 있을 수 없습니다. 그래서 "메뉴 1번"이 어느 행인지 항상 하나로 정해집니다.
  4. 4행 name TEXT NOT NULL — 이름은 글자(TEXT)이고, NOT NULL은 값을 아예 넣지 않는 것(NULL)을 막는다는 뜻입니다. 이름 칸을 비워 둔 메뉴는 만들 수 없습니다. 다만 글자가 하나도 없는 빈 문자열 ''은 값이 "있는" 것이라 NOT NULL로는 막히지 않습니다. 이것을 막는 규칙은 4장에서 다룹니다. 4장에서 다시 본다
  5. 5행 price INTEGER NOT NULL — 가격은 정수(원 단위)이고 비울 수 없습니다. 가격을 소수(float)가 아니라 정수로 둔 이유는 4장에서 설명합니다. 4장에서 다시 본다

읽을 때 기억할 것

열 하나는 "이름 타입 규칙" 세 조각으로 읽습니다. PRIMARY KEY나 NOT NULL 같은 규칙이 제약조건의 시작입니다. 이런 규칙을 DB에 적어 두면 어기는 입력을 DB가 거부합니다. 엑셀에는 없던 힘입니다.

최소 SQL ② — 조회 문장을 읽는다

주문 한 줄을 담는 테이블 order_line이 하나 더 있다고 합시다. 한 행은 "어느 주문의 어느 메뉴를 몇 개 샀는가"입니다.

order_idmenu_idquantity
10112
10131
10221

order_line에는 메뉴 이름이 없고 menu_id만 있습니다. "101번 주문에서 뭘 샀지?"를 알려면 menu 표와 이어 붙여야 합니다. 이 이어 붙이기가 JOIN입니다.

다시 보기: 화면 4의 menu 표

위 표의 menu_id를 이 표의 같은 번호와 맞춰 보면 이름과 가격을 알 수 있습니다.

menu_idnameprice
1아메리카노4500
2카페라떼5000
3치즈케이크6500
-- 101번 주문에 무엇이 들었나SELECT m.name, ol.quantity
FROM   order_line AS ol
JOIN   menu AS m ON m.menu_id = ol.menu_id
WHERE  ol.order_id = 101;
  1. 1행 SELECT 뒤는 결과 표에 보고 싶은 열입니다. m.name은 "m이라는 별칭의 표에서 name 열"입니다. 별칭 m은 3행에서 menu에 붙입니다.
  2. 2행 FROM은 어느 표에서 시작하는가입니다. AS ol은 order_line에 짧은 별칭 ol을 붙입니다. 긴 이름을 반복하지 않으려는 것뿐입니다.
  3. 3행 JOIN menu AS m ON m.menu_id = ol.menu_id — menu 표를 붙이는데, 두 표의 menu_id가 같은 행끼리 잇습니다(ON이 잇는 조건). 같은 menu_id가 없는 행은 결과에 나오지 않습니다.
  4. 4행 WHERE는 행을 걸러내는 조건입니다. 101번 주문의 라인만 남깁니다.

결과는 다음 표 하나입니다.

namequantity
아메리카노2
치즈케이크1

이 문장이 앞으로 계속 나오는 이유

표를 나눌수록 JOIN이 필요해집니다. 1장에서 "쪼갠 표를 키로 다시 잇는다"고 할 때 바로 이 문장입니다. 다만 표를 이어 붙이는 데도 비용이 든다는 사실은 3장(정규화)에서, 그리고 이어 붙이는 열에 인덱스를 거는 문제는 7장에서 다시 만납니다. 3장에서 다시 본다

최소 SQL ③ — 데이터를 바꾸는 문장, 그리고 트랜잭션

-- 행 추가 · 수정 · 삭제INSERT INTO menu (menu_id, name, price)
VALUES (4, '바닐라라떼', 5500);

UPDATE menu
SET    price = 5000
WHERE  menu_id = 4;

DELETE FROM menu
WHERE  menu_id = 4;
  1. 1~2행 INSERT INTO는 행 추가입니다. 괄호 안 열 이름 순서와 VALUES 안 값 순서가 짝을 이룹니다. 글자 값은 작은따옴표로 감쌉니다.
  2. 4~6행 UPDATE는 행 수정입니다. SET이 바꿀 값, WHERE가 어느 행을 바꿀지입니다.
  3. 8~9행 DELETE FROM은 행 삭제입니다. 역시 WHERE가 대상을 정합니다.

WHERE를 빼면 전부 바뀝니다

UPDATE menu SET price = 5000;처럼 WHERE 없이 쓰면 모든 행의 가격이 5000이 되고, DELETE FROM menu;는 모든 행을 지웁니다. DB는 "실수 아니냐"고 묻지 않고 그대로 실행합니다.

실제 동백커피에서는 주문 하나를 저장하려면 INSERT가 여러 번 필요합니다. 주문 1행과 라인 여러 행을 넣다가 중간에 실패하면 주문만 있고 라인은 없는 어정쩡한 데이터가 남습니다. 그래서 DB에는 여러 문장을 한 묶음으로 묶어 "전부 성공하거나 전부 없던 일로" 만드는 장치가 있습니다.

-- 묶음으로 실행 (맛보기)BEGIN;                -- 묶음 시작
INSERT INTO ...;   -- 주문 1행
INSERT INTO ...;   -- 라인 여러 행
COMMIT;            -- 여기서 확정. 중간에 ROLLBACK 하면 전부 취소

이것이 트랜잭션입니다. 지금은 "그런 장치가 있다"는 것만 기억하세요. 트랜잭션이 왜 필요한지, 그래도 동시에 요청이 들어오면 왜 깨지는지는 8장의 주제입니다. 8장에서 다시 본다

더 깊이 — 다른 DB에서는 어떤가

이 장의 CREATE TABLE, SELECT/JOIN, INSERT/UPDATE/DELETE는 PostgreSQL, MySQL, SQLite에서 거의 그대로 동작합니다. 제품마다 차이가 나는 것(타입, 제약 강제, 잠금)은 그것이 학습에 영향을 주는 장에서 "다른 DB에서는" 상자로 따로 알려 드립니다.

핵심 요약

  1. 이 교재는 SQL 문법이 아니라 테이블 구조를 고르는 설계를 배웁니다. 코드는 PostgreSQL 기준이고 키워드는 대문자입니다.
  2. 동백커피의 주문은 주문 → 제조 → 픽업 → 정산으로 흐르고, 주문 안의 한 줄이 주문 라인입니다.
  3. DBMS·스키마·키·제약조건·인덱스·트랜잭션은 이름표만 붙였습니다. 스키마와 키는 2장, 제약조건은 4장, 인덱스는 7장, 트랜잭션은 8장에서 제대로 다룹니다.
  4. 표를 볼 때는 먼저 "한 행이 무엇을 뜻하는가"를 묻습니다. CREATE TABLE은 표의 모양과 규칙을, SELECT ... JOIN ... WHERE는 조회를, INSERT/UPDATE/DELETE는 변경을 뜻하며 WHERE가 대상을 정합니다.
  5. 여러 문장을 전부 성공 아니면 전부 취소로 묶는 장치가 트랜잭션입니다(8장).

SELECT m.name, ol.quantity FROM order_line AS ol JOIN menu AS m ON m.menu_id = ol.menu_id WHERE ol.order_id = 101;

  1. 아메리카노 2, 치즈케이크 1
  2. 아메리카노 2, 카페라떼 1, 치즈케이크 1
  3. menu 표의 3행 전체

이 교재의 JOIN은 두 표 양쪽에 짝이 있는 행만 남깁니다(정식 이름은 INNER JOIN). 짝이 없는 행도 남기는 변형(LEFT JOIN)이 있지만 필요한 장에서 설명합니다. 또 ORDER BY가 없으므로 위 두 행이 어떤 순서로 나올지는 DB가 보장하지 않습니다. 화면에 보이는 순서에 의존하는 코드는 언젠가 깨집니다.

UPDATE menu SET price = 5000; (WHERE 없음)을 실행하면 어떻게 될까요?

  1. 첫 번째 행만 5000으로 바뀐다
  2. 모든 메뉴의 가격이 5000으로 바뀐다
  3. WHERE가 없다며 DB가 실행을 거부한다

실무 습관 두 가지. 먼저 같은 WHERE로 SELECT를 실행해 대상 행을 눈으로 확인하고, 변경은 트랜잭션 안에서 실행해 결과를 확인한 뒤 COMMIT합니다(8장에서 이 습관의 이유가 더 분명해집니다). 일부 DB 클라이언트에는 WHERE 없는 변경을 막는 옵션이 있지만 기본값은 아닙니다.

이미 menu_id가 1인 행이 있는 menu 표에 menu_id = 1인 행을 또 INSERT하면 어떻게 될까요?

  1. 기존 행이 새 값으로 덮어써진다
  2. 같은 menu_id를 가진 행 두 개가 함께 저장된다
  3. DB가 오류를 내며 입력을 거부한다

"있으면 수정하고 없으면 추가"를 한 문장으로 하는 문법을 흔히 UPSERT라고 하고, PostgreSQL에서는 INSERT ... ON CONFLICT ... DO UPDATE로 씁니다. 이 교재의 범위 밖이지만, 제약조건이 오류를 내는 것과 그 오류를 앱이 어떻게 처리할지는 별개의 설계 문제라는 점이 4장의 출발점입니다.

모범답안 — 그리고 흔한 오답이 왜 틀리는지 
-- 모범답안SELECT name, price
FROM   menu
WHERE  price >= 5000;

결과는 카페라떼 5000, 치즈케이크 6500입니다.

흔한 오답 1 — price > 5000. "이상"은 5000을 포함합니다. >로 쓰면 카페라떼가 빠집니다. 경계값을 포함하는지는 설계에서도 자주 틀리는 부분입니다(4장의 CHECK).

흔한 오답 2 — price = 5000. "이상"을 "같다"로 읽은 것입니다. 정확히 5000원인 카페라떼만 나오고 6500원인 치즈케이크가 빠집니다.
