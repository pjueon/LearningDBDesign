3장 · 페이지 1

정규화: 나눈 설계를 검증하는 도구

2장에서 요구사항 문장으로 스키마 v1을 뽑았습니다. 그런데 이 설계가 정말 중복 없이 옳은지는 어떻게 확인할까요? 이 장은 그 검증 도구를 만드는 장이고, 이 교재에서 가장 무거운 장입니다. 페이지 하나하나는 짧으니 이틀에 나눠 읽어도 됩니다.

서연

표를 나눴으니 이제 전화번호 바꾸는 건 한 군데만 고치면 되죠? 그럼 끝난 거죠?

개발자

1장에서 겪은 사고들이 정말 사라졌는지 v1에서 다시 해 볼게요.

다시 보기: 2장의 스키마 v1 (네 표의 열과 키)

표 (한 행은)열기본키외래키
menu (메뉴 한 종류)menu_id, name, pricemenu_id—
member (회원 한 명)member_id, name, phone (UNIQUE)member_id—

1장의 세 사고를 v1에서 다시 시도합니다. UPDATE, INSERT, DELETE는 0장에서 배운 그대로입니다.

-- v1에서 1장의 세 사고를 다시 시도-- 갱신: 민준의 전화번호를 바꾼다
UPDATE member SET phone = '010-7777-8888' WHERE member_id = 1;

-- 삽입: 아직 안 팔린 신메뉴를 등록한다
INSERT INTO menu (menu_id, name, price) VALUES (4, '바닐라라떼', 5500);

-- 삭제: 주문 101을 지운다 (라인을 먼저, 주문을 나중에)
DELETE FROM order_line WHERE order_id = 101;
DELETE FROM orders     WHERE order_id = 101;
  • 갱신 — 번호는 member의 한 행에만 있으니 한 문장으로 끝납니다.
  • 삽입 — 주문이 없어도 menu에 행이 들어갑니다.
  • 삭제 — 주문 101을 지워도 menu의 치즈케이크는 그대로입니다. 라인을 먼저 지우는 이유는 2장에서 본 외래키 때문입니다. 주문을 먼저 지우면 남은 라인이 사라진 주문을 가리키게 되므로 DB가 거부합니다.

(시연은 여기까지이고, 다음 페이지부터는 시연 전의 v1 데이터를 그대로 씁니다. 민준의 번호는 010-1111-2222, 주문 101도 남아 있습니다.)

세 사고 모두 통과했습니다. 그런데 이 확인에는 약점이 둘 있습니다.

  1. 이미 아는 사고만 시험했습니다. 열이 30개, 표가 20개인 설계에서는 어떤 사고가 생길지조차 미리 알 수 없습니다.
  2. 직관에 기댄 확인입니다. "이 열은 이 표에 있는 게 맞겠지"라는 감으로는 다른 사람과 의견이 갈렸을 때 근거가 없습니다. 2장에서 orders.barista가 문제인지 아닌지 미뤄 둔 것도 그래서입니다.

이 장의 진행

  1. 페이지 2~4 — "무엇이 무엇을 정하는가"를 뜻하는 함수 종속을 배웁니다. 이것이 모든 판단의 기준입니다.
  2. 페이지 5~6 — 1NF: 한 칸에는 값 하나.
  3. 페이지 7~9 — 2NF, 3NF, 파생값: 1장의 엑셀 시트를 기준으로 표가 어떻게 v1이 되는지 봅니다.
  4. 페이지 10~13 — BCNF(선택), 전체 정리, 요약표, 무손실 분해(선택).
  5. 페이지 14~16 — 정규화의 비용과 반대 의견, v2, 정리.

3장 · 페이지 2

"이것이 정해지면 저것이 정해진다"

먼저 menu 표에서 어떤 값이 어떤 값을 정하는지 봅시다.

menu_idnameprice
1아메리카노4500
2카페라떼5000
3치즈케이크6500

menu_id가 1이라고 알려 주면 이름은 아메리카노, 가격은 4500으로 하나로 정해집니다. menu_id가 같은 행이 둘 있을 수 없기 때문입니다. 이 관계를 "menu_id가 name을 정한다"고 말하고 menu_id → name으로 씁니다. 같은 이치로 menu_id → price입니다.

화살표는 한 방향입니다. 반대 방향도 성립하는지 볼까요?

  • price → name? 가격이 4500이라고 알려 주면 메뉴를 하나로 정할 수 있을까요? 지금 표에서는 가격이 모두 달라서 정해지는 것처럼 보이지만, 4500원짜리 쿠키가 신메뉴로 들어오면 4500원은 아메리카노일 수도 쿠키일 수도 있습니다. 성립하지 않습니다.
  • name → menu_id? "메뉴 이름이 같으면 같은 메뉴다"라는 규칙을 정한다면 성립하고, 정하지 않으면 성립하지 않습니다.
관계읽는 법성립?
menu_id → name번호가 같은 두 행은 이름도 반드시 같다성립
menu_id → price번호가 같은 두 행은 가격도 반드시 같다성립
price → name가격이 같은 두 행은 이름도 반드시 같다불성립 (4500원 쿠키가 생길 수 있음)

이름 붙이기

이 관계를 함수 종속(functional dependency)이라고 합니다. A → B는 "A 값이 정해지면 B 값이 하나로 정해진다"는 뜻이고, 왼쪽 A를 결정자, 오른쪽 B를 종속되는 열이라고 부릅니다. "함수"라는 이름은 입력 하나에 출력이 하나인 수학의 함수와 같기 때문입니다. C++ 개발자에게는 std::map의 키가 값을 정하는 것과 같다고 보면 됩니다. 키를 알면 값이 하나로 정해지고, 값에서 키로 가는 반대 방향은 보장되지 않습니다 (위의 name → menu_id처럼 업무 규칙이 있으면 따로 성립할 수는 있습니다). 다만 비유는 여기까지입니다. map은 키에서만 값을 찾지만, 함수 종속은 행을 구별하는 열이 아닌 열끼리도 생기고(페이지 3의 전화 → 고객명), DB는 그런 종속을 저절로 지켜 주지 않습니다.

이 관계는 업무의 사실입니다. "메뉴 번호가 가격을 정한다"는 DB가 아니라 가게의 규칙이고, 표는 그 규칙을 담는 그릇입니다. 다음 페이지에서 이런 규칙을 어떻게 찾는지 봅니다.

3장 · 페이지 3

함수 종속을 찾는 법 — 업무 규칙이지 데이터의 우연이 아니다

함수 종속은 표의 데이터를 보고 찾을 수 없습니다. 지금 데이터에서 성립해 보이는 것이 규칙이 아니라 우연일 수 있기 때문입니다. (페이지 2의 price → name이 그랬습니다.) 방법은 두 가지를 함께 쓰는 것입니다.

  1. 업무에 묻습니다. 열 두 개 A, B에 대해 "A가 같은데 B가 다른 경우가 있을 수 있나요?"라고 물었을 때 "있다"는 답이 나오면 A → B가 아닙니다.
  2. 데이터는 반례를 찾는 데만 씁니다. A가 같은데 B가 다른 두 행이 하나라도 있으면 A → B는 확실히 불성립입니다. 반대로 반례가 없다고 성립이 증명되지는 않습니다. 데이터가 적을수록 우연히 성립해 보이는 것이 많습니다.

1장의 시트에 주문번호 열을 하나 붙여서 봅시다. 1장에서는 같은 일시·같은 고객을 사람이 눈으로 묶었는데, 이제 번호로 구별합니다.

1013/4 09:10민준010-1111-2222치즈케이크65001카드지호

개발자

한 주문을 카드와 현금으로 나눠 내는 손님도 있나요?

서연

아니요, 한 주문은 한 가지 방법으로만 결제해요.

함수 종속업무에 묻는 질문 → 답성립?
주문번호 → 일시같은 주문번호인데 접수 시각이 다를 수 있나? 아니요성립
주문번호 → 결제한 주문의 결제수단이 둘일 수 있나? 서연이 아니라고 함성립
주문번호 → 바리스타한 주문을 접수한 바리스타는 한 명이다 (2장 요구사항)성립
주문번호 → 전화한 주문은 회원 한 명의 것이다성립
전화 → 고객명같은 번호의 회원이 둘일 수 있나? 아니요(2장 규칙)성립
메뉴 → 단가같은 메뉴의 단가가 다를 수 있나? 지금은 아니요성립
일시 → 결제같은 시각에 접수한 두 주문의 결제가 다를 수 있다불성립

규칙이 바뀌면 함수 종속도 바뀐다

만약 서연이 "카드와 현금을 나눠 내는 것을 받겠다"고 하면 주문번호 → 결제가 깨지고, 결제는 주문에서 떼어 표를 새로 만들어야 합니다. 표를 어디서 나눌지는 업무 규칙이 정합니다. 1장에서 "얼마나 쪼갤지"의 기준이 필요하다고 했는데, 그 기준이 바로 함수 종속입니다. "메뉴 → 단가"에 붙인 "지금은"이라는 말은 페이지 15에서 다시 만납니다.

3장 · 페이지 4

함수 종속으로 후보키를 다시 찾는다

2장에서 후보키를 "유일성과 최소성을 만족하는 열 조합"이라 했습니다. 함수 종속이 있으면 이 정의를 계산으로 바꿀 수 있습니다. 열 조합 K가 후보키이려면 K가 모든 열을 정해야 하고(모든 열이 K에서 나옴), K에서 열을 빼면 그렇지 않아야 합니다(최소).

페이지 3의 시트에서 후보키를 찾아 봅시다. 알려진 함수 종속은 다음과 같습니다.

  • 주문번호 → 일시, 전화, 결제, 바리스타
  • 전화 → 고객명
  • 메뉴 → 단가
  • (주문번호, 메뉴) → 수량 — 어느 주문의 어느 메뉴인지를 알아야 수량이 정해집니다.

후보로 주문번호 하나를 써 봅니다. 이 값에서 출발해 정해지는 열을 계속 늘려 가는 계산입니다.

단계정해진 열이유
시작주문번호출발점
1+ 일시, 전화, 결제, 바리스타주문번호 → …
2+ 고객명전화가 정해졌으니 전화 → 고객명
더 늘지 않음. 메뉴, 단가, 수량은 정해지지 않았다 → 주문번호만으로는 후보키가 아니다

이번에는 (주문번호, 메뉴)로 해 봅니다.

단계정해진 열이유
시작주문번호, 메뉴출발점
1+ 일시, 전화, 결제, 바리스타주문번호 → …
2+ 고객명전화 → 고객명
3+ 단가메뉴 → 단가
4+ 수량(주문번호, 메뉴) → 수량
아홉 열이 모두 정해졌다. 둘 중 하나를 빼면 안 된다 → 후보키

최소인지도 확인합니다. 메뉴 하나에서는 메뉴와 단가에서 멈추고(메뉴 이름이 메뉴를 구별한다고 가정합니다), 주문번호 하나는 위에서 봤듯 부족하므로 둘 다 필요합니다.

이 시트의 후보키는 (주문번호, 메뉴), 즉 열 두 개를 묶은 키입니다. 이 사실이 다음 페이지들의 열쇠입니다. 한 열이 키의 일부에만 종속되는 경우와, 키에서 다른 열을 거쳐 종속되는 경우를 가려내는 것이 2NF와 3NF입니다.

2장의 order_line과 같은 키입니다

v1의 order_line도 (order_id, menu_id)가 기본키였습니다. 연결 테이블의 키가 두 열의 조합이 되는 이유가 이 계산으로 설명됩니다. 수량은 주문과 메뉴 두 값이 함께 있어야 정해지기 때문입니다.

3장 · 페이지 5

1NF — 한 칸에는 값 하나

정규화의 첫 규칙은 함수 종속과 상관없이 표의 모양에 대한 것입니다. 두 개의 초안을 봅시다. 동료가 만든 설계라고 합시다.

초안 A — 회원이 번호를 여러 개 등록할 수 있게 하려는 표
member_idnamephones
1민준010-1111-2222, 010-9999-0000
2소라010-3333-4444
초안 B — 주문마다 메뉴를 한 칸에 적는 표
order_idordered_atmenus
1013/4 09:10아메리카노 2, 치즈케이크 1
1023/4 09:25카페라떼 1

둘 다 한 칸에 값이 여러 개 들어 있습니다. 어떤 문제가 생기는지 봅시다.

  • 찾을 수 없습니다. WHERE phones = '010-9999-0000'은 민준을 찾지 못합니다. 칸 전체가 두 번호를 이은 글자이기 때문입니다. 글자 일부를 찾는 LIKE를 쓰면 되지만 그것은 우회이고, 번호가 다른 번호의 일부와 겹치면 엉뚱한 결과가 나옵니다.
  • 센 수 없습니다. "아메리카노가 몇 잔 팔렸는가"를 구하려면 칸 안의 글자를 쪼개 해석해야 합니다. 1장의 시트에서 메뉴별로 셀 때 겪은 고통이 더 심해집니다.
  • 일부만 고칠 수 없습니다. 번호 하나만 바꾸려 해도 칸 전체를 다시 써야 하고, 그 과정에서 다른 번호를 망가뜨릴 수 있습니다.
  • 규칙을 걸 수 없습니다. 2장에서 배운 UNIQUE는 칸 전체에 걸리므로 "같은 번호를 두 번 등록하지 못한다"를 표현할 수 없습니다.

열을 phone1, phone2, phone3처럼 반복해서 늘리는 방법도 같은 종류의 실수입니다. 세 번째까지만 되고 네 번째 번호는 표를 고쳐야 넣을 수 있으며, 어느 열에 있는지 모르니 검색은 열마다 해야 합니다.

이름 붙이기

표의 모든 칸이 원자값, 즉 업무에서 더 쪼개면 뜻이 깨지는 값 하나여야 한다는 규칙이 제1정규형(1NF)입니다. 반복되는 열도 같은 이유로 1NF를 어긴 것으로 봅니다. 원자값의 기준은 업무가 정합니다. 이름을 성과 이름으로 쪼개지 않아도 되는 이유는 이 시스템이 그것을 따로 다루지 않기 때문입니다.

앞 장들의 표는 이미 1NF입니다

0~2장의 모든 표는 한 칸에 값 하나이므로 1NF를 만족합니다. 이 규칙이 필요한 것은 "편하니까 한 칸에 몰아 적자"는 유혹이 생길 때입니다.

3장 · 페이지 6

1NF 위반 고치기

고치는 방법은 언제나 같습니다. 여러 개인 값을 행으로 옮기는 것입니다. 먼저 초안 A를 생각해 봅시다. 스스로 어떻게 나누겠는지 잠깐 생각한 뒤 탭을 눌러 확인하세요.

-- 번호 여러 개를 한 칸에-- member(member_id, name, phones)
-- 1 | 민준 | 010-1111-2222, 010-9999-0000

SELECT name FROM member
WHERE  phones = '010-9999-0000';   -- 결과 0행: 민준을 못 찾는다

-- 번호를 행으로 옮긴다 (member 에서는 phones 열을 뺀다)CREATE TABLE member_phone (
    phone      TEXT    PRIMARY KEY,
    member_id  INTEGER NOT NULL REFERENCES member (member_id)
);
-- 1행: '010-1111-2222' → 회원 1
-- 2행: '010-9999-0000' → 회원 1

SELECT m.name
FROM   member_phone AS mp
JOIN   member AS m ON m.member_id = mp.member_id
WHERE  mp.phone = '010-9999-0000';  -- 민준 1행
  • 번호 하나가 한 행이 되었습니다. 표의 한 행이 무엇인지 물어보면 "회원이 가진 전화번호 하나"입니다.
  • phone이 기본키이므로 같은 번호를 두 번 등록할 수 없습니다. 페이지 5에서 못 걸던 규칙을 이제 걸 수 있습니다.
  • 회원과 번호는 1:N 관계입니다. 2장에서 배운 대로 N쪽인 member_phone에 외래키를 둡니다.
  • 번호를 기본키로 써도 괜찮은 이유가 있습니다. 다른 표가 이 번호를 가리키지 않아서, 번호가 바뀌어도 2장에서 본 값의 전파 문제가 없습니다.

초안 B도 같습니다. 주문 한 건에 메뉴가 여러 개 담기는 것은 2장에서 본 N:M 관계이고, 그것을 풀어낸 것이 order_line입니다. 한 칸에 적힌 "아메리카노 2, 치즈케이크 1"이 order_line의 두 행이 됩니다.

초안 B의 칸order_line의 행 (order_id, menu_id, quantity)

(101, 3, 1)

2장이 이미 1NF를 지킨 것입니다

2장에서 N:M을 연결 테이블로 푼 것은 결국 1NF를 지키는 방법이었습니다. 1:N과 N:M에서 "여러 개"를 한 칸에 담지 않고 행으로 옮긴다는 원리는 같습니다. 설계를 ER로 뽑는 사람은 1NF 위반을 처음부터 잘 만들지 않는 편이라, 이 규칙은 동료의 초안을 검토할 때 특히 쓸모가 있습니다.

3장 · 페이지 7

2NF — 키의 일부에만 종속된 열

페이지 3의 시트로 돌아갑니다. 키는 (주문번호, 메뉴)였습니다. 이제부터 키가 아닌 열은 어떤 후보키에도 속하지 않는 열을 뜻합니다(이 시트에서는 주문번호와 메뉴를 뺀 나머지). 키가 아닌 열 각각이 키 전체에 종속되는지, 키의 일부에만 종속되는지 봅니다.

이름 붙이기

키의 일부에만 종속되는 열이 있는 상태를 부분 종속이라 하고, 부분 종속이 없는 것이 제2정규형(2NF)입니다. 정확히는 1NF이면서 키가 아닌 열이 모두 각 후보키의 일부가 아니라 전체에 종속된 표입니다. 키에 속한 열(주문번호, 메뉴)은 이 검사의 대상이 아닙니다.

고치는 법은 부분 종속을 결정자와 함께 떼어 새 표로 옮기는 것입니다.

키가 열 하나인 표는 2NF가 자동입니다

부분 종속은 키가 두 열 이상일 때만 생길 수 있습니다. 키가 열 하나인 표에서는 "일부"라는 것이 없기 때문입니다. 그래서 2NF는 연결 테이블(order_line 같은 복합키 표)과 시트처럼 키가 복합인 한 장짜리 표를 점검할 때 쓰는 규칙입니다.

3장 · 페이지 8

3NF — 다른 열을 거쳐서 정해지는 열

페이지 7의 주문 표를 다시 봅시다. 키가 주문번호 하나라서 2NF는 통과했습니다. 그런데 한 가지 이상한 점이 있습니다.

주문번호일시고객명전화결제바리스타
1013/4 09:10민준010-1111-2222카드지호

민준의 이름과 전화번호가 주문 101과 103에 각각 적혀 있습니다. 왜일까요? 함수 종속을 따라가 보면 이렇습니다.

  • 주문번호 → 전화 — 주문이 회원을 정합니다.
  • 전화 → 고객명 — 회원이 이름을 정합니다.
  • 그러므로 주문번호 → 전화 → 고객명. 고객명은 주문이 아니라 전화(회원)가 정하는데, 주문 표에 실려 있습니다.

고객명은 키(주문번호)에 직접 종속되지 않고 다른 열(전화)을 거쳐서 종속됩니다. 그래서 같은 회원의 주문이 늘 때마다 이름이 반복됩니다.

이름 붙이기

키가 아닌 열이 다른 키가 아닌 열을 정하는 이행 종속이 없는 것이 제3정규형(3NF)입니다. 2NF와 3NF를 한 문장으로 외우는 유명한 표현이 있습니다. 키가 아닌 열은 모두 "키에 의해, 키 전체에 의해, 오직 키에 의해" 정해져야 한다는 것입니다. "키에 의해"는 1NF의 기본, "키 전체"는 2NF(부분 종속 금지), "오직 키"는 3NF(이행 종속 금지)입니다.

고치는 법은 같습니다. 이행 종속을 결정자(전화)와 함께 떼어 새 표로 옮깁니다. 회원 표가 생기고, 2장에서 골랐듯(바뀔 수 있는 전화번호 대신 바뀌지 않는 번호를 기본키로) 번호 member_id를 대리키로 붙이면 주문 표는 회원을 그 번호로 가리킵니다.

3장 · 페이지 9

파생값 — 계산할 수 있는 값을 저장해도 될까

1장의 시트에는 합계 열이 있었고 v1에는 없습니다. 페이지 3에서 이 열을 뺀 이유를 이제 설명할 차례입니다. 합계 = 단가 × 수량은 다른 열에서 계산할 수 있는 값입니다. 이런 값을 파생값이라고 합니다.

함수 종속으로 보면 (단가, 수량) → 합계입니다. 키가 아닌 열이 키가 아닌 열을 정하는 모양이라 3NF의 이행 종속과 같은 문제를 가집니다. 주문 전체의 총액은 조금 다릅니다. 총액은 다른 표(order_line, menu)의 여러 행에서 나오는 값이라 정규형 검사에는 걸리지 않습니다. 하지만 같은 사실을 두 곳에 적는다는 점에서 같은 종류의 문제를 일으킵니다. 그래서 정규형과 별개로 이 페이지에서 따로 판단합니다.

총액을 저장하면 어떻게 될까요? 라인의 수량을 하나 고치면 총액도 함께 고쳐야 합니다. 하나만 고치고 하나를 놓치면 총액이 라인의 합과 어긋나는 상태가 됩니다. 1장에서 본 갱신 이상이 다시 생기는 것입니다.

결정: 총액은 저장하지 않고 계산합니다. 이유는 정확성이 먼저이기 때문입니다. 느려지면 그때 되돌려도 되고, 그 판단은 측정한 뒤에 하는 것이 옳습니다. 이 결정을 스키마의 기록된 결정(D4)으로 남깁니다. 7장에서 다시 본다

-- 주문별 총액을 계산으로 구한다SELECT o.order_id,
       SUM(m.price * ol.quantity) AS total
FROM   orders AS o
JOIN   order_line AS ol ON ol.order_id = o.order_id
JOIN   menu AS m        ON m.menu_id   = ol.menu_id
GROUP BY o.order_id
ORDER BY o.order_id;
  1. 1~2행 SUM(m.price * ol.quantity)는 묶음 안의 값을 모두 더하는 집계 함수입니다. 라인 하나의 금액(단가 × 수량)을 만들어 더합니다. AS total은 결과 열의 이름입니다.
  2. 3~5행 주문, 라인, 메뉴를 번호로 잇습니다. 0장과 1장의 JOIN과 같습니다.
  3. 6행 GROUP BY o.order_id는 주문번호가 같은 행끼리 묶는다는 뜻이고, 묶음마다 SUM이 한 번씩 실행됩니다.
  4. 7행 결과 순서를 요청합니다.

3장 · 페이지 10 · 선택

BCNF 맛보기 (선택) — 3NF로 못 잡는 드문 경우

이 페이지는 선택입니다. 건너뛰어도 뒤를 읽는 데 지장이 없습니다.

3NF까지 지켰는데도 중복이 남는 드문 경우가 있습니다. 동백커피가 원두 클래스를 열어 회원이 클래스 종류별로 강사를 배정받는다고 해 봅시다. (2장 직접 해보기의 클래스와 관계없는 설명용 예입니다.) 규칙은 이렇습니다.

  • 회원은 한 클래스 종류에 강사 한 명을 배정받는다.
  • 강사는 한 가지 클래스 종류만 가르친다.

함수 종속은 (회원, 클래스 종류) → 강사와 강사 → 클래스 종류입니다. 후보키는 (회원, 클래스 종류)와 (회원, 강사) 둘입니다. 강사 → 클래스 종류에서 클래스 종류는 후보키의 일부이므로 "키가 아닌 열이 키가 아닌 열을 정하는" 3NF 위반의 정의에 걸리지 않습니다. 그러나 가온이 핸드드립을 가르친다는 사실이 가온의 배정마다 반복됩니다.

이름 붙이기

모든 결정자가 후보키여야 한다는 더 엄격한 규칙이 BCNF(보이스-코드 정규형)입니다. 위 표에서 강사는 결정자인데 후보키가 아니므로 BCNF 위반입니다. 고치면 (강사, 클래스 종류)와 (회원, 강사)로 나뉩니다. 3NF와 BCNF가 다른 것은 후보키가 겹치는 드문 경우뿐이라 v1의 모든 표는 3NF이면서 BCNF입니다.

대가가 있습니다

나누고 나면 원래 표에 있던 규칙 (회원, 클래스 종류) → 강사가 한 표 안에 없어서 DB의 키 제약만으로는 지킬 수 없습니다. 같은 회원이 같은 종류에 서로 다른 강사를 배정받는 행이 들어가는 것을 막지 못합니다. 이 문제는 페이지 13에서 "종속 보존"이라는 이름으로 다시 나옵니다.

이 표가 말해 주는 것

3장 · 페이지 13 · 선택

무손실 분해와 종속 보존 (선택) — 나눌 때 지킬 두 가지

이 페이지는 선택입니다. 표를 나눌 때 어디서 나누느냐에 따라 나눈 결과가 원래 정보를 잃어버릴 수 있다는 직관을 봅니다.

설명용 표 T(주문번호, 결제, 바리스타, 메뉴)의 두 행을 잘못 나눠 봅시다. (v1의 orders와 다른 표입니다. 한 주문은 한 가지 방법으로만 결제하므로 주문번호 → 결제입니다.)

주문번호결제바리스타메뉴
101카드지호아메리카노
102현금지호카페라떼

바리스타를 공통 열로 남기고 나눕니다. P(주문번호, 바리스타, 메뉴)와 Q(바리스타, 결제) 두 표입니다. 원래 표의 네 열은 모두 어느 한쪽에 들어 있습니다.

PQ
주문번호바리스타메뉴바리스타결제
101지호아메리카노지호카드
102지호카페라떼지호현금

P와 Q를 바리스타로 JOIN하면 4행이 나옵니다. P의 행마다 Q에서 지호인 행 두 개가 모두 짝이 되기 때문입니다.

주문번호바리스타메뉴결제
101지호아메리카노카드원래 있던 행
101지호아메리카노현금가짜 행
102지호카페라떼카드가짜 행
102지호카페라떼현금원래 있던 행

원래 두 행이 네 행으로 늘어났습니다. 이제 주문 101이 카드로도 현금으로도 결제한 것처럼 보이고, 표만 봐서는 어느 것이 진짜인지 알 수 없습니다. 이렇게 나눈 결과를 다시 이었을 때 원래에 없던 행이 섞여 원래 표로 돌아가지 않는 분해를 손실 분해라고 합니다.

두 가지 원칙

  • 무손실 분해 — 나눈 표를 다시 이으면 원래의 행이 정확히 나옵니다. 나눌 때 공통으로 남기는 열이 한쪽 표의 후보키이면 보장됩니다(충분조건). 위 예에서 바리스타는 어느 쪽에서도 키가 아니어서 실패했고, 페이지 8에서 회원 표를 떼어낼 때의 공통 열(전화)은 회원 표의 키여서 성공했습니다(그 뒤 대리키 member_id로 바꿔 가리켜도 마찬가지입니다).
  • 종속 보존 — 원래 표에 있던 함수 종속이 나눈 표 어딘가 한 표 안에서 여전히 지켜질 수 있습니다. 페이지 10의 BCNF 분해가 이것을 잃는 예였습니다.

2NF와 3NF의 분해는 결정자를 함께 떼어내므로 항상 무손실입니다. 페이지 10의 BCNF 분해도 공통 열 강사가 (강사, 클래스 종류) 표의 키라서 무손실이고, 그 분해가 잃는 것은 정보가 아니라 종속 보존입니다. 그래서 이 장에서 실제로 걱정할 것은 이 정도입니다. 직접 나눌 때는 공통 열이 키인지만 확인하세요.

3장 · 페이지 14

정규화의 비용과 반대 의견 — 언제 멈추는가

정규화는 공짜가 아닙니다. 0장과 1장에서 미룬 질문 "표를 나누면 JOIN을 해야 하는데 그 비용은?"에 답합니다.

  • 조회가 복잡해집니다. 페이지 9의 총액 조회는 표 세 개를 이었습니다. 시트라면 열 하나를 더하면 되었습니다.
  • 이어 붙이는 데 일이 듭니다. DB는 JOIN할 때 두 표의 행을 짝지어야 하고, 행이 많아질수록 이 일이 커집니다. 다만 이어 붙이는 열에 인덱스가 있으면 그 일이 크게 줄어듭니다. 그래서 "정규화하면 느리다"는 말은 반만 맞습니다. 7장에서 다시 본다
  • 표가 늘어납니다. 표가 많으면 이해하고 관리하기 어려워집니다.
주장내용
정규화를 지지중복이 없어서 정확하고, 고치기 쉽고, 규칙을 DB에 맡기기 쉽다. 데이터 정확성은 나중에 고치기 어렵다. 속도는 나중에 고칠 수 있다.
정규화를 의심읽기가 압도적으로 많은 보고서·분석에서는 미리 합쳐 둔 표가 훨씬 편하고 빠르다. 표를 지나치게 쪼개면 조회 작성이 고통스럽다.
이 교재의 입장먼저 정규화하고, 측정해서 문제가 나오면 그 부분만 의도적으로 되돌린다. 미리 짐작해서 합치지 않는다. 되돌리는 방법은 7장에서 다룬다.

언제 멈출까요? 실무에서 널리 쓰는 기준은 3NF(또는 BCNF)입니다. 그 아래로 내려가면 중복 때문에 이상현상이 생기고, 그 위로 올라가는 정규형은 실제로 만나기 드뭅니다. 위로 올라가는 것이 있다는 것만 알아 둡니다.

4NF와 5NF는 이름만

  • 4NF — 한 회원에게 서로 무관한 여러 값 목록이 있을 때 생깁니다. 예를 들어 회원 한 명의 좋아하는 메뉴 3개와 알레르기 2개를 한 표에 넣으면 서로 무관한데도 3 × 2 = 6행이 필요해집니다. 즐겨찾기 표와 알레르기 표로 따로 두면 해결됩니다.
  • 5NF — 세 방향 이상의 결합에서 생기는 아주 드문 경우입니다. 이 교재에서는 다루지 않습니다.

1장 페이지 11에서 물은 "얼마나 쪼갤지"의 답도 이제 나옵니다. 함수 종속이 표를 나눌 이유를 만드는 곳까지입니다. 전화번호의 국번을 표로 빼거나 색상마다 표를 만드는 것은 종속에서 나오는 이유가 없으므로 과분할입니다.

정규화가 보장하는 것과 못 하는 것

정규화는 같은 사실을 두 번 적지 않게 해서 갱신·삽입·삭제 이상을 막습니다. 그러나 다음은 보장하지 않습니다.

  • 값의 의미: "가격"이 지금의 가격인지 그때의 가격인지는 정규화가 알 수 없습니다.
  • 규칙: 수량이 1 이상이어야 한다 같은 규칙은 정규형과 무관합니다(4장).
  • 변하는 요구사항: 요구사항이 바뀌면 표를 나눌 이유도 바뀝니다.

"정규화했으니 끝이다"가 아니라 "정규화는 시작점이다"가 이 교재의 태도입니다. 이 구멍이 실제 요구사항으로 닥치는 것이 6장입니다.

핵심 요약

  1. 함수 종속 A → B는 "A가 정해지면 B가 하나로 정해진다"는 업무 규칙입니다. 데이터는 반례를 찾는 데만 쓰고, 성립 여부는 업무에 묻습니다.
  2. 1NF는 한 칸에 값 하나, 2NF는 키의 일부에만 종속된 열 금지, 3NF는 다른 열을 거쳐 종속된 열 금지입니다. 키가 아닌 열은 모두 "키에 의해, 키 전체에 의해, 오직 키에 의해" 정해져야 합니다.
  3. 1장 시트에 2NF와 3NF를 적용하면 v1의 네 표가 나옵니다. 스키마 v2 = v1이고, 정규화는 새로 만드는 도구이기보다 검증 도구입니다.
  4. 계산할 수 있는 파생값(총액)은 저장하지 않는다가 기본이고, 느려지면 측정한 뒤 의도적으로 되돌립니다(7장).
  5. 정규화는 중복을 없앨 뿐 값의 의미는 보장하지 않습니다. 과거 주문 금액이 위험한 이유는 6장에서 다룹니다.

퀴즈에 쓰는 표

페이지 2의 menu 표입니다.

menu_idnameprice
1아메리카노4500
2카페라떼5000
3치즈케이크6500

위 menu 표에서는 price가 같은 두 행이 없습니다. 그러면 price → name(가격이 이름을 정한다)은 함수 종속일까요?

  1. 그렇다. 가격이 같은 행이 없으니 성립한다
  2. 아니다. 지금 데이터의 우연일 뿐 업무 규칙이 아니다
  3. 함수 종속은 키 열에서만 생길 수 있다

데이터가 적을수록 우연히 성립해 보이는 종속이 많아서, 테스트 데이터로 종속을 정하는 것은 위험합니다. 또 하나의 사실: 키 제약(PRIMARY KEY, UNIQUE)이 지켜 주는 함수 종속은 키에서 나머지 열로 가는 것뿐입니다. "메뉴 번호가 가격을 정한다"는 기본키가 지켜 주지만, 키가 아닌 열 사이의 종속(전화 → 고객명 같은 것)은 표를 나누어 구조로 지키는 것이 기본입니다.

표 order_line2(order_id, menu_id, quantity, menu_name)의 기본키는 (order_id, menu_id)이고 menu_id → menu_name입니다. 이 표는 어떤 규칙을 어길까요?

  1. 2NF (부분 종속)
  2. 1NF (원자값)
  3. 어기는 규칙이 없다

이 표에서 메뉴 이름 하나를 고치려면 그 메뉴가 나온 라인 수만큼의 행을 모두 고쳐야 하고, 하나라도 빠지면 같은 메뉴가 이름 두 개를 갖습니다. 1장의 갱신 이상이 키 자리를 바꿔 다시 나타난 것입니다. 2NF 위반은 이렇게 이름을 고치는 UPDATE 한 번이 행 여러 개에 걸치는 것으로 알아챌 수 있습니다.

표 orders2(order_id, member_id, member_name)의 기본키는 order_id이고 member_id → member_name입니다. 이 표는 어떤 규칙을 어길까요?

  1. 2NF (부분 종속)
  2. 1NF (원자값)
  3. 3NF (이행 종속)

이 위반은 member_name처럼 이름이 열 이름에 그대로 보이면 알아채기 쉽지만, 실무에서는 payment_code와 payment_label처럼 코드와 그 코드의 설명이 함께 들어 있는 열로 나타나는 경우가 흔합니다. 열 두 개가 "짝을 이루어 함께 바뀌는가"를 물으면 찾을 수 있습니다. 그리고 이 이름 열이 실제로 잘못되는 것은 이름을 고칠 때입니다. 조회만 하는 동안에는 문제가 없어 보여서 발견이 늦습니다.

직접 해보기

동백커피가 원두를 판매하기 시작했습니다(홀빈 판매 장부, 100g 단위). 한 줄이 "한 판매의 원두 한 종류"입니다. 원두 이름은 원두를 유일하게 구별한다고 합시다.

판매번호판매일회원전화회원명원두원산지100g단가수량
13/6010-1000-1000하나예가체프에티오피아32002
13/6010-1000-1000하나수프리모콜롬비아28001
23/7010-2000-2000세진예가체프에티오피아32001
  1. 함수 종속을 모두 적고, 후보키를 구하세요. (한 판매에 여러 원두가 담길 수 있고, 회원은 전화번호로 구별합니다.)
  2. 이 표의 2NF 위반과 3NF 위반을 각각 지적하세요.
  3. 3NF까지 만족하도록 표를 나누고, 각 표의 열과 기본키를 적으세요.
모범답안 — 그리고 흔한 오답이 왜 틀리는지

1. 함수 종속과 후보키

  • 판매번호 → 판매일, 회원전화 (한 판매는 한 날, 한 회원)
  • 회원전화 → 회원명
  • 원두 → 원산지, 100g단가
  • (판매번호, 원두) → 수량

계산해 보면 (판매번호, 원두)에서 모든 열이 나오고 하나라도 빼면 안 되므로 후보키는 (판매번호, 원두)입니다.

2. 위반

  • 2NF 위반 — 판매일, 회원전화는 판매번호만으로, 원산지, 100g단가는 원두만으로 정해집니다(키의 일부에만 종속). 회원명도 판매번호만으로 정해지지만 전화를 거치는 이행 종속이기도 해서 아래 3NF에서 다룹니다.
  • 3NF 위반 — 회원명은 회원전화를 거쳐 판매번호에 종속됩니다(이행 종속).

3. 나눈 결과

-- 열과 기본키bean(bean_id, name, origin, price_per_100g)      -- PK bean_id, 원두 한 종류
member(member_id, name, phone)                   -- PK member_id, phone 은 UNIQUE
sale(sale_id, sold_on, member_id)                -- PK sale_id, 판매 한 건
sale_line(sale_id, bean_id, quantity)            -- PK (sale_id, bean_id)

나눈 표의 번호(bean_id, member_id)는 2장의 대리키입니다. 원두 이름이나 전화번호를 그대로 키로 써도 위 종속 분석은 같으니 그렇게 답해도 틀린 것이 아닙니다.

흔한 오답 1 — 수량을 bean 표로 옮긴다. 수량은 어느 판매의 어느 원두인지 두 값이 함께 있어야 정해지므로 키 전체에 종속입니다. 원두 표에 두면 판매마다 다른 수량을 표현할 수 없습니다.

흔한 오답 2 — 원산지와 단가만 떼고 회원명은 판매 표에 남긴다. 이렇게 하면 2NF는 통과해도 회원전화 → 회원명이라는 이행 종속이 남아 같은 회원의 판매마다 이름이 반복됩니다(3NF 위반).

흔한 오답 3 — 판매일까지 별도 표로 뺀다. 판매일은 판매번호에 직접 종속되는 열이라 sale 표에 있어야 하고, 더 쪼갤 종속이 없으므로 과분할입니다(페이지 14).
