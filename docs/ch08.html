8장 · 화면 1

동시에 들어올 때: 트랜잭션과 제약

5장은 새 요구사항이, 7장은 데이터량이 설계를 흔들었습니다. 이번에는 같은 순간에 여러 요청이 들어온다는 것이 문제입니다. 지금까지의 모든 규칙은 "요청 하나가 혼자 실행된다"는 가정 위에 서 있었습니다. 키오스크 두 대와 앱이 동시에 주문을 보내는 순간 그 가정이 깨집니다.

서연

케이크와 쿠키는 제가 구워 놓는 거라 그날 개수가 정해져 있어요. 원두, 우유, 시럽은 잔을 만들 때마다 줄어들고요. 지금은 지호 씨가 눈으로 세다가 떨어지면 키오스크 앞에 '품절' 종이를 붙이는데, 손님이 주문을 누른 다음에야 "없습니다"라고 말씀드리는 일이 잦아요.

지호

우유가 조금 남았을 때가 제일 곤란해요. 라떼 한 잔은 되는데 '우유 추가'를 붙이면 모자라는 경우요. 재료가 모자라는 메뉴나 옵션은 키오스크에서 아예 눌리지 않고 '품절'로 보였으면 해요.

하윤

앱에는 픽업 시간 예약을 넣으려고 해요. 8시 반에서 9시 사이에 주문이 몰리니까, 시간대마다 받을 수 있는 주문 수를 정해 두고 꽉 찬 시간대는 못 고르게요.

개발자

세 가지네요. 개수를 세는 것, 재료가 모자라는 메뉴·옵션을 막는 것, 시간대마다 정원을 지키는 것. v5.1에는 재고도 시간대도 없으니 표부터 만들어야 합니다. 그런데 더 큰 문제는 세 가지가 모두 "확인하고 줄이는" 규칙이라는 점입니다.

8장 · 화면 2

재고의 두 종류와 레시피 — 무엇을 세고, 누가 얼마를 쓰는가

서연의 말에는 재고가 두 부류 들어 있습니다. 둘 다 "수량을 세어 관리하는 대상"이라 한 표에 담고 이름을 재고 품목이라 합니다.

  • 완제품 — 치즈케이크, 티라미수, 쿠키. 손님이 사는 것이 곧 재고라서 주문 1개가 재고 1개를 줄입니다.
  • 원재료 — 원두, 우유, 시럽. 손님이 사는 것이 아니라 메뉴를 만드는 데 들어갑니다. 카페라떼 한 잔은 원두 18g, 우유 200ml, 시럽 10ml를 쓰고, 옵션도 씁니다. 샷 추가는 원두 18g을, 우유 추가는 우유 100ml를 더 씁니다.

"얼마나 쓰는가"를 어디에 적을까요? 메뉴 표의 열 하나로는 안 됩니다. 라떼는 재료가 셋이고, 원두는 여러 메뉴가 씁니다. 메뉴와 품목은 N:M이라 2장의 연결 테이블이 필요하고, 소요량은 쌍 (메뉴, 품목)에 딸린 값입니다(amount는 메뉴만으로도, 품목만으로도 정해지지 않습니다). 5장에서 샷 추가의 횟수가 연결(order_line_option)의 속성이었던 것과 같은 모양입니다. 이 연결을 레시피라 부르고, 옵션도 같은 구조로 하나 더 둡니다.

-- 새 표 셋: 재고 품목, 메뉴 레시피, 옵션 레시피-- 재고 품목 한 가지 (완제품: 케이크·쿠키, 원재료: 원두·우유·시럽). qty 는 지금 남은 양
CREATE TABLE stock_item (
    item_id  INTEGER PRIMARY KEY,
    name     TEXT    NOT NULL UNIQUE
             CHECK (name <> '' AND name = btrim(name)),
    kind     TEXT    NOT NULL CHECK (kind IN ('완제품', '원재료')),
    unit     TEXT    NOT NULL CHECK (unit <> ''),
    qty      INTEGER NOT NULL CHECK (qty >= 0)
);

-- 메뉴 1개를 만들 때 이 품목을 amount 만큼 쓴다 (완제품은 소요량 1)
CREATE TABLE menu_recipe (
    menu_id  INTEGER NOT NULL REFERENCES menu (menu_id),
    item_id  INTEGER NOT NULL REFERENCES stock_item (item_id),
    amount   INTEGER NOT NULL CHECK (amount > 0),
    PRIMARY KEY (menu_id, item_id)
);

-- 옵션을 1회 고를 때마다 이 품목을 amount 만큼 더 쓴다
CREATE TABLE option_recipe (
    option_id  INTEGER NOT NULL REFERENCES option_item (option_id),
    item_id    INTEGER NOT NULL REFERENCES stock_item (item_id),
    amount     INTEGER NOT NULL CHECK (amount > 0),
    PRIMARY KEY (option_id, item_id)
);
  1. 2~9행 한 행은 "재고 품목 하나"입니다(치즈케이크, 원두 ...). qty는 정수이고 기본 단위(원두 g, 우유·시럽 ml, 완제품 개)로 저장하며, 8행의 CHECK (qty >= 0)가 재고 음수 금지(C13)의 마지막 방어선입니다. 6행 kind는 완제품·원재료를 가르지만 아래 결정 때문에 동작을 바꾸지 않고 목록·발주를 구분할 때 씁니다.
  2. 12~17행 한 행은 "이 메뉴 1개에 이 품목이 amount만큼 든다"입니다. 기본키 (menu_id, item_id)가 같은 품목을 한 메뉴에 두 줄 적는 것을 막고, amount > 0이라 "0g 쓴다" 같은 행은 저장되지 않습니다.
  3. 20~25행 옵션도 같은 모양이고, 기준은 옵션 1회입니다. 줄의 잔 수와 옵션 횟수(option_qty)는 곱해서 씁니다(화면 8).

결정 — 완제품도 "소요량 1"의 레시피로 둡니다

치즈케이크는 menu_recipe (3, 1, 1), 곧 "치즈케이크 1개에 품목 1(치즈케이크)이 1개"입니다. 완제품만 별도 경로(menu에 재고 품목 열)로 두는 안도 있었지만, 그러면 주문 트랜잭션이 "완제품이면 이렇게, 원재료면 저렇게" 갈라집니다. 통일하면 차감 경로가 하나(메뉴 → 레시피 → 품목)입니다. 대가는 소요량 1 행이 군더더기처럼 보이는 것입니다.

그래서 나중에 무슨 문제가 되는가

① "시럽 빼기"처럼 덜 쓰는 옵션은 amount > 0이라 적을 수 없어서, 시럽 10ml가 그대로 차감됩니다(재고가 실제보다 빨리 줄어드는 안전한 쪽의 오차입니다). 음수를 허용하는 안은 "메뉴 + 옵션의 합이 0 이상"이라는 또 하나의 여러 행 규칙을 만들어 채택하지 않았습니다. ② 케이크 세트(메뉴 5)에는 레시피를 두지 않습니다. 세트가 쓰는 재고는 고른 구성 메뉴의 레시피입니다(화면 12). ③ 재고 변동 이력은 두지 않습니다. 6장의 포인트는 정정과 감사가 핵심이라 원장이었지만, 재고는 "지금 몇 개"와 "음수 금지"가 중심이고 qty 행이 동시 요청을 줄 세울 자리이기도 합니다(화면 10에서 두 선택을 비교합니다). ④ qty를 동시에 줄이는 순간이 이 장의 본론입니다.

키오스크가 "품절"을 보이려면 어딘가에 "이 메뉴는 지금 못 판다"는 사실이 있어야 합니다. 두 길이 있습니다. menu에 is_sold_out 열을 저장하거나, 재고와 레시피에서 매번 계산하는 것입니다. 3장의 파생값 질문, D4(총액을 저장할까)와 같은 질문입니다.

-- 키오스크 메뉴판: 필요한 재료 중 하나라도 남은 양이 모자라면 available 이 falseSELECT m.menu_id, m.name, p.price,
       NOT EXISTS (SELECT 1
                   FROM   menu_recipe AS r
                   JOIN   stock_item  AS s ON s.item_id = r.item_id
                   WHERE  r.menu_id = m.menu_id
                     AND  s.qty < r.amount) AS available
FROM   menu AS m
JOIN   menu_price AS p ON p.menu_id = m.menu_id
WHERE  m.is_active
  AND  p.valid_from <= NOW()
  AND (p.valid_to IS NULL OR NOW() < p.valid_to)
ORDER BY m.menu_id;
-- 치즈케이크 qty 가 0 이면:      (3, 치즈케이크, 6500, false)
-- 우유가 90ml 남았다면:          (2, 카페라떼, 5000, false)
  • NOT EXISTS (...)는 4장에서 본 대로 "안쪽 조회가 한 행도 안 돌려줄 때" 참입니다. 안쪽은 "이 메뉴의 레시피 중 남은 양이 소요량보다 작은 품목"을 찾으므로, 그런 품목이 없으면 주문 가능입니다. 레시피가 없는 메뉴는 항상 true입니다.
  • 옵션도 같은 모양입니다. menu_recipe 자리에 option_recipe를, menu 자리에 option_item을 두면 됩니다. 우유가 90ml면 우유 추가(100ml 필요)도 눌리지 않습니다(실행 확인).

표시만으로는 왜 안 되는가

키오스크의 "주문 가능"은 보는 순간의 사실이고 두 군데에서 틀릴 수 있습니다. 첫째, 손님이 담는 사이에 다른 손님이 먼저 주문합니다. 둘째, 위 조회는 메뉴와 옵션을 각각 따로 봅니다. 우유가 250ml면 라떼(200ml)도 우유 추가(100ml)도 각각 가능으로 보이지만, 둘을 합친 300ml는 모자랍니다. 그래서 주문을 받는 순간 줄 전체의 필요량을 합쳐 한 번 더 검사해야 합니다(C17).

그래서 나중에 무슨 문제가 되는가

확정 때의 재검사를 "다시 읽어서 확인"으로 만들면 같은 틈이 다시 생깁니다. 읽는 순간과 줄이는 순간 사이에 또 다른 주문이 끼어들기 때문입니다. 재검사는 줄이는 동작 자체가 검사를 겸해야 하고, 그 방법이 이 장의 나머지입니다. 또 이 조회는 세트를 항상 주문 가능으로 봅니다(세트 메뉴에는 레시피가 없습니다). 세트의 품절은 "슬롯마다 팔 수 있는 후보가 하나라도 있다"라서 한 겹 더 안쪽의 NOT EXISTS가 필요하고, 이 교재는 한계로 남깁니다. 담아 둔 동안 재고를 잡아 두는 예약 재고도 범위 밖입니다(풀어 주는 시한을 정해야 합니다).

8장 · 화면 4

트랜잭션과 ACID — 묶음이 지키는 네 가지

0장은 BEGIN과 COMMIT을 맛보기로 보였고, 4장은 "주문과 줄을 한 묶음으로 저장한다"고 약속만 했습니다. 이제 정식으로 이름을 붙입니다. 트랜잭션은 BEGIN에서 시작해 COMMIT(확정) 또는 ROLLBACK(전부 취소)으로 끝나는 문장의 묶음입니다. 먼저 한 번 겪어 봅시다. 카페라떼 한 잔(원두 36g, 우유 300ml)을 위해 두 재료를 줄이는데, 우유가 100ml밖에 안 남았습니다.

-- 우유가 100ml 남았을 때, 두 재료를 한 묶음으로 줄이기BEGIN;
UPDATE stock_item SET qty = qty - 36  WHERE item_id = 3;   -- 원두: 1000 → 964
UPDATE stock_item SET qty = qty - 300 WHERE item_id = 4;   -- 우유: 100 → -200 ?
-- ERROR:  new row for relation "stock_item" violates check constraint
--         "stock_item_qty_check"
-- DETAIL:  Failing row contains (4, 우유, 원재료, ml, -200).
ROLLBACK;

SELECT item_id, qty FROM stock_item WHERE item_id IN (3, 4) ORDER BY item_id;
-- (3, 1000) (4, 100)      ← 성공했던 원두 차감도 없던 일이 되었다
  • BEGIN 뒤의 변경은 COMMIT 전까지 다른 연결에는 보이지 않고, ROLLBACK은 그 변경을 전부 버립니다. COMMIT이 성공으로 돌아오면 그때부터 확정입니다.
  • 묶음 안에서 오류가 나면 그 트랜잭션은 "중단됨" 상태가 됩니다. 이후 문장은 current transaction is aborted, commands ignored until end of transaction block 오류로 거부되고, 이때 COMMIT을 보내도 ROLLBACK으로 처리됩니다(실행 확인). 앱은 오류를 받으면 묶음을 끝내고 처음부터 다시 시작해야 합니다.

이 묶음이 지키는 네 가지 성질의 머리글자가 ACID입니다. 동백커피의 사례로 읽으면 이렇습니다.

C++ 비유와 그 한계 — 롤백되는 lock_guard + 임시 사본

트랜잭션은 "임시 사본에서 작업하다 마음에 들면 한 번에 교체하고, 아니면 버리는 lock_guard 구간"과 닮았습니다. 그러나 두 곳에서 비유가 깨집니다. ① lock_guard는 뮤텍스를 내가 명시해서 잡지만, DB는 UPDATE가 행에 자동으로 거는 것이 있고 일반 SELECT는 아무것도 잡지 않습니다. 임시 사본을 읽고 판단한 값이 이미 낡았을 수 있다는 뜻입니다. ② ROLLBACK은 DB 안의 변경만 되돌립니다. 이미 보낸 문자 메시지나 카드 승인은 되돌리지 못하므로 트랜잭션 안에 넣지 않습니다.

그래서 나중에 무슨 문제가 되는가

트랜잭션을 썼다고 동시성 문제가 저절로 풀리지는 않습니다. 격리성은 "동시에 실행해도 서로 안 보이게"가 아니라 정도 문제이고, 위의 일관성은 업무적 옳음까지 지켜 주지 않습니다. 다음 화면이 보여 주는 사고는 트랜잭션 두 개가 각자 완벽하게 원자적으로 실행되었는데도 케이크가 두 번 팔리는 경우입니다.

8장 · 화면 5

마지막 케이크를 두 명이 동시에 — 순서를 바꿔 사고 찾기

아침 8시 31분, 치즈케이크가 1개 남았습니다. 키오스크의 손님 A와 앱의 손님 B가 같은 순간에 주문하고, 서버는 주문마다 트랜잭션(T1, T2)을 하나씩 엽니다. 두 트랜잭션은 같은 네 단계를 거칩니다. 읽기(SELECT qty), 검사(앱이 "1 이상이면 진행"), 쓰기(UPDATE ... SET qty = qty - 1), 커밋입니다. 각 트랜잭션은 자기 안에서는 완벽하게 원자적입니다. 진짜 PostgreSQL에서 두 연결로 실행한 결과입니다.

순서T1 (손님 A)T2 (손님 B)커밋된 qty
1읽기 → qty = 11
2읽기 → qty = 11
3검사 통과(1 ≥ 1), 쓰기 → 1행 갱신1
4검사 통과(1 ≥ 1), 쓰기 → 기다림1
5커밋0
6기다림이 끝나고 쓰기 완료, 커밋-1

순서 4에서 T2가 기다린 이유는 락 때문입니다. UPDATE는 고치는 행에 락(잠금)을 걸어, 같은 행을 고치려는 다른 트랜잭션이 앞 트랜잭션이 끝날 때까지 멈추게 합니다. 일반 SELECT는 락을 걸지도, 기다리지도 않습니다. 그런데 락은 쓰는 순간에만 작동하므로 읽기와 쓰기 사이의 틈은 막아 주지 못했습니다. T2는 T1의 커밋 전 값(1)을 읽어 검사를 통과했고, 기다렸다가 풀린 뒤에는 최신 값(0)에서 1을 뺐습니다. 이런 사고를 경쟁 상태(동시 요청의 실행 순서에 따라 결과가 달라지는 버그)라 부릅니다. 이 장의 규칙 C13이 깨진 모양입니다.

재고 열에 CHECK (qty >= 0)가 있으면 순서 6의 쓰기가 오류(23514)로 거부되고 두 번째 손님은 오류 화면을 봅니다(실행 확인). 사고는 막히지만 손님에게는 오류입니다. 더 나쁜 변형도 있습니다. 앱이 읽은 값에서 빼서 계산한 값을 쓰면(SET qty = 0) 두 트랜잭션 모두 0을 써서 재고가 음수도 아닌 채 케이크가 두 번 팔립니다(실행 확인). 이것이 갱신 손실이고, "음수만 아니면 안전하다"는 생각이 틀리는 이유입니다. 이제 순서를 직접 바꿔 봅시다.

지금 재고(커밋된 값) 1 개 · 케이크를 받아 간 손님 0 명

조작: 위에서 방식을 고르고, T1·T2 버튼을 눌러 그 트랜잭션의 다음 단계를 하나씩 실행해 순서를 만드세요. 상대가 같은 행을 고치는 중이면 그 단계는 기다리고, 상대가 커밋하면 이어서 실행됩니다. 번갈아는 T1, T2, T1, T2 … 순으로 끝까지 실행하고, 모든 순서는 가능한 순서를 전부 돌려 결과를 셉니다. 방식을 바꾸면 처음으로 돌아갑니다.

눌러 보고 확인할 것

  • ① 읽고 쓰기에서 T1을 끝까지(읽기·검사·쓰기·커밋) 실행한 뒤 T2를 실행하세요. 안전합니다. T2는 읽기에서 0을 보고 품절을 안내합니다. 이번에는 번갈아를 눌러 보세요. T1과 T2가 둘 다 읽기를 마친 시점에 이미 사고가 정해졌습니다. 모든 순서 세기는 50가지 중 48가지가 사고라고 셉니다. 안전한 순서는 한 트랜잭션이 읽기부터 커밋까지 끝낸 뒤에야 다른 쪽이 읽는 둘뿐입니다.
  • ② + CHECK는 사고를 오류로 바꿉니다. 재고는 지켜지지만 48가지에서 한 손님이 오류를 받습니다. 마지막 방어선이지 해법은 아닙니다.
  • ③ 조건부 UPDATE는 읽기와 검사가 쓰기와 한 문장이라 틈이 없습니다. 두 번째 차감을 눌러 보면 기다리다가, 첫 트랜잭션이 커밋하면 0행이 됩니다. 모든 순서(4가지)가 안전합니다(화면 6).
  • ④ FOR UPDATE는 읽기부터 락을 잡아서 틈이 없습니다. T2는 읽기 단계에서 기다리고, 풀리면 최신 값 0을 읽습니다. 모든 순서(8가지)가 안전합니다(화면 7).

이 위젯의 규칙은 진짜 PostgreSQL 18.4에서 얻은 것이고, 위젯이 세는 순서 112개(① 50, ② 50, ③ 4, ④ 8)를 전부 같은 서버에서 두 연결로 재생해 결과가 일치하는 것을 확인했습니다.

8장 · 화면 6

해법 1 — 조건부 UPDATE와 CHECK (C13, C7)

사고의 원인은 "읽기, 검사, 쓰기"가 세 번의 따로 놀이였다는 것입니다. 틈을 없애는 가장 싼 방법은 셋을 한 문장으로 합치는 것입니다. 4장의 상태 전이에서 이미 썼던 모양, 검사를 WHERE에 넣은 UPDATE입니다.

-- 해법 1: 읽기·검사·쓰기를 한 문장으로 (qty 가 1 일 때)UPDATE stock_item
SET    qty = qty - 1
WHERE  item_id = 1 AND qty >= 1
RETURNING item_id, qty;            -- 1행: (1, 0)   ← 성공

UPDATE stock_item                  -- 같은 문장을 다시 실행
SET    qty = qty - 1
WHERE  item_id = 1 AND qty >= 1
RETURNING item_id, qty;            -- 0행           ← 품절 (오류가 아니다)
  • WHERE ... AND qty >= 1이 검사입니다. 조건이 맞는 행만 줄어들고, 앱은 갱신된 행 수로 성공(1)과 품절(0)을 압니다. 0행은 오류가 아니라 정상 경로이니 손님에게 품절을 안내하면 됩니다.
  • RETURNING 열, ...은 PostgreSQL 문법으로, 고친 행의 고친 뒤의 값을 같은 문장에서 돌려줍니다. 줄인 뒤 몇 개 남았는지 따로 읽을 필요가 없습니다. 다른 DB에서는 문법이 다릅니다.
  • 동시에 두 번 실행하면 이렇게 됩니다(실행 확인). 두 번째 UPDATE는 같은 행의 락 때문에 기다리고, 첫 트랜잭션이 커밋하면 새 값(0)으로 WHERE를 다시 평가해서 0행이 됩니다. 첫 트랜잭션이 롤백하면 기다리던 쪽이 그대로 1행을 줄입니다. 이 "기다린 뒤 다시 평가"는 PostgreSQL의 기본 격리 수준(READ COMMITTED)의 동작이고, 다른 수준에서는 달라집니다(화면 9).
  • CHECK (qty >= 0)는 마지막 방어선입니다. 누군가 AND qty >= 1을 빠뜨린 문장을 짜면 음수가 되는 쓰기가 23514 오류로 거부되어 버그가 데이터 오염 대신 오류로 드러납니다. 앱은 0행(정상)과 23514(버그 신호)를 구분해 처리합니다.

C7 상환 — 전이 순서도 같은 모양입니다

4장은 "이전 상태를 조건에 넣어 UPDATE하라"고 했습니다. 이제 이유가 보입니다. 제조 중인 주문(601)에 바리스타의 완료 처리와 손님의 취소가 동시에 들어옵니다.

순서바리스타 (완료 처리)손님 (취소)
1UPDATE ... SET status = '완료' WHERE order_id = 601 AND status = '제조중' → 1행
2UPDATE ... SET status = '취소' WHERE order_id = 601 AND status IN ('접수', '제조중') → 기다림
3커밋
4새 상태 '완료'로 WHERE를 다시 평가 → 0행. "이미 완료되어 취소할 수 없습니다"

반대로 앱이 '조회 후 저장'을 하면(SELECT status로 읽고 "제조중이니 취소 가능"이라 판단한 뒤 조건 없는 UPDATE ... SET status = '취소') 둘 다 '제조중'을 읽은 상태에서 완료가 취소로 덮어써집니다(실행 확인: 최종 상태 '취소'). 4장이 "읽고, 판단하고, 쓰기를 따로 하면 그 사이에 다른 요청이 끼어들 수 있다"고 한 경쟁입니다. 해법은 판단을 쓰기 문장 안으로 넣는 것입니다.

더 깊이 — 낙관적 락: 값 대신 버전 번호를 조건에 넣는 방법

충돌이 드물다고 보고 미리 잠그지 않고, 쓰는 순간 "내가 읽은 뒤로 안 바뀌었는가"만 확인하는 방식을 낙관적 락이라 합니다(미리 잠그는 쪽은 비관적 락, 화면 7). 보통 행에 version 열을 두고 읽을 때의 값을 조건에 넣습니다. 이 장의 qty >= 1과 status = '제조중'도 값 자체를 버전처럼 쓴 같은 뿌리입니다.

-- 가정: orders 에 version 열(기본 0)이 있다면 (v6 에는 없는 설명용 열)UPDATE orders SET status = '완료', version = version + 1
WHERE  order_id = 601 AND version = 0;   -- 읽을 때의 version. 0행이면 그사이 바뀐 것

0행이면 앱이 다시 읽어 판단부터 다시 합니다. 값 조건만으로는 "같은 값으로 되돌아온 변경"(A→B→A)을 못 알아보지만 버전은 알아봅니다. 대가는 열 하나와 모든 갱신 경로가 버전을 올려야 한다는 규율입니다.

그래서 나중에 무슨 문제가 되는가

조건부 UPDATE는 판단이 그 행 하나의 값으로 끝날 때만 통합니다. "재고 여러 개를 한꺼번에 줄이고 하나라도 모자라면 전부 취소"(화면 8), "여러 행의 합계가 기준 이하인가"(포인트 잔액, 화면 10)는 문장 하나에 안 들어갑니다. 그때 쓰는 도구가 다음 화면의 SELECT ... FOR UPDATE입니다.

8장 · 화면 7

해법 2 — SELECT ... FOR UPDATE로 읽으면서 잠그기

판단이 UPDATE 문장 하나에 안 들어갈 때가 있습니다. 읽은 값을 앱이 여러 규칙으로 따져야 하거나, 여러 행을 읽어야 하는 경우입니다. 그때는 읽는 순간부터 락을 잡아 판단하는 동안 아무도 그 행을 못 고치게 합니다. SELECT 끝에 FOR UPDATE를 붙입니다.

-- 해법 2: 읽으면서 잠그고, 판단하고, 쓴다BEGIN;
SELECT qty FROM stock_item WHERE item_id = 1 FOR UPDATE;
-- ↑ 읽으면서 이 행에 락. 다른 트랜잭션의 UPDATE·FOR UPDATE 는 여기서 기다린다
-- 앱: 읽은 qty 가 1 이상인가? (판단하는 동안 아무도 이 행을 못 고친다)
UPDATE stock_item SET qty = qty - 1 WHERE item_id = 1;
COMMIT;   -- 락은 COMMIT·ROLLBACK 에서 풀린다
  • FOR UPDATE가 건 락은 UPDATE가 거는 락과 같은 것입니다. 그래서 같은 행에 대한 다른 FOR UPDATE와 UPDATE가 기다리고, 풀리면 최신 값을 읽습니다(실행 확인: 두 번째 트랜잭션이 qty = 0을 읽었습니다).
  • 일반 SELECT는 막히지 않습니다. 누가 이 행을 FOR UPDATE로 잡고 있어도 화면 3의 품절 조회는 기다리지 않고 바로 값을 돌려받습니다(실행 확인). 읽기가 쓰기를 막지 않는 것이 키오스크 화면을 가볍게 유지하는 이유입니다.
  • 락은 트랜잭션이 끝날 때까지 유지됩니다. 락을 쥔 채 카드 승인 응답을 기다리면 그동안 같은 행을 건드리는 모든 주문이 줄을 섭니다. 트랜잭션은 짧게, 외부 호출은 밖에서 합니다.

기다리고 싶지 않을 때를 위한 꼬리표가 둘 있습니다.

-- 다른 트랜잭션이 item 1 을 잠그고 있는 중에SELECT qty FROM stock_item WHERE item_id = 1 FOR UPDATE NOWAIT;
-- ERROR:  could not obtain lock on row in relation "stock_item"   (오류 코드 55P03)

SELECT item_id, qty FROM stock_item
WHERE  item_id IN (1, 2) ORDER BY item_id FOR UPDATE SKIP LOCKED;
-- (2, 3)   ← 잠긴 item 1 은 건너뛰고 나머지만 돌려준다
  • NOWAIT는 락이 이미 있으면 기다리지 않고 오류를 냅니다. "지금 바쁘니 잠시 후 다시"를 손님에게 바로 말해야 할 때 씁니다.
  • SKIP LOCKED는 잠긴 행을 없는 셈 치고 건너뜁니다. 여러 일꾼이 작업 큐에서 서로 다른 일을 집어 갈 때 쓰는 도구입니다. 재고 차감에는 맞지 않습니다. 잠긴 케이크 행을 건너뛰면 재고가 없는 것처럼 보이기 때문입니다.
조건부 UPDATE (화면 6)FOR UPDATE
판단하는 곳문장 안(WHERE), 한 행의 값문장 밖(앱이 읽은 값으로)

반대 의견 — DB 락 말고 앱 큐, 낙관적 락, 재고를 DB 밖에 두기

앱 큐(직렬 처리자): 재고를 바꾸는 요청을 한 프로세스가 줄 세워 하나씩 처리하면 락이 필요 없습니다. 대신 그 프로세스가 단일 장애점이고, 서버를 여러 대로 늘리면 줄 세우는 일이 다시 어려워집니다. DB가 이미 가진 락이 더 단순한 경우가 많습니다.

낙관적 락(화면 6): 충돌이 드물면 락 없이 버전을 확인합니다. 마지막 케이크처럼 충돌이 몰리는 곳에서는 재시도가 폭주해 비관적 락(FOR UPDATE)이 낫습니다. 케이크는 인기 메뉴일수록 충돌이 잦습니다.

재고를 DB 밖(Redis 등)에 두기: 메모리 저장소의 원자적 감소 명령은 빠르고 락 경쟁이 없습니다. 그러나 "주문 저장"과 "재고 차감"이 서로 다른 시스템이 되어 한 트랜잭션으로 묶이지 않습니다. 주문은 저장됐는데 재고는 안 줄었거나 그 반대가 생기고, 그 어긋남을 맞추는 코드가 필요합니다. 이 장의 원자성(화면 4)을 포기하는 교환입니다. 이 교재는 한 DB 안에서 푸는 길을 택했고, 초당 수천 건이 몰리는 규모가 되면 다시 따져 볼 선택입니다.

그래서 나중에 무슨 문제가 되는가

락은 하나일 때는 줄 세우기이지만 둘 이상이 되면 서로를 기다리는 일이 생길 수 있습니다. 라떼 한 잔은 원두·우유·시럽 행을 모두 줄이므로 락도 셋입니다. 다음 화면은 한 주문이 여러 재료를 줄일 때의 원자성과, 그 락들이 맞물리는 교착입니다.

8장 · 화면 8

한 주문이 여러 재료를 줄일 때 — 전부 성공 아니면 전부 취소, 그리고 교착

주문 하나는 재고 행 여럿을 줄입니다. 줄마다, 옵션마다 쓰는 양을 품목별로 합친 것이 그 주문의 필요량입니다.

필요량 공식 (화면 2의 소요량이 곱해지는 자리)

품목 하나의 필요량 = Σ 줄의 잔 수 × (메뉴 소요량 + Σ 옵션 소요량 × 옵션 횟수). 카페라떼 1잔 + 샷 추가 1 + 우유 추가 1, 치즈케이크 1개라면 원두 18 + 18 = 36g, 우유 200 + 100 = 300ml, 시럽 10ml, 치즈케이크 1개입니다.

-- 주문 501 의 줄과 옵션이 저장되어 있을 때: 품목별 필요량 (품목 번호 순)SELECT item_id, SUM(amount) AS need
FROM  (SELECT r.item_id, r.amount * ol.quantity AS amount
       FROM   order_line AS ol
       JOIN   menu_recipe AS r ON r.menu_id = ol.menu_id
       WHERE  ol.order_id = 501
       UNION ALL
       SELECT r.item_id, r.amount * o.option_qty * ol.quantity
       FROM   order_line_option AS o
       JOIN   order_line AS ol ON ol.order_id = o.order_id AND ol.line_no = o.line_no
       JOIN   option_recipe AS r ON r.option_id = o.option_id
       WHERE  o.order_id = 501) AS u
GROUP BY item_id ORDER BY item_id;
-- (1, 1) (3, 36) (4, 300) (5, 10)
  • 안쪽의 UNION ALL은 두 조회(메뉴가 쓰는 양, 옵션이 쓰는 양)를 이어 붙입니다. ALL이 중요합니다. 그냥 UNION은 같은 행을 하나로 합쳐 버려서, 두 줄이 우연히 같은 양을 쓰면 필요량이 줄어듭니다. 바깥의 GROUP BY item_id가 품목별로 합칩니다.
  • 세트 줄은 세트 메뉴에 레시피가 없으므로 고른 구성 메뉴(order_line_pick)의 레시피를 줄 수량만큼 더하는 세 번째 가지가 필요합니다(실행 확인: 주문 202의 세트 줄 → 원두 18, 티라미수 1). 이 장의 주문 트랜잭션은 단품 줄만 보입니다.

품목마다 화면 6의 조건부 UPDATE를 하고, 하나라도 0행이면 전부 취소해야 합니다. 원자성이 하는 일이 정확히 이것입니다. 우유가 100ml뿐인 경우를 봅시다.

-- 원두는 되고 우유는 모자란 주문BEGIN;
UPDATE stock_item SET qty = qty - 36  WHERE item_id = 3 AND qty >= 36;    -- 원두: 1행
UPDATE stock_item SET qty = qty - 300 WHERE item_id = 4 AND qty >= 300;   -- 우유: 0행
-- 앱: 한 품목이라도 0행이면 ROLLBACK. 성공했던 원두 차감도 없던 일이 된다
ROLLBACK;

0행은 오류가 아니라서 트랜잭션이 스스로 취소되지 않습니다

화면 4의 CHECK 오류는 트랜잭션을 "중단됨"으로 만들었지만, 조건부 UPDATE의 0행은 정상 결과입니다. 앱이 0행을 확인하고 ROLLBACK을 보내지 않으면 다음 COMMIT에서 원두 차감만 확정됩니다. 영향 행 수 확인은 선택이 아니라 이 설계의 일부입니다.

락이 둘이 되면 — 교착

이제 두 주문이 같은 두 품목을 반대 순서로 줄인다고 합시다(줄 순서가 주문마다 다르면 흔히 생깁니다). 진짜 PostgreSQL에서 이렇게 실행됩니다.

순서주문 A주문 B
1원두 차감 → 1행 (원두 행 락)
2우유 차감 → 1행 (우유 행 락)
3우유 차감 → 기다림 (B 가 쥐고 있음)
4원두 차감 → 기다림 (A 가 쥐고 있음)
5약 1초 뒤 ERROR: deadlock detected (오류 코드 40P01)로 중단이어서 실행되어 커밋

순서 4에서 서로가 상대의 락을 기다리니 누구도 영원히 못 나아갑니다. 이것이 교착(데드락)입니다. C++의 두 뮤텍스를 반대 순서로 잡는 바로 그 문제입니다. DB는 deadlock_timeout(기본 1초) 동안 기다려도 풀리지 않으면 교착을 찾아 한쪽을 오류로 중단시킵니다. 어느 쪽이 중단될지는 정해져 있지 않으므로 앱은 40P01을 받으면 트랜잭션 전체를 처음부터 다시 시도해야 합니다. 같은 오류가 자주 나면 다시 시도로 덮을 일이 아니라 순서를 고칠 신호입니다.

예방은 C++과 같은 규칙입니다. 항상 같은 순서로 잡습니다. 이 교재의 규칙은 품목 번호 오름차순입니다.

-- 필요한 품목을 번호 순서로 먼저 잠그고, 같은 순서로 차감한다BEGIN;
SELECT item_id FROM stock_item
WHERE  item_id IN (3, 4) ORDER BY item_id FOR UPDATE;      -- 원두(3), 우유(4) 순
UPDATE stock_item SET qty = qty - 36  WHERE item_id = 3 AND qty >= 36;
UPDATE stock_item SET qty = qty - 300 WHERE item_id = 4 AND qty >= 300;
COMMIT;
  • ORDER BY item_id FOR UPDATE는 행을 번호 순서로 잠급니다. 두 주문이 같은 순서로 잡으니 뒤에 온 주문은 첫 락에서 기다릴 뿐 맞물리지 않습니다(실행 확인: 교착 없이 둘 다 커밋). 앱이 품목을 번호 순으로 정렬해 조건부 UPDATE를 차례로 보내는 것도 같은 효과이고, 화면 12가 그 방법을 씁니다.
  • 여러 행을 한 문장 UPDATE ... FROM (VALUES ...)로 줄이면 편해 보이지만, 그 문장이 행을 잠그는 순서는 실행 계획이 정합니다(같은 서버에서 실험하니, 통계가 없을 때는 VALUES에 적은 순서대로, 통계를 모은 뒤에는 표의 저장 순서대로 잠겼습니다). 순서를 보장으로 삼을 수 없으니 순서가 중요한 곳에는 쓰지 않습니다.

그래서 나중에 무슨 문제가 되는가

락 순서 규칙은 품목끼리만이 아니라 주문이 잡는 모든 자원에 걸립니다. 화면 12의 주문 트랜잭션은 회원 → 재고(번호 순) → 픽업 슬롯 순서로 잡고, 취소 트랜잭션도 같은 순서를 따라야 합니다. 규칙은 코드 한 곳에 모아 두어야 새 코드가 어기지 않습니다. 또 원두처럼 모든 주문이 건드리는 행은 락을 쥐는 시간이 곧 주문 처리량의 한계이므로, 그 락을 쥔 채 느린 일(외부 호출, 긴 조회)을 하지 않습니다.

8장 · 화면 9

격리 수준의 감각 — 그리고 요약 갱신은 동시에 어떻게 되는가

지금까지 "T2가 T1의 커밋 전 값을 읽었다"처럼 어느 시점의 데이터를 보는가를 슬쩍 말해 왔습니다. 그 기준을 정하는 설정이 격리 수준입니다. 화면 4가 "격리성은 정도를 고른다"고 한 그 정도입니다. 여기서는 세 가지만 감각으로 잡습니다.

수준무엇을 보는가이 장의 해법에 미치는 영향
READ COMMITTED
(PostgreSQL 기본)		문장마다 그 문장이 시작될 때 커밋되어 있던 데이터해법 1·2가 기대는 수준입니다. 락을 기다린 뒤 새 값을 봅니다
REPEATABLE READ트랜잭션의 첫 문장 시점의 데이터로 고정같은 조건부 UPDATE가 기다린 뒤 오류(40001)가 됩니다
SERIALIZABLE트랜잭션을 한 번에 하나씩 실행한 것과 같은 결과를 보장락 없이 짠 코드도 안전해지지만 어긋날 것 같으면 한쪽을 40001로 중단합니다

PostgreSQL은 READ UNCOMMITTED를 READ COMMITTED와 같게 다룹니다(공식 문서). 여기서 "시점의 데이터"를 DB 용어로 스냅샷이라 부르지만 6장의 주문 스냅샷(값 복사)과는 다른 말입니다.

-- 리포트가 같은 표를 두 번 읽는 사이에 다른 연결이 주문 1건을 커밋한다BEGIN ISOLATION LEVEL READ COMMITTED;
SELECT COUNT(*) FROM orders;      -- 9
-- (다른 연결: 주문 1건 INSERT 후 COMMIT)
SELECT COUNT(*) FROM orders;      -- 10  ← 같은 트랜잭션인데 값이 달라졌다
COMMIT;
-- BEGIN ISOLATION LEVEL REPEATABLE READ 로 시작했다면 두 번째도 9

수준을 올리면 보이는 것이 고정되어 편해 보이지만, 이 장의 해법과 만나면 세 가지가 달라집니다(모두 실행 확인).

  • 조건부 UPDATE: REPEATABLE READ·SERIALIZABLE에서는 기다린 뒤 0행이 아니라 ERROR: could not serialize access due to concurrent update입니다. 앱은 트랜잭션 전체를 처음부터 다시 실행해야 합니다(재시도 코드가 필수).
  • 잠근 뒤 합계 읽기(화면 10): READ COMMITTED에서는 락을 얻은 뒤 읽는 합계가 최신이라 안전합니다. REPEATABLE READ에서는 시점이 첫 문장에 고정되어 락을 기다리고도 앞선 트랜잭션의 삽입을 못 봅니다. 락 패턴의 전제가 깨집니다.
  • 락 없이 짠 코드: SERIALIZABLE에서는 한쪽의 COMMIT이 could not serialize access due to read/write dependencies among transactions로 실패하고, 다시 하면 올바르게 판단합니다. 대가는 모든 트랜잭션의 재시도 코드와 중단 비율입니다.

7장의 빚 — 요약 테이블을 갱신하는 동안

7장은 요약 daily_sales의 갱신이 동시 요청과 만나는 일을 8장에 넘겼습니다.

  • 배치(지우고 다시 계산): 재계산 INSERT ... SELECT는 문장 하나가 하나의 시점을 보고, 주문 하나는 한 트랜잭션이라 커밋 전에는 안 보이므로 계산 도중 들어온 주문이 반쪽만 집계되지는 않습니다. 문제는 같은 날 배치 두 개가 겹칠 때입니다. 한쪽의 DELETE가 기다렸다가 0행을 지우고 INSERT가 duplicate key value violates unique constraint "daily_sales_pkey"(23505)로 실패합니다. 기본키가 두 벌의 행을 막은 것이니 배치는 한 번에 하나만 돌게 운영하고 실패하면 다시 돌립니다(멱등이라 안전).
  • 증분(트리거·앱): 모든 주문이 같은 "오늘 행"에 더하므로 앞 트랜잭션이 끝날 때까지 기다립니다(실행 확인). 이 갱신을 주문 트랜잭션 안에 넣으면 주문 처리가 오늘 행 하나에 줄을 섭니다. 그래서 이 교재의 주문 생성 트랜잭션(화면 12)은 요약을 건드리지 않고, 요약은 배치가 만듭니다. 7장 퀴즈가 말한 "처리한 주문 번호 표와 요약 갱신을 한 묶음으로"는 이 줄 서기를 감수하는 선택입니다.

그래서 나중에 무슨 문제가 되는가

이 교재는 기본 수준(READ COMMITTED)에 락과 조건부 UPDATE를 얹는 길을 택했습니다. 수준을 올려 코드를 단순하게 만드는 길(SERIALIZABLE)도 정당하지만, 재시도를 전제로 설계해야 하고 수준이 바뀌면 락 패턴이 깨질 수 있다는 점을 코드 곁에 적어 둬야 합니다. 어느 쪽이든 40001과 40P01을 받으면 처음부터 다시 하는 재시도 층이 앱에 필요합니다(화면 12).

8장 · 화면 10

쿠폰의 중복 사용과 포인트 잔액 — 선언이 막는 것, 락이 막는 것 (C11, C12)

6장이 남긴 두 규칙입니다. 하나는 UNIQUE로 선언할 수 있었고, 하나는 선언할 수 없었습니다. 동시 요청에서 둘이 어떻게 다른지 봅시다.

쿠폰 — UNIQUE는 동시에도 막지만, 오류를 어떻게 받을지는 앱의 일

소라의 쿠폰(발급 2번)을 두 주문(501, 502)이 동시에 쓰려 합니다. 두 번째 INSERT는 첫 트랜잭션이 끝날 때까지 기다립니다(실행 확인).

순서주문 501주문 502
1INSERT INTO order_discount ... issue_id = 2 → 1행
2같은 issue_id = 2를 INSERT → 기다림 (아직 커밋될지 모르는 유일성 항목)
3a커밋ERROR: duplicate key value violates unique constraint "order_discount_issue_id_key" (23505)
3b(롤백했다면)기다림이 끝나고 통과

4장이 "조회한 뒤 없으면 저장하면 동시에 통과하지만, 제약은 검사와 저장이 한곳에서 일어난다"고 한 말의 실체입니다. 남는 일은 오류의 뒤처리입니다. 502의 오류는 트랜잭션을 중단시키므로 앱은 ROLLBACK으로 주문 502 전체(주문 행, 줄, 재고 차감)를 취소하고, 오류 코드와 제약 이름으로 손님에게 "이미 사용한 쿠폰입니다"를 안내합니다(실행 확인: 502 행이 남지 않았습니다). 6장의 "'N회' 쿠폰은 UNIQUE로 안 된다"는 아래 포인트와 같은 모양입니다. 쿠폰 발급 행을 FOR UPDATE로 잠근 뒤 사용 횟수를 세어 비교합니다.

포인트 — 합계는 잠글 행이 없다

소라의 원장에 '조정' 3000 한 행(entry 10)만 있어 잔액이 3000일 때 두 주문이 각각 2000포인트를 쓰려 합니다. 둘 다 합계 3000을 읽고 통과해 잔액 -1000이 됩니다(실행 확인). 합계는 행이 아니라 여러 행의 계산 결과라서 화면 6의 조건부 UPDATE도, 그 합계를 직접 FOR UPDATE로 잠그는 것도 안 됩니다. 대신 그 합계를 바꾸는 모든 경로가 먼저 잡기로 약속한 행을 하나 정합니다. 회원 행입니다.

-- 포인트 사용: 회원 행을 잠가 같은 회원의 주문을 한 줄로 세운 뒤 합계를 확인한다BEGIN;
SELECT member_id FROM member WHERE member_id = 2 FOR UPDATE;   -- 대리 락: 회원 행
SELECT COALESCE(SUM(delta), 0) AS balance
FROM   point_ledger WHERE member_id = 2;                       -- 3000 (잠근 뒤라 최신)
-- 앱: balance >= 2000 이면 진행, 아니면 ROLLBACK
INSERT INTO point_ledger (entry_id, member_id, reason, delta, order_id)
VALUES (11, 2, '사용', -2000, 501);
COMMIT;

  • 이 락은 약속입니다. 적립·조정 등 포인트 원장에 쓰는 모든 코드가 같은 락을 먼저 잡아야 하고, 한 곳이 빠지면 DB는 막아 주지 않습니다.

7장의 판단 — 잔액 캐시 열을 둘까

원장과 함께 member.point_balance 열을 두면 CHECK (point_balance >= 0) 한 줄로 음수 금지를 선언할 수 있습니다. 대신 원장 행과 잔액 갱신을 같은 트랜잭션에서 해야 합니다.

픽업 슬롯의 정원 — 시간대마다 받을 수 있는 주문 수 (C14)

하윤의 요구를 구조부터 정리합니다. 픽업 슬롯은 30분 간격의 픽업 시간대(8:30, 9:00, ...) 하나이고, 시간대마다 정원(받을 수 있는 주문 수)이 있습니다. 주문 1건이 정원 1을 씁니다(잔 수와 무관). 5장의 "구성 슬롯"(세트의 자리)과는 이름만 닮은 다른 개념이라 이 장에서는 늘 "픽업 슬롯"이라 부릅니다.

한 행뜻
pickup_slot시간대 하나: 시작 시각, 정원(capacity), 지금까지 받은 주문 수(reserved)
orders.pickup_start그 주문이 예약한 시간대(현장 주문이면 NULL)
-- 새 표 pickup_slot 과, 열 하나가 늘어난 orders (v6)-- 픽업 시간대(픽업 슬롯) 하나: 정원과 지금까지 받은 주문 수 (주문 1건이 정원 1을 쓴다)
CREATE TABLE pickup_slot (
    slot_start  TIMESTAMPTZ PRIMARY KEY,
    capacity    INTEGER     NOT NULL CHECK (capacity >= 0),
    reserved    INTEGER     NOT NULL DEFAULT 0 CHECK (reserved >= 0),
    CHECK (reserved <= capacity)
);

-- 주문 한 건 (v5 와 다른 곳은 pickup_start 한 줄: 픽업 시간을 예약한 주문이면 그 슬롯)
CREATE TABLE orders (
    order_id      INTEGER     PRIMARY KEY,
    member_id     INTEGER     REFERENCES member (member_id),
    ordered_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    payment       TEXT        NOT NULL CHECK (payment IN ('카드', '현금')),
    barista       TEXT        NOT NULL,
    status        TEXT        NOT NULL DEFAULT '접수'
                  CHECK (status IN ('접수', '제조중', '완료', '픽업', '취소')),
    member_grade  TEXT        REFERENCES membership_grade (grade),
    pickup_start  TIMESTAMPTZ REFERENCES pickup_slot (slot_start),
    CHECK (member_id IS NOT NULL OR member_grade IS NULL)
);
  1. 2~7행 시작 시각이 곧 슬롯을 가리키므로 slot_start를 기본키로 둡니다(시각은 바뀌지 않는 값입니다). 6행의 CHECK (reserved <= capacity)가 정원 초과 금지(C14)의 마지막 방어선이고, 표 수준 CHECK라 PostgreSQL이 pickup_slot_check라는 이름을 붙입니다(앱이 이 오류를 알아볼 때 쓰는 이름). 슬롯 길이는 저장하지 않습니다(모두 30분이라는 앱의 약속).
  2. 10~21행 orders는 v5와 한 줄만 다릅니다. 19행 pickup_start(FK, NULL 허용)가 새 열이고 나머지(11~18행, 20행)는 글자까지 같습니다. 그 슬롯이 아직 안 지났는지, 지금 시각에 준비할 시간이 있는지는 DB가 못 보는 규칙이라 앱이 확인합니다.

reserved는 중복입니다 — 그래도 둔 이유

reserved는 사실 orders에서 그 시간대 주문을 센 수와 같아야 하는 파생값입니다. 같은 사실을 두 곳에 두는 것이니 D4와 7장의 요약 테이블과 같은 질문입니다. 카운터를 두는 이유는 둘입니다. ① CHECK (reserved <= capacity)가 선언으로 마지막 방어선을 세웁니다. ② 락을 걸 행이 생깁니다. 대가는 취소할 때 같은 트랜잭션에서 줄여야 하고 점검이 필요하다는 것입니다. 반대 의견은 카운터 없이 슬롯 행만 FOR UPDATE로 잠그고 COUNT하는 방법입니다. 중복이 없지만 방어선이 선언이 아니라 앱 코드에 있습니다. 이 교재는 카운터를 택합니다.

-- 자리 잡기: 조건부로 늘린다. 1행이면 성공, 0행이면 이 시간대는 마감UPDATE pickup_slot SET reserved = reserved + 1
WHERE  slot_start = '2026-10-02 09:00+09' AND reserved < capacity;

-- 취소: 상태 전이가 1행일 때만 같은 트랜잭션에서 자리를 돌려준다
BEGIN;
UPDATE orders SET status = '취소' WHERE order_id = 501 AND status = '접수';
UPDATE pickup_slot SET reserved = reserved - 1
WHERE  slot_start = (SELECT pickup_start FROM orders WHERE order_id = 501);
COMMIT;

-- 점검: 카운터와 실제 주문 수가 다른 시간대 (비어 있어야 정상)
SELECT s.slot_start, s.reserved, COUNT(o.order_id) AS actual
FROM   pickup_slot AS s
LEFT JOIN orders AS o ON o.pickup_start = s.slot_start AND o.status <> '취소'
GROUP BY s.slot_start, s.reserved
HAVING s.reserved <> COUNT(o.order_id);
  • 동시 예약: 정원이 2이고 1자리가 남았을 때 두 요청이 겹치면 첫 요청이 자리를 잡고, 둘째는 기다린 뒤 0행이 됩니다(실행 확인). 조건 없이 reserved = reserved + 1만 하면 둘째의 쓰기가 pickup_slot_check 위반(23514)으로 터집니다. 방어선이 사고를 오류로 바꾼 것이고, 손님에게는 오류 화면이 됩니다. 조건부 UPDATE를 써야 "마감되었습니다"가 정상 안내가 됩니다.
  • 취소: 첫 UPDATE가 0행이면(이미 제조 중이거나 이미 취소된 주문) 두 번째 문장을 하지 않고 ROLLBACK합니다. 조건부라서 두 번 취소해도 두 번째는 0행이라 자리가 이중으로 돌아오지 않습니다(실행 확인).

8장 마무리

핵심 요약

  1. 재고는 품목과 레시피로 둡니다. 완제품도 소요량 1의 레시피로 통일해 차감 경로를 하나로 하고, 소요량은 (메뉴, 품목)·(옵션, 품목) 연결의 속성입니다. 품절은 저장하지 않고 조회로 계산해 키오스크에 보이되, 그것은 참고용이고 주문 확정의 조건부 차감이 최종 판정입니다(C17).
  2. 트랜잭션이 ACID를 지켜도 "읽고, 판단하고, 쓰기"를 따로 하면 동시 요청이 틈으로 들어옵니다. 케이크가 두 번 팔리거나(갱신 손실) 재고가 음수가 됩니다. 판단을 UPDATE ... WHERE qty >= n 한 문장에 넣고 영향 행 수를 확인하며(0행은 오류가 아니라 품절), CHECK (qty >= 0)는 마지막 방어선으로 둡니다(C13). 판단이 문장에 안 들어가면 SELECT ... FOR UPDATE로 읽으면서 잠급니다.
  3. 여러 행을 줄이면 하나라도 모자랄 때 전부 ROLLBACK(앱이 0행을 보고 해야 합니다), 락은 항상 같은 순서(회원 → 재고 번호 순 → 슬롯)로 잡아 교착을 예방하고, 40P01·40001은 트랜잭션 전체를 재시도합니다.
  4. 이 교재는 기본 격리 수준(READ COMMITTED) 위에 락과 조건부 UPDATE를 얹었습니다. 수준을 올리면 같은 코드가 40001로 바뀌고 잠근 뒤의 합계 읽기가 깨질 수 있습니다.
  5. 주문 생성은 한 트랜잭션(복사, C1 확인, 재고, 슬롯, 할인·쿠폰, 포인트)이고 커밋 순간에야 한꺼번에 보입니다. 이것이 C1(D5)의 답이고, 결과가 스키마 v6(표 22개)입니다. D2(매장)는 9장, 재고와 슬롯도 매장마다 달라집니다.

치즈케이크 재고가 1일 때 두 요청이 거의 동시에 UPDATE stock_item SET qty = qty - 1 WHERE item_id = 1 AND qty >= 1을 보냈습니다. 두 번째 요청은 어떻게 될까요(기본 격리 수준)?

  1. CHECK 위반 오류(23514)가 난다
  2. 락을 기다렸다가 새 값으로 조건을 다시 평가해 0행이 된다(오류 없음)
  3. 둘 다 1행이 되어 재고가 -1이 된다

앱이 이 0행을 알아보는 방법은 드라이버마다 다릅니다. C++의 libpq에서는 실행 결과에서 PQcmdTuples로 영향 행 수를 문자열로 얻습니다. 영향 행 수를 확인하는 코드는 "있으면 좋은 것"이 아니라 이 설계가 성공과 품절을 가르는 유일한 신호입니다. 빠뜨리면 품절인데도 주문이 저장됩니다.

"키오스크의 품절 표시를 믿고 주문을 받아도 되는가?" — 이 장의 답은 무엇일까요?

  1. 표시가 DB에서 계산한 값이므로 믿어도 된다
  2. 안 된다. 표시는 참고용이고, 주문 확정 때 조건부 차감으로 다시 판정한다
  3. 품절을 is_sold_out 열로 저장하면 믿어도 된다

키오스크나 앱이 서버에 "이 메뉴는 주문 가능이었다"고 알려 주어도 서버는 그 말을 믿지 않습니다. 화면에서 품절 항목을 못 누르게 하는 것은 손님을 위한 편의이고, 정합성의 경계는 언제나 서버(DB)입니다. 클라이언트가 보낸 값으로 규칙을 확인하지 않는다는 원칙은 재고뿐 아니라 가격(6장에서 DB의 가격으로 복사한 이유)에도 같습니다.

"트랜잭션을 썼는데도 재고가 음수가 될 수 있는 경우"는 어느 것일까요?

  1. 트랜잭션은 원자적이므로 그런 경우는 없다
  2. 커밋을 너무 늦게 한 경우
  3. 읽고 판단하고 쓰기를 따로 한 두 트랜잭션이 겹친 경우

ORM(객체를 표의 행으로 자동 변환해 주는 라이브러리)에서 객체를 읽어 필드를 고친 뒤 save()하는 흔한 코드는 기본적으로 바로 이 "읽고 쓰기"입니다. JPA의 @Version처럼 ORM이 낙관적 락(화면 6의 version 열)을 기본 도구로 제공하는 이유가 이것입니다. DB를 직접 다루는 C++ 코드는 이 보호가 저절로 붙지 않으니 쓰기 문장에 조건을 직접 넣어야 합니다.

두 주문 트랜잭션이 같은 두 재고 행을 서로 반대 순서로 UPDATE해 deadlock detected가 났습니다. 가장 근본적인 예방은 무엇일까요?

  1. deadlock_timeout을 늘린다
  2. 모든 트랜잭션이 같은 순서로 락을 잡게 한다
  3. 오류가 난 주문은 그냥 무시한다

deadlock_timeout이 따로 있는 이유가 흥미롭습니다. 교착 검사는 비싸서 락을 기다릴 때마다 돌리지 않고, 기다림이 이 시간을 넘을 때에야 돌립니다. 그래서 교착은 즉시가 아니라 약 1초 뒤에 오류로 나타납니다. 짧게 줄이면 빨리 찾지만 기다리기만 하는 정상 트랜잭션에도 검사 비용이 듭니다.

모범답안 — 그리고 흔한 오답이 왜 부족한지 
-- 모범답안: 접수 상태 주문 취소 (회원 → 재고(번호 순) → 슬롯)BEGIN;
SELECT member_id FROM member WHERE member_id = 2 FOR UPDATE;
UPDATE orders SET status = '취소' WHERE order_id = 501 AND status = '접수';
-- 위 문장이 1행일 때만 아래를 한다. 0행이면 ROLLBACK
UPDATE stock_item SET qty = qty + 1   WHERE item_id = 1;
UPDATE stock_item SET qty = qty + 36  WHERE item_id = 3;
UPDATE stock_item SET qty = qty + 300 WHERE item_id = 4;
UPDATE stock_item SET qty = qty + 10  WHERE item_id = 5;
UPDATE pickup_slot SET reserved = reserved - 1
WHERE  slot_start = (SELECT pickup_start FROM orders WHERE order_id = 501);
COMMIT;

1·2. 회원 행을 먼저 잠그고(생성 트랜잭션과 같은 순서) 상태를 조건부로 바꿉니다. 두 번째 취소 요청은 첫 요청의 커밋을 기다렸다가 새 상태 '취소'로 WHERE를 다시 평가해 0행이 되고, 앱이 그것을 보고 ROLLBACK하므로 재고 복원과 슬롯 반환은 실행되지 않습니다(실행 확인). 상태 전이가 곧 "이미 돌려줬는가"를 가르는 문턱입니다. 쿠폰은 6장 정책대로 돌아오지 않고 포인트는 '조정' 행으로 정정하는 일을 같은 묶음에 더할 수 있습니다.

3. 제조중은 재료를 이미 썼으므로 상태만 '취소'로 바꾸고 재료는 돌려주지 않습니다. 슬롯 자리는 돌려줍니다. 앱은 먼저 status = '접수' 조건으로 시도하고, 0행이면 status = '제조중' 조건으로 한 번 더 시도해 어느 쪽이 성공했는지로 갈라집니다.

4. 취소 때 레시피로 다시 계산하면 주문한 뒤 레시피가 바뀐 경우(라떼의 우유를 200에서 180으로 고쳤다면) 차감한 양과 돌려주는 양이 다릅니다. 6장 스냅샷과 같은 논리로, 주문 시점의 차감량을 기록해야 정확합니다. 주문별·품목별 차감량 표(또는 재고 변동 원장 stock_movement)를 더하고, 이 교재의 v6은 이 기록을 두지 않는 한계를 인정했습니다.

흔한 오답 1 — 상태 조건 없이 재고와 슬롯을 되돌린다. 취소 요청이 두 번 오면 재고가 두 번 늘어 없던 케이크가 생깁니다. 이것은 CHECK가 못 막는 방향의 오염입니다(qty >= 0은 늘어나는 쪽을 보지 않습니다).

흔한 오답 2 — 슬롯을 먼저 줄이고 재고를 나중에 되돌린다. 생성 트랜잭션은 재고 → 슬롯 순서로 잡으므로 반대 순서가 되어 교착이 납니다(화면 8).

흔한 오답 3 — 취소 전에 SELECT status로 읽어 "접수니까 취소 가능"이라 판단한다. 읽은 뒤 쓰기 전에 바리스타가 제조를 시작하면 제조 중인 주문의 재료가 돌아옵니다(화면 6의 조회 후 저장).
