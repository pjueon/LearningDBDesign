스냅샷 — 주문한 그때의 값을 줄에 복사해 둔다 (C8)

영수증에는 그날 받은 가격이 찍혀 있습니다. 가게의 메뉴판 가격이 나중에 바뀌어도 영수증은 그대로입니다. 지금 v4에 없는 것이 바로 이 영수증 쪽의 가격입니다. v4는 줄에 메뉴 번호만 적고 가격은 메뉴에서 그때그때 찾아 읽기 때문에, 메뉴의 가격이 바뀌면 영수증도 같이 바뀝니다.

고치는 방법은 주문을 만드는 순간 그때의 이름과 단가를 주문 줄에 복사해 두는 것입니다. 이것을 스냅샷이라 부르고, 이 교재의 규칙 번호로는 C8입니다.

이것은 중복이 아닌가 — 3장의 기준으로 따져 보기

"단가를 order_line에도 적으면 menu와 같은 값을 두 번 적는 것이니 3장이 금지한 중복 아닌가요?" 3장의 기준은 값이 같은가가 아니라 함수 종속이었습니다. 종속은 데이터가 아니라 업무 규칙이라고 했습니다(3장 화면 3). 이 줄 표에서 성립하는 규칙은 (order_id, line_no) → unit_price, 즉 "이 주문의 이 줄에서 받은 단가"입니다. 만약 menu_id → unit_price가 성립한다면 키가 아닌 열이 키가 아닌 열을 정하는 이행 종속(3장 화면 8)이라 3NF 위반이겠지만, 성립하지 않습니다. 같은 메뉴 1번이 3월 주문 101에서는 4500원이고 4월 주문에서는 4800원이기 때문입니다. 반례가 있으니 종속이 아니고, 따라서 정규화를 위반하지 않습니다.

같은 값이라도 의미가 다른 사실은 중복이 아니다

menu의 가격은 "지금 이 메뉴의 가격"이고 order_line.unit_price는 "그때 이 줄이 받은 돈"입니다. 주문을 만든 그 순간에 두 값이 우연히 같을 뿐이고, 그 뒤로는 서로 다른 길을 갑니다. 하나를 고쳐도 다른 하나를 따라 고쳐서는 안 됩니다. 중복은 "고칠 때 같이 고쳐야 하는 같은 사실"이고, 이것은 그 반대입니다.

더 깊이 — 이름은 왜 복사하고, 복사가 틀리면 무슨 일이 생기나

메뉴 이름에도 같은 논증이 섭니다. 업무가 "같은 메뉴면 영수증 이름도 항상 같다"고 말하면 menu_id → menu_name이 종속이라 복사는 위반입니다. 동백커피는 "이름을 바꿀 수 있고 영수증에는 그때 이름이 찍혀야 한다"고 말하므로 종속이 아닙니다. 함수 종속은 업무가 정하는 것이라 같은 열이 업무에 따라 위반이 되기도 하고 아니기도 합니다.

세트 구성품의 이름 스냅샷은 order_line_pick에 menu_name 한 열을 더합니다(영수증에 구성품이 찍히기 때문입니다).

-- 스키마 v5 ①-2: 세트 구성 선택 (v4 에서 바뀐 표)-- 세트 줄이 슬롯마다 고른 메뉴 (menu_name 은 그때의 이름)
CREATE TABLE order_line_pick (
    order_id   INTEGER NOT NULL,
    line_no    INTEGER NOT NULL,
    slot_id    INTEGER NOT NULL,
    menu_id    INTEGER NOT NULL,
    menu_name  TEXT    NOT NULL CHECK (menu_name <> ''),
    PRIMARY KEY (order_id, line_no, slot_id),
    FOREIGN KEY (order_id, line_no) REFERENCES order_line (order_id, line_no),
    FOREIGN KEY (slot_id, menu_id)  REFERENCES set_slot_menu (slot_id, menu_id)
                                    ON DELETE RESTRICT
);

복사에는 위험이 하나 있습니다. 복사를 잘못하면 돌이킬 방법이 없습니다. 오래된 화면이 들고 있던 가격을 복사했다면 그 잘못된 값이 영원히 그 줄의 사실이 됩니다. 그래서 복사는 메뉴 번호로 저장 시점에 DB에서 다시 읽어 같은 트랜잭션 안에서 하는 것이 안전합니다.

const Menu& m = menu; ... m.price처럼 참조로 읽으면 원본이 바뀔 때 같이 바뀌고(v4), int unit_price = m.price;처럼 값을 복사하면 그 뒤로 독립입니다(v5). 다만 C++에서 낡은 복사본은 대개 버그이지만, 여기서는 낡는 것이 목적입니다. 또 C++ 복사는 컴파일러가 빠뜨리지 않게 해 주지만, 이 복사는 DB가 해 주지 않습니다. NOT NULL로 빠뜨림만 막을 뿐입니다.

하윤의 첫 요구에는 스냅샷이 못 하는 것이 있습니다. "올리는 날짜를 미리 입력해 두면 그 시각에 바뀐다"입니다. 스냅샷은 주문이 있어야 생기므로 아직 아무도 주문하지 않은 4월의 가격은 적을 자리가 없습니다. 필요한 것은 메뉴 쪽에 가격의 변천을 기간과 함께 쌓아 두는 두 번째 도구입니다. 이것을 이력이라 부릅니다.

  • 이력은 보관 기간 정책이 있을 수 있습니다. 오래된 가격 행을 정리해도 주문 금액이 같이 사라지면 안 됩니다.

반대도 성립하지 않습니다. 스냅샷만 있으면 4월 1일의 가격을 미리 적어 둘 수 없고, 그날 주문이 하나도 없던 메뉴의 가격은 알 길이 없으며, "이 메뉴 가격이 언제 바뀌었나"를 주문 기록에서 역으로 추측해야 합니다.

  • 받은 돈과 영수증 → 스냅샷. 바꾸지 않는 사실입니다.
  • 예약, 그날의 가격표, 변화 분석 → 이력. 바로잡는 사실입니다.
  • 둘 다 필요하면 둘 다 둡니다. "메뉴가 가졌던 가격"과 "이 줄이 받은 가격"은 다른 사실이라 중복이 아닙니다(화면 2).
  • 한쪽만 필요하면 한쪽만 둡니다. 이력을 두는 것은 공짜가 아니라서 요구가 있을 때 둡니다(화면 12).

동백커피는 메뉴 가격에는 둘 다 필요합니다(하윤이 예약을 요구했습니다). 옵션 가격에는 예약 요구가 없으므로 스냅샷만 두고 이력은 만들지 않습니다(화면 4에서 다시 다룹니다).

가격 이력 — 유효 기간 모델과 겹침 방지

구조부터 봅니다. 새 표 menu_price의 한 행은 "이 메뉴는 이 기간 동안 이 가격이다"는 사실 하나입니다. 기간은 유효 기간(언제부터 언제까지)으로 적고, 끝을 모르는 행(지금도 유효한 행)은 끝을 NULL로 둡니다. 끝은 포함하지 않는 것으로 약속합니다. 4월 1일 00시에 끝나는 행과 4월 1일 00시에 시작하는 행이 같은 순간을 두 번 차지하지 않게 하려는 약속입니다(시작 포함, 끝 제외).

겹치면 왜 안 될까요? 같은 메뉴에 같은 시각을 덮는 행이 둘이면 "그 시각의 가격"이 하나로 정해지지 않습니다. 3장의 함수 종속으로 쓰면 (menu_id, 시각) → price인데 그 규칙이 깨집니다. 앱이 "겹치는 행이 있나" 확인한 뒤 넣어도, 두 요청이 동시에 확인하고 둘 다 통과하면 깨집니다(C1과 같은 모양). PostgreSQL에서는 이것을 DB가 막을 수 있습니다.

겹침 방지에 쓰는 이름 셋

  • tstzrange(시작, 끝) — 두 시각으로 구간 값을 만드는 함수입니다. 기본은 시작 포함·끝 제외이고 끝이 NULL이면 끝이 없는 구간입니다. &&는 "두 구간이 겹치는가"를 묻는 연산자입니다. tstzrange('2026-03-01', '2026-04-01') && tstzrange('2026-04-01', NULL)은 거짓(경계만 맞닿음)입니다.
  • EXCLUDE 제약 — "이 조건을 만족하는 행 쌍이 존재하면 거부한다"는 제약입니다. UNIQUE가 "같은 값"을 막는다면 EXCLUDE는 "겹치는 값"도 막을 수 있습니다. 아래에서는 같은 메뉴(=)이면서 구간이 겹치는(&&) 두 행을 거부합니다.
  • btree_gist — 정수 열(menu_id)을 =로 비교하는 일을 EXCLUDE가 쓰는 색인 방식(gist)에서도 하게 해 주는 확장입니다. 데이터베이스마다 한 번 CREATE EXTENSION으로 켭니다. 없으면 표를 만들 때 오류가 납니다.
-- 스키마 v5 ②: 가격 이력 (새 표 하나와 확장)-- 겹침 방지(EXCLUDE)에서 정수와 구간을 함께 비교하려면 필요한 확장
CREATE EXTENSION btree_gist;

-- 메뉴 가격의 유효 기간 (valid_to 가 NULL 이면 지금도 유효하다)
CREATE TABLE menu_price (
    menu_id     INTEGER     NOT NULL REFERENCES menu (menu_id),
    valid_from  TIMESTAMPTZ NOT NULL,
    valid_to    TIMESTAMPTZ,
    price       INTEGER     NOT NULL CHECK (price >= 0),
    PRIMARY KEY (menu_id, valid_from),
    CHECK (valid_to IS NULL OR valid_to > valid_from),
    EXCLUDE USING gist (menu_id WITH =, tstzrange(valid_from, valid_to) WITH &&)
);
  1. 2행 확장을 켭니다. 이 한 줄을 빼면 12행에서 data type integer has no default operator class for access method "gist" 오류가 납니다(PostgreSQL 18에서 확인).
  2. 4~13행 가격 행 하나. 9행 4장의 price >= 0 규칙이 menu에서 이리로 옮겨 왔습니다. 10행 기본키 (menu_id, valid_from)은 "같은 메뉴가 같은 시각에 시작하는 행은 하나"를 지키고, 11행 CHECK는 끝이 시작보다 늦어야 한다는 규칙입니다(NULL이면 통과).
  3. 12행 EXCLUDE USING gist (...)가 겹침을 막는 줄입니다. menu_id WITH =(같은 메뉴)와 tstzrange(valid_from, valid_to) WITH &&(구간이 겹침)을 모두 만족하는 행 쌍이 있으면 거부합니다. 다른 메뉴의 행과는 겹쳐도 됩니다.
-- 4/1 부터 아메리카노를 4800원으로: 새 행을 먼저 넣으면 거부된다INSERT INTO menu_price (menu_id, valid_from, price)
VALUES (1, '2026-04-01 00:00+09', 4800);
-- ERROR:  conflicting key value violates exclusion constraint
--         "menu_price_menu_id_tstzrange_excl"
-- DETAIL: Key (menu_id, tstzrange(valid_from, valid_to))=(1, ["2026-04-01
--         00:00:00+09",)) conflicts with existing key (...)=(1, [-infinity,)).

-- 올바른 순서: 지금 행을 닫고 새 행을 연다 (한 트랜잭션)
BEGIN;
UPDATE menu_price SET valid_to = '2026-04-01 00:00+09'
WHERE  menu_id = 1 AND valid_to IS NULL;
INSERT INTO menu_price (menu_id, valid_from, price)
VALUES (1, '2026-04-01 00:00+09', 4800);
COMMIT;

"4월 2일 09시 12분의 가격"은 그 시각을 덮는 행을 찾으면 됩니다. 행은 기껏해야 하나입니다(겹침을 막았으므로). 키오스크가 지금 가격을 보여 줄 때도 같은 조회에 NOW()를 넣습니다. TIMESTAMPTZ '...'는 글자를 시각 값으로 읽으라는 표기이고 +09는 한국 시간(UTC보다 9시간 빠름)입니다.

-- 주문 401 이 만들어지는 순간의 아메리카노 가격SELECT price
FROM   menu_price
WHERE  menu_id = 1
  AND  valid_from <= TIMESTAMPTZ '2026-04-02 09:12+09'
  AND (valid_to IS NULL OR TIMESTAMPTZ '2026-04-02 09:12+09' < valid_to);
-- (4800)

가격의 집은 한 곳 — menu.price 는 이사를 갔습니다

v4의 menu.price는 "지금 가격"이고 이력의 끝이 NULL인 행도 "지금 가격"입니다. 같은 사실을 두 곳에 두면 가격을 올릴 때 둘 다 고쳐야 하고 하나를 놓치면 어긋납니다. 화면 2의 스냅샷과 달리 이 둘은 같은 의미라 진짜 중복입니다(3장 D4의 총액과 같은 문제). 그래서 가격의 집을 menu_price 하나로 정하고 menu에서 price를 지웁니다(menu의 새 모양은 화면 5). "지금 가격"은 저장하지 않고 위 조회로 계산합니다. 대가는 셋입니다.

  • menu.price를 읽던 앱과 조회가 이사 순간 깨집니다. 그래서 화면 11의 이전은 "새 곳을 만들고, 옮기고, 마지막에 옛 열을 지우는" 순서를 따릅니다. 9장에서 다시 본다
  • 지금 가격 조회가 시간 조건이 붙은 조인이 됩니다.
  • "판매 중인 모든 메뉴에 열린 가격 행이 있다"는 여러 행을 보아야 하는 규칙이라 DB가 막지 못합니다. 가격 행이 없는 메뉴는 앱이 주문을 거부하고 점검 조회로 찾습니다(화면 5).

옵션 가격에는 이력이 없습니다

option_item.price는 "지금 가격"으로 그대로 두고 이력 표를 만들지 않습니다. 하윤이 예약을 요구한 것은 메뉴 가격이고, 과거 주문의 옵션 금액은 스냅샷이 지키기 때문입니다. 옵션 가격도 예약이 필요해지면 menu_price와 같은 모양의 표를 하나 더 만들면 됩니다. 정확성은 스냅샷이 지키고, 이력은 예약·분석이라는 별개의 요구가 있을 때만 둔다는 원칙입니다(화면 12). 메뉴만 이력이 있는 비대칭은 이 원칙의 결과입니다.

다른 DB에서는 — 그리고 PostgreSQL 18 의 새 문법

EXCLUDE는 PostgreSQL의 확장 문법입니다. MySQL, SQLite, Oracle 같은 다른 DB에는 없어서 겹침은 앱과 트랜잭션이 지킵니다(MariaDB처럼 기간 열에 WITHOUT OVERLAPS를 직접 지원하는 제품도 있습니다). 같은 메뉴의 "지금 행"을 먼저 잠그고(SELECT ... FOR UPDATE, 8장) 겹침을 확인한 뒤 넣는 식입니다. 조금만 틈이 있어도 겹침이 들어올 수 있고 DB가 그것을 알려 주지 않는다는 것이 차이입니다.

PostgreSQL 18부터는 기간 열을 TSTZRANGE 하나로 두고 PRIMARY KEY (menu_id, valid_at WITHOUT OVERLAPS)처럼 기본키 자체에 "겹치지 않음"을 적을 수 있습니다(이 경우에도 btree_gist가 필요합니다). 겹치는 행을 넣으면 같은 종류의 배제 제약 오류가 납니다. 이 교재는 두 열(valid_from, valid_to)로 적어서 다른 DB의 독자도 구조를 읽을 수 있게 했습니다.

더 깊이 — EXCLUDE 가 못 막는 것: 빈틈

EXCLUDE는 겹침만 막습니다. 앞 행을 3월 31일에 닫고 새 행을 4월 3일에 열면 그 사이 이틀은 가격이 없는 빈틈이 생기고 DB는 조용히 받아 줍니다. 빈틈이 일부러(판매 중단 기간)일 수도 있어서 DB가 일률적으로 막을 수 없습니다. 빈틈을 찾는 점검 조회는 이렇습니다.

-- 앞 행이 끝났는데 다음 행이 곧바로 시작하지 않는 메뉴SELECT menu_id, valid_to, next_from
FROM  (SELECT menu_id, valid_to,
              LEAD(valid_from) OVER (PARTITION BY menu_id
                                     ORDER BY valid_from) AS next_from
       FROM   menu_price) AS t
WHERE  valid_to IS NOT NULL AND valid_to <> next_from;

LEAD(열) OVER (PARTITION BY 묶음 ORDER BY 순서)는 같은 묶음 안에서 다음 행의 값을 가져오는 윈도 함수입니다(5장의 ROW_NUMBER와 같은 계열). 메뉴별로 시작 시각 순서로 줄을 세워 각 행에 다음 행의 시작 시각을 붙이고, 내 끝과 다음 시작이 다른 행을 고릅니다.

소프트 삭제와 판매중지 — C6 을 완성한다

갚는 빚

4장 화면 6은 C6("메뉴를 내려도 과거 주문은 남는다")을 ON DELETE RESTRICT와 is_active 플래그로 세웠지만 두 가지를 6장으로 미뤘습니다. ① 이름·가격을 고치면 과거 조회가 바뀐다는 것은 화면 2의 스냅샷과 화면 4의 이력이 갚았습니다. ② 판매중지한 메뉴를 새 주문에 못 담게 하는 것이 이 화면입니다.

먼저 menu의 새 모양입니다. 화면 4에서 price 열이 이력 표로 옮겨 가서 열 하나만 빠졌고 나머지(이름 규칙, is_active)는 v4와 글자까지 같습니다.

-- 스키마 v5 ②-2: 메뉴 (v4 에서 price 열이 빠진 표)-- 메뉴 한 종류 (가격은 menu_price 로 옮겨 갔다)
CREATE TABLE menu (
    menu_id    INTEGER PRIMARY KEY,
    name       TEXT    NOT NULL UNIQUE
               CHECK (name <> '' AND name = btrim(name)),
    is_active  BOOLEAN NOT NULL DEFAULT TRUE
);

소프트 삭제를 다시 확인합니다. 메뉴를 내릴 때는 행을 지우지 않고 is_active만 FALSE로 바꿉니다. 과거 주문이 가리키는 행은 지울 수도 없습니다.

-- 티라미수를 판매중지하고, 과거 주문이 가리키는 메뉴를 지워 본다UPDATE menu SET is_active = FALSE WHERE menu_id = 4;

DELETE FROM menu WHERE menu_id = 3;
-- ERROR:  update or delete on table "menu" violates RESTRICT setting of
--         foreign key constraint "order_line_menu_id_fkey" on table "order_line"

여기까지는 4장과 같습니다. 문제는 그다음입니다. DB는 판매중지 메뉴를 새 주문 줄이 가리키는 것도 받아 줍니다. order_line.menu_id의 외래키는 "그 메뉴 행이 있는가"만 묻고 is_active는 보지 않습니다(PostgreSQL 18에서 실제로 저장되는 것을 확인했습니다). 다른 표의 값을 조건으로 삼는 CHECK는 쓸 수 없으므로, 새 주문에서 판매중지 메뉴를 거르는 일은 주문을 만드는 앱의 몫입니다. 트리거라는 DB 안의 장치로 막는 방법도 있지만 이 교재는 다루지 않습니다.

앱이 흩어져서 제각각 is_active를 확인하면 한 곳에서 빠뜨리는 순간 판매중지 메뉴가 샙니다. 그래서 "지금 주문할 수 있는 메뉴와 가격"을 조회 한 곳으로 모으고 모든 화면이 그것을 씁니다. 화면 4의 지금 가격 조회와 is_active 조건이 합쳐진 모양입니다.

-- 키오스크가 보여 주는 메뉴판 (판매중지와 가격 행이 없는 메뉴는 빠진다)SELECT m.menu_id, m.name, p.price
FROM   menu AS m
JOIN   menu_price AS p ON p.menu_id = m.menu_id
WHERE  m.is_active
  AND  p.valid_from <= NOW()
  AND (p.valid_to IS NULL OR NOW() < p.valid_to)
ORDER BY m.menu_id;
-- 4/2 이후: (1, 아메리카노, 4800) (2, 카페라떼, 5000) (3, 치즈케이크, 6500)
--           (5, 케이크 세트, 9500)   ← 판매중지한 티라미수는 없다

이 조회는 JOIN이라서 가격 행이 없는 메뉴도 메뉴판에서 사라집니다. 화면 4가 말한 "모든 판매 메뉴에 열린 가격 행이 있다"는 규칙은 DB가 막지 못하니, 이렇게 조용히 사라지는 일을 점검 조회로 찾습니다.

-- 점검: 판매 중인데 지금 유효한 가격 행이 없는 메뉴SELECT m.menu_id, m.name
FROM   menu AS m
WHERE  m.is_active
  AND  NOT EXISTS (SELECT 1 FROM menu_price AS p
                   WHERE  p.menu_id = m.menu_id AND p.valid_to IS NULL);

NOT EXISTS (조회)는 괄호 안 조회가 한 행도 돌려주지 않을 때만 참입니다. 안쪽의 SELECT 1에서 1은 아무 값이어도 되고 "행이 있는가"만 봅니다.

소프트 삭제의 함정

  • 모든 조회가 is_active를 기억해야 합니다. 위 "한 곳으로 모으기"가 그 대책이지만 DB가 강제하지는 않습니다.
  • 이름이 묶입니다. 판매중지한 "티라미수"의 이름을 새 메뉴가 쓰려 하면 4장 C4의 UNIQUE가 거부합니다(duplicate key value violates unique constraint "menu_name_key"). 이 교재는 C4를 그대로 두고, 이름을 다시 쓰고 싶으면 옛 메뉴의 이름을 바꿔 보관하는(티라미수(종료)) 쪽을 택합니다.
  • 행이 영원히 쌓입니다. 판매중지한 메뉴도 과거 주문이 가리키는 한 지울 수 없습니다. 오래된 것을 정리하는 문제는 7장의 보관 이야기입니다. 7장에서 다시 본다
더 깊이 — 이름 묶임을 부분 UNIQUE 인덱스로 푸는 길과 그 대가

C4를 "판매 중인 메뉴 사이에서만 이름이 겹치지 않는다"로 약하게 바꾸면 이름을 재사용할 수 있습니다. 조건을 붙인 색인을 부분 UNIQUE 인덱스라 하고, WHERE 조건을 만족하는 행 사이에서만 유일성을 검사합니다.

CREATE UNIQUE INDEX menu_name_active ON menu (name) WHERE is_active;

INSERT INTO menu (menu_id, name) VALUES (8, '티라미수');

구분하는 세 가지 질문

  1. 받는 사람이 정해져 있는가? 그렇다면 "누구에게 줬나"를 적는 발급 기록이 필요합니다(쿠폰). 주인이 없는 이벤트에는 발급이 없습니다(프로모션).
  2. 쓰면 사라지는가? 그렇다면 "썼나"를 적는 사용 기록이 필요하고 "한 번만"이라는 규칙(C11)이 생깁니다(쿠폰). 등급은 쓴다고 사라지지 않습니다.
  3. 회원의 상태인가? 그렇다면 회원에게 붙고, 상태가 바뀌면 과거 주문은 그때의 상태를 기억해야 합니다(등급, 화면 8).

프로모션은 새 표를 만들지 않습니다

프로모션은 "이 기간에는 카페라떼가 4500원"이라는 기간을 가진 가격이라 화면 4의 menu_price가 그대로 담습니다. 영수증에 할인 줄이 따로 찍히지 않고 단가 자체가 4500원으로 찍힙니다. EXCLUDE가 겹침을 막기 때문에 기존 행을 행사 시작에서 닫고 행사 행과 복귀 행을 넣어야 합니다. 그 대신 행사가 끝나면 원래 가격이 저절로 돌아옵니다(복귀 행이 이미 있으므로 끝나는 날 할 일이 없습니다).

-- 카페라떼 4/6~4/12 행사가 4500원: 기존 행을 닫고, 행사 행과 복귀 행을 넣는다BEGIN;
UPDATE menu_price SET valid_to = '2026-04-06 00:00+09'
WHERE  menu_id = 2 AND valid_to IS NULL;
INSERT INTO menu_price (menu_id, valid_from, valid_to, price)
VALUES (2, '2026-04-06 00:00+09', '2026-04-13 00:00+09', 4500),
       (2, '2026-04-13 00:00+09', NULL, 5000);
COMMIT;

카페라떼의 기간 행은 이제 셋입니다. (-∞, 4/6) 5000원 → [4/6, 4/13) 4500원 → [4/13, 끝 없음) 5000원. 이 행사가 끝난 뒤에도 4/7 주문의 스냅샷은 4500원으로 남습니다. "할인 줄로 영수증에 보여 주어야 한다"는 마케팅 요구가 생기면 그때 order_discount의 종류에 프로모션을 더하는 것을 검토합니다. v5는 담지 않습니다.

할인이 겹칠 때의 정책 — 앱이 계산하고 결과만 저장합니다

  • 가격 행사는 이미 단가에 들어 있으므로 소계가 작아진 상태에서 나머지 할인이 계산됩니다.
  • 등급 할인은 쿠폰을 적용하기 전의 소계에 할인율을 곱하고 원 미만은 버립니다. 쿠폰은 정액을 뺍니다. 둘은 함께 적용할 수 있습니다.
  • 할인의 합은 소계를 넘을 수 없습니다. 이것은 여러 행의 합을 비교하는 규칙이라 DB가 못 막고 앱이 지킵니다.
  • 포인트는 할인이 아니라 돈 대신 내는 결제수단이라 이 표에 넣지 않습니다(화면 10).

이 정책은 저장하지 않고 앱이 주문을 만들 때 계산합니다. 계산의 결과(얼마를 깎았나)는 나중에 정책이 바뀌어도 변하면 안 되므로 주문에 저장합니다(화면 9).

쿠폰 모델 — 발급과 사용 (C11)

쿠폰 업무의 낱말부터 정합니다. 쿠폰은 종류입니다("오픈 기념 1000원, 4월 한 달"). 발급은 "이 회원에게 이 쿠폰을 준다"는 사건이고, 사용은 "회원이 주문에서 그 쿠폰을 썼다"는 사건입니다. 회원 3명에게 같은 쿠폰을 나눠 주면 쿠폰은 하나이고 발급은 셋입니다.

손이 먼저 가는 설계는 표 하나에 쿠폰 이름, 금액, 기간, 회원, 사용 여부를 모두 넣는 것입니다. 발급 100건마다 이름·금액·기간이 100번 반복되고, 금액을 정정하면 100행을 고쳐야 하니 3장의 이행 종속입니다(쿠폰 번호 → 이름·금액·기간). 그래서 종류와 발급을 두 표로 나눕니다.

표한 행이 뜻하는 것이 표만 가진 사실
coupon쿠폰 종류 하나이름, 할인 금액(정액), 유효 기간 [valid_from, valid_to) — 화면 4와 같은 "시작 포함, 끝 제외"
coupon_issue이 회원이 이 쿠폰을 받았다는 사건 하나발급 시각
-- 스키마 v5 ③: 쿠폰 (새 표 둘)-- 쿠폰 한 종류 (정액 할인)
CREATE TABLE coupon (
    coupon_id   INTEGER     PRIMARY KEY,
    name        TEXT        NOT NULL UNIQUE
                CHECK (name <> '' AND name = btrim(name)),
    amount      INTEGER     NOT NULL CHECK (amount > 0),
    valid_from  TIMESTAMPTZ NOT NULL,
    valid_to    TIMESTAMPTZ NOT NULL,
    CHECK (valid_to > valid_from)
);

-- 쿠폰 발급: 이 회원이 이 쿠폰을 받았다 (같은 쿠폰은 회원당 한 번만 받는다)
CREATE TABLE coupon_issue (
    issue_id   INTEGER     PRIMARY KEY,
    coupon_id  INTEGER     NOT NULL REFERENCES coupon (coupon_id),
    member_id  INTEGER     NOT NULL REFERENCES member (member_id),
    issued_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (coupon_id, member_id)
);

이 장의 예시 행은 이렇습니다. 쿠폰은 하나이고 발급은 회원 세 명에게 하나씩입니다.

그래서 나중에 무슨 문제가 되는가 — DB가 못 하는 것

멤버십 등급과 주문 시점 등급 스냅샷

하윤의 등급은 일반(0%), 실버(5%), 골드(10%)입니다. 멤버십 등급은 회원의 상태이고(화면 6), 이 상태가 바뀌면 과거 주문이 그때의 상태를 기억해야 합니다. 표로는 세 곳이 생깁니다.

자리한 행(열)이 뜻하는 것
membership_grade등급 하나와 그 등급의 할인율
member.grade이 회원의 지금 등급
orders.member_grade이 주문을 한 그때의 등급(스냅샷)

이 장의 예시에서 민준은 골드, 소라는 실버, 도윤은 일반입니다.

할인율을 member에 바로 두지 않고 등급 표로 뺀 이유는 3장 화면 8에서 배운 그대로입니다. member_id → grade → discount_pct는 키가 아닌 열이 키가 아닌 열을 정하는 이행 종속이라, 골드 회원 천 명의 행에 10이 천 번 적히고 "골드는 8%로 낮춘다"가 천 행의 수정이 됩니다. 등급 이름('일반', '실버', '골드')은 읽기 쉬워서 그 자체를 기본키로 씁니다(2장의 자연키 논쟁의 한 사례이고, 이름이 거의 안 바뀐다는 판단입니다). 등급을 없애지 않고 새 등급을 더하는 식으로 운영합니다.

-- 스키마 v5 ④: 멤버십 등급 (새 표 하나와 바뀐 표 둘)-- 회원 등급과 등급별 할인율
CREATE TABLE membership_grade (
    grade         TEXT    PRIMARY KEY
                  CHECK (grade <> '' AND grade = btrim(grade)),
    discount_pct  INTEGER NOT NULL CHECK (discount_pct BETWEEN 0 AND 100)
);

-- 회원 한 명 (grade 는 지금 등급)
CREATE TABLE member (
    member_id  INTEGER PRIMARY KEY,
    name       TEXT    NOT NULL,
    phone      TEXT    NOT NULL UNIQUE
               CHECK (phone ~ '^01[0-9]-[0-9]{3,4}-[0-9]{4}$'),
    grade      TEXT    NOT NULL DEFAULT '일반' REFERENCES membership_grade (grade)
);

-- 주문 한 건 (비회원 주문이면 member_id 가 NULL, member_grade 는 주문한 그때의 등급)
CREATE TABLE orders (
    order_id      INTEGER     PRIMARY KEY,
    member_id     INTEGER     REFERENCES member (member_id),
    ordered_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    payment       TEXT        NOT NULL CHECK (payment IN ('카드', '현금')),
    barista       TEXT        NOT NULL,
    status        TEXT        NOT NULL DEFAULT '접수'
                  CHECK (status IN ('접수', '제조중', '완료', '픽업', '취소')),
    member_grade  TEXT        REFERENCES membership_grade (grade),
    CHECK (member_id IS NOT NULL OR member_grade IS NULL)
);
  1. 5행 BETWEEN 0 AND 100은 양 끝을 포함하는 범위 검사입니다(>= 0 AND <= 100과 같습니다). 할인율이 음수이거나 100을 넘는 등급은 저장되지 않습니다.
  2. 14행 member의 새 열. DEFAULT '일반'이라 가입만 하면 일반 등급으로 시작하고, 외래키가 없는 등급 이름(예: '플래티넘')을 넣는 것은 거부됩니다. 10~13행은 v3와 같습니다.
  3. 26행 orders의 새 열. NOT NULL을 걸지 않았습니다. 비회원 주문에는 등급이 없고, 등급제 이전의 옛 주문은 그때 등급을 알 수 없어서입니다(아래).
  4. 27행 표 수준 CHECK는 "비회원 주문에는 등급이 붙지 않는다"를 지킵니다. A OR B에서 회원 주문이면 앞이 참이라 통과하고, 비회원 주문이면 member_grade IS NULL이어야 통과합니다.

등급이 바뀌어도 과거 주문은 그때 등급을 기억한다

SELECT o.order_id, m.grade AS now_grade, o.member_grade AS at_order
FROM   orders AS o
JOIN   member AS m ON m.member_id = o.member_id
WHERE  m.member_id = 1
ORDER BY o.order_id;
-- (101, 실버, NULL) (103, 실버, NULL) (201, 실버, NULL)
-- (401, 실버, 골드) (402, 실버, 골드)

4월의 주문 401·402(화면 9)는 민준이 골드였을 때의 주문이라 그때 골드가 남습니다. 지금 등급만 있었다면 이 두 주문도 "실버 주문"으로 읽혔을 것입니다. 할인 금액은 화면 9의 표에 따로 남지만, "그때 무슨 등급이었나"는 등급별 매출이나 등급 분쟁에서 별도로 묻는 사실이라 스냅샷으로 둡니다.

옛 주문의 NULL — 모르는 값을 지어내지 않는다

101, 103, 201은 등급제가 생기기 전 주문입니다. member_grade가 NULL인 것은 "그때 등급을 기록하지 않았다"는 뜻입니다. 5장 화면 13에서 "모르는 값을 지어내지 말고 기록 없음으로 둔다"고 했던 원칙입니다. 그 대가로 NULL이 두 가지 의미(비회원이라 해당 없음, 회원인데 기록 없음)를 갖습니다. "회원 주문이면 등급이 있어야 한다"를 DB가 강제할 수 없는 이유이기도 합니다. 옛 행이 이미 NULL이라 제약을 걸 수 없어서, 이 규칙은 새 주문부터 앱이 지킵니다.

더 깊이 — 옛 행을 건너뛰는 NOT VALID 가 이 표에는 맞지 않은 이유

제약을 걸면서 옛 행은 검사하지 않는 방법이 있습니다. ADD CHECK (...) NOT VALID는 새로 넣거나 고치는 행만 검사합니다. "회원 주문이면 등급 필수"를 이렇게 걸어 보면 함정이 드러납니다.

-- 회원 주문은 등급 필수, 옛 행은 검사하지 않고 (이 교재는 채택하지 않음)ALTER TABLE orders
    ADD CONSTRAINT orders_grade_needed
    CHECK ((member_id IS NULL) = (member_grade IS NULL)) NOT VALID;

UPDATE orders SET status = '취소' WHERE order_id = 101;
-- ERROR:  new row for relation "orders" violates check constraint "orders_grade_needed"
-- DETAIL: Failing row contains (101, 1, 2026-03-04 09:10:00+09, 카드, 지호, 취소, null).

검사하지 않는 것은 "이미 저장된 상태"뿐이고, 옛 행을 어느 열이든 UPDATE하는 순간 그 행 전체를 다시 검사합니다. 이 제약이 있으면 옛 주문에 store_id 같은 열을 채우는 전체 행 갱신이 전부 막힙니다. 9장에서 다시 본다 그래서 v5는 약한 CHECK(27행)와 앱의 규칙을 택했습니다.

적용된 할인 내역 — 계산 규칙은 바뀌어도 결과는 남는다

등급 할인율(10%)도 쿠폰 금액(1000원)도 언젠가 바뀝니다. 그런데 주문 401에서 "얼마를 깎아 주었나"는 그때 계산된 사실이라 규칙이 바뀌어도 변하면 안 됩니다. 화면 2의 스냅샷과 같은 이유로 할인의 결과 금액을 주문 쪽에 저장합니다. 계산 규칙(화면 6의 정책)은 앱이 들고 있고 DB에는 결과만 남습니다.

표한 행이 뜻하는 것이 표만 가진 사실
order_discount이 주문에 적용된 할인 한 건종류(쿠폰 또는 등급), 쿠폰이면 어느 발급인지, 그때 계산된 할인액
-- 스키마 v5 ⑤: 적용된 할인 내역 (새 표 하나와 부분 UNIQUE 인덱스)-- 주문에 적용된 할인 한 건 (amount 는 그때 계산된 할인액)
CREATE TABLE order_discount (
    order_id     INTEGER NOT NULL REFERENCES orders (order_id),
    discount_no  INTEGER NOT NULL CHECK (discount_no >= 1),
    kind         TEXT    NOT NULL CHECK (kind IN ('쿠폰', '등급')),
    issue_id     INTEGER UNIQUE REFERENCES coupon_issue (issue_id),
    amount       INTEGER NOT NULL CHECK (amount > 0),
    PRIMARY KEY (order_id, discount_no),
    CHECK ((kind = '쿠폰') = (issue_id IS NOT NULL))
);

-- 한 주문에 등급 할인은 한 번만
CREATE UNIQUE INDEX order_discount_grade_once
    ON order_discount (order_id) WHERE kind = '등급';
  • 4행 discount_no는 5장의 줄 번호와 같은 생각입니다. 한 주문의 할인 행이 여럿이라 주문 안의 번호로 구별합니다.
  • 6행 issue_id ... UNIQUE가 C11의 나머지 조각입니다. 같은 발급은 할인 내역에 한 번만 나올 수 있으므로 한 쿠폰은 한 번만 쓰입니다. NULL은 서로 같다고 보지 않아 등급 할인 행(issue_id가 NULL)은 얼마든지 들어갑니다(4장의 UNIQUE와 NULL).
  • 9행 표 수준 CHECK는 "쿠폰 행은 발급 번호가 있고, 등급 행은 없다"를 지킵니다. (kind = '쿠폰')과 (issue_id IS NOT NULL)의 참/거짓이 같아야 통과합니다.
  • 7행 amount > 0 — 깎은 것이 없으면 행을 만들지 않습니다(0원 할인 행은 저장되지 않습니다).
  • 13~14행은 부분 UNIQUE 인덱스입니다. WHERE kind = '등급'인 행들 사이에서만 order_id가 겹치지 않게 해서 한 주문에 등급 할인은 한 번만 허용합니다. 쿠폰 행은 여럿이어도 됩니다.
-- 주문 401: 등급 할인 10% (소계 16100 의 10% = 1610)와 쿠폰 1000원INSERT INTO order_discount (order_id, discount_no, kind, issue_id, amount)
VALUES (401, 1, '등급', NULL, 1610),
       (401, 2, '쿠폰', 1, 1000);

-- 같은 쿠폰(발급 1)을 다른 주문(402)에도 쓰려 하면
INSERT INTO order_discount (order_id, discount_no, kind, issue_id, amount)
VALUES (402, 1, '쿠폰', 1, 1000);
-- ERROR:  duplicate key value violates unique constraint "order_discount_issue_id_key"
-- DETAIL: Key (issue_id)=(1) already exists.

주문줄소계할인할인 후 금액

주문이 '취소'가 되어도 할인 행은 남기 때문에 쿠폰은 돌아오지 않습니다. 지우면 "그때 이 할인이 적용되었다"는 사실이 사라지기 때문입니다. 돌려주는 설계는 이 장의 직접 해보기입니다.

총액과 결제금액은 저장하지 않습니다 — D4 결정은 그대로

이 교재는 세 가지 금액을 구별합니다. 소계 = 줄 금액의 합, 할인 후 금액 = 소계 − 할인의 합, 청구액 = 할인 후 금액 − 그 주문에서 쓴 포인트(화면 10). 셋 모두 그 주문 자신의 행(스냅샷이 붙은 줄·옵션, 할인 내역, 포인트 기록, 화면 10)만으로 계산되며, 저장하지 않습니다.

  • 저장하는 것은 "그때 계산된 사실"(줄의 단가, 할인액)입니다. 규칙이 바뀌면 달라질 값이기 때문입니다. 합계는 그 사실들에서 다시 계산할 수 있는 파생값이라 3장 화면 9의 이유(같은 사실을 두 번 적지 않는다)로 저장하지 않습니다.
  • 스냅샷 덕분에 계산이 틀어질 원인(가격 변경)은 사라졌습니다. 끝난 주문의 행은 고치지 않으므로(앱 규칙) 합계는 영원히 같은 값입니다. 조회가 느려졌을 때 요약 테이블을 얹어도 어긋날 위험이 작다는 뜻이라, D4를 7장에서 되돌리는 일이 쉬워집니다. 7장에서 다시 본다
더 깊이 — 소계·할인·할인 후 금액을 구하는 조회와 "행이 곱해지는" 함정 
-- 주문별 소계, 할인, 할인 후 금액 (저장하지 않고 계산한다)SELECT o.order_id,
       s.subtotal,
       COALESCE(d.discount, 0)              AS discount,
       s.subtotal - COALESCE(d.discount, 0) AS after_discount
FROM   orders AS o
JOIN  (SELECT ol.order_id,
              SUM(ol.quantity * (ol.unit_price + COALESCE(x.extra, 0))) AS subtotal
       FROM   order_line AS ol
       LEFT JOIN (SELECT order_id, line_no, SUM(unit_price * option_qty) AS extra
                  FROM   order_line_option
                  GROUP BY order_id, line_no) AS x
              ON x.order_id = ol.order_id AND x.line_no = ol.line_no
       GROUP BY ol.order_id) AS s ON s.order_id = o.order_id
LEFT JOIN (SELECT order_id, SUM(amount) AS discount
           FROM   order_discount
           GROUP BY order_id) AS d ON d.order_id = o.order_id
ORDER BY o.order_id;
-- (401, 16100, 2610, 13490) (402, 5000, 500, 4500) ... 할인이 없는 주문은 discount 0

FROM 자리에 괄호로 감싼 조회에 별명(AS s)을 붙이면 작은 표처럼 쓸 수 있습니다. 줄 쪽 합계(s)와 할인 쪽 합계(d)를 각자 먼저 주문별로 합친 뒤 주문에 붙였습니다. 줄 표와 할인 표를 한꺼번에 조인해서 SUM하면 주문 401(줄 2개, 할인 2건)이 2 × 2 = 4행으로 불어나 소계가 32200, 할인이 5220으로 두 배가 됩니다. 한 주문에 "여럿"인 자식 표 둘을 동시에 조인하면 생기는 전형적인 오류입니다.

포인트 — 잔액 컬럼 vs 원장 (C12)

하윤의 규칙은 "내가 실제로 낸 금액의 1%를 적립하고 다음 주문에서 돈처럼 쓴다"입니다. 포인트는 할인이 아니라 돈 대신 내는 결제수단이라서, 주문 401처럼 포인트를 쓰지 않으면 청구액 13490원의 1%인 134포인트(원 미만은 버림)가 쌓이고, 주문 402처럼 2000포인트를 쓰면 청구액 2500원의 25포인트가 쌓입니다. 그리고 잔액은 음수가 될 수 없습니다(C12).

첫 번째 설계 — 잔액 컬럼 하나

가장 쉬운 방법은 member에 point_balance 열을 두고 적립·사용 때마다 덮어쓰는 것입니다. 음수 금지가 CHECK 한 줄로 끝납니다.

-- 잔액 컬럼 방식 (이 교재는 채택하지 않음)ALTER TABLE member ADD COLUMN point_balance INTEGER NOT NULL DEFAULT 0
    CHECK (point_balance >= 0);
UPDATE member SET point_balance = point_balance - 2000 WHERE member_id = 1;
-- ERROR:  new row for relation "member" violates check constraint
--         "member_point_balance_check"

음수를 DB가 막아 준다는 큰 장점이 있습니다. 대신 기록이 남지 않습니다. 잔액 159가 왜 159인지, 어느 주문에서 얼마를 썼는지 알 수 없고, 재시도로 같은 차감이 두 번 적용되어도 흔적이 없으며, 잘못 고친 잔액을 바로잡을 근거가 없습니다. 이것은 화면 2의 문제와 같은 종류입니다(과거가 덮여 사라집니다).

두 번째 설계 — 원장

원장(ledger)은 증감 사건을 쌓기만 하는 표이고 잔액은 사건의 합입니다. 행 하나가 "이 회원의 포인트가 이만큼 늘었다/줄었다"는 사실입니다. 잘못이 있으면 고치지 않고 반대 방향의 행을 더해 바로잡습니다(조정).

-- 스키마 v5 ⑥: 포인트 원장 (새 표 하나와 부분 UNIQUE 인덱스)-- 포인트 원장: 늘고 주는 내역을 쌓기만 한다 (잔액은 delta 의 합)
CREATE TABLE point_ledger (
    entry_id    INTEGER     PRIMARY KEY,
    member_id   INTEGER     NOT NULL REFERENCES member (member_id),
    reason      TEXT        NOT NULL CHECK (reason IN ('적립', '사용', '조정')),
    delta       INTEGER     NOT NULL,
    order_id    INTEGER     REFERENCES orders (order_id),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CHECK ((reason = '적립' AND delta > 0)
        OR (reason = '사용' AND delta < 0)
        OR (reason = '조정' AND delta <> 0)),
    CHECK (reason = '조정' OR order_id IS NOT NULL)
);

-- 한 주문에 적립도 사용도 한 번씩만
CREATE UNIQUE INDEX point_ledger_once
    ON point_ledger (order_id, reason) WHERE reason IN ('적립', '사용');
  • 9~11행 표 수준 CHECK — 적립은 양수, 사용은 음수, 조정은 0이 아닌 아무 부호입니다. 부호가 뒤집힌 행은 저장되지 않습니다.
  • 12행 적립과 사용은 어느 주문의 것인지 반드시 적습니다. 조정(이벤트 지급, 소멸, 정정)만 주문 없이 들어올 수 있습니다.
  • 16~17행 부분 UNIQUE 인덱스가 같은 주문의 적립을 두 번 넣는 재시도 사고를 막습니다(duplicate key value violates unique constraint "point_ledger_once"). 포인트를 한 번 쓴 주문은 사용 행이 하나뿐입니다.
  • "원장은 고치지 않는다"를 DB가 강제하려면 앱 계정에서 UPDATE·DELETE 권한을 빼야 하는데, 권한 관리는 이 교재의 범위 밖이라 앱의 규칙으로 둡니다.
-- 민준(회원 1)의 원장과 그때그때의 잔액SELECT entry_id, reason, delta,
       SUM(delta) OVER (ORDER BY entry_id) AS running
FROM   point_ledger
WHERE  member_id = 1
ORDER BY entry_id;
-- (1, 조정, 3000, 3000) (2, 적립, 134, 3134) (3, 사용, -2000, 1134) (4, 적립, 25, 1159)

SUM(delta) OVER (ORDER BY entry_id)는 줄 번호 순으로 지금까지의 합(누적합)을 각 행에 붙이는 윈도 함수입니다. 마지막 값이 잔액 1159이고, 잔액만 필요하면 그냥 SUM(delta)입니다. "왜 1159인가"에 행 네 개가 답합니다.

원장이 못 막는 것 — C12

대가는 음수 금지를 선언할 수 없다는 것입니다. 잔액은 여러 행의 합이고 CHECK는 한 행만 봅니다. 잔액이 1159인 회원이 5000포인트를 쓰는 행도 DB는 받아 줍니다(C1, C9처럼 여러 행을 세는 규칙입니다).

-- 가정 주문 403 을 만들고, 잔액(1159)보다 큰 5000 포인트를 쓰는 행: DB 는 받아 준다INSERT INTO orders (order_id, member_id, payment, barista)
VALUES (403, 1, '카드', '지호');
INSERT INTO point_ledger (entry_id, member_id, reason, delta, order_id)
VALUES (5, 1, '사용', -5000, 403);

-- 점검: 잔액이 음수인 회원
SELECT member_id, SUM(delta) AS balance
FROM   point_ledger
GROUP BY member_id
HAVING SUM(delta) < 0;
-- (1, -3841)

그래서 C12는 사용 행을 넣기 직전에 합계를 확인하는 앱의 검사와 점검 조회로 지킵니다. 그런데 "합계를 확인하고 넣는" 사이에 다른 요청이 같은 회원의 포인트를 쓰면 둘 다 통과합니다. 이것을 막는 잠금은 8장의 주제입니다. 8장에서 다시 본다 한편 잔액을 열로 함께 두어 조회를 빠르게 하는 방법(원장이 진실이고 잔액 열은 복사본)은 7장의 의도적 비정규화입니다. 7장에서 다시 본다

  3. 9~17행 기존 행을 지금 값으로 채웁니다(backfill). backfill은 새로 더한 열에 이미 있던 행의 값을 채우는 작업입니다. 이것은 "이전 전에는 가격이 바뀐 적이 없다"는 가정 위에서만 맞습니다. 이미 올린 뒤에 실행하면 옛 주문에 새 가격이 복사되어 틀린 값이 사실처럼 굳습니다. 그때는 옛 가격을 아는 다른 기록으로 채우거나, 모르면 채우지 말고 조사해야 합니다.

시간 이력 테이블(temporal) — 시간이 두 개라면

화면 4의 menu_price는 "사실이 현실에서 참이던 기간"(유효 시간)만 적습니다. 그런데 DB가 그 사실을 알고 있던 기간(기록 시간)은 별개입니다. 오타를 정정한 경우가 그 차이입니다.

방식기억하는 것"정정이 금액을 바꿨나"에 답할 수 있나
현재 값만 + 스냅샷지금 값, 주문이 받은 값정정 전 값을 모른다
유효 시간 이력(v5)언제 얼마였나정정하면 덮어쓴다. 4800이라고 알았던 시기는 사라진다
양방향 시간(bitemporal)언제 얼마였나 + 언제 그렇게 알았나"4/2에는 4800으로 알았고 4/5에 4700으로 정정했다"를 둘 다 조회한다

이렇게 행에 시간 축을 붙여 관리하는 표를 시간 이력 테이블(temporal table)이라 합니다. SQL 표준(SQL:2011)에 기간과 시스템 버전 표가 정의되어 있고, SQL Server의 system-versioned 표, MariaDB 같은 제품이 기록 시간을 DB가 자동으로 관리해 줍니다. PostgreSQL은 기록 시간을 자동으로 쌓는 기능은 내장하지 않고, 유효 시간의 겹침 방지는 화면 4의 EXCLUDE(18부터는 WITHOUT OVERLAPS)로 지원합니다.

이 교재가 그 길을 가지 않은 이유는 셋입니다. 하윤의 요구에 "정정의 기록"이 없고, 받은 돈은 스냅샷이 지키며, 양방향 시간은 모든 조회에 시간 조건이 둘씩 붙어 읽기 어려워지기 때문입니다. 세금·감사처럼 정정 기록 자체가 의무인 업무라면 이야기가 달라집니다. 더 읽을 책으로는 Snodgrass의 Developing Time-Oriented Database Applications in SQL과 Date·Darwen·Lorentzos의 Temporal Data and the Relational Model이 있습니다.

핵심 요약

  1. D1은 스냅샷으로 갚았습니다. 주문을 만들 때 그때의 이름·단가·옵션가를 줄에 복사합니다(C8). 같은 값이라도 의미가 다른 사실은 중복이 아닙니다. "지금 메뉴의 가격"과 "그때 이 줄이 받은 돈"은 menu_id → unit_price 종속이 성립하지 않으므로 정규화 위반이 아닙니다.
  2. 스냅샷은 그때 받은 것(고치지 않음), 이력은 언제 얼마였나(바로잡음, 예약)입니다. 가격 이력은 유효 기간 행으로 두고 겹침은 EXCLUDE가 막습니다(다른 DB는 앱·트랜잭션). 빈틈은 못 막습니다. 같은 사실은 한 곳에만 두어 menu.price는 이력으로 이사했고, 이력은 요구가 있을 때만 둡니다.
  3. C6은 판매중지(소프트 삭제) + RESTRICT + 스냅샷·이력으로 완성되고, 새 주문에서 판매중지 메뉴를 거르는 일은 앱의 몫입니다.
  4. 프로모션(기간 가격)·쿠폰(발급 + 사용)·멤버십 등급(회원의 상태 + 그때 등급 스냅샷)은 누가 어떤 조건으로 갖는가로 구분합니다. 할인의 결과 금액은 주문에 저장하고, 쿠폰 1회(C11)는 UNIQUE 둘(발급, 사용)이 지킵니다.
  5. 포인트는 원장(사건을 쌓고 잔액은 합계)으로 두며 음수 금지(C12)는 선언할 수 없어 앱과 8장의 잠금이 지킵니다. 소계·할인 후 금액·청구액은 저장하지 않습니다(D4). 결과가 스키마 v5이고 D2·D4·D5는 남았습니다.

order_line.unit_price가 주문하는 순간 menu의 가격과 같은 값을 다시 적는 것이 정규화(3NF) 위반이 아닌 이유는 무엇일까요?

  1. 메뉴 가격은 자주 바뀌지 않기 때문이다
  2. 같은 메뉴라도 주문 시점마다 다른 단가를 받을 수 있어 menu_id → unit_price 종속이 성립하지 않기 때문이다
  3. 복사한 열에 NOT NULL 과 CHECK 가 걸려 있기 때문이다

같은 논증이 반대로도 작동합니다. menu.is_active(지금 판매 중인가)를 order_line에 복사한다면 그것은 "지금 상태"라 원본과 같은 사실을 두 번 적는 진짜 중복이 되어, 메뉴를 내릴 때 모든 줄을 고쳐야 합니다. 그래서 화면 2는 스냅샷의 범위를 "금액에 쓰이는 값과 영수증에 찍히는 값"으로 한정했습니다. 무엇을 복사하느냐가 곧 무엇이 그때의 사실인가를 고르는 일입니다.

4/1부터의 아메리카노 가격을 4800원으로 적었다가 4700원이 맞아서 이력 행을 고쳤습니다. 이미 끝난 주문 401(4800원을 받았다)의 금액을 고치기 전 그대로 지켜 주는 것은 무엇일까요?

  1. 주문 줄의 스냅샷 열(unit_price)
  2. 이력 행의 유효 기간 열(valid_from, valid_to)
  3. 가격 이력 표의 EXCLUDE 제약

이력을 덮어쓰지 않고 정정하고 싶다면 행을 고치는 대신 정정 기록을 남기는 길이 있습니다. 행에 "이 행이 정정으로 대체된 시각" 열을 더해 틀린 행을 지우지 않고 표시만 하고(겹침 방지는 대체되지 않은 행 사이에서만 걸어야 합니다), 바른 행을 새로 넣는 것입니다. 그러면 "4800이라고 알았던 시기"가 남습니다. 이것이 화면 12의 양방향 시간(bitemporal)을 가장 가볍게 흉내 낸 모양입니다. 단, 그래도 받은 돈은 여전히 스냅샷의 몫입니다. 이력은 "메뉴가 가진 가격", 스냅샷은 "이 줄이 받은 가격"이라는 다른 사실을 적기 때문입니다.

"같은 쿠폰은 회원당 한 번만 쓸 수 있다"(C11)를 DB 선언으로 지키는 구성은 무엇일까요?

  1. 발급 표의 UNIQUE (coupon_id, member_id) 하나
  2. 발급 표에 used 열을 두고 앱이 확인한다
  3. 발급 표의 UNIQUE (coupon_id, member_id) + 할인 내역 표의 UNIQUE (issue_id)

이 구성이 통하는 것은 "회원당 한 번"이 유일성으로 표현되기 때문입니다. "한 사람이 세 번까지" 쓰는 쿠폰이 되면 UNIQUE로는 표현되지 않고 사용 횟수를 세어 3을 넘는지 봐야 합니다. 그 순간 포인트 잔액(C12)과 같은 "세고 나서 넣는" 규칙이 되어, 동시 요청에서 깨질 수 있는 8장의 문제가 됩니다.

포인트를 원장(point_ledger)으로 두면 잔액이 음수가 되는 것을 DB가 선언만으로 막지 못합니다. 이유는 무엇일까요?

  1. 원장 표에는 CHECK를 쓸 수 없기 때문이다
  2. 잔액은 여러 행의 합이라 한 행만 보는 CHECK나 외래키가 볼 수 없기 때문이다
  3. 잔액 컬럼 방식도 마찬가지로 못 막기 때문이다

두 장점을 함께 얻는 조합이 있습니다. 원장을 진실로 두고 잔액 열을 복사본으로 같은 트랜잭션에서 갱신하면 잔액 열의 CHECK (point_balance >= 0)로 음수 금지를 되살릴 수 있습니다. 대가는 원장과 잔액이 어긋날 위험이고, 이것이 7장의 의도적 비정규화와 8장의 원자성이 만나는 자리입니다.

-- 모범답안: 행은 두고 무효 표시, 유일성은 "유효한 행"에만ALTER TABLE order_discount ADD COLUMN voided_at TIMESTAMPTZ;

    ON order_discount (issue_id) WHERE voided_at IS NULL;

-- 주문 401 을 취소할 때
UPDATE order_discount SET voided_at = NOW() WHERE order_id = 401;

1. 거부됩니다. 취소해도 할인 행은 남아 있고 issue_id의 UNIQUE가 "같은 발급은 할인 내역에 한 번"을 지키기 때문입니다(화면 9).

2. 무효 표시가 맞습니다. 할인 행은 "그때 이 할인이 적용되었다"는 사실이라 지우면 그 주문의 금액 재계산과 감사가 틀어집니다. 4장의 소프트 삭제와 같은 생각입니다.

3. 표 수준 UNIQUE는 조건을 붙일 수 없으므로 없애고, 부분 UNIQUE 인덱스로 voided_at IS NULL(유효한 행) 사이에서만 겹치지 않게 합니다. 그러면 무효가 된 행의 발급은 다시 쓸 수 있고 유효한 행 둘이 같은 발급을 가리키는 것은 여전히 막힙니다.

4. 모든 합계 조회에 voided_at IS NULL을 붙여야 합니다. 빼먹으면 취소된 할인이 할인 후 금액에 계속 들어갑니다. 화면 5의 소프트 삭제 함정과 같은 대가입니다.

흔한 오답 1 — 할인 행을 DELETE한다. 위 2번의 이유로 틀리고, 지운 행이 가리키던 쿠폰 사용의 흔적도 사라집니다.

흔한 오답 2 — 같은 쿠폰을 회원에게 한 번 더 발급한다(coupon_issue에 새 행). UNIQUE (coupon_id, member_id)에 걸려 거부됩니다. 새 발급이 아니라 같은 발급을 다시 쓸 수 있게 하는 문제입니다.

흔한 오답 3 — orders.status = '취소'이면 할인 행을 합계에서 빼는 CHECK를 건다. CHECK는 다른 표의 값을 볼 수 없어 불가능합니다. 주문 상태는 합계 조회가 조인해서 보아야 하는 앱의 몫입니다.
