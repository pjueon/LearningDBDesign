용어집

본문에서 점선 밑줄로 뜻이 뜨던 용어와, 본문에서 이름을 붙여 쓴 용어를 모았습니다. 용어마다 한 줄 정의(본문 툴팁과 같은 짧은 문장이며 ~다 체입니다. 슈퍼키·BCNF는 본문에 툴팁이 없어 같은 문체로 새로 적었습니다), 무엇과 다른가(헷갈리는 짝), 처음 깊게 다룬 페이지을 적었습니다. 정의는 본문이 우선입니다. 이 용어집은 본문을 요약한 것이고 새 사실을 더하지 않습니다.

찾는 법

아래 가나다 찾아보기에서 용어를 누르면 그 용어가 있는 페이지로 넘어갑니다. 페이지 2~9는 개념 묶음(장 순서)으로 나뉘어 있습니다. 각 용어의 장·페이지 링크는 본문에서 그 용어를 가장 깊게 다룬 자리입니다.

부록 · 페이지 2

표·키·관계

0~2장. 표가 무엇이고, 행을 어떻게 구별하고, 표끼리 어떻게 이어지는가.

용어 · 처음 다룬 곳한 줄 정의무엇과 다른가
테이블 (릴레이션)
0장 페이지 4		같은 모양의 행을 모은 표. 엑셀 시트와 달리 행 순서가 없고, 열마다 타입이 있고, 제약이 붙는다.엑셀 시트와 다릅니다. 시트는 칸마다 아무 값이나 넣을 수 있고 행 순서가 의미를 갖지만, 테이블은 열 타입과 제약이 있고 행 순서에 기대지 않습니다.
DBMS
Database Management System, 데이터베이스 관리 시스템
0장 페이지 3		데이터를 저장하고 꺼내 주고 규칙을 지켜 주는 프로그램. PostgreSQL, MySQL, SQLite가 DBMS다. "DB"는 데이터 자체를, DBMS는 그것을 관리하는 소프트웨어를 가리키지만 일상에서는 섞어 쓴다.DB(데이터 자체)와 다릅니다. 스키마·테이블 같은 구조와도 다릅니다. DBMS는 그것들을 담고 지켜 주는 프로그램입니다.
스키마
2장 페이지 11		어떤 테이블이 있고 각 테이블에 어떤 열과 규칙이 있는지 정한 설계. 데이터(행)가 아니라 그 데이터를 담는 틀이다.데이터(행)와 다릅니다. 스키마는 틀이고 행은 그 안의 내용입니다. 이 교재의 v1~v7(v5.1 포함)은 스키마의 버전입니다.
엔터티
2장 페이지 3		요구사항에서 독립해서 구별되고 여러 사실이 딸린 대상(메뉴, 회원, 주문). 나중에 테이블이 된다.테이블과 다릅니다. 엔터티는 요구사항에서 뽑는 개념이고, 테이블은 그것을 DB에 옮긴 결과입니다.
속성
2장 페이지 3		엔터티에 딸린 정보 하나(메뉴의 이름, 가격). 나중에 테이블의 열이 된다.열과 다릅니다. 속성은 개념이고 열은 그것을 옮긴 결과입니다. 값이 여럿 딸리거나 독립해서 구별되면 속성이 아니라 엔터티입니다.
기본키 (PK, Primary Key)
2장 페이지 4		행 하나를 유일하게 가리키는 열(들). 같은 값이 두 행에 있을 수 없고 비어 있을 수 없다.후보키와 다릅니다. 후보키는 조건을 만족하는 모든 후보이고 기본키는 그중 대표로 뽑은 하나입니다. UNIQUE와도 다릅니다(기본키는 NULL 불가, 표당 하나).
후보키
2장 페이지 4		행을 유일하게 구별하면서(유일성) 열을 하나라도 빼면 그 성질이 깨지는(최소성) 열 조합. 그중 대표로 뽑은 것이 기본키다.슈퍼키와 다릅니다. 유일성만 만족하면 슈퍼키이고, 열을 하나라도 빼면 유일성이 깨지는 최소의 것만 후보키입니다.
슈퍼키
2장 페이지 4		행을 유일하게 구별하는 열 조합. 최소일 필요는 없다.후보키와 다릅니다. (name, phone)처럼 이미 유일한 열에 열을 더한 조합도 슈퍼키이지만 후보키는 아닙니다.
복합키 (복합 키)
2장 페이지 7		열 둘 이상을 묶어 하나의 키로 쓴 것. 한 열만으로는 유일하지 않아도 조합이 유일하면 된다(order_line의 (order_id, menu_id)).열마다 따로 건 키 여럿과 다릅니다. 열 하나하나가 아니라 조합 전체가 유일해야 하고, 그 조합을 가리키는 외래키도 열 조합 전체로 가리킵니다(복합 외래키, 5장).
자연키
2장 페이지 5		업무에 원래 있는 값을 그대로 키로 쓴 것(전화번호, 이메일). 바뀔 수 있다는 것이 약점이다.대리키와 다릅니다. 자연키는 업무에 이미 있는 값이라 "안 바뀔 줄 알았는데 바뀐다"가 문제이고, 대리키는 의미가 없다는 것이 문제입니다.
대리키
2장 페이지 5		의미 없이 시스템이 붙인 번호를 키로 쓴 것(member_id). 값이 바뀌지 않지만 같은 사람인지는 알려 주지 못한다.자연키와 다릅니다. 값은 바뀌지 않지만 같은 사람인지는 알려 주지 못해서, 자연키였던 열에는 UNIQUE를 함께 둡니다.
외래키 (FK, Foreign Key)
2장 페이지 9		다른 테이블의 행을 가리키는 열. 없는 행을 가리키는 값은 DB가 막는다. C++ 포인터와 닮았지만 댕글링을 DB가 막아 준다는 점이 다르다.C++ 포인터와 닮았지만 다릅니다. 포인터는 댕글링이 가능하고, 외래키는 없는 행을 가리키는 값을 DB가 막습니다. 외래키 열에 인덱스가 자동으로 생기지는 않습니다.
참조 무결성
2장 페이지 9		외래키가 가리키는 행이 실제로 존재한다는 보장. 없는 행을 가리키는 값은 DB가 거부한다.외래키와 다릅니다. 외래키는 그것을 지키는 장치이고, 참조 무결성은 그렇게 지켜진 상태입니다.
ER 다이어그램
2장 페이지 10		엔터티(상자), 속성, 키, 관계(선, 1과 N)를 한 장에 그린 설계도.CREATE TABLE과 다릅니다. ER 다이어그램은 사람이 읽는 설계도이고, CREATE TABLE은 그 결과를 DB에 만드는 문장입니다.
카디널리티
2장 페이지 6		관계에서는 두 엔터티가 몇 대 몇으로 이어지는가(1:N, N:M). 인덱스 문맥(7장)에서는 열이 가진 서로 다른 값의 수를 뜻해 다른 개념이다.같은 낱말이 두 뜻입니다. 관계의 대응 수(1:N)와 인덱스 문맥에서 열이 가진 서로 다른 값의 수입니다. 문맥으로 구분합니다.
연결 테이블
2장 페이지 7		N:M 관계를 풀려고 두 표 사이에 끼운 표. 한 행이 두 엔터티의 짝 하나(이 주문에 이 메뉴)를 뜻하고, 관계 자체에 딸린 값(수량)이 여기에 자리를 얻는다.엔터티 표와 다릅니다. 연결 테이블은 독립된 대상이 아니라 두 엔터티의 관계를 담는 표입니다(order_line).
조인 (JOIN)
0장 페이지 6		두 테이블의 행을 키가 같은 것끼리 이어 붙여 한 결과 표로 만드는 조회.표를 나누는 정규화의 반대 방향입니다. 저장은 나누고 보기는 합칩니다. 합치면 조회가 복잡해지고 이어 붙이는 일이 듭니다.

부록 · 페이지 3

중복과 정규화

1장과 3장. 같은 사실이 여러 곳에 적히면 무슨 일이 생기고, 어떻게 검증하는가.

용어 · 처음 다룬 곳한 줄 정의무엇과 다른가
이상현상
1장 페이지 8		같은 사실이 여러 곳에 적히거나 서로 다른 종류의 사실이 한 행에 섞여서, 고치기·넣기·지우기에서 생기는 오류(갱신·삽입·삭제 이상). 버그가 아니라 설계 결함이다.버그와 다릅니다. 코드가 맞게 동작해도 설계 때문에 생기는 오류입니다.
중복
1장 페이지 8		같은 사실이 둘 이상의 자리에 저장된 것. 값이 우연히 같은 것과는 다르다.값이 우연히 같은 것과 다릅니다. 같은 사실을 두 곳에 적은 것이 중복이고, 값이 같아도 다른 사실이면 중복이 아닙니다(스냅샷).
무결성
1장 페이지 7		데이터가 서로 모순되지 않고 정해진 규칙에 맞는 상태.값이 현실과 맞는다는 보장과 다릅니다. 모순이 없고 규칙을 지킨다는 뜻이라, 손으로 적은 이름이 흔들려 틀린 숫자가 나오는 것은 무결성이 깨진 것입니다.
함수 종속 (FD)
3장 페이지 2		A 값이 정해지면 B 값이 하나로 정해지는 관계(A → B). 데이터가 아니라 업무 규칙이다. 왼쪽 A를 결정자라고 부른다.데이터에서 우연히 그렇게 보이는 것과 다릅니다. 함수 종속은 업무 규칙이라 업무에 묻고, 데이터는 반례를 찾는 데만 씁니다.
결정자
3장 페이지 2		함수 종속 A → B의 왼쪽 A. 이 값이 정해지면 오른쪽 값이 하나로 정해진다.키와 다릅니다. 결정자는 종속의 왼쪽일 뿐이고, 모든 결정자가 후보키이면 BCNF 입니다.
정규화
3장 페이지 11 · 12		함수 종속을 따라 표를 나눠 같은 사실이 한 곳에만 있게 하는 과정이자, 설계를 검증하는 도구. 단계가 정규형이다(1NF 원자값, 2NF 부분 종속 없음, 3NF 이행 종속 없음, 더 엄격한 BCNF). 이 교재는 3NF에서 멈추고, 값의 의미(그때의 가격인지 지금의 가격인지)까지는 보장하지 않는다.비정규화와 다릅니다. 정규화는 중복을 없애는 방향이고, 비정규화는 그것을 한 뒤에 되돌리는 방향입니다.
원자값
3장 페이지 5		업무에서 더 쪼개면 뜻이 깨지는 값 하나. 한 칸에 목록을 넣지 않는 것이 1NF의 요구다."값이 작다"와 다릅니다. 업무에서 쪼개면 뜻이 깨지는 단위가 원자입니다. 쉼표로 이은 메뉴 목록은 원자값이 아닙니다.
부분 종속
3장 페이지 7		복합 키의 일부만으로 정해지는 키가 아닌 열이 있는 상태. 2NF가 금지한다.이행 종속과 다릅니다. 부분 종속은 복합 키의 일부로 정해지고, 이행 종속은 키가 아닌 열을 거쳐 정해집니다.
이행 종속
3장 페이지 8		키가 아닌 열이 다른 키가 아닌 열을 거쳐서 정해지는 상태(키 → 열 → 열). 3NF가 금지한다.부분 종속과 다릅니다. 이행 종속은 키(전체)에서 다른 열을 거쳐 정해지는 모양입니다.
BCNF (보이스-코드 정규형)
3장 페이지 10		모든 결정자가 후보키여야 한다는, 3NF보다 엄격한 규칙.3NF와 다릅니다. 후보키가 겹치는 드문 경우에만 갈립니다. 나누고 나면 원래 표의 규칙을 키 제약만으로 못 지키는 대가가 생길 수 있습니다.
파생값
3장 페이지 9		다른 열에서 계산할 수 있는 값(합계 = 단가 × 수량). 저장하면 원본과 어긋날 위험이 생긴다.정규형 검사와 따로 판단합니다. 총액은 정규형 검사에 걸리지 않아도 같은 사실을 두 번 적는 문제를 만듭니다.
무손실 분해
3장 페이지 13		표를 나눈 뒤 다시 이었을 때 원래의 행이 정확히 복원되는 분해. 공통 열이 한쪽 표의 후보키이면 보장된다.종속 보존과 다릅니다. 무손실은 다시 이으면 행이 복원되는가이고, 종속 보존은 규칙을 나눈 뒤에도 키로 지킬 수 있는가입니다.
비정규화
7장 페이지 8		성능을 위해 정규화된 설계를 일부러 되돌려 같은 사실을 중복해 두는 것. 정규화를 안 한 것이 아니라 한 뒤에 되돌린 것이며, 어긋남을 막는 갱신 경로와 점검이 따라와야 한다.정규화를 안 한 것과 다릅니다. 정규화를 한 뒤 측정하고 일부러 되돌린 것입니다.

부록 · 페이지 4

제약·NULL·타입

4장과 6장 일부. 규칙을 DB에 선언하는 도구들과 NULL.

용어 · 처음 다룬 곳한 줄 정의무엇과 다른가
제약조건
4장 페이지 1		데이터가 지켜야 할 규칙을 DB에 선언한 것(NOT NULL, UNIQUE, CHECK, 외래키 등). 어기는 입력은 DB가 거부한다.인덱스와 다릅니다. 제약은 규칙을 강제하고 인덱스는 찾기를 빠르게 합니다. UNIQUE는 둘을 겸합니다.
NULL
4장 페이지 2		값이 없다 또는 알 수 없다는 표시. 0도 빈 글자도 아니다. NULL과의 비교는 참도 거짓도 아닌 "알 수 없음"이 되어 NULL = NULL도 참이 아니다. NULL 여부는 IS NULL로 묻는다.0이나 빈 글자와 다릅니다. NULL = NULL도 참이 아니라서 IS NULL로 묻습니다.
3값 논리
4장 페이지 2		SQL의 조건식이 참·거짓·알 수 없음 세 가지 결과를 갖는 셈법. WHERE는 참인 행만 남기고, CHECK는 거짓인 행만 거부하므로 알 수 없음이면 통과한다.참·거짓 두 값의 논리와 다릅니다. WHERE는 참인 행만 남기고 CHECK는 거짓인 행만 거부해서 "알 수 없음"이 서로 다르게 처리됩니다.
부동소수점 (float)
4장 페이지 3		2진수로 실수를 근사해 저장하는 타입. 0.1 같은 값을 정확히 담지 못해 금액에는 쓰지 않는다. 정확한 십진수는 NUMERIC.NUMERIC과 다릅니다. 부동소수점은 근사값이고 NUMERIC은 정확한 십진수입니다.
DEFAULT
4장 페이지 4		INSERT에서 그 열을 적지 않았을 때 DB가 대신 넣는 값. 규칙이 아니라 편의이며, 열에 NULL을 명시하면 적용되지 않는다.제약과 다릅니다. DEFAULT는 규칙이 아니라 편의이고, NULL을 명시한 입력에는 적용되지 않습니다.
UNIQUE
4장 페이지 5		같은 값이 두 행에 있을 수 없게 하는 제약. 기본키와 달리 한 표에 여러 개 둘 수 있고 PostgreSQL에서는 NULL을 여러 행에 넣을 수 있다.기본키와 다릅니다. 한 표에 여러 개 둘 수 있고 PostgreSQL 에서는 NULL을 여러 행에 넣을 수 있습니다.
CHECK
4장 페이지 7		한 행의 값이 조건식을 만족해야 저장되게 하는 제약. 그 행의 열만 볼 수 있고, 조건이 NULL(알 수 없음)이면 통과한다.외래키·UNIQUE와 다릅니다. 한 행의 열만 볼 수 있어서 여러 행을 세는 규칙(C1)은 못 막습니다. 조건이 NULL이면 통과합니다.
ON DELETE
4장 페이지 6		외래키가 가리키는 행(부모)을 지울 때 참조하는 행(자식)을 어떻게 할지 정하는 절. NO ACTION(기본)·RESTRICT는 거부, CASCADE는 함께 삭제, SET NULL·SET DEFAULT는 값 변경.소프트 삭제와 다릅니다. ON DELETE는 진짜로 지울 때 자식을 어떻게 할지이고, CASCADE는 부모가 사라지면 자식이 의미를 잃는 관계에 맞는 선택입니다.
지연 가능 제약 (DEFERRABLE)
4장 페이지 9		검사를 저장할 때마다가 아니라 트랜잭션이 끝날 때(커밋)까지 미루도록 선언한 제약(DEFERRABLE INITIALLY DEFERRED). 이 교재는 외래키에서 다루며, 중복 열과 그 열을 늘 맞춰야 하는 부담 때문에 쓰지 않는다.보통의 외래키와 다릅니다. 보통은 저장할 때마다 바로 검사하고, 지연 가능 외래키는 커밋 때 검사합니다. 제약 트리거(CONSTRAINT TRIGGER)와도 다릅니다. 그것은 선언이 아니라 DB 안에 넣는 프로그램 코드입니다.
소프트 삭제
6장 페이지 5		행을 실제로 지우지 않고 "쓰지 않음" 표시(판매중지 플래그)만 남기는 방식. 과거 기록이 가리키는 행을 보존한다.DELETE와 다릅니다. 행이 남고 표시만 바뀌므로, 새 주문에서 거르는 일은 앱의 몫입니다.
EXCLUDE 제약
6장 페이지 4		조건을 만족하는 두 행이 함께 있으면 거부하는 PostgreSQL 제약. UNIQUE가 같은 값을 막는다면 EXCLUDE는 겹치는 구간도 막을 수 있다. 정수 열을 함께 쓰려면 btree_gist 확장이 필요하다.UNIQUE와 다릅니다. UNIQUE는 같은 값을, EXCLUDE는 겹치는 구간도 막습니다. 빈틈은 못 막고 PostgreSQL 에만 있습니다.
부분 UNIQUE 인덱스
6장 페이지 5		WHERE 조건을 만족하는 행 사이에서만 유일성을 검사하는 인덱스(CREATE UNIQUE INDEX ... WHERE ...). "한 주문에 등급 할인은 한 번"처럼 조건부 유일성에 쓴다.일반 UNIQUE 인덱스와 다릅니다. 조건을 만족하는 행 사이에서만 유일성을 검사합니다. 인덱스이지만 제약처럼 씁니다.

부록 · 페이지 5

옵션·세트·트리

5장. 종류가 늘어나는 메뉴를 행으로 담는 구조.

용어 · 처음 다룬 곳한 줄 정의무엇과 다른가
옵션
5장 페이지 2		손님이 메뉴에 덧붙이거나 바꾸는 선택지 하나(샷 추가, 얼음 적게). 메뉴를 바꾸지만 다른 메뉴로 만들지는 않으며, 가격이 붙고 0원일 수도 있다. 세트와 달리 메뉴를 묶지 않는다.세트와 다릅니다. 옵션은 메뉴를 바꾸고 세트는 메뉴를 묶습니다. 옵션을 붙여도 다른 메뉴가 되지는 않습니다.
옵션 그룹
5장 페이지 5		같은 종류의 옵션을 모은 묶음(샷, 시럽, 얼음). 그룹마다 고를 수 있는 개수의 범위(최소~최대)를 가진다.세트의 구성 슬롯과 다릅니다. 옵션 그룹은 같은 종류의 옵션 묶음이고 선택 개수의 범위를 가집니다.
세트
5장 페이지 8		여러 메뉴를 묶어 하나의 가격으로 파는 상품(음료 + 케이크). 옵션이 메뉴를 바꾼다면 세트는 메뉴를 묶는다.옵션과 다릅니다. 세트는 menu의 한 행이고 구성은 슬롯·후보·선택 세 표로 담습니다.
구성 슬롯
5장 페이지 9		세트 안에서 채워야 하는 자리(음료 1, 디저트 1). 슬롯마다 들어갈 수 있는 후보 메뉴가 정해져 있다.픽업 슬롯과 다릅니다. 구성 슬롯은 세트 안의 자리이고, 픽업 슬롯은 시간대와 정원입니다(8장).
복합 외래키
5장 페이지 6		열 둘 이상을 한 덩어리로 묶어 다른 표의 복합키를 가리키는 외래키. 열 조합 전체가 그 표에 있는 행이어야 저장된다.열마다 따로 건 외래키 둘과 다릅니다. 열 조합 전체가 대상 표에 있어야 하고, 열 하나라도 NULL이면 검사하지 않습니다.
자기 참조
5장 페이지 10		외래키가 같은 표의 기본키를 가리키는 것(분류의 상위 분류). 트리를 한 표에 담는 방법이다.두 표를 잇는 외래키와 다릅니다. 같은 표 안에서 상위 행을 가리킵니다. 깊이를 모르는 트리는 재귀 조회가 필요합니다.
재귀 조회 (WITH RECURSIVE)
5장 페이지 10		조회 결과를 다시 조회의 입력으로 넣어 트리를 위아래로 끝까지 따라가는 SQL 문법.일반 JOIN과 다릅니다. 결과를 다시 입력으로 넣어 깊이를 모르는 트리를 끝까지 따라갑니다.
EAV
Entity-Attribute-Value
5장 페이지 11		속성 이름과 값을 행으로 쌓는 설계(엔터티, 속성 이름, 값 세 열). 열을 늘리지 않고 속성을 더할 수 있지만 타입·제약·외래키·조회를 잃는다.이 교재의 옵션 모델과 다릅니다. 옵션은 종류·가격·개수 규칙이 있는 행이고, EAV는 이름과 값만 쌓아서 타입과 제약을 잃습니다. 정당한 드문 경우가 있습니다.

부록 · 페이지 6

과거를 지키기

6장. 가격·할인·포인트가 바뀌어도 과거가 틀어지지 않게 하는 구조.

용어 · 처음 다룬 곳한 줄 정의무엇과 다른가
스냅샷
6장 페이지 2		주문을 만들 때 그 순간의 이름·단가·옵션가를 주문 라인에 복사해 둔 값. 메뉴가 바뀌어도 고치지 않는다. 지금 값과 잠시 같을 뿐 의미가 다른 사실이라 중복이 아니다.이력과 다릅니다. 스냅샷은 "그때 받은 값"이라 고치지 않고, 이력은 "언제 얼마였나"라 잘못 적었으면 바로잡습니다.
이력
6장 페이지 3		값이 바뀐 내역을 기간과 함께 쌓아 둔 기록. 스냅샷이 "이 주문이 받은 값"이라면 이력은 "이 메뉴가 언제 얼마였나"이고, 잘못 적었으면 바로잡는다.스냅샷과 다릅니다. 이력은 메뉴가 가진 값의 변천이고, 이 라인이 받은 금액은 스냅샷이 지킵니다.
유효 기간
6장 페이지 4		한 값이 참이던 기간 [시작, 끝). 이 교재는 시작 포함·끝 제외로 적고 끝이 NULL이면 지금도 유효하다는 뜻이다.시작과 끝을 모두 포함하는 구간과 다릅니다. [시작, 끝)이라 앞 행의 끝과 뒤 행의 시작이 같은 순간을 두 번 차지하지 않습니다.
시간 이력 테이블 (temporal table)
6장 페이지 12		행에 시간 축(유효 시간, 기록 시간)을 붙여 관리하는 표. SQL:2011에 표준이 있고 제품마다 지원이 다르다. 두 시간을 모두 쓰면 양방향(bitemporal)이라 한다.이 교재의 menu_price처럼 직접 만든 이력 표와 다릅니다. 시간 축을 제품이나 표준이 관리해 주는 방식이고 지원이 제품마다 다릅니다.
프로모션
6장 페이지 6		기간을 정한 이벤트. 받는 주인이 없고 조건(기간, 대상 메뉴)만 맞으면 누구나 받는다. 회원이 받는 쿠폰, 회원의 상태인 등급과 구별된다.쿠폰·등급과 다릅니다. 셋 다 할인이지만 프로모션은 받는 주인이 없습니다. 누가 어떤 조건으로 갖는지가 다릅니다.
쿠폰
6장 페이지 7		회원이 발급받아 한 번 쓰는 혜택. 종류(coupon)와 발급(coupon_issue)을 나누어 적고, 사용 여부는 열로 저장하지 않고 할인 내역에서 유도한다.프로모션·등급과 다릅니다. 회원이 발급받아 한 번 쓰는 혜택이라 발급과 사용을 따로 적습니다.
멤버십 등급
6장 페이지 8		회원에게 붙은 상시 자격(일반·실버·골드)과 등급별 할인율. 등급은 바뀌므로 주문이 그때의 등급을 스냅샷으로 들고 있어야 한다.쿠폰과 다릅니다. 회원에게 붙은 상시 자격이라 바뀌고, 그래서 주문이 그때의 등급을 스냅샷으로 가집니다.
원장 (ledger)
6장 페이지 10		증감 사건을 쌓기만 하는 표. 잔액은 사건의 합계로 구하고, 잘못은 고치지 않고 반대 방향의 행을 더해 바로잡는다. 덮어쓰는 잔액 열과 다르다.잔액 열과 다릅니다. 원장은 쌓기만 하고 잔액은 합계입니다. 잘못은 고치지 않고 반대 방향의 행을 더합니다.

부록 · 페이지 7

인덱스와 큰 데이터

7장. 데이터가 커졌을 때 찾는 법과 일부러 되돌리는 법.

용어 · 처음 다룬 곳한 줄 정의무엇과 다른가
인덱스
7장 페이지 2		원하는 행을 빨리 찾게 해 주는 색인 구조. 제약조건과 목적이 다르다(찾기 속도 vs 규칙 강제). 자세히는 7장.제약조건과 다릅니다. 인덱스는 찾기 속도, 제약은 규칙 강제입니다. UNIQUE는 둘을 겸합니다.
페이지 (버퍼)
7장 페이지 2		DB가 디스크를 읽고 쓰는 고정 크기 덩어리(PostgreSQL은 8KB). 행 하나가 필요해도 그 행이 든 페이지 전체를 읽는다. 이 교재의 "읽은 페이지 수"가 비용의 척도다.행과 다릅니다. 행 하나가 필요해도 그 행이 든 페이지 전체를 읽습니다. 그래서 비용 척도는 시간이 아니라 읽은 페이지 수입니다.
풀스캔 (full scan)
7장 페이지 2		인덱스 없이 표의 모든 행을 처음부터 끝까지 읽으며 조건을 검사하는 것. PostgreSQL 실행 계획의 Seq Scan. 비용은 표의 페이지 수에 비례한다.인덱스를 쓴 조회와 다릅니다. 인덱스가 있어도 많은 행을 고르면 DB가 풀스캔을 고를 수 있습니다.
B-tree
7장 페이지 3		값을 정렬해 페이지에 담고 루트·중간·잎의 나무로 쌓은 인덱스 구조. 모든 잎이 같은 깊이이고 한 페이지에 수백 개의 갈래가 있어 100만 행도 3~4쪽으로 찾는다. 등호·범위·정렬에 쓰이는 기본 인덱스 종류다.정렬된 std::map과 다릅니다. 메모리 포인터를 따라가는 노드가 아니라 8KB 페이지 하나가 노드 하나이고, 한 페이지에 갈래가 수백 개라 나무가 낮습니다.
복합 인덱스
7장 페이지 4		열 둘 이상을 앞 열부터 차례로 정렬해 담은 인덱스. 앞 열(선두 열)의 조건이 있어야 잘 쓰이고, 등호 조건 열을 앞에, 범위나 정렬 열을 뒤에 둔다.열마다 만든 인덱스 여러 개와 다릅니다. 앞 열부터 정렬된 하나의 구조라서 선두 열의 조건이 있어야 잘 쓰입니다.
선택도
7장 페이지 7		조건 하나가 행을 얼마나 잘 걸러 내는가. 고르는 행의 비율이 작을수록 선택도가 높다고 말한다(PostgreSQL 문서는 그 비율 자체를 선택도라 부르니 숫자로는 작을수록 "높은" 것이다). 인덱스는 선택도가 높은 조건에서 듣는다. 열의 카디널리티(서로 다른 값의 수)와 관련되지만 값의 분포에 따라 값마다 다르다.카디널리티와 다릅니다. 카디널리티는 열의 서로 다른 값의 수이고, 선택도는 조건 하나가 고르는 행의 비율이며 값마다 다릅니다.
EXPLAIN
7장 페이지 6		DB가 조회를 어떻게 실행할지의 계획을 보여 주는 명령. EXPLAIN ANALYZE는 실제로 실행해 실제 행 수와 시간을, BUFFERS는 읽은 페이지 수를 붙인다.실제 실행과 다릅니다. EXPLAIN은 계획만 보이고, ANALYZE를 붙여야 실제로 실행해 실제 값을 보입니다.
요약 테이블
7장 페이지 8		원본을 미리 집계해 저장한 파생 표(일 매출 daily_sales). 읽는 단위에 맞춰 행 수를 줄여 조회를 빠르게 하지만 원본의 사본이라 어긋날 수 있다.원본(정규형)과 다릅니다. 원본의 사본이라 어긋날 수 있고, 지우고 다시 만들 수 있어야 합니다.
멱등
7장 페이지 9		같은 작업을 몇 번 실행해도 한 번 실행한 것과 결과가 같은 성질. 지우고 다시 계산하기는 멱등이고 증감을 더하기는 아니다.단순히 안전하다는 뜻과 다릅니다. 같은 요청을 두 번 받아도 한 번과 같다는 성질이고, 증감을 더하는 갱신은 아닙니다.
keyset 페이지네이션
7장 페이지 10		OFFSET으로 건너뛰는 대신 마지막으로 본 행의 키를 기억하고 그 이후를 조회하는 방식. 몇 번째 페이지든 읽는 양이 같다.OFFSET과 다릅니다. OFFSET은 건너뛴 만큼 읽고, keyset은 마지막 키 이후부터 읽습니다. 대신 임의의 쪽 번호로 바로 갈 수 없습니다.
파티셔닝
7장 페이지 11		큰 표를 기간 같은 기준으로 여러 물리 표(파티션)로 나누어 한 표처럼 쓰는 것. 기간 조회는 해당 파티션만 읽고 오래된 기간은 표째로 버릴 수 있다.아카이브와 다릅니다. 파티셔닝은 한 표처럼 쓰는 물리적 분할이고, 아카이브는 다른 표로 옮기고 원본을 지웁니다. v7은 파티셔닝을 하지 않기로 했습니다(9장).
아카이브
7장 페이지 11		오래된 행을 보관용 표로 옮기고 원본에서 지우는 것. 자식 표의 순서, 합계가 필요한 표(원장), 요약의 재생성 가능성을 따져야 한다.파티셔닝과 다릅니다. 원본에서 지우므로 요약이 원본의 사본에서 유일한 기록으로 바뀔 수 있습니다.

부록 · 페이지 8

트랜잭션·동시성·재고

8장. 동시에 들어오는 요청에서 규칙을 지키는 법.

용어 · 처음 다룬 곳한 줄 정의무엇과 다른가
트랜잭션
8장 페이지 4		여러 작업을 한 묶음으로 처리해 전부 성공하거나 전부 취소되게 하는 단위. 자세히는 8장.락과 다릅니다. 트랜잭션은 전부 되거나 전부 취소되는 묶음이고 락은 동시 접근을 막는 장치입니다. 트랜잭션만으로 동시성이 자동 해결되지는 않습니다.
ACID
8장 페이지 4		트랜잭션이 지키는 네 성질. 원자성(전부 되거나 전부 안 됨), 일관성(커밋된 상태는 선언한 제약을 지킴), 격리성(동시 트랜잭션이 서로의 중간 상태를 못 봄, 정도를 고른다), 지속성(커밋은 서버가 꺼져도 남음). 일관성은 업무적 옳음을 뜻하지 않는다.네 성질 모두가 완벽하지는 않습니다. 격리성은 수준을 고르고, 일관성은 "제약을 지킨다"이지 "업무적으로 옳다"가 아닙니다.
커밋 / 롤백
8장 페이지 4		트랜잭션을 끝내는 두 방법. COMMIT은 묶음의 변경을 확정하고, ROLLBACK은 그 변경을 전부 버린다. 커밋 전의 변경은 다른 연결에 보이지 않는다.ROLLBACK은 DB 안의 변경만 되돌립니다. 이미 보낸 문자 메시지 같은 DB 밖의 일은 되돌리지 못합니다. 오류가 난 트랜잭션에 COMMIT을 보내도 ROLLBACK으로 처리됩니다.
락 (잠금)
8장 페이지 5		행을 고치는 트랜잭션이 끝날 때까지 다른 트랜잭션이 같은 행을 고치지 못하게 막는 표시. UPDATE가 자동으로 걸고 SELECT ... FOR UPDATE는 읽으면서 건다. 막힌 쪽은 기다린다. 일반 SELECT는 락을 걸지도 기다리지도 않는다.트랜잭션과 다릅니다. 이 락은 행 단위이고, 표 전체에 거는 표 잠금(9장)과는 층이 다릅니다.
경쟁 상태 (race condition)
8장 페이지 5		동시 요청의 실행 순서에 따라 결과가 달라지는 버그. 읽고 판단하고 쓰는 사이의 틈에서 생긴다.교착과 다릅니다. 경쟁 상태는 순서에 따라 결과가 틀리고, 교착은 서로 기다려 멈춥니다.
갱신 손실 (lost update)
8장 페이지 5		두 트랜잭션이 같은 값을 읽고 각자 계산한 값을 써서 한쪽의 변경이 사라지는 사고. 앱이 계산한 값으로 덮어쓸 때 생긴다.오류가 나는 사고와 다릅니다. 오류 없이 한쪽의 변경이 조용히 사라집니다.
낙관적 락
8장 페이지 6		충돌이 드물다고 보고 미리 잠그지 않고, 쓸 때 읽은 뒤로 바뀌지 않았는지(version 열 등)만 조건에 넣어 확인하는 방식. 미리 잠그는 쪽은 비관적 락(FOR UPDATE)이다.비관적 락(SELECT ... FOR UPDATE)과 다릅니다. 미리 잠그지 않고 쓸 때 확인합니다.
비관적 락
8장 페이지 7		충돌이 잦다고 보고 읽을 때부터 행에 락을 걸어 두는 방식(SELECT ... FOR UPDATE). 락을 쥐는 시간이 읽는 순간부터 커밋까지라 길어지기 쉽고, 충돌이 몰리는 곳에 어울린다.낙관적 락과 다릅니다. 비관적 락은 읽으면서 미리 잠그고, 낙관적 락은 잠그지 않고 쓸 때 바뀌지 않았는지 확인합니다.
교착 (데드락)
8장 페이지 8		두 트랜잭션이 서로 상대가 쥔 락을 기다려 영원히 못 나아가는 상태. DB가 감지해 한쪽을 오류(40P01)로 중단시키며, 모두가 같은 순서로 락을 잡는 것이 예방이다.일반적인 락 대기와 다릅니다. 기다림이 순환이라 스스로 풀리지 않아 DB가 한쪽을 중단시킵니다.
격리 수준
8장 페이지 9		동시에 실행되는 트랜잭션이 서로의 변경을 얼마나 보는지 정하는 설정. PostgreSQL은 READ COMMITTED(기본), REPEATABLE READ, SERIALIZABLE. 올릴수록 보이는 것이 고정되지만 직렬화 실패(40001) 재시도가 필요해진다.ACID의 격리성과 같은 말이지만, 정도를 고르는 설정입니다. 올릴수록 직렬화 실패의 재시도가 필요해집니다.
재고 품목
8장 페이지 2		수량을 세어 관리하는 대상 한 가지(치즈케이크, 원두). 손님이 사는 그대로인 완제품과 메뉴를 만드는 데 들어가는 원재료로 나뉜다. 남은 양은 기본 단위(g, ml, 개)의 정수로 저장한다.메뉴와 다릅니다. 메뉴는 파는 상품이고 재고 품목은 수량을 세는 대상이며, 레시피로 이어집니다.
레시피 (소요량)
8장 페이지 2		메뉴 1개 또는 옵션 1회가 재고 품목을 얼마나 쓰는지 적은 연결. 소요량은 (메뉴, 품목) 쌍에 딸린 값이라 연결 테이블의 속성이다.품목의 속성과 다릅니다. 소요량은 (메뉴, 품목) 쌍에 딸린 값이라 연결 테이블에 둡니다.
픽업 슬롯
8장 페이지 11		픽업 시간대 하나(30분 간격)와 그 정원. 주문 1건이 정원 1을 쓴다. 5장의 세트 구성 슬롯과는 다른 개념이다.세트의 구성 슬롯과 다릅니다. 픽업 슬롯은 시간대와 정원이고, 주문 1건이 정원 1을 씁니다.

부록 · 페이지 9

다점포·스키마 변경·앱 경계

9장과 10장. 운영 중인 스키마를 바꾸는 법과 앱이 DB를 만나는 자리.

용어 · 처음 다룬 곳한 줄 정의무엇과 다른가
매장 범위
9장 페이지 2		표의 행이 매장 소유인지(store_id가 키나 열에 들어간다), 부모 행을 따라 매장을 아는지(상속, 열을 더하지 않는다), 모든 매장이 같은 행을 보는지(브랜드 공통)의 분류. 값이 매장마다 다른가, 한 매장의 사건인가, 부모로 알 수 있는가를 묻는다.모든 표에 store_id를 붙이는 것과 다릅니다. 부모를 따라 매장을 아는 라인 표는 열을 더하지 않습니다(3장의 부분 종속).
멀티테넌시
9장 페이지 4		여러 고객(여기서는 매장)이 한 시스템을 나눠 쓰는 구조. 같은 표에 store_id 열을 두는 공유 스키마, 고객마다 스키마를 나누는 방식, 고객마다 DB를 나누는 방식이 있다.매장마다 DB를 따로 두는 것과 다릅니다. 이 교재는 공유 스키마에 store_id 열을 두는 방식을 택했습니다.
확장→이전→축소 (expand-contract)
9장 페이지 6		운영 중인 구조를 바꿀 때 새 구조를 옛 구조 옆에 더하고(확장), 새 앱을 배포하고 데이터를 채워 옮기고(이전), 아무도 옛 구조를 안 쓰는 것을 확인한 뒤 지우는(축소) 순서. 각 단계 사이에 옛 앱과 새 앱이 모두 동작해야 하고 되돌릴 수 없는 일은 맨 끝에 몰아 둔다.한 번에 바꾸는 방식과 다릅니다. 새 구조를 옆에 더하고 옛 구조를 마지막에 지웁니다. 더하는 것이 먼저, 지우는 것이 나중입니다.
마이그레이션
9장 페이지 11 (선택)		스키마를 바꾸는 SQL을 번호 붙은 파일로 두고 순서대로 적용하며, 어디까지 적용했는지를 DB 안에 기록하는 방식. 실패하면 되돌릴 수 있는지를 단계마다 따진다.확장→이전→축소와 다릅니다. 확장→이전→축소는 변경을 단계로 나누는 순서이고, 마이그레이션은 그 단계를 번호 붙은 파일로 두고 적용 기록을 남기는 관리 방식입니다.
표 잠금
9장 페이지 5		표 전체에 거는 락. ALTER TABLE은 대개 ACCESS EXCLUSIVE(읽기까지 막는 가장 센 락)를 요구하고, 그 표를 쓰는 트랜잭션이 끝나지 않았으면 기다린다. 기다리는 동안 뒤에 온 요청도 줄을 선다. 행을 잠그는 8장의 락과 층이 다르다.행 락과 다릅니다. 표 전체의 락이라 ALTER TABLE이 쥐면 뒤에 온 읽기까지 줄을 섭니다.
lock_timeout
9장 페이지 5		락을 이 시간 안에 못 얻으면 기다리지 않고 오류(55P03)로 포기하게 하는 설정. 스키마 변경이 줄을 세워 서비스를 멈추는 것을 막는다.deadlock_timeout과 다릅니다. deadlock_timeout은 교착 검사를 시작하는 대기 시간이고, lock_timeout은 락을 포기하는 한도입니다.
NOT VALID
9장 페이지 7		CHECK·외래키 제약을 "앞으로 들어오는 행만" 검사하는 상태로 걸고, 기존 행 검사는 나중에 VALIDATE CONSTRAINT로 하는 방법. 긴 검사가 쓰기를 막지 않는다. 단 기존 행을 UPDATE 하면 그 행은 검사된다.VALIDATE와 다릅니다. NOT VALID는 기존 행의 검사를 미루고 VALIDATE CONSTRAINT가 나중에 합니다.
backfill
9장 페이지 7		새 열을 더한 뒤 이미 있던 행의 값을 채우는 작업. 채울 값을 지금 값에서 가져오면 "그 뒤로 바뀐 적이 없다"는 가정이 필요하다.UPDATE 한 번과 다릅니다. 큰 표에서는 전 행 UPDATE가 표를 두 배로 부풀리므로 범위를 나눠 반복합니다.
ORM
Object-Relational Mapping
10장 페이지 5		표의 행과 프로그램의 객체를 자동으로 오가게 해 주는 라이브러리. 반복 코드가 줄지만 읽어서 고치고 저장하는 흐름이 8장의 읽고 판단하고 쓰기와 같아서, 낙관적 락 같은 보호를 직접 켜야 한다.드라이버·쿼리 빌더와 다릅니다. 행과 객체를 자동으로 오가므로 반복 코드는 줄지만, 읽고 고쳐 저장하는 흐름이 경쟁 상태의 재료가 됩니다.
SQLSTATE
10장 페이지 5		DB가 오류를 알릴 때 붙이는 다섯 글자 분류 코드(표준 SQL의 개념이고 PostgreSQL이 따른다). 23505 유일성 위반, 23503 외래키 위반, 23514 CHECK 위반, 40001 직렬화 실패, 40P01 교착, 55P03 락 시간 초과. 글자 P가 든 40P01, 55P03은 PostgreSQL이 따로 정한 코드다. 앱은 이 코드와 제약 이름으로 오류를 번역할지 재시도할지 가른다.오류 메시지와 다릅니다. 메시지는 사람이 읽는 문장이고, SQLSTATE는 프로그램이 분기하는 코드입니다. 제약 이름이 함께 오면 어느 규칙인지 알 수 있습니다.
