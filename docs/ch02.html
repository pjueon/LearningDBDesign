2장 · 화면 1

테이블 나누기: 엔터티·키·관계

1장에서는 이미 있는 시트가 왜 아픈지 겪었습니다. 이번에는 아무 표도 없는 상태에서 요구사항 문장만 보고 테이블을 뽑아냅니다. 나누는 직관을 방법으로 바꾸는 장입니다.

동백커피가 키오스크와 앱 주문을 시작하기로 했습니다. 서연과 지호가 원하는 것을 들어 봅시다.

서연

손님이 키오스크에서 메뉴를 골라 주문하면 돼요. 한 번에 여러 메뉴를 담을 수 있어야 하고, 같은 메뉴를 두 잔 이상 시키는 것도 되어야 해요.

서연

회원 가입은 이름이랑 전화번호로 받아요. 같은 번호로 두 번 가입하는 건 안 되고요. 그런데 회원이 아니어도 주문은 받아야 해요. 비회원한테는 이름이나 번호를 안 받아요.

지호

저는 주문마다 언제 받았는지, 카드인지 현금인지, 누가 받았는지만 남아 있으면 돼요.

개발자

말씀하신 것을 문장으로 정리해 볼게요. 이 문장에서 테이블을 뽑겠습니다.

정리한 요구사항

  1. 손님은 회원이거나 비회원이다. 회원은 이름과 전화번호를 가지며, 같은 전화번호로 두 번 가입할 수 없다. 비회원의 정보는 받지 않고 주문만 받는다.
  2. 손님은 메뉴를 골라 주문한다. 한 주문에는 여러 메뉴가 담기고, 같은 메뉴는 수량으로 나타낸다.
  3. 메뉴는 이름과 가격을 가진다.
  4. 주문마다 접수 시각, 결제수단(카드 또는 현금), 접수한 바리스타를 기록한다.
  5. 회원은 여러 번 주문할 수 있다.

이 장의 진행

  1. 화면 2~3 — 문장에서 명사와 동사를 뽑고, 무엇이 테이블이 될 만한 것인지 가릅니다.
  2. 화면 4~5 — 행을 구별하는 열(키)을 고릅니다.
  3. 화면 6~9 — 표 사이의 관계(1:N, N:M, 1:1)와 외래키를 봅니다.
  4. 화면 10~12 — 그림(ER 다이어그램)으로 그리고 CREATE TABLE로 옮긴 뒤, 이 설계가 몰래 깔고 있는 가정을 확인합니다.

1장에서 표를 사실의 종류별로 나눴습니다. 이번에는 그 나누는 일을 요구사항 문장에서 시작해 순서대로 해 보는 것입니다. 1장 시트의 "고객"은 이 장부터 회원이라고 부릅니다(1장의 세 사람은 모두 회원이었습니다).

문장에서 명사와 동사를 뽑는다

설계의 첫 단계는 단순합니다. 요구사항 문장에서 명사는 저장할 대상이나 정보의 후보로, 동사는 대상 사이의 관계의 후보로 뽑아 둡니다. 뽑은 것을 곧바로 테이블로 만들지 않고 후보로만 적습니다. 앞 화면의 다섯 문장에서 명사에 표시해 봅니다.

동사는 관계를 알려 줍니다.

  • "주문한다" — 손님과 주문이 이어져 있습니다. (누가 주문했는가)
  • "담기다" — 주문과 메뉴가 이어져 있습니다. (무엇이 주문에 들었는가)
  • "가진다" — 대상과 그 대상에 딸린 정보입니다. 관계가 아니라 딸린 정보입니다(다음 화면에서 이름을 붙입니다).

명사가 모두 테이블이 되지는 않는다

표에 뽑아 놓고 보면 어떤 명사는 다른 명사에 딸린 정보입니다. "전화번호"는 회원에 딸려 있고, "가격"은 메뉴에 딸려 있습니다. 어떤 명사가 독립된 대상이고 어떤 명사가 딸린 정보인지 가르는 것이 다음 화면의 주제입니다. "비회원"도 그런 후보입니다. 비회원을 위한 표가 필요한지도 다음 화면에서 판단합니다.

2장 · 화면 3

무엇이 독립된 대상이고, 무엇이 딸린 정보인가

1장에서 표의 한 행이 한 종류의 사실만 뜻해야 한다고 했습니다. 그 "한 종류"가 되는 것, 즉 독립해서 구별되고 여러 사실이 딸려 있는 대상을 엔터티라고 부릅니다. 엔터티에 딸린 정보 하나하나는 속성입니다. "메뉴"는 엔터티이고, "이름"과 "가격"은 메뉴의 속성입니다. 엔터티는 나중에 테이블이 되고, 속성은 그 테이블의 열이 됩니다.

명사가 엔터티인지 속성인지 가르는 질문 세 개를 씁니다.

  1. 같은 종류가 여러 개 있는가? 메뉴는 여러 개이고 전화번호도 여러 개입니다. (이 질문은 통과하기 쉽습니다.)
  2. 그것에 대해 적어야 할 사실이 둘 이상인가? 메뉴는 이름과 가격을 가집니다. 전화번호는 그 자체가 값 하나입니다.
  3. 다른 것 없이 혼자서도 구별되는가? 메뉴는 주문이 없어도 존재합니다. 수량은 "어느 주문의 어느 메뉴"가 정해져야 뜻이 생깁니다.

비회원이 왜 엔터티가 아닐까요? 서연은 비회원의 이름도 전화번호도 받지 않겠다고 했습니다. 딸린 사실이 하나도 없으니 표를 만들어도 열이 없습니다. 비회원 주문은 "주문 옆에 회원이 없는 것"으로 충분합니다. 이 표현은 화면 8의 선택적 관계에서 다시 만납니다.

경계는 요구사항이 정한다

"결제수단"이나 "바리스타"처럼 속성인지 엔터티인지 정답이 하나가 아닌 경우가 많습니다. 기준은 이 시스템이 그 대상에 대해 무엇을 알고 싶은가입니다. 카드사별 수수료를 관리하게 되면 결제수단이 엔터티가 되고, 직원별 근태를 저장하게 되면 바리스타가 엔터티가 됩니다. 지금은 아닙니다. 요구사항이 바뀌면 속성이 엔터티로 승격되는 일은 흔합니다.

2장 · 화면 4

행을 구별하는 열 — 후보키와 기본키

엔터티를 테이블로 옮기려면 먼저 표의 행 하나를 어떻게 구별할지 정해야 합니다. 1장에서 표들을 잇는 번호(member_id 같은 것)가 필요하다고 봤습니다. 이번에는 그 번호를 어떻게 정하는지 봅니다.

회원 표가 다음과 같다고 합시다. 동명이인이 있다고 가정합니다.

member_idnamephone
1민준010-1111-2222
2소라010-3333-4444
3도윤010-5555-6666
4소라010-2222-3333

행 하나를 구별해 낼 수 있는 열 조합의 자격은 두 가지입니다.

  • 유일성 — 그 조합의 값이 모든 행에서 다릅니다.
  • 최소성 — 그 조합에서 열을 하나라도 빼면 유일성이 깨집니다. (필요 없는 열이 붙어 있지 않다는 뜻입니다)

유일하기만 하면 되는 열 묶음을 슈퍼키, 그중 군더더기가 없는 것을 후보키라고 합니다. 곧 유일성과 최소성을 모두 만족하는 열 조합이 후보키입니다. 이 표의 후보키는 phone과 member_id 둘입니다. 후보키 중에서 대표로 뽑아 행의 신분증으로 쓰는 것이 기본키(PK)입니다. 나머지 후보키는 UNIQUE로 "겹치면 안 된다"는 규칙만 걸어 둡니다.

유일성은 "지금 데이터"가 아니라 "규칙"이어야 한다

위 표에서는 소라가 둘이라 name이 바로 탈락했습니다. 그런데 소라가 한 명뿐이었더라도 name은 후보키가 될 수 없습니다. 이름이 같은 회원이 생기는 것이 업무상 자연스럽기 때문입니다. 지금 데이터에 동명이인이 없다고 해서 name을 키로 삼으면, 동명이인이 가입하는 날 깨집니다. 유일성은 업무 규칙에서 나와야 합니다. 이 구별은 3장의 함수 종속에서도 다시 나옵니다.

후보가 둘인데 어느 쪽을 기본키로 뽑아야 할까요? 다음 화면의 주제입니다.

2장 · 화면 5

자연키와 대리키 — 전화번호를 기본키로 써도 될까

후보키 중 phone은 업무에 원래 있는 값이고, member_id는 우리가 붙인 번호입니다. 앞의 것을 자연키, 뒤의 것을 대리키라고 부릅니다. 전화번호를 기본키로 쓰면 번호를 따로 만들 필요가 없어서 간단해 보입니다. 그런데 문제가 생기는 장면을 봅시다.

민준

저 번호 바뀌었어요. 010-7777-8888로 바꿔 주세요.

회원 표에서 전화번호가 기본키이고, 주문이 회원을 전화번호로 가리킨다면 어떻게 될까요? 민준의 번호를 바꾸는 순간 민준을 가리키던 모든 주문의 값도 함께 바꿔야 합니다. 주문이 수만 건이면 그 수만 행을 다 고쳐야 합니다. 외래키가 없다면(화면 9) 하나라도 빠진 주문은 "없는 회원의 주문"이 되고, 외래키가 있다면 DB가 번호 수정을 거부하므로 주문을 함께 고치는 절차를 따로 밟아야 합니다. 어느 쪽이든 수만 행을 건드리게 됩니다. 1장에서 겪은 갱신 이상이 열쇠 자리에서 다시 생기는 셈입니다.

대리키는 다릅니다. 민준의 member_id는 1이고, 전화번호가 바뀌어도 1입니다. 주문은 1을 가리키므로 회원 표에서 전화번호 한 곳만 고치면 끝입니다.

자연키가 위험한 예왜 위험한가
전화번호사람이 번호를 바꾼다. 통신사가 해지된 번호를 다른 사람에게 다시 주기도 해서, 과거 데이터와 새 사람이 섞일 수 있다. 가족이 한 번호를 함께 쓰기도 하지만, 이 교재의 요구사항은 "한 번호에 회원 하나"(화면 1)다.
주민등록번호수집과 저장이 법으로 엄격히 제한된다. 유출되면 피해가 크고, 한 번 노출되면 바꾸기도 어렵다. 키가 되면 다른 모든 표가 이 값을 복사하게 되므로 피해가 퍼진다.
이메일바꾸는 사람이 많고 대소문자 표기가 흔들린다.

그래서 이 교재는 회원·주문 같은 엔터티에 번호를 하나 붙여 기본키로 씁니다. 이 대리키는 의미가 없어서 "무엇이 같은 사람인가"는 알려 주지 못합니다. 같은 사람이 다른 번호로 두 번 가입해도 대리키만으로는 막을 수 없습니다. 그래서 전화번호에는 UNIQUE를 걸어 같은 번호로 두 번 가입할 수 없게 함께 둡니다. 기본키와 UNIQUE를 나란히 쓰는 것이 흔한 패턴입니다.

0장에서 기본키를 객체 ID에 비유했는데, 그 비유가 깨지는 곳이 여기입니다. C++ 객체는 필드 값이 모두 같아도 주소로 서로 구별되지만, 표의 행에는 그런 숨은 주소가 없어서 값으로만 구별됩니다. 그래서 행을 구별할 키를 설계자가 직접 고르거나 번호를 붙여 줘야 합니다.

자연키가 늘 나쁜 것은 아닙니다

국가 코드나 통화 코드(KRW)처럼 표준으로 고정된 짧은 값은 자연키로 써도 안전하고, 조회할 때 표를 이어 붙이지 않아도 뜻이 보인다는 장점이 있습니다. 대리키 옹호와 자연키 옹호의 논쟁은 실무에서도 끝나지 않았습니다. 이 교재의 기준은 "바뀔 수 있으면 대리키"입니다. 메뉴 이름, 전화번호, 이메일은 모두 바뀝니다.

한 가지 사실을 알아 둡시다. DB는 기본키와 UNIQUE를 선언하면 값을 빨리 찾기 위한 색인(인덱스)을 자동으로 만듭니다. 인덱스가 무엇이고 언제 직접 만들어야 하는지는 7장에서 다룹니다.

더 깊이 — 번호는 누가 붙이나

이 교재의 CREATE TABLE은 간결하게 보이려고 member_id INTEGER PRIMARY KEY로 씁니다. 실제로는 새 행이 들어올 때 번호를 DB가 자동으로 붙이게 하는 것이 보통입니다. PostgreSQL에서는 다음처럼 씁니다.

CREATE TABLE member (
    member_id  INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name       TEXT    NOT NULL,
    phone      TEXT    NOT NULL UNIQUE
);

GENERATED ALWAYS AS IDENTITY는 INSERT할 때 번호를 적지 않아도 1, 2, 3 … 순서로 채워 준다는 뜻입니다. MySQL의 AUTO_INCREMENT에 해당하는 표준 문법입니다. 제품마다 문법이 다르고 학습 내용은 같으므로 본문에서는 생략합니다.

주의할 점이 둘 있습니다. ALWAYS이면 번호를 직접 적은 INSERT는 오류가 납니다. 이 교재의 예시는 설명을 간결하게 하려고 101, 102처럼 번호를 직접 씁니다(번호를 직접 적을 일이 있다면 GENERATED BY DEFAULT AS IDENTITY로 선언하면 됩니다). 또 자동 번호는 실패한 입력(롤백) 때문에 건너뛸 수 있으니 "빈틈없는 연속 번호"로 믿으면 안 됩니다.

2장 · 화면 6

엔터티 사이의 관계 — 1:N

엔터티가 정해졌으니 동사에서 뽑은 관계를 봅니다. 관계에서 가장 중요한 것은 몇 대 몇으로 이어지는가이고, 이것을 카디널리티라고 합니다.

"회원은 여러 번 주문할 수 있다"를 양쪽에서 읽어 봅시다.

  • 회원 → 주문: 회원 한 명은 주문을 여러 건 가진다. (한 건도 없을 수도 있다)
  • 주문 → 회원: 주문 한 건은 회원을 많아야 한 명 가진다. (비회원이면 0명)

한쪽은 "하나", 다른 쪽은 "여러 개"입니다. 이런 관계를 1:N (일대다)라고 부릅니다. 구체적인 데이터로 보면 이렇습니다.

member_idname
1민준
2소라
order_idmember_idordered_at
10113/4 09:10
10223/4 09:25
10313/4 10:02

민준(1번)은 주문 101과 103을 가졌습니다. 1:N에서는 "N쪽 표에 1쪽의 번호를 넣습니다." 주문 표에 member_id 열을 두어 어느 회원의 주문인지 가리키게 합니다. 이렇게 다른 표의 행을 가리키는 열이 외래키(FK)입니다. 자세한 성질은 화면 9에서 봅니다.

1쪽에 번호를 넣으면 안 되는 이유

반대로 회원 표에 "주문번호" 열을 두면 민준 행에는 주문번호가 여러 개 들어가야 합니다. 한 칸에 "101, 103"처럼 여러 값을 적거나, "주문1, 주문2, 주문3…" 열을 늘려 가야 합니다. 앞의 방법은 값을 하나씩 다루기 어렵고 뒤의 방법은 몇 개까지 열을 만들지 정할 수 없습니다. 한 칸에 여러 값을 넣는 문제는 3장(1NF)에서 정식으로 다룹니다. 지금은 번호는 N쪽에 넣는다만 기억하세요.

"카디널리티"는 문맥에 따라 뜻이 둘

이 장에서는 관계의 대응 수(1:N)를 뜻합니다. 인덱스를 다루는 7장에서는 같은 낱말이 열이 가진 서로 다른 값의 수를 뜻합니다. 이름은 같지만 다른 개념이니 문맥으로 구별하세요.

2장 · 화면 7

N:M 관계와 연결 테이블 — 주문과 메뉴

"한 주문에는 여러 메뉴가 담기고, 같은 메뉴는 여러 주문에 담긴다." 양쪽에서 읽어 봅시다.

  • 주문 → 메뉴: 주문 한 건에 메뉴가 여러 종류 담긴다.
  • 메뉴 → 주문: 메뉴 한 종류가 여러 주문에 담긴다. (아메리카노는 주문 101에도 103에도 있다)

양쪽이 모두 "여러 개"입니다. 이런 관계를 N:M (다대다)라고 부릅니다. 1:N처럼 한쪽 표에 번호를 넣으려 해도 안 됩니다. 주문 표에 menu_id를 넣으면 한 주문에 메뉴를 하나만 담을 수 있고, 메뉴 표에 order_id를 넣으면 한 메뉴가 주문 하나에만 들어갑니다.

N:M을 알아보는 법

두 엔터티 사이에서 양쪽 방향으로 읽어 모두 "여러"이면 N:M입니다. 한쪽이라도 "하나"면 1:N입니다. "손님은 메뉴를 주문한다"처럼 동사만 보면 방향이 헷갈리니, 항상 양쪽에서 각각 문장으로 읽어 보세요.

N:M은 두 표 사이에 표를 하나 끼워서 풀어냅니다. 끼운 표의 한 행이 "이 주문에 이 메뉴가 이만큼 담겼다"는 짝 하나를 뜻합니다. 이 표가 이미 아는 order_line입니다.

order_line — 한 행은 "이 주문에 이 메뉴가 몇 개"
order_idmenu_idquantity
10112
10131

  • 이 표를 연결 테이블이라고 부릅니다. 주문과 메뉴의 번호를 둘 다 가지고, N:M을 두 개의 1:N으로 바꿉니다. (주문 1 — N 라인, 메뉴 1 — N 라인)
  • 관계 자체에 딸린 속성이 자리를 얻습니다. "몇 개"는 주문의 것도 메뉴의 것도 아니고 둘의 짝에 딸린 정보입니다. 그래서 quantity가 order_line에 있습니다. 화면 3에서 미뤄 둔 질문의 답입니다.
  • 기본키는 두 번호의 조합 (order_id, menu_id)로 정했습니다. 그러면 "한 주문 안에 같은 메뉴 행이 두 개 있을 수 없다"는 규칙이 저절로 따라옵니다. 같은 메뉴를 또 시키면 새 행이 아니라 수량을 올립니다.

모든 테이블이 엔터티인 것은 아닙니다. order_line은 주문과 메뉴라는 두 엔터티의 관계를 담는 표입니다. 화면 3의 질문 3("다른 것 없이 혼자서도 구별되는가?")을 이 표에 던져 보면, 라인 한 줄은 주문과 메뉴가 정해져야 뜻이 생기므로 독립된 대상이 아닙니다.

기본키를 이렇게 정한 것에는 몰래 깔린 가정이 있습니다. 그 이야기는 화면 12에서 합니다.

2장 · 화면 8

1:1 관계와 선택적 관계

관계의 세 번째 모양은 1:1 (일대일)입니다. 양쪽이 모두 "많아야 하나"입니다. 동백커피에서 예를 들어 봅시다. 메뉴마다 영양성분표를 붙이려 한다고 합시다(동백커피의 요구사항은 아니고 설명용입니다). 메뉴 하나에 성분표는 하나이고, 성분표 하나는 메뉴 하나에 속합니다.

menumenu_nutrition (설명용)
menu_idnamepricemenu_idkcalcaffeine_mg
1아메리카노4500110150
2카페라떼5000218075
3치즈케이크6500———

1:1은 한 표에 합쳐도 되는 관계입니다. 열 kcal과 caffeine_mg를 menu에 넣으면 끝입니다. 그래서 1:1을 굳이 두 표로 나누는 경우는 드물고, 나눌 이유가 뚜렷할 때만 나눕니다.

  • 일부 행에만 있는 정보 — 성분표가 있는 메뉴가 절반이라면, 합친 표는 빈칸이 많아집니다. (위 표에서 치즈케이크에는 성분표가 없다)
  • 접근 권한이 다른 정보 — 회원의 민감한 정보를 다른 표에 두고 일부 사람에게만 열어 줄 때.
  • 생기는 시점이 다른 정보 — 메뉴는 먼저 등록하고 성분표는 나중에 채울 때.

DB에서 1:1을 지키려면 성분표 쪽의 menu_id를 기본키이면서 외래키로 둡니다. 기본키이므로 메뉴 하나에 성분표가 둘 붙을 수 없습니다. 기본키를 겸하지 않으면 성분표 여러 개가 한 메뉴에 붙는 1:N이 됩니다.

관계를 한쪽에서 볼 때 짝이 없어도 되면 그쪽에서 관계가 선택적이고, 짝이 반드시 있어야 하면 필수적이라고 합니다. 위 표에서 메뉴에게 성분표는 선택적이고(치즈케이크에는 없음), 성분표에게 메뉴는 필수적입니다(어느 메뉴의 것도 아닌 성분표는 없음). 이처럼 선택·필수는 관계의 양쪽에서 따로 정합니다. 이 교재에서 그냥 선택적 관계라고 하면, 외래키를 가진 N쪽 행이 짝 없이도 있을 수 있는(외래키를 비워 둘 수 있는) 관계를 말합니다. 선택적인지 필수인지는 요구사항 문장이 정합니다. 동백커피 v1(지금까지 설계한 네 표. 화면 11에서 이 이름을 붙입니다)의 관계를 다시 읽어 봅시다.

관계카디널리티짝이 있어야 하는가근거 문장
회원 — 주문1:N주문에게 회원은 선택적(비회원이면 없음), 회원에게 주문도 선택적(0건 가능)"회원이 아니어도 주문은 받아야 한다"
주문 — 주문 라인1:N라인에게 주문은 필수(라인은 반드시 주문에 속함)"한 주문에는 여러 메뉴가 담긴다"
메뉴 — 주문 라인1:N라인에게 메뉴는 필수(라인은 반드시 메뉴를 가리킴), 메뉴에게 라인은 선택적(아직 안 팔린 메뉴)"메뉴를 골라 주문한다"

외래키와 참조 무결성 — 포인터와 닮았지만 다른 점

화면 6에서 "다른 표의 행을 가리키는 열"을 외래키(FK)라고 불렀습니다. order_line.menu_id가 menu의 행을 가리키는 것이 그 예입니다. 외래키는 단순한 표시가 아닙니다. DB에 선언하면 DB가 가리키는 행이 실제로 있는지 지켜 줍니다. (외래키가 가리킬 수 있는 열은 기본키나 UNIQUE가 걸린 열입니다.) 이것을 참조 무결성이라고 합니다.

order_line에 menu_id = 9인 행을 넣어 봅시다. menu에는 1, 2, 3번뿐입니다.

-- 없는 메뉴를 가리키는 라인 넣기 (외래키가 선언되어 있다면)INSERT INTO order_line (order_id, menu_id, quantity)
VALUES (101, 9, 1);

PostgreSQL은 이 입력을 거부합니다.

-- 오류 메시지 (요지, 줄바꿈은 지면 때문에 넣음)ERROR:  insert or update on table "order_line" violates
        foreign key constraint "order_line_menu_id_fkey"
DETAIL:  Key (menu_id)=(9) is not present in table "menu".

외래키 열에는 인덱스가 자동으로 생기지 않습니다

2장 · 화면 10

ER 다이어그램 — 설계를 한 장의 그림으로

엔터티, 속성, 키, 관계를 한 장에 그린 것을 ER 다이어그램이라고 합니다. 설계를 말로만 나누면 빠진 것이 보이지 않지만 그림으로 그리면 한눈에 보입니다. 동백커피의 지금까지의 설계입니다.

읽는 순서는 이렇습니다. 상자의 이름을 보고 "한 행이 무엇인가"를 묻고, 선을 양쪽에서 문장으로 읽습니다.

  • member — orders: "회원 한 명은 주문을 여러 건 가진다. 주문 한 건은 회원이 많아야 한 명이다(없을 수 있다)."
  • orders — order_line: "주문 한 건은 라인을 여러 개 가진다. 라인 하나는 주문 한 건에 속한다."
  • menu — order_line: "메뉴 한 종류는 여러 라인에 나온다. 라인 하나는 메뉴 한 종류를 가리킨다."
  • order_line은 orders와 menu의 N:M 연결 테이블이고, 기본키가 두 외래키의 조합이라 "PK,FK"가 겹쳐 적혀 있습니다.

그릴 때의 순서

  1. 요구사항 문장에서 엔터티(화면 3)를 정해 상자로 그린다.
  2. 각 상자에 속성과 기본키(화면 4·5)를 적는다.
  3. 동사로 관계를 찾아 선을 잇고 양쪽을 문장으로 읽어 1:N, N:M(화면 6·7)을 정한다.
  4. N:M은 연결 테이블로 풀고, 1:N은 N쪽에 외래키를 적는다(화면 9).
  5. N쪽 행이 짝 없이도 있을 수 있는(외래키를 비워 둘 수 있는) 선택적 관계는 점선이나 표시로 남긴다(화면 8).

이 다이어그램에서 표기법(까마귀발 기호, 사각형 모양)은 도구마다 다릅니다. 기호가 달라도 엔터티·속성·키·카디널리티라는 네 가지 정보는 같습니다.

2장 · 화면 11

그림을 테이블로 — 스키마 v1

화면 10의 다이어그램을 CREATE TABLE로 옮깁니다. 교재 전체가 이 스키마를 시작점으로 삼고 장마다 키우기 때문에 스키마 v1이라는 이름을 붙입니다.

다시 보기: 화면 10의 ER 다이어그램 (관계만)

  • member 1 — N orders (점선, 선택적: 비회원 주문은 orders.member_id를 비워 둠)
  • orders 1 — N order_line
  • menu 1 — N order_line

외래키는 N쪽 표에 있습니다. order_line은 orders와 menu를 잇는 연결 테이블이고, 기본키는 (order_id, menu_id)입니다.

-- 스키마 v1: 동백커피 1호점-- 메뉴 한 종류 (0장과 같은 표)
CREATE TABLE menu (
    menu_id  INTEGER PRIMARY KEY,
    name     TEXT    NOT NULL,
    price    INTEGER NOT NULL
);

-- 회원 한 명
CREATE TABLE member (
    member_id  INTEGER PRIMARY KEY,
    name       TEXT    NOT NULL,
    phone      TEXT    NOT NULL UNIQUE
);

-- 주문 한 건 (비회원 주문이면 member_id 는 NULL)
CREATE TABLE orders (
    order_id    INTEGER     PRIMARY KEY,
    member_id   INTEGER     REFERENCES member (member_id),
    ordered_at  TIMESTAMPTZ NOT NULL,
    payment     TEXT        NOT NULL,
    barista     TEXT        NOT NULL
);

-- 주문 안의 메뉴 한 줄
CREATE TABLE order_line (
    order_id  INTEGER NOT NULL REFERENCES orders (order_id),
    menu_id   INTEGER NOT NULL REFERENCES menu (menu_id),
    quantity  INTEGER NOT NULL,
    PRIMARY KEY (order_id, menu_id)
);
  1. 1~6행 menu — 0장에서 본 표 그대로입니다. 한 행은 메뉴 한 종류입니다.
  2. 8~13행 member — 한 행은 회원 한 명입니다. 10행 member_id가 대리키 기본키이고(화면 5), 12행의 UNIQUE는 같은 전화번호로 두 번 가입할 수 없게 하는 규칙입니다. 전화번호가 후보키라는 뜻이며, DB는 이를 위해 인덱스를 자동으로 만듭니다(7장).
  3. 15~22행 orders — 한 행은 주문 한 건입니다. 18행 REFERENCES member (member_id)가 외래키 선언입니다("이 열의 값은 member 표의 member_id에 있어야 한다"). NOT NULL이 없어서 비워 둘 수 있고, 그 행이 비회원 주문입니다(화면 8). 4장에서 다시 본다
  4. 19행 TIMESTAMPTZ는 시간대를 고려해 저장하는 시각 타입입니다(내부적으로는 UTC로 바꿔 저장하고, 보여 줄 때 접속 세션에 설정된 시간대(TimeZone 설정)로 바꿉니다). 타입을 고르는 기준은 4장에서 다룹니다. 4장에서 다시 본다
  5. 20행 payment는 '카드', '현금' 같은 글자로 적습니다. 1장 화면 7에서 본 것처럼 글자로 적는 열은 표기가 흔들릴 수 있고, 이를 막는 방법은 4장에서 봅니다. 4장에서 다시 본다
  6. 24~30행 order_line — 한 행은 "이 주문에 이 메뉴가 몇 개"입니다. 26행과 27행이 각각 주문과 메뉴를 가리키는 외래키이고, 29행 PRIMARY KEY (order_id, menu_id)는 두 열을 묶은 기본키입니다(화면 7). 열 옆에 쓰지 않고 표의 마지막에 따로 쓰는 이유는 열이 둘이기 때문입니다.
  7. 28행 quantity에는 "1 이상이어야 한다"는 규칙이 아직 없습니다. 0이나 음수도 들어갑니다. 이 규칙은 4장에서 붙입니다. 4장에서 다시 본다

표를 만드는 순서가 있습니다

REFERENCES는 이미 있는 표를 가리켜야 하므로, 가리키는 쪽보다 가리켜지는 쪽을 먼저 만듭니다. orders가 member를, order_line이 orders와 menu를 가리키므로 menu, member, orders, order_line 순서로 씁니다. 지울 때는 반대 순서입니다. 순서를 바꾸면 CREATE TABLE이 오류를 냅니다.

1장의 직관 초안(1장 화면 9에서 시트를 나눈 네 표)이 CREATE TABLE 문이 되었습니다. 표의 이름과 열은 같고, 키와 외래키와 UNIQUE가 새로 붙었습니다. 이 설계가 DB에 선언한 핵심 규칙은 세 가지입니다. "행은 번호로 구별된다", "가리키는 행은 있어야 한다", "같은 전화번호로 두 번 가입할 수 없다." (그 밖에 NOT NULL로 "비워 둘 수 없다"는 규칙도 있습니다.)

2장 · 화면 12

v1이 몰래 깔고 있는 가정 세 가지

v1은 요구사항 다섯 문장을 잘 담았습니다. 하지만 문장에 없어서 아무도 말하지 않은 가정이 스키마 곳곳에 박혀 있습니다. 요구사항이 바뀌면 이 가정부터 깨집니다. 지금은 찾아서 표시만 해 둡니다.

가정 1 — 가격은 바뀌지 않는다

order_line에는 단가가 없습니다. 주문 금액은 menu.price를 찾아서 계산합니다. "그 메뉴의 가격은 언제나 하나뿐이다"라는 가정입니다. 메뉴의 가격이 바뀌는 일이 생기면 이 가정이 어떤 결과를 부르는지는 3장과 6장에서 확인합니다. 6장에서 다시 본다

가정 2 — 매장은 하나뿐이다

어느 표에도 매장이라는 개념이 없습니다. 주문은 "어느 가게에서"를 말하지 않고, 메뉴 가격은 모든 곳에서 같다고 전제합니다. 가게가 하나뿐이면 문제가 없습니다. 9장에서 다시 본다

가정 3 — 한 주문에서 같은 메뉴는 한 줄이다

order_line의 기본키가 (order_id, menu_id)이므로, 한 주문에 같은 메뉴는 한 행만 있을 수 있습니다. 같은 메뉴는 수량을 올려서 표현합니다. "같은 메뉴는 어차피 같은 물건이다"라는 가정입니다. 5장에서 다시 본다

세 가지 모두 1호점의 지금 요구사항에서는 참입니다. 그래서 설계 잘못이 아닙니다. 다만 참이라고 깔아 둔 가정이 언제 거짓이 되는지를 알고 있는 것이 설계자의 일입니다. 뒤의 장에서 이 셋이 하나씩 깨집니다.

이 설계가 옳은지 어떻게 확인하나

이 장은 요구사항에서 테이블을 뽑는 방법을 다뤘습니다. 그런데 뽑은 설계가 중복 없이 옳은지는 어떻게 확인할까요? 직관으로 봐서는 놓치는 것이 있습니다. 예를 들어 orders.barista는 직원이라는 다른 종류의 사실이 섞인 것처럼 보이는 열인데, 이 열이 정말 문제인지는 엄밀한 기준으로 따져야 합니다. 그 기준이 3장의 정규화입니다. 3장에서 다시 본다

더 깊이 — ER 설계와 정규화 중 무엇을 먼저 해야 하나

교과서에는 정규화를 먼저 가르치는 순서가 많습니다. 이 교재는 ER 설계를 먼저 합니다. 실무에서는 요구사항 문장에서 엔터티를 뽑고 나서 그 결과를 정규화로 점검하는 흐름이 흔하기 때문입니다. 경험이 많은 설계자는 ER 단계에서 이미 정규화된 표를 뽑아내기도 합니다. 그렇더라도 검증 단계는 필요합니다.

2장 · 화면 13

2장 마무리

핵심 요약

  1. 요구사항 문장의 명사에서 엔터티와 속성을, 동사에서 관계를 뽑습니다. 독립되어 구별되고 여러 사실이 딸린 것이 엔터티, 딸린 값이 속성입니다. 엔터티는 테이블이, 속성은 열이 됩니다(N:M 관계를 담는 연결 테이블도 테이블입니다).
  2. 행을 구별하는 열 조합 중 유일성과 최소성을 만족하는 것이 후보키, 그중 대표가 기본키입니다. 바뀔 수 있는 자연키(전화번호)보다 대리키가 안전하고, 자연키였던 열에는 UNIQUE를 함께 겁니다.
  3. 1:N은 N쪽 표에 외래키를 넣고(N쪽 행에 짝이 없어도 되는 선택적 관계는 외래키를 비워 표현하고), N:M은 연결 테이블로 풀며, 관계 자체에 딸린 값(수량)은 연결 테이블에 둡니다. 1:1은 나눌 이유가 뚜렷할 때만 나눕니다.
  4. 외래키는 포인터와 달리 없는 행을 가리키는 값을 DB가 막아 줍니다. 그러나 외래키 열에는 인덱스가 자동으로 생기지 않습니다.
  5. ER 다이어그램과 CREATE TABLE로 스키마 v1(menu, member, orders, order_line)을 얻었고, v1에는 참이라고 깔아 둔 가정(가격 불변, 매장 하나, 같은 메뉴는 한 줄)이 있습니다.

퀴즈에 쓰는 표

퀴즈 2에 쓰는 화면 4의 회원 표입니다(동명이인 소라가 두 명).

회원 표의 기본키로 전화번호를 쓰고, 주문이 회원을 전화번호로 가리키게 했습니다. 회원이 번호를 바꾸면 어떤 문제가 생길까요?

  1. 번호가 바뀌어도 외래키가 자동으로 따라가므로 문제가 없다
  2. 그 회원을 가리키던 모든 주문의 값도 함께 바꿔야 한다
  3. 주문 표에 회원의 전화번호를 복사해 두면 해결된다

키가 여러 열의 조합이면 문제가 더 커집니다. 예를 들어 여러 해에 걸쳐 학생을 담는 표에서 학생을 (학년, 반, 번호)로 구별해 기본키로 쓰면 이 키를 가리키는 표마다 열이 세 개씩 늘고 JOIN 조건도 길어집니다. 게다가 해가 바뀌면 같은 학생의 세 값이 한꺼번에 바뀝니다. 또 주민등록번호처럼 수집할 근거가 없으면 저장 자체가 문제가 되는 값은 키로 쓰기 전에 저장해도 되는지부터 따져야 합니다. 대리키는 이런 부담을 모두 피하는 대신, 같은 사람인지 알려 주지 못하므로 UNIQUE를 함께 둡니다.

화면 4의 회원 표에서 (name, phone) 조합은 모든 행에서 값이 다릅니다. 그런데도 후보키가 아닌 이유는 무엇일까요?

  1. 이름이 같은 회원(소라)이 있어서 유일하지 않다
  2. 두 열을 묶어서는 키로 쓸 수 없다
  3. phone 하나만으로 이미 유일해서, 최소성을 만족하지 못한다

유일성만 만족하는 열 조합은 슈퍼키라고 부르고, 그중 열을 더 뺄 수 없는 최소의 것이 후보키입니다. (name, phone)은 슈퍼키이고 후보키는 아닙니다. 반대로 order_line의 (order_id, menu_id)는 어느 한 열만으로는 유일하지 않으므로 두 열이 모두 필요한 복합 후보키입니다. 후보키를 판정할 때는 데이터를 눈으로 보는 것에 그치지 말고 "이 열 없이도 구별되는가?"를 업무 규칙으로 물어야 합니다.

외래키가 선언된 상태에서 menu에 없는 menu_id = 9를 가진 order_line 행을 INSERT하면 어떻게 될까요?

  1. DB가 오류를 내며 입력을 거부한다
  2. 저장되고, 조회할 때 메뉴 이름이 빈칸으로 나온다
  3. menu 표에 9번 행이 자동으로 만들어진다

외래키가 없으면 없는 메뉴를 가리키는 행이 조용히 쌓이고, 그 행은 보통의 JOIN에서 오류 없이 결과에서 빠져 매출 합계가 줄어듭니다. 1장 화면 7에서 본 "오류 없이 틀린 숫자"와 같은 종류의 문제입니다. 검사는 DB 서버가 하므로 어떤 앱이 접근하든 같은 규칙이 적용되고, 외래키가 가리키는 열이 기본키나 UNIQUE여야 한다는 점도 함께 기억해 두세요.

직접 해보기

동백커피가 원두 클래스를 열기로 했습니다. 다음 요구사항 문장에서 엔터티를 뽑고 테이블로 옮겨 보세요.

  1. 동백커피는 원두 클래스를 연다. 클래스는 이름과 정원을 가진다.
  2. 회원은 여러 클래스에 신청할 수 있고, 한 클래스에는 여러 회원이 신청한다.
  3. 신청할 때 신청일이 기록된다.
  4. 같은 회원이 같은 클래스에 두 번 신청할 수 없다.
  1. 엔터티와 속성을 적고, 관계의 카디널리티를 정하세요. member 표는 화면 11의 것을 씁니다.
  2. N:M이라면 어떤 표가 필요하고, 신청일은 어느 표의 열이며 기본키는 무엇인지 적으세요.
  3. 새 표를 CREATE TABLE로 쓰세요. (테이블 이름은 bean_class, enrollment를 쓰세요. 정원 초과를 막는 것은 지금 다루지 않습니다.)

이 문제에 쓰는 표

화면 11의 v1에서 member 부분만 가져왔습니다.

-- 화면 11의 member (그대로 씀)CREATE TABLE member (
    member_id  INTEGER PRIMARY KEY,
    name       TEXT    NOT NULL,
    phone      TEXT    NOT NULL UNIQUE
);
모범답안 — 그리고 흔한 오답이 왜 틀리는지

1. 엔터티와 관계 — 엔터티는 클래스(이름, 정원)와 회원(이미 있음)입니다. 회원과 클래스는 양쪽에서 읽어도 "여러 개"이므로 N:M입니다.

2. 연결 테이블 — 신청 하나가 "이 회원이 이 클래스에 신청했다"는 짝이므로 enrollment가 필요합니다. 신청일은 회원의 것도 클래스의 것도 아니고 짝의 속성이므로 enrollment에 둡니다. 기본키는 (member_id, class_id)이고, 그러면 네 번째 문장("같은 회원이 같은 클래스에 두 번 신청 불가")이 자동으로 지켜집니다.

3. CREATE TABLE

-- 모범답안CREATE TABLE bean_class (
    class_id  INTEGER PRIMARY KEY,
    name      TEXT    NOT NULL,
    capacity  INTEGER NOT NULL
);

CREATE TABLE enrollment (
    member_id    INTEGER NOT NULL REFERENCES member (member_id),
    class_id     INTEGER NOT NULL REFERENCES bean_class (class_id),
    enrolled_on  DATE    NOT NULL,
    PRIMARY KEY (member_id, class_id)
);

흔한 오답 1 — 신청일을 member나 bean_class에 둔다. 신청일은 회원 한 명 또는 클래스 하나가 아니라 둘의 짝에 딸린 값입니다. 회원 표에 두면 그 회원의 여러 신청을 구별할 수 없고, 클래스 표에 두면 어느 회원의 신청인지 알 수 없습니다.

흔한 오답 2 — 회원 표에 "신청 클래스1, 클래스2…" 열을 만든다. 몇 개까지 열을 만들지 정할 수 없고, 클래스별 조회를 하려면 열마다 찾아야 합니다. 화면 6의 "번호는 N쪽에" 규칙과 화면 7의 연결 테이블 규칙을 어긴 것입니다.

흔한 오답 3 — enrollment의 기본키를 class_id 하나로 둔다. 그러면 한 클래스에 한 명만 신청할 수 있게 됩니다. 짝을 구별하려면 두 번호를 함께 써야 합니다.

흔한 오답 4 — 신청마다 번호(enrollment_id)를 붙여 기본키로 삼고 (member_id, class_id)에는 아무 규칙도 걸지 않는다. 기본키는 번호이므로 같은 회원이 같은 클래스에 두 번 신청한 행이 저장되어 네 번째 문장이 깨집니다. 번호를 기본키로 쓰려면 UNIQUE (member_id, class_id)를 함께 선언해야 합니다.
