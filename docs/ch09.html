store_id는 어디에 들어가나 — 22개 표 훑기

"모든 표에 store_id를 붙이면 되지 않나요?"가 첫 반응이지만, 그러면 회원이 매장마다 따로 생기고 옵션 정의가 열 벌이 됩니다. 표마다 이 세 질문을 던져 매장 범위를 가릅니다.

상속 — 라인 표에 store_id를 또 적지 않는 이유

order_line의 한 행에 store_id를 적었다고 합시다. 이 값은 order_id만으로 정해집니다(order_id → store_id). 기본키 (order_id, line_no)의 일부만으로 정해지는 열이므로 3장의 부분 종속, 곧 2NF 위반입니다. 두 곳에 적힌 매장이 어긋나면(주문은 2호점인데 라인은 1호점) 어느 쪽이 맞는지 DB는 모릅니다. 그래서 order_line, order_line_option, order_line_pick, order_discount 네 표는 주문을 따라가서 매장을 알고, 새 열이 없으며 기본키도 그대로입니다.

애매한 표 셋의 판단

point_ledger는 order_id를 가지니 상속처럼 보이지만, 행의 주인은 회원입니다. 잔액은 회원의 모든 행의 합이라 매장별로 쪼개면 "어느 매장에서든 쓴다"가 깨집니다(화면 4). 브랜드 공통입니다. menu_recipe·option_recipe는 "라떼 한 잔에 원두 18g"이라는 메뉴의 성질이지 매장의 성질이 아닙니다. 브랜드 공통입니다(매장마다 레시피가 달라지면 그때 키를 넓힙니다). option_item의 가격은 6장 결정대로 이력이 없는 "지금 값"이고, 이 장은 옵션 가격을 매장 공통으로 둡니다. 샷 추가 가격이 매장마다 달라지는 요구는 아직 없습니다(한계로 남깁니다).

반대 의견 — 자식 표에도 store_id를 넣고 DB가 일치를 강제하게 하는 설계

"어느 매장 라인인지 라인 표만 봐도 알고 싶다", "매장이 안 파는 메뉴가 주문 라인에 들어오는 것을 DB가 막았으면 한다"는 요구가 있으면 자식에 store_id를 복사하고 복합 외래키 두 개를 겁니다. orders에 UNIQUE (order_id, store_id)를 두고, 라인 표가 (order_id, store_id)로 orders를, (store_id, menu_id)로 store_menu(화면 3)를 가리킵니다. 실제 서버에서 실행한 결과, 주문 801(2호점)에 store_id 1인 라인은 violates foreign key constraint "line_x_order_id_store_id_fkey", 2호점이 취급하지 않는 메뉴 4는 line_x_store_id_menu_id_fkey로 거부되었습니다. 이 방식은 매장 일관성을 DB가 지키는 대신 자식 표마다 열 하나와 복합 외래키가 늘고, 부분 종속이라는 중복을 제약으로 감시하며 받아들이는 것입니다. 이 교재 v7은 "그 매장이 파는 메뉴만 주문받는다"를 주문 생성 트랜잭션이 지키게 하고(화면 10: 가격 조회가 store_id로 걸러 행이 없으면 주문을 거부), 자식 표는 건드리지 않습니다.

매장별 판매 메뉴와 가격 — C15

규칙 C15는 "매장마다 판매 메뉴·가격이 다를 수 있다"입니다. 먼저 떠오르는 풀이는 "menu의 가격을 menu + store_menu로 쪼갠다"입니다. 그런데 6장이 menu에서 price를 이미 지웠습니다. 가격은 menu_price(이력)가 가지고 있어서 menu에는 쪼갤 가격 열이 남아 있지 않습니다. 그래서 매장별 가격을 어디에 둘지부터 다시 따져 봅니다.

방법구조판단
가격 열을 store_menu에store_menu(store_id, menu_id, price)기각. 6장이 menu.price를 지운 이유(지금 값과 이력의 열린 행이 같은 사실의 중복)가 그대로 되살아나고, 매장별 가격 이력이 사라진다
본사 기본가 + 매장 예외store_id가 NULL이면 전 매장 공통 행기각. 기본키 열은 NULL일 수 없고, "예외가 있으면 그것, 없으면 기본"이라는 조회가 모든 가격 질문에 붙는다
menu_price에 store_id가격 이력이 매장별로 갈라진다. 매장마다 명시적인 행채택. 가격의 집이 한 곳(menu_price)인 6장의 결정이 유지된다. 본사 일괄 인상은 한 문장의 INSERT ... SELECT

그러면 store_menu는 무엇을 담을까요. "이 매장 메뉴판에 이 메뉴가 있다, 그리고 지금 팔고 있다"는 사실입니다. 가격이 아닌, 매장과 메뉴 사이의 N:M 관계입니다. 2호점은 티라미수를 취급하지 않으므로 store_menu에 그 행이 없고, 메뉴판에 있지만 오늘은 팔지 않는 것은 is_active = FALSE입니다. menu.is_active는 브랜드 전체의 단종으로 남고, 매장 단위의 판매 여부가 store_menu.is_active입니다(두 값의 의미가 다르다는 점은 6장 스냅샷과 같은 논리입니다). C15의 PK(store_id, menu_id)가 이 표의 기본키입니다. 그리고 menu_price는 이 표를 가리켜 "메뉴판에 없는 메뉴에는 가격을 붙일 수 없다"를 DB가 지키게 합니다.

-- v7: 새 표 둘과 바뀐 menu_price (v7 기준 DDL 중 이 화면의 부분)-- 매장 한 곳 (1호점도 가맹점도 한 행). 번호는 대리키
CREATE TABLE store (
    store_id  INTEGER PRIMARY KEY,
    name      TEXT    NOT NULL UNIQUE
              CHECK (name <> '' AND name = btrim(name))
);

-- 이 매장 메뉴판에 오른 메뉴. is_active 는 지금 이 매장에서 파는가
CREATE TABLE store_menu (
    store_id   INTEGER NOT NULL REFERENCES store (store_id),
    menu_id    INTEGER NOT NULL REFERENCES menu (menu_id),
    is_active  BOOLEAN NOT NULL DEFAULT TRUE,
    PRIMARY KEY (store_id, menu_id)
);

-- 매장별 메뉴 가격의 유효 기간 (valid_to 가 NULL 이면 끝나는 때가 정해지지 않은 행이다)
CREATE TABLE menu_price (
    menu_id     INTEGER     NOT NULL,
    valid_from  TIMESTAMPTZ NOT NULL,
    valid_to    TIMESTAMPTZ,
    price       INTEGER     NOT NULL CHECK (price >= 0),
    store_id    INTEGER     NOT NULL,
    PRIMARY KEY (store_id, menu_id, valid_from),
    FOREIGN KEY (store_id, menu_id) REFERENCES store_menu (store_id, menu_id),
    CHECK (valid_to IS NULL OR valid_to > valid_from),
    EXCLUDE USING gist (store_id WITH =, menu_id WITH =,
                        tstzrange(valid_from, valid_to) WITH &&)
);
  1. 1~6행 store는 매장 한 곳이 한 행입니다. 번호는 대리키이고 이름은 겹치지 않으며(UNIQUE) 빈 문자열과 양끝 공백을 막습니다(4장과 같은 관용구).
  2. 9~14행 store_menu의 기본키 (store_id, menu_id)가 C15입니다. 같은 메뉴가 한 매장에 두 번 오를 수 없습니다. 두 열이 각각 부모를 가리키는 외래키입니다.
  3. 17~22행 menu_price의 열은 v6 그대로이고 store_id가 맨 끝에 붙었습니다. 열 순서를 지킨 것은 기존 표에 ADD COLUMN으로 더하면 열이 끝에 붙기 때문입니다(화면 12에서 이전한 DB와 처음부터 만든 DB를 비교한 결과를 적습니다).
  4. 23행 기본키는 (store_id, menu_id, valid_from)입니다. 열 순서와 키 순서는 별개입니다. 키에서는 store_id가 앞에 와야 "한 매장의 한 메뉴의 이력"이 한 덩어리로 정렬됩니다.
  5. 24행 복합 외래키가 (store_id, menu_id) 쌍을 통째로 store_menu에 겁니다. v6의 menu_id → menu 외래키는 이것이 대신하므로 사라집니다(store_menu가 이미 menu를 가리킨다).
  6. 26~27행 6장의 겹침 방지가 매장 단위로 넓어졌습니다. store_id WITH =가 앞에 붙어 "같은 매장·같은 메뉴의 기간끼리만" 겹치면 안 됩니다. 1호점의 5000원과 2호점의 5300원은 같은 시각에 있어도 됩니다. 그래서 나중에는 이 EXCLUDE를 어떻게 바꿔 끼우느냐가 문제가 됩니다. 화면 9에서 다시 봅니다.

실제 서버에서 돌려 보았습니다. 2호점의 라떼를 11월 1일부터 5500원으로 올리려면 6장과 같이 열린 행을 닫고 새 행을 넣되 store_id로 한 매장만 고릅니다(1호점은 그대로). 본사가 아메리카노를 전 매장 5000원으로 올릴 때는 닫는 UPDATE를 store_id 조건 없이, 새 행은 INSERT INTO menu_price (...) SELECT store_id, menu_id, '2026-11-15 00:00+09', 5000 FROM store_menu WHERE menu_id = 1 한 문장으로 두 매장 몫을 넣었습니다. 취급하지 않는 메뉴에 가격을 넣으면 violates foreign key constraint "menu_price_store_id_menu_id_fkey"로 거부됩니다.

그래서 나중에 무슨 문제가 되는가

이 표들이 데이터가 든 채로 v6에서 만들어져야 합니다. 새 EXCLUDE와 기본키가 옛 것을 대체하기 전에는 2호점의 가격 행을 넣을 수 없고(옛 기본키 (menu_id, valid_from)가 같은 메뉴의 두 번째 -infinity 행을 duplicate key value violates unique constraint "menu_price_pkey"로 거부, 실행 확인), 옛 것을 먼저 지우면 그사이 무방비입니다. 순서가 문제의 전부입니다(화면 6~9).

(-infinity: 6장 화면 11의 이전이 "언제부터 그 가격이었는지 모르는" 옛 가격을 이력의 첫 행으로 옮기며 적은 시작 시각입니다. 2호점의 첫 가격 행도 같은 시작으로 넣으므로, 매장이 키에 없으면 메뉴마다 이 행이 둘이 됩니다.)

판단 — 회원은 매장 소속인가, 브랜드 전체인가

화면 2에서 member를 브랜드 공통 바구니에 넣었지만 이것은 설계의 가장 큰 결정 하나이므로 근거를 따로 적습니다. 두 선택지는 표 모양이 이렇게 달라집니다.

선택지표 모양따라오는 것
A. 브랜드 전체member 그대로. 매장과 무관같은 사람이 한 행. 전화번호는 브랜드에서 하나(UNIQUE 유지)
B. 매장 소속member(store_id, member_id, ...), 전화번호는 UNIQUE (store_id, phone)같은 사람이 가 본 매장 수만큼 행이 생긴다. 포인트·등급·쿠폰이 매장 안에 갇힌다
C. A + 주 이용 매장A에 선택 열 home_store_id필요가 생기면 열 하나만 더하면 되므로 지금은 만들지 않는다

결정: A. 근거는 세 가지입니다

  1. 이미 쌓인 설계가 회원 단위입니다. 6장의 포인트 원장은 member_id의 행 합계가 잔액이고(C12), 등급 할인과 쿠폰 발급(C11)도 회원에 붙어 있습니다. 하윤의 요구 "어느 매장에서든 포인트를 쓴다"는 잔액이 한 곳에 있다는 뜻입니다. B를 택하면 이 세 구조를 모두 (store_id, member_id)로 다시 짜야 합니다.
  2. 같은 사람이 같은 행이어야 중복이 안 생깁니다. 전화번호가 회원을 식별하는 업무 규칙(phone UNIQUE)은 "한 사람 = 한 행"입니다. B에서는 한 사람이 매장마다 다른 member_id를 가져 3장의 중복(같은 사실이 여러 곳)이 생깁니다.
  3. 되돌리기 쉬운 쪽이 A입니다. A에서 B로 가려면 행을 쪼개야 하지만, A에 "주 이용 매장"이나 "가맹점별 동의"를 열·표로 더하는 것은 확장만으로 됩니다.

이 결정의 대가 — 8장의 회원 락이 매장을 가로지른다

8장의 주문 생성 트랜잭션은 맨 처음 member 행을 FOR UPDATE로 잠가 한 회원의 동시 주문을 한 줄로 세웁니다. 회원이 브랜드 공통이므로 같은 회원이 두 매장에서 동시에 주문하면 서로 기다립니다. 실제 서버에서 확인했습니다. 한 연결이 회원 2번을 잠근 동안 다른 연결의 SELECT ... FOR UPDATE는 pg_stat_activity에서 wait_event_type = 'Lock'으로 대기했고, 첫 연결이 끝나자 풀렸습니다. 쿠폰·포인트를 한 번에 한 주문씩 처리해야 정확하므로 의도한 직렬화이고, 같은 회원의 동시 주문은 드물어 비용도 작습니다. 반면 다른 회원의 주문은 매장이 같든 다르든 회원 락에서 부딪치지 않습니다.

반대 의견 — 매장마다 DB(또는 스키마)를 따로 두는 길과 "가맹점 데이터의 주인"

한 시스템을 여러 고객(여기서는 매장)이 나눠 쓰는 구조를 멀티테넌시라 부릅니다. 이 장은 공유 스키마 + store_id 열을 택했지만 세 가지 길이 있습니다. ① 매장마다 DB를 따로: 격리가 가장 강하고 한 매장의 사고가 번지지 않지만, 본사 리포트와 "어느 매장에서든 포인트"가 DB 사이 조인이 되어 앱이 합쳐야 하고, 스키마 변경(이 장 전체)을 매장 수만큼 반복해야 합니다. ② 매장마다 스키마를 따로(같은 DB): 중간 정도. ③ 공유 스키마: 변경은 한 번이지만 매장 조건을 빠뜨린 쿼리 하나가 다른 매장 데이터를 보여 줍니다. 가맹점이 수십 곳이고 회원이 공통이므로 ③이 맞다는 것이 이 교재의 판단입니다. ①의 비용은 매장 수에 비례하므로 매장이 많아질수록 불리해지고, ①이 정당해지는 것은 매장마다 법·계약상 데이터를 물리적으로 떼어 두어야 하거나 한 매장의 데이터와 부하가 DB 하나를 따로 둘 만큼 클 때입니다. PostgreSQL의 행 단위 보안(RLS)으로 ③에서도 DB가 매장 조건을 강제할 수 있지만 권한 관리라 범위 밖입니다. "가맹점주가 자기 매장 회원만 보게 하는" 개인정보 정책도 DB 설계가 아니라 권한과 계약의 문제입니다.

운영 중 스키마 변경의 위험 — ALTER의 락과 데이터 보존

설계는 정했으니 v6 DB를 v7로 바꿔야 합니다. 개발용 DB라면 ALTER TABLE을 치면 끝입니다. 운영 DB에는 두 가지가 걸려 있습니다.

위험무슨 일이 생기나
① 락 줄 서기ALTER TABLE의 대부분은 그 표에 표 잠금(ACCESS EXCLUSIVE, 읽기까지 막는 가장 센 락)을 요구합니다. 그 표를 이미 읽고 있는 트랜잭션이 하나라도 끝나지 않았으면 ALTER는 기다리고, 그 뒤에 온 요청도 ALTER 뒤에 줄을 섭니다.
② 오래 걸리는 작업표를 다시 쓰거나(재작성), 모든 행을 검사하거나, 모든 행을 고치는 문장은 그동안 락을 쥐거나 표를 부풀립니다(화면 7·8)
③ 데이터 보존열을 지우는 순간 그 안의 값은 돌아오지 않습니다. 옛 앱이 새 구조에서 조용히 틀린 일을 하기도 합니다(화면 6)

① 줄 서기를 눈으로 보기

8장의 락은 "행"에 거는 것이었습니다(그때 "일반 SELECT는 락을 걸지도 기다리지도 않는다"고 한 것은 행 락 이야기입니다). 표 전체에 거는 락은 층이 다르고, 여기서는 SELECT도 가장 약한 표 락(ACCESS SHARE)을 잡습니다. 실제 PostgreSQL에서 연결 셋으로 재현했습니다. 연결 A가 orders를 읽은 채 트랜잭션을 열어 두고(BEGIN 뒤 SELECT, 아직 COMMIT 안 함), B가 ALTER TABLE orders ADD COLUMN store_id INTEGER, C가 단순 SELECT를 보냅니다.

-- 연결 A: 읽기만 하고 트랜잭션을 안 닫는다 (실제로는 느린 리포트나 잊힌 세션)BEGIN;
SELECT order_id FROM orders WHERE order_id = 101;

-- 연결 B: 열 추가 (A 때문에 기다린다)
ALTER TABLE orders ADD COLUMN store_id INTEGER;

-- 연결 C: 평범한 조회 (B 뒤에 줄을 선다)
SELECT order_id FROM orders WHERE order_id = 102;

pg_locks를 보면 A는 AccessShareLock을 쥐고(granted = true), B는 AccessExclusiveLock을 기다리고(false), C는 AccessShareLock을 기다렸습니다(false). 읽기끼리는 서로 막지 않는데, 중간에 ALTER가 끼어들면 C가 A와 충돌하지도 않으면서 막힙니다. 먼저 와서 기다리는 ALTER를 새치기하지 않는 줄 규칙 때문입니다. 결과적으로 가장 짧은 ALTER 한 줄이 가게의 모든 주문 조회를 멈춥니다. A가 끝나자(COMMIT) B는 곧바로 끝났고 C가 풀렸습니다.

방어는 lock_timeout입니다. 락 타임아웃을 짧게(예: 2초) 걸어 두면 ALTER가 자리를 못 얻을 때 스스로 포기하고 줄이 풀립니다. 같은 실험에서 B에 SET lock_timeout = '2s'를 걸자 2.0초 뒤 ERROR 55P03: canceling statement due to lock timeout이 났고, 그 순간 C의 조회도 통과했습니다. 스키마 변경 스크립트는 맨 앞에 짧은 lock_timeout을 걸고, 실패하면 한가한 때 다시 시도하는 것이 습관입니다.

운영 중 구조 바꾸기는 옛 바이너리와 새 바이너리가 같은 공유 메모리를 동시에 쓰는 상태에서 구조체 필드를 더하는 일(ABI 호환 유지)과 닮았습니다. 다른 점은 DB에는 "재컴파일해서 한 번에 갈아 끼운다"가 없다는 것입니다. 데이터는 디스크에 남아 있고 앱은 하나씩 배포되므로 옛 모양과 새 모양이 한동안 같이 살아야 합니다.

확장 → 이전 → 축소 — C16 "스키마를 바꿔도 과거 데이터는 보존된다"

한 번에 바꾸면 무엇이 깨지는지부터 봅니다. v6 앱이 돌고 있는 DB에서 stock_item.qty를 지우면(실행 확인) 옛 앱의 UPDATE stock_item SET qty = qty - 1 ...는 ERROR 42703: column "qty" does not exist로 모든 주문이 실패합니다. orders.store_id를 NOT NULL로 만든 뒤에 옛 앱이 store_id 없이 주문을 넣으면 null value in column "store_id" of relation "orders" violates not-null constraint입니다. 소리가 나는 쪽은 그나마 낫습니다. 2호점이 열린 뒤 옛 앱이 UPDATE pickup_slot SET reserved = reserved + 1 WHERE slot_start = '2026-10-02 08:30+09' AND reserved < capacity를 보내면 오류 없이 두 매장의 슬롯 행 둘을 모두 갱신했습니다(영향 행 2). 옛 앱은 슬롯이 전국에 하나라고 믿기 때문입니다.

해법은 새 구조를 옛 구조 옆에 먼저 놓는 것입니다. 이것을 확장→이전→축소(expand-contract)라 부릅니다.

NOT NULL로 조이는 길 — CHECK를 거쳐서

SET NOT NULL을 곧장 치면 DB가 전 행을 훑는 동안(1,547ms) 표 락을 쥐고 있습니다. 대신 CHECK (store_id IS NOT NULL)을 NOT VALID로 겁니다. 앞으로 들어오는 행만 검사하고 기존 행은 건너뛰므로 순간에 끝나고(실행 확인: 락 ACCESS EXCLUSIVE, 스캔 없음), 이어서 VALIDATE CONSTRAINT가 기존 행을 훑는데 이때 락은 SHARE UPDATE EXCLUSIVE라 쓰기가 막히지 않습니다(검증에 1,784ms 걸렸고, 그 락을 쥔 트랜잭션이 열려 있는 동안 다른 연결의 INSERT가 바로 통과. 반대로 NOT VALID 없이 CHECK를 걸어 둔 트랜잭션이 열려 있으면 INSERT는 대기). 검증이 끝난 CHECK가 "NULL이 없다"는 증거라서 그 뒤의 SET NOT NULL은 스캔 없이 1ms에 끝납니다. debug1 알림으로 existing constraints on column "orders.store_id" are sufficient to prove that it does not contain nulls가 찍혔고, 증거 CHECK가 없는 열에서는 verifying table "orders"가 찍히며 1,547ms 걸렸습니다. 이 최적화는 PostgreSQL 12부터입니다. 외래키도 같은 모양입니다. NOT VALID로 걸면 SHARE ROW EXCLUSIVE가 두 표에 순간 걸리고, VALIDATE(201ms)는 SHARE UPDATE EXCLUSIVE(자식) + ROW SHARE(부모)라 쓰기를 막지 않았습니다.

함정 — NOT VALID CHECK는 채우기가 끝난 뒤에 건다

6장 화면 8의 "NOT VALID를 걸어도 옛 행을 어느 열이든 UPDATE하면 그 행 전체를 다시 검사한다"는 경고가 여기서 실제가 됩니다. 채우기 전에 CHECK (store_id IS NOT NULL) NOT VALID를 걸고 옛 주문의 상태를 바꾸면(UPDATE orders SET status = '취소' WHERE order_id = 101) ERROR 23514: new row for relation "orders" violates check constraint "orders_store_id_nn"이고, 새 앱이 store_id를 빠뜨린 INSERT도 같은 오류입니다(실행 확인). 운영 중이면 바리스타의 상태 변경이 전부 실패합니다. 그래서 순서는 확장 → (새 앱이 store_id를 적는다) → 채우기 → 그다음에 제약입니다. 6장이 "전 행 UPDATE가 막힌다"는 이유로 약한 CHECK를 택한 결정이 이 장의 채우기를 가능하게 했습니다.

마지막으로 8장이 남긴 질문, "ALTER TABLE orders ADD COLUMN pickup_start TIMESTAMPTZ REFERENCES pickup_slot (slot_start) 한 줄이 200만 행 표에서 무엇을 하나"의 답입니다. 같은 서버에서 2ms 만에 끝났습니다. 열은 전부 NULL이라 검증할 것이 없고, 대신 한 문장이 세 가지 락을 한꺼번에 잡았습니다. orders에 ACCESS EXCLUSIVE와 SHARE ROW EXCLUSIVE, pickup_slot에 SHARE ROW EXCLUSIVE입니다(pg_locks 확인). 가볍지만 "순간"이라 안전한 것은 줄이 안 설 때뿐이므로(화면 5) lock_timeout 아래에서 실행해야 합니다.

제약 둘 — 트랜잭션 안에서 못 쓴다, 실패하면 찌꺼기가 남는다

① 트랜잭션 블록 안에서 못 씁니다. BEGIN 뒤에 쓰면 ERROR 25001: CREATE INDEX CONCURRENTLY cannot run inside a transaction block입니다(실행 확인). 그래서 이 장의 이전 스크립트는 한 파일을 통째로 BEGIN ... COMMIT으로 감쌀 수 없고 단계마다 따로 실행합니다. 마이그레이션 도구가 파일 하나를 자동으로 트랜잭션에 넣는다면 이 문장은 그 밖에 두어야 합니다(화면 11).

② 실패하면 무효(INVALID) 인덱스가 남습니다. 값이 겹치는 열에 CREATE UNIQUE INDEX CONCURRENTLY를 걸자 ERROR 23505: could not create unique index "orders_dup_idx"로 실패했고, pg_index.indisvalid = false인 인덱스가 남았습니다. 이 인덱스는 쓰기 때마다 갱신 비용만 내고 조회에는 쓰이지 않으므로 DROP INDEX로 치우고 다시 시도합니다.

    ON menu_price (store_id, menu_id, valid_from);

    ON daily_sales (store_id, sales_date);

화면 3에서 C15의 "menu 쪼개기"는 menu_price에 store_id를 넣는 일로 바뀌었습니다. 이 교재에서 진짜로 표를 쪼개는 실습은 재고입니다. v6의 stock_item(item_id, name, kind, unit, qty)는 3장의 눈으로 보면 한 표에 두 종류의 사실이 섞여 있습니다. item_id → name, kind, unit(품목이 무엇인가)과 (store_id, item_id) → qty(그 매장에 얼마 남았나)입니다. 키에 store_id가 들어오면 qty만 키 전체에 종속하고 나머지는 키의 일부(item_id)에만 종속합니다. 부분 종속, 곧 2NF 위반의 모양입니다.

반대 의견 — 마이그레이션 도구를 쓸까, 손으로 SQL을 칠까

도구(Flyway, Liquibase, Alembic 등)는 파일 순서, 적용 기록, 중복 방지, 여러 환경(개발·검증·운영)에서 같은 순서 보장을 줍니다. 대가는 두 가지입니다. 도구는 보통 파일 하나를 한 트랜잭션으로 감싸므로 CREATE INDEX CONCURRENTLY(화면 8)는 따로 빼거나 "트랜잭션 없이 실행" 설정을 해야 하고, 도구가 만든 기록표와 도구의 학습 비용이 생깁니다. 손 SQL은 단발이거나 담당자가 한두 명일 때 단순하고 위처럼 기록표만 직접 만들어도 되지만, "어느 환경에 어디까지 적용됐는가"가 사람의 기억에 의존하는 순간 사고가 납니다. 이 교재는 도구를 고르지 않습니다. 어느 쪽이든 지켜야 하는 것은 번호 순서, 적용 기록, 되돌리기 가능 여부의 표시, 그리고 트랜잭션 밖에서 돌려야 하는 문장의 표시입니다. 4장 화면 1의 "규칙 바꾸기는 스키마를 바꾼다(운영 중이면 조심할 일, 9장)"의 답이 이것입니다.

9장 마무리

핵심 요약

  1. 매장 범위는 표마다 세 질문으로 가릅니다. 값이 매장마다 다르거나 한 매장의 사건이면 store_id가 들어가고(orders, menu_price, pickup_slot, daily_sales, 재고 수량), 부모를 따라 매장을 알면 열을 더하지 않으며(라인 표 넷, 3장의 부분 종속), 나머지는 브랜드 공통입니다. 회원은 브랜드 공통으로 정했고 그 대가는 회원 락이 매장을 가로질러 직렬화되는 것입니다.
  2. C15는 "menu_price에 store_id"로 풀렸습니다. 6장이 가격을 이력 표로 옮겼으므로 가격의 집을 한 곳에 두고, store_menu는 "이 매장 메뉴판에 있고 지금 파는가"를 담습니다. 키는 (store_id, ...)로, EXCLUDE도 매장 단위로 넓어집니다.
  3. 운영 중 변경의 위험은 락 줄 서기와 오래 걸리는 문장입니다. 가장 짧은 ALTER도 열린 트랜잭션 하나 때문에 모든 조회를 세웁니다(lock_timeout으로 방어). 상수 DEFAULT는 재작성이 없고(PostgreSQL 11), 전 행 UPDATE는 표를 두 배로 부풀립니다(범위를 나눠 반복). 무중단이 늘 정답은 아닙니다.
  4. 확장 → 이전 → 축소(C16): 새 구조를 옛 구조 옆에 놓고, 새 앱을 배포하고, 값을 채우고, 조이고, 마지막에 옛 것을 지웁니다. NOT NULL은 CHECK ... NOT VALID → VALIDATE → SET NOT NULL(PostgreSQL 12), 인덱스는 CONCURRENTLY(트랜잭션 밖), 기본키는 새 유일 인덱스 + 새 외래키를 옆에 놓고 USING INDEX로 한 문장 교체합니다. 되돌릴 수 없는 단계는 맨 끝 하나로 몰고 점검 조회로 데이터 보존을 확인합니다.
  5. 결과가 스키마 v7(표 25개)이고 D2는 갚았습니다. 8장의 주문 트랜잭션은 골격과 락 순서를 유지한 채 store_id를 세 군데(가격 조회, 재고, 슬롯)에 더해 성립합니다.

order_line에 store_id 열을 더하지 않은 가장 근본적인 이유는 무엇일까요?

  1. 열 하나만큼 늘어나는 저장 공간을 아끼려고
  2. 라인 표에는 store_id 외래키를 걸 수 없어서
  3. 라인의 매장은 order_id로 정해지는 부분 종속이라 두 곳에 적으면 어긋날 수 있어서

"자식에 부모의 키를 복사해 두면 조인이 줄어든다"는 직관이 맞는 때도 있습니다. 7장의 의도적 비정규화가 그 예입니다. 차이는 복사한 값이 어긋나지 않게 누가 지키느냐입니다. 요약 표는 배치와 점검 조회가, 대각선 외래키는 DB가 지킵니다. 지키는 장치 없이 복사만 하는 것이 부분 종속의 위험입니다.

200만 행 orders에 열을 더할 때 표를 통째로 다시 쓰는 문장은 무엇일까요(PostgreSQL 11 이상)?

  1. ADD COLUMN r DOUBLE PRECISION DEFAULT random()
  2. ADD COLUMN store_id INTEGER
  3. ADD COLUMN store_id INTEGER NOT NULL DEFAULT 1

"기본값이 있으면 느리다"는 PostgreSQL 10 이하의 상식이 지금도 돌아다닙니다. 반대로 "상수 기본값은 항상 공짜"도 반쪽입니다. 기본값이 붙은 채로 새 앱이 배포되면 열을 빠뜨린 쓰기가 오류 없이 기본값으로 저장되어 조용히 틀립니다. 이전용 기본값은 이전이 끝나면 DROP DEFAULT로 거둡니다.

옛 행을 채우기 전에 CHECK (store_id IS NOT NULL) NOT VALID를 걸면 운영 중에 어떤 일이 생길까요?

  1. 새로 들어오는 주문 행이 모두 검사에서 거부된다
  2. 채우지 않은 옛 행을 고치는 UPDATE(예: 상태 변경)가 거부된다
  3. 기존 200만 행을 전부 검사하느라 표가 오래 잠긴다

이 퀴즈의 답은 6장 화면 8에서 "이 제약이 있으면 옛 주문에 store_id 같은 열을 채우는 전체 행 갱신이 막힌다"고 한 예고입니다. 6장이 약한 CHECK를 택한 덕에 이 장의 채우기가 가능했습니다. 앞 장의 제약 선택이 뒷장의 이전 가능성을 정한다는 것이 이 교재의 뼈대 중 하나입니다.

pickup_slot의 기본키를 바꿀 때 orders의 새 외래키를 먼저 옛 것 옆에 걸고 나중에 옛 것을 지우는 이유는 무엇일까요?

  1. 외래키가 둘이면 검사가 나뉘어 돌아 더 빨라져서
  2. 두 외래키가 동시에 있어야 DB가 오류를 내지 않아서
  3. 옛 것을 지우는 순간부터 새것이 걸리기까지의 빈틈에 잘못된 행이 들어오는 것을 막으려고

같은 모양이 화면 9에서 매장 단위로 넓힌 이력 겹침 방지(EXCLUDE, 6장에서 처음 건 것)에도 있습니다. 넓힌 제약을 먼저 옆에 걸고 옛 것을 나중에 지우므로 그 사이에 보호가 끊기지 않고, 대신 옛 것이 지워지기 전까지는 2호점 가격 행이 옛 기본키에 거부됩니다(그래서 2호점 데이터는 4단계 뒤에 넣습니다). "더하는 것이 먼저, 지우는 것이 나중"이 확장→이전→축소의 한 줄 요약입니다.

방법걸린 시간무슨 일이 일어났나
ADD COLUMN ... NOT NULL DEFAULT 1 (상수 기본값)2msPostgreSQL 11부터 기본값이 비휘발성(상수처럼 모든 행에 같은 값)이면 재작성이 없다. 기본값을 카탈로그에 적어 두고 읽을 때 채워 준다. 파일 그대로

화면 7의 3단계 조이기에서 NOT NULL 부분만 가져왔습니다. NOT VALID로 걸기는 순간에 끝나고, VALIDATE는 쓰기를 막지 않으며, 검증된 CHECK가 있으면 SET NOT NULL은 스캔 없이 끝납니다.

-- 화면 7의 3단계 조이기에서 발췌 (orders.store_id)-- NOT NULL: CHECK 를 NOT VALID 로 걸고, 검증하고, SET NOT NULL 뒤 CHECK 를 지운다
ALTER TABLE orders
    ADD CONSTRAINT orders_store_id_nn CHECK (store_id IS NOT NULL) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_store_id_nn;
ALTER TABLE orders ALTER COLUMN store_id SET NOT NULL;
ALTER TABLE orders DROP CONSTRAINT orders_store_id_nn;
모범답안 — 그리고 흔한 오답이 왜 부족한지 
-- 모범답안 (서버에서 실행 확인)ALTER TABLE orders ADD COLUMN channel TEXT NOT NULL DEFAULT '키오스크';
ALTER TABLE orders ADD CONSTRAINT orders_channel_check
    CHECK (channel IN ('키오스크', '앱')) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_channel_check;
-- 새 앱이 channel 을 적는 것을 확인한 뒤
ALTER TABLE orders ALTER COLUMN channel DROP DEFAULT;

1. 상수 DEFAULT라 재작성 없이 순간에 끝납니다(PostgreSQL 11). 기존 행은 읽을 때 '키오스크'로 보입니다. 값 목록은 CHECK를 NOT VALID로 걸고 VALIDATE합니다(쓰기를 막지 않는다). 새로 만들 때 한 줄로 쓰는 CHECK는 이미 행이 있는 표에서는 전 행 검사 동안 락을 쥡니다. 역시 lock_timeout 아래에서 실행합니다.

2. DROP DEFAULT입니다. 안 거두면 앱이 channel을 빠뜨려도 오류 없이 전부 '키오스크'가 되어 앱 주문이 키오스크 주문으로 조용히 집계됩니다. 거두면 빠뜨린 쓰기가 NOT NULL 위반으로 즉시 드러납니다(서버에서 확인: null value in column "channel" ... violates not-null constraint).

3. '키오스크'로 채우면 지어낸 값이 됩니다. 5·6장의 NULL 두 의미처럼 "해당 없음"과 "기록 없음"을 구분해야 하면 channel은 NULL을 허용하고 기본값 없이 더하며, 과거 행은 NULL로 둡니다. 대신 앞으로 들어오는 행은 반드시 적게 하고 싶다면 이전일을 박은 CHECK (channel IS NOT NULL OR ordered_at < TIMESTAMPTZ '2026-11-01 00:00+09')를 NOT VALID로 걸고 VALIDATE합니다. 옛 행은 날짜 조건으로 통과해 옛 행 갱신이 막히지 않고, 이전일 이후에 channel을 빠뜨린 행은 23514로 거부됩니다(서버에서 확인).

흔한 오답 1 — 열을 더하고 UPDATE orders SET channel = '키오스크' 한 번. 200만 행이 두 벌이 되고 표·인덱스가 두 배로 부풀며 16초 가까이 행 락이 쌓입니다.

흔한 오답 2 — ADD COLUMN ... NOT NULL을 기본값 없이 시도. 행이 있는 표에서는 column "channel" of relation "orders" contains null values 오류가 납니다.

흔한 오답 3 — 값 목록 CHECK를 ADD COLUMN 문장 안에 함께 쓰거나 NOT VALID 없이 겁니다. 이미 200만 행이 있는 표라 전 행을 검사하는 동안 ACCESS EXCLUSIVE를 쥐어 주문 조회까지 멈춥니다(화면 5·7).
