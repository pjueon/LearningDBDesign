7장 · 페이지 2

DB는 행을 어떻게 찾나 — 풀스캔과 인덱스

주문 100만 건 중 "2025-10-01 06:59:37.928에 들어온 주문" 하나를 찾는 일을 생각해 봅시다. C++이라면 주문 구조체를 std::vector에 담아 두고 std::find_if로 처음부터 끝까지 비교할 것입니다. 100만 개를 모두 비교할 수도 있는 선형 탐색입니다.

orders에 이 시각으로 찾는 인덱스가 없으면 DB가 하는 일이 정확히 이것입니다. 표의 모든 행을 처음부터 읽으며 조건을 검사하는 것을 풀스캔(full scan, PostgreSQL 이름은 Seq Scan)이라고 합니다. 실험에서 이 조회는 행 999,999개를 읽고 버렸습니다.

"행을 읽는다"는 사실은 "페이지를 읽는다"입니다 — 벡터 비유가 깨지는 곳

std::vector는 메모리에 있지만 DB의 표는 디스크에 있고, DB는 디스크를 페이지(PostgreSQL은 8KB)라는 덩어리로만 읽습니다. 행 하나가 필요해도 그 행이 든 페이지 전체를 읽습니다. 그래서 비용의 기본 단위는 "행 수"보다 "읽은 페이지 수"입니다. orders 100만 행은 9,141쪽이고, 풀스캔은 그 전부를 읽습니다. 이 교재가 "버퍼 수"라고 적는 것이 이 페이지 수입니다.

책의 색인처럼

책 한 권에서 "샷 추가"가 나오는 곳을 찾을 때 본문을 처음부터 읽지 않고 뒤의 색인을 봅니다. 색인은 "낱말 → 쪽 번호"를 가나다 순으로 정렬해 따로 모아 둔 것이고, 본문은 그대로입니다. DB도 같습니다. 열의 값을 정렬해서 그 값이 든 행의 위치와 함께 따로 저장해 두는 구조가 인덱스(색인)입니다. 표 본문은 그대로이고 인덱스는 별도로 저장되는 추가 구조입니다.

찾는 방식C++ 비유PostgreSQL읽은 페이지(실측)
인덱스 없이std::vector 전체를 find_ifSeq Scan9,141쪽
인덱스로정렬된 std::map<키, 행 위치>에서 findIndex Scan4쪽

정렬된 std::map과 다른 점 넷

  1. 디스크 페이지 위의 나무입니다. 메모리 포인터를 따라가는 노드가 아니라 8KB 페이지 하나가 노드 하나입니다(페이지 3).
  2. 쓰기마다 갱신됩니다. 행을 넣고 고칠 때 인덱스도 고쳐야 해서 쓰기가 느려집니다(페이지 7).
  3. 공간을 더 씁니다. 표와 별개의 저장 공간이 듭니다(페이지 7).
  4. 언제 쓸지는 DB가 고릅니다. 조회문에 인덱스를 지정하지 않고, 계획을 세우는 DB가 "풀스캔이 더 싸다"고 판단하면 있어도 안 씁니다(페이지 7).

우리는 이미 28개를 갖고 있습니다

0장의 개념 지도가 "인덱스는 7장"이라고 미뤘지만, v5에는 이미 인덱스가 28개 있습니다. 한 번도 CREATE INDEX를 쓰지 않았는데도 그렇습니다. PRIMARY KEY 17개, UNIQUE 8개, 6장의 부분 UNIQUE 인덱스 2개(order_discount_grade_once, point_ledger_once), EXCLUDE 1개(menu_price의 겹침 방지)입니다. "같은 값이 둘 있을 수 없다"를 검사하려면 기존 값을 빨리 찾아야 하니 DB가 인덱스를 자동으로 만들어서 제약을 지키는 것입니다. 2장과 4장의 "제약과 인덱스는 UNIQUE가 겸한다"는 말이 이것입니다. 그래서 WHERE order_id = 501000은 실험에서 4쪽만 읽었습니다.

반대 방향은 성립하지 않습니다. 인덱스가 있다고 규칙이 생기지는 않고(일반 인덱스는 중복을 막지 않습니다), 외래키 열에는 자동으로 인덱스가 생기지 않습니다. 이것이 페이지 5의 주제입니다. 직접 만드는 문법은 간단합니다.

-- 시각으로 찾는 인덱스 하나 (조회문은 그대로 둔다)CREATE INDEX orders_ordered_at_idx ON orders (ordered_at);
-- 같은 조회: 풀스캔 9,141쪽  →  인덱스 4쪽
SELECT * FROM orders WHERE ordered_at = '2025-10-01 06:59:37.928+09';

CREATE INDEX 이름 ON 표 (열)이 전부입니다. 이름은 이 교재가 표_열_idx 꼴로 붙입니다. 조회문은 한 글자도 바꾸지 않았는데 읽는 양이 약 2,000분의 1이 되었습니다. 이렇게 큰 차이가 어떻게 가능한지가 다음 페이지입니다.

7장 · 페이지 3

B-tree 탐색 스텝퍼 — 찾는 길을 눌러서 따라가기

인덱스가 어떻게 약 2,000분의 1만 읽고도 찾는지를 글로 먼저 적습니다. 위젯은 이것이 정말 그렇게 되는지 눌러서 확인하는 도구입니다.

  1. PostgreSQL 인덱스의 기본 구조는 B-tree입니다. 값을 정렬해서 페이지에 담고, 그 페이지들을 나무로 쌓습니다. 맨 아래 잎에는 "값 → 표의 행 위치"가 정렬되어 들어 있습니다.
  2. 위 층의 중간과 루트 페이지에는 행이 아니라 구분값이 있습니다. "17 미만은 왼쪽, 17 이상 33 미만은 가운데, 33 이상은 오른쪽 자식"처럼 어느 자식으로 내려갈지만 알려 줍니다. 모든 잎은 루트에서 같은 깊이에 있습니다.
  3. 찾는 길은 루트 → 중간 → 잎 → 표의 행입니다. 깊이가 3이면 인덱스 페이지 3쪽에 표 페이지 1쪽, 모두 4쪽입니다. 표가 커져도 이 모양은 같고 깊이만 아주 천천히 늘어납니다(이 페이지 끝).
읽은 곳 0 곳

조작: 위에서 방식(풀스캔 또는 B-tree)과 찾는 값을 고르고 다음 단계를 눌러 한 곳씩 읽어 보세요. 끝까지는 한 번에 끝내고, 방식이나 값을 바꾸면 처음으로 돌아갑니다.

눌러 보고 확인할 것

  • 37을 풀스캔과 B-tree로 각각 끝까지 실행해 읽은 곳을 비교하세요. 37은 표의 31번째 행에 있어 풀스캔이 31곳, 인덱스가 4곳입니다. 15는 47번째 행이라 풀스캔이 47곳입니다. 인덱스는 어느 값이든 4곳으로 같습니다. 그런데 2는 표의 3번째 행이라 풀스캔이 3곳으로 인덱스(4곳)보다 싸게 끝납니다. 풀스캔의 비용은 값이 표의 어디에 있느냐에 달렸고, 작은 표에서는 풀스캔이 이길 수 있다는 것이 페이지 7의 단서입니다.
  • 50(표에 없는 값)을 풀스캔으로 해 보세요. 48행을 전부 읽어야 "없다"고 말할 수 있습니다. B-tree는 잎까지 3곳만 읽고 끝납니다.
  • 표의 행은 흩어져 있지만 인덱스는 정렬되어 있습니다. 정렬된 것을 따로 하나 더 들고 있다는 것이 전부이고, 이것이 4장·7장의 비용 이야기의 뿌리입니다.

실제 잎 페이지 하나에는 위젯의 4개가 아니라 수백 개(이 실험에서는 약 365개)의 값이 들어갑니다. 한 층에 수백 개의 갈래가 있으니 깊이 3으로 대략 5천만 개, 깊이 4면 백억 단위의 값까지 담을 수 있습니다. 행이 100만 배 늘어도 읽는 페이지는 한두 쪽 늘 뿐입니다. 이것이 "로그 시간"의 실감입니다. C++의 std::map도 O(log N)이지만, 이쪽은 갈래가 수백 개라 깊이가 훨씬 얕습니다. 디스크를 한 번 읽는 값이 비싸서 나무를 넓고 낮게 만든 것입니다.

범위 조건도 돕습니다

잎은 값 순서대로 이웃 잎과 이어져 있습니다. "3월 5일 하루"처럼 범위는 시작점을 나무로 찾은 뒤 잎을 옆으로 훑으면 됩니다. 그래서 같은 인덱스가 =뿐 아니라 >=, <, BETWEEN, 그리고 ORDER BY(이미 정렬되어 있으니 정렬을 생략)에도 쓰입니다. 안 돕는 경우는 페이지 4와 7에서 봅니다.

인덱스의 종류, 그리고 열이 둘일 때의 순서

페이지 3의 나무는 PostgreSQL이 CREATE INDEX에 종류를 안 적으면 만드는 B-tree입니다. 이 교재의 인덱스는 거의 전부 B-tree이고, 다른 종류는 "이런 것이 있다"만 알아 두면 됩니다.

종류잘하는 것이 교재에서
B-tree=, 범위(<, BETWEEN), 정렬(ORDER BY)기본. 앞으로 만드는 인덱스 전부
Hash=만B-tree도 =를 잘해서 쓸 일이 드물다
GiST범위의 겹침, 좌표 같은 "크기 비교가 안 되는" 값6장 menu_price의 EXCLUDE가 이것이다

BRIN시간순으로 쌓이는 아주 큰 표를 아주 작은 인덱스로존재만. 페이지 11의 대용량에서 다시 떠오른다

6장의 부분 UNIQUE 인덱스(WHERE가 붙은 것)도 B-tree입니다. 일부 행만 담는 인덱스라는 생각은 페이지 7에서 성능 쪽으로 다시 씁니다.

열이 둘일 때 — 복합 인덱스

하윤이 "민준의 주문을 최근 것부터 10건"을 보려 한다고 합시다. 조건은 member_id = 77, 정렬은 ordered_at 최신순입니다. 열 둘을 한 인덱스에 담는 복합 인덱스는 앞 열로 먼저 정렬하고, 같은 값 안에서 뒤 열로 정렬합니다. 전화번호부가 "성 → 이름" 순으로 정렬된 것과 같습니다. C++로는 std::map<std::pair<회원, 시각>, 행>이 그 모양이고, pair는 첫 원소부터 비교합니다.

성을 알면 "김씨 중 이름순"으로 바로 갈 수 있고, 성과 이름을 둘 다 알면 더 좁힙니다. 그런데 이름만 알면 못 찾습니다. 성으로 묶여 있어서 이름은 사방에 흩어져 있기 때문입니다. 이것이 선두 열 규칙입니다. 복합 인덱스는 앞 열의 조건이 있어야 잘 쓰입니다.

SELECT order_id, ordered_at, status
FROM   orders
WHERE  member_id = 77

조회 패턴에서 인덱스를 고른다 — 외래키 열 포함

3장은 "정규화하면 느리다는 말은 반만 맞다"고 했습니다. 조인할 열에 인덱스가 있으면 조인은 쌉니다. 예를 들어 주문 한 건의 라인은 order_line의 PK 인덱스(앞 열이 order_id)로 바로 찾습니다(페이지 4의 선두 열 규칙). 그러면 어떤 열에 거는가가 문제입니다.

7장 · 페이지 6 · 선택

(선택) 실행 계획 읽기 — EXPLAIN

이 페이지는 읽지 않고 넘어가도 12페이지의 흐름이 이어집니다. 앞 페이지의 "9,141쪽", "4쪽" 같은 숫자를 직접 재는 방법이므로 PostgreSQL을 직접 만져 볼 때 돌아와서 읽으세요. DB는 조회 하나를 받으면 "어떤 순서로 어떻게 읽을지" 계획을 세우고 실행하고, EXPLAIN은 그 계획을 보여 줍니다. 계획을 세우는 것도 DB라서 "인덱스를 만들었는데 쓰였는가"는 이걸로 확인하는 수밖에 없습니다.

EXPLAIN (ANALYZE, BUFFERS)는 계획을 실제로 실행해 실제 행 수와 읽은 페이지까지 붙여 줍니다. 아래는 페이지 2의 "시각으로 한 건 찾기"의 실제 출력입니다(지면 폭 때문에 한 줄을 둘로 나눴습니다).

조회가 여러 겹이면

계획은 들여쓰기가 나무입니다. 가장 안쪽(오른쪽)의 줄이 표나 인덱스에서 행을 읽어 바깥 줄로 올려 보냅니다. 페이지 1의 리포트라면 가장 많이 읽힌 order_line(페이지 1의 표: 200만 행을 두 번)을 읽는 안쪽의 읽기 줄부터 보게 됩니다. 행 수가 큰 줄을 먼저 찾고 바깥으로 올라가면 됩니다. 페이지 5의 "삭제 검사 183ms"는 DELETE의 출력 끝에 붙는 Trigger for constraint order_line_menu_id_fkey: time=183.432 calls=1 줄이 알려 준 것입니다. 외래키 검사는 계획의 나무가 아니라 이런 줄로 나옵니다.

ANALYZE는 진짜 실행합니다

EXPLAIN ANALYZE DELETE ...는 행을 정말 지웁니다. 쓰기 문장은 BEGIN; EXPLAIN ANALYZE ...; ROLLBACK;으로 감싸서 되돌립니다. ANALYZE 없이 EXPLAIN만 쓰면 실행하지 않고 짐작만 보여 줍니다. 또 작은 표에서는 풀스캔이 정상 답입니다. 행이 수십 개뿐인 menu에 인덱스가 안 쓰인다고 놀랄 일이 아닙니다(페이지 7).

7장 · 페이지 7

인덱스가 안 듣는 경우, 그리고 인덱스의 비용

"그럼 자주 쓰는 열에 전부 걸면 되나요?" 안 됩니다. 이유가 둘입니다. 걸어도 안 듣는 경우가 있고, 들어도 공짜가 아닙니다.

카디널리티 — 이 장에서는 두 번째 뜻입니다

2장에서 카디널리티는 관계의 대응 수(1:N)였습니다. 인덱스 문맥에서는 같은 낱말이 열이 가진 서로 다른 값의 수입니다. orders.status의 카디널리티는 5(접수·제조중·완료·픽업·취소), order_id는 100만입니다. 이름은 같지만 다른 개념이니 문맥으로 구별하세요. 여기에 선택도가 붙습니다. 조건 하나가 행을 얼마나 잘 걸러 내는가이고, 고르는 행의 비율이 작을수록 선택도가 높다고 말합니다(PostgreSQL 문서는 그 비율 자체를 선택도라 부르니 숫자로는 작을수록 "높은" 것입니다). 인덱스는 선택도가 높은 조건에서 듣습니다.

값 종류가 적은 열 — 그래도 드문 값이면 듣는다

orders.status에 인덱스를 걸고(849쪽) 값마다 찾아 봤습니다. 읽은 페이지로 비교합니다. 풀스캔은 표 전체인 9,141쪽입니다.

인덱스의 비용 — 쓰기와 공간

인덱스는 정렬된 사본이라 행을 넣고 고칠 때마다 모든 인덱스를 함께 고칩니다. orders와 같은 열의 표 셋(외래키·CHECK는 뺐습니다)에 인덱스만 다르게 걸고, 같은 주문 10만 건을 번갈아 여섯 번 넣어 중앙값을 비교했습니다.

  • 읽기가 99%인 표는 이 비용이 문제가 안 되지만, orders처럼 모든 주문이 곧 쓰기인 표에서는 인덱스 하나하나가 주문 처리 경로에 붙습니다.

  • 원칙은 세 줄입니다. 조회 목록에 이름이 나온 것만 만들고, 쓰기가 많은 표일수록 적게, 위의 idx_scan 조회로 안 쓰이는 것은 지웁니다. 단 통계를 모은 기간이 충분할 때만 믿고, PRIMARY KEY·UNIQUE의 인덱스는 idx_scan이 0이어도 규칙을 지키는 일을 하므로 지우지 않습니다. 이 장이 만드는 인덱스는 5개뿐입니다(페이지 11).
  • 운영 중인 큰 표에 CREATE INDEX는 만드는 동안 쓰기를 막습니다. CREATE INDEX CONCURRENTLY가 막지 않고 만드는 길이지만 트랜잭션 안에서 못 쓰는 제약이 따릅니다. 9장에서 다시 본다

하윤은 "하루"가 아니라 "하루치의 합"을 읽는다

리포트가 원하는 것은 날마다 한 줄(주문 수, 소계, 할인)입니다. 그 값은 끝난 날에는 바뀌지 않으니 매번 주문 47만 건에서 다시 만들 이유가 없습니다. 날짜마다 한 행을 가진 요약 테이블에 미리 계산해 저장합니다. 한 행이 무엇을 뜻하는지(2장의 질문)는 "그 날(서울 시각)에 들어온 취소 아닌 주문 전체의 합"이고 2년이면 730행입니다.

D4와 3장의 "되돌린 것" — 모순이 아닙니다

3장은 총액을 파생값이라 저장하지 않는다고 했습니다(D4). 이 표는 그 결정을 뒤집는 것이 아니라 측정한 뒤에 일부러 되돌린 것입니다. "비정규화는 정규화를 안 한 것이 아니라 한 뒤에 되돌린 것"입니다. 원본(주문·라인·옵션·할인)은 그대로 정규형이고, 그 위에 버려도 다시 만들 수 있는 파생 표를 얹었습니다. orders에 total 열을 넣지 않은 것도 그대로입니다. 그 열이 있어도 1년치는 주문 47만 행을 더해야 하지만, 요약은 읽는 단위(하루)에 맞춰 365행이 되기 때문입니다.

-- 스키마 v5.1 ①: 일 매출 요약 테이블 (새 표 하나, 기존 17개 표는 그대로)-- 일 매출 요약: 한 행 = 그 날(서울 시각) 들어온 취소 아닌 주문 전체의 합
CREATE TABLE daily_sales (
    sales_date    DATE        PRIMARY KEY,
    order_count   INTEGER     NOT NULL CHECK (order_count >= 0),
    subtotal      BIGINT      NOT NULL CHECK (subtotal >= 0),
    discount      BIGINT      NOT NULL CHECK (discount >= 0),
    refreshed_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CHECK (discount <= subtotal)
);
  • PK가 sales_date라서 같은 날 행이 둘 있을 수 없습니다(이 표의 "한 행 = 하루"를 DB가 지킵니다). BIGINT인 것은 SUM이 bigint를 돌려주는 것과 맞추려는 것입니다.
  • 할인 후 금액(매출)은 저장하지 않습니다. subtotal - discount로 읽을 때 뺍니다. 표 안에서도 계산할 수 있는 값은 저장하지 않는다는 3장의 원칙을 요약 표에서도 지킵니다. CHECK (discount <= subtotal)은 6장 "할인의 합은 소계 이하" 규칙의 집계판이라, 잘못 집계하면 저장이 거부됩니다.
  • refreshed_at은 그 행을 마지막으로 계산한 시각입니다. 어긋남을 조사할 때 페이지 9가 씁니다.

비정규화의 원칙 — 원본을 지키고, 갱신 경로를 하나로, 어긋남을 찾는다

같은 사실을 둘 이상의 자리에 두면 어긋날 수 있다는 것이 1장부터의 교훈이었습니다. 요약 테이블은 그 위험을 알고 얻은 속도라서 세 가지를 약속으로 둡니다.

           GROUP BY ol.order_id) AS l ON l.order_id = o.order_id

           JOIN   o ON o.order_id = ol.order_id

LEFT JOIN (SELECT di.order_id, SUM(di.amount) AS amount
           FROM   order_discount AS di JOIN o ON o.order_id = di.order_id

목록 조회와 페이지네이션 — OFFSET, keyset, COUNT(*)

관리 화면은 주문 목록을 20건씩 보여 줍니다. "다음 쪽"을 누를 때마다 같은 화면이 점점 느려지는 일이 흔합니다. 인덱스가 있는데도 그렇습니다.

OFFSET — 건너뛴 만큼 읽는다

가장 흔한 쓰임은 LIMIT 20 OFFSET 건너뛸 개수입니다. 60만 건을 건너뛰고 20건을 달라는 조회를 order_id 역순(최신순)으로 실행했습니다.

-- (A) OFFSET: 뒤쪽 페이지   (B) keyset: 같은 20건SELECT order_id, ordered_at, status FROM orders
ORDER BY order_id DESC
LIMIT 20 OFFSET 600000;

SELECT order_id, ordered_at, status FROM orders
WHERE  order_id < 401001      -- 앞 페이지의 맨 아래 주문 번호
ORDER BY order_id DESC
LIMIT 20;

(A) OFFSET 600000600,0207,610쪽 (시간은 수천~1만 배)

OFFSET은 "앞의 N개를 만들고 버린다"입니다. C++로는 이터레이터를 std::advance(it, 600000)로 하나씩 밀어서 가는 것과 같습니다. 인덱스가 정렬해 둔 덕에 정렬은 피했지만 건너뛰는 행은 세어야 하므로 읽은 행이 600,020개입니다. 비용이 페이지 번호에 비례하고, 사용자가 뒤로 갈수록 느려집니다.

keyset — 마지막으로 본 자리에서 시작한다

(B)는 "건너뛴 개수" 대신 "마지막으로 본 행의 키"를 기억합니다. 정렬 열에 대한 범위 조건이라 인덱스가 시작점으로 바로 가고, 몇 번째 페이지든 20행만 읽습니다. 이것을 keyset 페이지네이션이라 합니다(std::map::lower_bound로 다음 구간을 잡는 것과 같습니다). 조건이 있습니다.

  • 정렬 기준이 행마다 다르고 순서가 정해져야 합니다. order_id(PK)는 됩니다. "시각순"으로 보여 주려면 같은 시각이 있을 수 있으므로 (ordered_at, order_id) 쌍으로 비교하고(WHERE (ordered_at, order_id) < (…, …)), 같은 순서의 복합 인덱스를 둡니다. 실험 DB에서 이 방식도 몇 쪽만 읽었습니다. ordered_at만으로 비교하면 같은 시각의 행이 건너뛰어지거나 중복됩니다.
  • "목록 15페이지로 바로 가기"가 안 됩니다. 이전·다음만 됩니다. 번호 이동이 꼭 필요하면 OFFSET을 쓰되 뒤쪽 페이지는 제한(예: 목록 100페이지까지)합니다.
  • 대신 목록을 보는 중에 새 주문이 들어와도 안정적입니다. OFFSET은 새 행이 앞에 끼면 다음 목록 페이지에서 같은 행이 또 보이거나 빠지지만, keyset은 "이 번호 이후"라 흔들리지 않습니다.

COUNT(*) — 세는 것도 읽는 일이다

"총 N건, 목록 5만 페이지" 표시를 위한 SELECT COUNT(*) FROM orders는 행 1,000,000개를 읽는 풀스캔 9,141쪽이었습니다. WHERE status = '픽업'을 붙여도 같았습니다. PostgreSQL은 행마다 "내 트랜잭션에게 보이는 행인가"를 확인해야 해서(8장의 주제) 전체 건수를 어디에 적어 두고 읽지 못합니다. 정리가 잘 된 표에서는 가장 작은 인덱스만 훑는 index-only scan(페이지 4의 접힌 상자)이 쪽 수를 줄여 줄 수도 있지만, 행 수에 비례해 읽는 것은 같습니다. 대안은 필요에 따라 고릅니다.

파티셔닝(개념) — 지우는 일을 "표 하나 버리기"로

-- 월별 파티션 (실험 DB에서 실행해 확인)CREATE TABLE orders_p (
    order_id    INTEGER     NOT NULL,
    ordered_at  TIMESTAMPTZ NOT NULL,
    status      TEXT        NOT NULL,
    PRIMARY KEY (order_id, ordered_at)
) PARTITION BY RANGE (ordered_at);
CREATE TABLE orders_p_2026_08 PARTITION OF orders_p
    FOR VALUES FROM ('2026-08-01 00:00+09') TO ('2026-09-01 00:00+09');
-- 기간 조건을 주면 해당 월 파티션만 읽는다. 오래된 달은 통째로 버린다
ALTER TABLE orders_p DETACH PARTITION orders_p_2026_08;
DROP TABLE orders_p_2026_08;

이렇게 큰 표를 기간 같은 기준으로 나누어 쓰는 것이 파티셔닝입니다. PARTITION BY RANGE (ordered_at)은 행을 시각 범위에 따라 서로 다른 물리 표(파티션)에 넣습니다. 이득은 둘입니다. 기간 조건으로 조회하면 해당 파티션만 읽고(실험의 계획에는 조회한 달의 파티션 하나만 나왔습니다), 오래된 달은 수백만 행을 DELETE하는 대신 표 하나를 떼어 버립니다(DETACH, DROP). 함정은 v5에 그대로 적용됩니다. 첫째, PK를 order_id만으로 만들면 unique constraint on partitioned table must include all partitioning columns 오류로 거부됩니다. 둘째, PK가 (order_id, ordered_at)이 되면 order_line 등이 orders (order_id)를 가리키는 외래키는 there is no unique constraint matching given keys for referenced table로 막힙니다. 자식 표도 ordered_at을 들고 다니도록 바꿔야 하는 스키마 변경이라 지금은 하지 않습니다. 9장에서 다시 본다

오래된 행을 보관용 표로 옮기고 원본에서 지우는 것이 아카이브입니다.

  • 자식 먼저. 라인·옵션·할인이 orders를 가리키므로 같은 기간의 자식 행을 먼저 옮기고 orders를 마지막에 지웁니다(옮기는 쪽은 한 트랜잭션).

  2. 복합 인덱스는 선두 열 규칙이 전부입니다. 등호 조건 열을 앞에, 범위·정렬 열을 뒤에 두고, 열에 함수를 씌우지 말고 범위로 씁니다.
  3. 선택도가 높은(드문 값을 고르는) 조건에서만 듣습니다. 95%를 고르는 값에서는 인덱스가 있어도 풀스캔이고, 5%에서도 이득이 없었습니다. 드문 값은 부분 인덱스로 담습니다. 인덱스는 쓰기와 공간으로 값을 치르므로 조회 목록에 이름이 있는 것만 만듭니다.
  4. 인덱스는 "찾기"를 줄일 뿐 "더하기"는 못 줄입니다. 그래서 요약 테이블(D4 상환)을 얹었고, 이것은 정규화를 한 뒤에 일부러 되돌린 것입니다. 원본이 진실이고, 갱신 경로는 하나(멱등한 배치)로 두고, 어긋남을 찾는 점검을 같이 둡니다.
  5. 목록은 OFFSET 대신 keyset으로, 개수는 필요한 만큼만 셉니다. 오래된 데이터는 보존 정책을 먼저 정하고 파티셔닝·아카이브를 고릅니다. 결과가 스키마 v5.1(표 18개, 인덱스 5개 추가)이고, D2는 9장, D5와 동시성(요약 갱신, 잔액, 쿠폰)은 8장이 이어받습니다.

퀴즈 3 — 페이지 9의 두 갱신 문장이 하는 일

  • (A) 배치: 한 트랜잭션 안에서 그날 행을 DELETE한 뒤, 원본(주문·라인·옵션·할인)에서 그날 전체를 다시 집계해 INSERT합니다.
  • (B) 증분: 주문 하나의 값으로 INSERT ... ON CONFLICT (sales_date) DO UPDATE SET order_count = daily_sales.order_count + EXCLUDED.order_count, ...를 실행한다(그날 행이 있으면 거기에 더한다).

WHERE member_id = 77 ORDER BY ordered_at DESC LIMIT 10을 돕는 인덱스를 (ordered_at, member_id) 순서로 만들었습니다. 이 순서가 (member_id, ordered_at)보다 나쁜 이유는 무엇일까요?

  1. 복합 인덱스는 값 종류가 많은 열을 항상 뒤에 두어야 하는 규칙이 있기 때문이다
  2. 복합 인덱스는 앞 열만 쓰는 구조라서 열 순서를 바꿔도 읽는 페이지 수가 같기 때문이다
  3. 선두 열이 ordered_at이라 member_id 조건으로는 그 회원의 구간으로 곧장 갈 수 없기 때문이다

덧붙이면, ORDER BY ordered_at DESC를 위해 내림차순 인덱스를 따로 만들 필요는 없습니다. 실험 계획에는 Index Scan Backward가 나왔습니다. 정렬된 나무는 앞에서도 뒤에서도 읽을 수 있기 때문입니다. 방향이 다른 정렬을 섞어야(a ASC, b DESC) 할 때만 열마다 방향을 적습니다.

orders.status(값 5종)에 일반 인덱스를 걸었습니다. WHERE status = '픽업'(전체의 95%)을 실행하면 어떻게 될까요?

  1. DB가 인덱스를 두고도 풀스캔을 고를 수 있다
  2. 인덱스를 써서 풀스캔보다 빨라진다
  3. 값 종류가 적은 열의 인덱스는 에러가 난다

값 종류가 적다고 해서 늘 쓸모없는 것은 아닙니다. 분포가 한쪽으로 쏠려 있고 드문 값을 찾는다면 부분 인덱스로 큰 이득을 봅니다(주방 화면은 16KB로 2쪽). 반대로 payment(카드 70%, 현금 30%)처럼 두 값이 비슷하게 흔하면 어느 쪽을 찾아도 선택도가 낮아서 인덱스가 듣지 않기 쉽습니다. 값 종류보다 "내가 찾는 값이 얼마나 흔한가"입니다.

일 매출 요약을 갱신하는 작업이 네트워크 오류로 같은 날에 두 번 실행되었습니다. 결과가 틀려지지 않는 것은 어느 방식일까요?

  1. 주문이 끝날 때마다 ON CONFLICT DO UPDATE로 그날 행에 증감을 더한다
  2. 그날 행을 지우고 원본에서 그날 전체를 다시 계산해 넣는다
  3. 둘 다 안전하다. 키가 같으면 한 행뿐이기 때문이다

"같은 요청을 두 번 받아도 한 번 받은 것과 같게" 만드는 성질을 멱등이라 하고 결제 API의 멱등 키가 같은 이유로 생겼습니다. 더하기 방식을 쓰려면 "이 주문은 이미 반영했다"를 기록하는 장치(처리한 주문 번호 표)가 따로 필요하고, 그 장치와 요약의 갱신을 한 묶음으로 만드는 것이 8장의 트랜잭션 주제입니다.

3장은 "총액은 파생값이라 저장하지 않는다"고 결정했습니다. 일 매출 요약 테이블이 이 결정과 모순이 아닌 이유는 무엇일까요?

  1. 원본은 정규형 그대로이고, 다시 만들 수 있는 파생 표를 측정 뒤에 일부러 얹은 것이다
  2. 3장이 파생값을 저장하지 않기로 한 결정이 틀렸다는 뜻이다
  3. 요약 테이블은 보고용 사본이라 정규화 규칙에서 면제되기 때문이다

이 구분이 중요해지는 때는 원본을 지울 때입니다. 페이지 11처럼 오래된 주문을 아카이브로 옮겨 지우면 그날의 요약은 "원본에서 다시 만들 수 있는 사본"에서 유일한 기록으로 바뀝니다. 그때는 요약이 원본의 지위를 가지므로 보존 정책과 백업이 요약에도 같은 무게로 적용되어야 합니다.

-- 모범답안: 한 행 = 그 날(서울 시각)·그 메뉴의 판매 수량CREATE TABLE daily_menu_sales (
    sales_date  DATE    NOT NULL,
    menu_id     INTEGER NOT NULL,
    quantity    INTEGER NOT NULL CHECK (quantity >= 1),
    PRIMARY KEY (sales_date, menu_id)
);

-- 하루치 (기간의 시작·끝만 바꿔 다시 실행한다. 먼저 그 날의 행을 DELETE)
INSERT INTO daily_menu_sales (sales_date, menu_id, quantity)
SELECT (o.ordered_at AT TIME ZONE 'Asia/Seoul')::date AS sales_date,
       ol.menu_id, SUM(ol.quantity)
FROM   orders AS o
JOIN   order_line AS ol ON ol.order_id = o.order_id
WHERE  o.status <> '취소'
  AND  o.ordered_at >= TIMESTAMPTZ '2026-03-04 00:00+09'
  AND  o.ordered_at <  TIMESTAMPTZ '2026-03-05 00:00+09'
GROUP BY sales_date, ol.menu_id;
-- 3/4 → (1, 3) (2, 1) (3, 1): 아메리카노 3잔, 카페라떼 1잔, 치즈케이크 1개

1. order_line.menu_id 인덱스는 도움이 안 됩니다. 메뉴 하나가 라인의 20%를 차지해 인덱스를 써도 풀스캔과 읽는 양이 같고, 날짜 조건은 orders에 있어 orders_ordered_at_idx가 기간의 주문을 고른 뒤 라인은 PK로 따라가는 것이 이미 최선입니다. 이 조회는 기간이 길면 더하는 양이 문제라 인덱스가 아니라 요약의 일입니다.

2. 판단 근거는 측정입니다. 필요한 기간(월간 추이)으로 이 조회의 읽은 페이지와 시간을 재고, 하윤이 얼마나 자주 보며 얼마나 기다릴 수 있는지와 비교합니다. 하루치만 보는 리포트였다면 인덱스로 끝났을 것입니다. 한 행은 "하루·메뉴 하나", PK는 (sales_date, menu_id)로 같은 조합이 두 행이 되는 것을 DB가 막습니다. 원본에서 만든 값이라 menu로의 외래키는 걸지 않았습니다(원본이 이미 지킵니다).

3. 이번에는 행이 곱해지지 않습니다. 라인 표 하나만 조인하고 옵션·할인은 이 질문에 필요 없어 읽지 않기 때문입니다. 곱해지는 문제는 "여럿"인 자식 표 둘 이상을 한꺼번에 조인할 때 생깁니다(6장 페이지 9: 라인 2개·할인 2건인 주문 401이 4행으로 불어나 소계 16100이 32200이 되었습니다). 이번 요구가 "수량"이 아니라 "옵션 포함 매출"이었다면 페이지 8처럼 자식 표마다 주문별로 먼저 합해야 합니다.

4. 배치를 고릅니다. 그날 행을 지우고 다시 계산하므로 두 번 실행해도 같고(멱등), 판매 수량이 0이 된 날의 옛 행도 지워집니다. 트리거·앱의 증분 갱신은 두 번 실행하면 수량이 두 번 더해지고, 그날 주문이 모두 같은 날의 행들에 써서 쓰기가 몰립니다(8장).

흔한 오답 1 — order_line (menu_id) 인덱스만 걸고 끝냅니다. 위 1번의 이유로 이 리포트는 빨라지지 않습니다.

흔한 오답 2 — PK 없이 날마다 쌓기만 합니다. 같은 날을 다시 계산하면 행이 두 벌이 되어 수량이 두 배로 읽히고, "한 행 = 하루·메뉴 하나"를 아무도 지켜 주지 않습니다.

흔한 오답 3 — menu 표에 sold_total 같은 열을 더해 거기에 누적합니다. 날짜별 추이를 잃고, 한 열을 모든 주문이 고치므로 쓰기가 몰리며, 값이 어긋났을 때 원본으로 검증할 기준이 없습니다.
