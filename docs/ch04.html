제약조건: 규칙을 DB에 맡기기

3장까지 v2는 구조가 옳다는 것을 확인했습니다. 그러나 구조가 옳다는 것과 들어오는 값이 옳다는 것은 다른 이야기입니다. 이 장은 "수량은 1 이상이다" 같은 규칙을 누가 지킬지 정하고, DB에 맡길 수 있는 것은 맡기는 장입니다. 끝에서 스키마는 v3가 됩니다.

개발자

키오스크 앱은 수량 0을 못 넣게 만들었어요. 이제 안전하겠죠?

C++ 비유와 그 한계

DB 제약은 모든 호출자가 반드시 지나가는 세터(setter)의 검사와 닮았습니다. 값을 바꾸는 길이 그 하나뿐이면 검사를 빼먹을 수가 없습니다. 다만 C++의 세터 검사는 같은 프로그램 안에서만 강제됩니다. DB 제약은 프로그램이 달라도, 언어가 달라도, 사람이 손으로 입력해도 강제됩니다. 또 세터가 예외를 던지면 호출한 쪽이 처리해야 하듯, 제약 위반도 오류로 앱에 돌아옵니다. 그 오류를 사용자에게 어떻게 보여 줄지는 여전히 앱의 일입니다(0장 퀴즈가 남긴 질문입니다).

주장내용
DB 제약을 지지앱이 몇 개든, 버그가 있든, 사람 손이 들어가든 마지막 방어선이 된다. 또 앱에서 "이미 있나 조회한 뒤 없으면 저장"하면 두 요청이 동시에 검사를 통과할 수 있지만, DB 제약은 검사와 저장이 한 곳에서 일어난다. 8장에서 다시 본다
앱 검증을 지지규칙이 자주 바뀌면 스키마 변경이 무겁다. 오류 메시지가 불친절하다. 규칙이 DB와 앱 두 곳에 있으면 서로 어긋날 수 있다. 일부 조직은 대규모 운영 사정으로 외래키를 일부러 쓰지 않는다.
이 교재의 입장DB가 싸게 표현할 수 있는 규칙(한 행·키·참조)은 DB에 맡기고, 그 밖의 규칙은 앱과 트랜잭션이 지킨다. 앱의 검사는 친절을 위해, DB 제약은 최후 방어선으로 둘 다 둔다. 중복이 아니라 역할 분담이다.

NULL — 값이 없다는 표시, 그리고 세 가지 함정

2장에서 비회원 주문은 orders.member_id를 비워 두는 것으로 표현했습니다. 그 "비어 있음"이 NULL입니다. v2의 orders에 비회원 주문 106이 있다고 가정해 봅시다(정본 데이터에는 없는, 설명용 행입니다).

이 표에 네 가지를 물어봅니다. 결과를 예상한 뒤 주석을 보세요.

-- NULL 을 만난 조회 네 가지SELECT order_id FROM orders WHERE member_id = NULL;    -- 0행
SELECT order_id FROM orders WHERE member_id IS NULL;   -- 106
SELECT order_id FROM orders WHERE member_id <> 1;      -- 102 (106 은 빠진다)
SELECT COUNT(*), COUNT(member_id) FROM orders;         -- 3, 2
  1. 1행 = NULL은 아무 행도 고르지 못합니다. 106의 member_id가 NULL인데도 그렇습니다.
  2. 2행 NULL인지 묻는 문법은 따로 있습니다. IS NULL, 반대는 IS NOT NULL입니다.
  3. 3행 <>는 "같지 않다"입니다. 그런데 NULL인 106은 "1이 아니다"에도 해당하지 않아서 결과에서 사라집니다. 비회원 주문이 조용히 빠지는 이 버그는 실무에서 매우 흔합니다.
  4. 4행 COUNT(*)는 행 수(3)를, COUNT(member_id)는 그 열이 NULL이 아닌 행 수(2)를 셉니다. SUM, AVG도 NULL인 칸은 건너뜁니다.

이 세 가지 함정에는 같은 원인이 있습니다. 아래 이름 붙이기에서 설명합니다.

이름 붙이기

NULL은 값이 없다, 또는 알 수 없다는 표시입니다. 0도, 빈 글자 ''도 아닙니다. NULL과의 비교는 참도 거짓도 아닌 "알 수 없음"이 되고, WHERE는 참인 행만 남깁니다. 이런 식의 셈법을 3값 논리라고 합니다. "알 수 없는 값"과 "1"이 같은지는 알 수 없고, "알 수 없는 값" 둘이 같은지도 알 수 없습니다. 그래서 NULL = NULL도 참이 아닙니다.

C++의 비유는 여기서 틀립니다

C++에서는 nullptr == nullptr이 참이고 비어 있는 std::optional 둘도 같다고 나옵니다. SQL의 NULL은 값이 아니라 "모른다"는 표시라서 비교하면 참이 되지 않습니다. (NaN끼리의 비교가 참이 되지 않는 것과 조금 닮았지만, SQL은 거짓이 아니라 "알 수 없음"으로 셈합니다.) NULL끼리도 같다고 보고 싶으면 IS NOT DISTINCT FROM이라는 비교 연산자가 따로 있습니다.

더 깊이 — NOT IN 과 NULL, 그리고 다른 DB의 빈 글자

x NOT IN (1, NULL)은 어떤 x에 대해서도 참이 되지 않습니다. "1도 아니고 NULL(모르는 값)도 아닌가"에서 뒷부분이 알 수 없음이 되기 때문입니다. 그래서 WHERE menu_id NOT IN (SELECT menu_id FROM order_line)처럼 서브쿼리의 결과에 NULL이 하나라도 섞이면 조회가 통째로 빈 결과를 돌려줍니다. 이 교재의 order_line.menu_id는 NOT NULL이라 안전하지만, NULL이 들어올 수 있는 열이라면 NOT EXISTS로 쓰는 것이 안전합니다.

또 하나, Oracle은 빈 글자 ''를 NULL로 취급합니다. PostgreSQL은 둘을 구별합니다. 이 교재는 PostgreSQL 기준이라 앞의 표가 맞지만, 다른 DB로 옮길 때는 이 차이를 확인해야 합니다.

열의 타입은 가장 기본적인 제약입니다. INTEGER 열에 글자를 넣으려 하면 DB가 거부합니다. 그래서 타입을 고르는 것은 "이 열에 들어올 수 있는 값의 범위를 정하는" 설계 결정입니다. v2의 열 몇 개를 다시 봅시다. 0~2장에서는 이유를 미뤄 두었습니다.

금액: float 이 안 되는 이유

같은 덧셈을 두 가지 타입으로 해 봅니다. 값::타입은 PostgreSQL에서 값의 타입을 바꾸는 문법이고, float8은 C++의 double과 같은 8바이트 부동소수점입니다.

-- 0.1 + 0.2 가 0.3 인가?SELECT 0.1::float8  + 0.2::float8  = 0.3::float8;    -- f (거짓)
SELECT 0.1::numeric + 0.2::numeric = 0.3::numeric;   -- t (참)

C++에서 0.1 + 0.2 == 0.3이 거짓인 것과 같은 이유입니다. 부동소수점은 2진수라 0.1을 정확히 담지 못합니다. 금액을 이 타입으로 저장하면 합계가 1원씩 어긋나거나 "같은 금액"의 비교가 실패합니다. 그래서 선택지는 둘입니다.

  • 원 단위 정수(INTEGER) — 동백커피의 선택. 정확하고 단순합니다. INTEGER는 약 ±21억까지라 동백커피의 금액에는 충분합니다.
  • NUMERIC(p, s) — 정확한 십진수입니다. p는 전체 자릿수, s는 소수점 아래 자릿수(NUMERIC(10, 2)는 소수 둘째 자리까지 8자리 정수부)입니다. 소수 단가, 외화, 세금을 나눠 계산해야 하는 경우에 씁니다. 정확한 대신 정수보다 느리고 계산 규칙(반올림)을 정해야 합니다.

금액 열에 float 을 쓰지 않습니다

SQL 책의 예제에서도 price FLOAT를 가끔 볼 수 있지만, 돈은 정확해야 하는 값입니다. 오차는 합계·비교·정산 모든 곳에서 조용히 쌓입니다.

더 깊이 — TEXT 와 VARCHAR(n), 그리고 다른 DB에서는

PostgreSQL에서는 TEXT와 VARCHAR(n)의 성능 차이가 없습니다. VARCHAR(n)의 의미는 "n자를 넘으면 거부"라는 길이 규칙 하나뿐입니다. 길이 한도가 업무 규칙이면(예: 메뉴 이름은 30자까지) VARCHAR(30)이나 CHECK (length(name) <= 30)으로 적고, 그렇지 않다면 TEXT로 충분합니다. "습관적으로 VARCHAR(255)"는 근거 없는 한도입니다.

다른 DB에서는 다릅니다. MySQL 등에서는 TEXT와 VARCHAR의 저장·인덱스 취급이 달라서 옮길 때 확인이 필요합니다. 이 교재는 PostgreSQL 기준입니다. 번호 열(INTEGER)은 주문이 수십억 건을 넘을 일이 없다고 보고 그대로 두지만, 그럴 가능성이 있는 열은 BIGINT를 씁니다.

NOT NULL 과 DEFAULT — 비워도 되는 열은 이유를 댈 수 있어야 한다

화면 2에서 NULL은 쓰기는 쉬워도 조회에서 함정을 만든다는 것을 보았습니다. 그런데 열에 아무 선언도 하지 않으면 기본값은 "NULL 허용"입니다. 그래서 설계의 원칙은 이렇습니다.

원칙

NOT NULL이 기본이고, NULL을 허용하는 열은 이유를 문장으로 댈 수 있어야 합니다. 기본키는 자동으로 NOT NULL입니다.

v2의 열을 이 원칙으로 훑으면 NULL을 허용하는 열은 orders.member_id 하나입니다. 이유는 "비회원 주문은 주인이 없다"입니다. 나머지 열은 모두 NOT NULL로 이미 선언되어 있습니다.

비회원 주문을 NULL 없이 표현하는 대안도 있습니다. 동료가 제안할 법한 세 가지를 비교합니다.

DEFAULT는 INSERT에서 그 열을 적지 않았을 때 DB가 대신 넣어 줄 값입니다. 주문 시각이 대표적입니다. v3에서 orders.ordered_at에 붙입니다.

ordered_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()

-- ordered_at 을 적지 않았다: DB 가 지금 시각을 채운다
INSERT INTO orders (order_id, member_id, payment, barista)
VALUES (106, NULL, '카드', '지호');
  • NOW()는 현재 시각을 돌려주는 함수이고, 정확히는 현재 트랜잭션이 시작된 시각입니다.
  • 이렇게 하면 시계를 DB 서버 하나로 통일할 수 있습니다. 키오스크가 여러 대이고 시계가 조금씩 다르면 주문 순서가 뒤바뀔 수 있습니다.
  • 이 INSERT는 member_id에 NULL을 명시했습니다. 비회원 주문이라는 뜻이 코드에 드러납니다.

DEFAULT 의 함정 두 가지

  • DEFAULT 는 "열을 적지 않았을 때"만 작동합니다. 열 이름을 적고 값으로 NULL을 넣으면 DEFAULT가 아니라 NULL이 들어가려다 NOT NULL 위반으로 거부됩니다.
  • DEFAULT 는 규칙이 아니라 편의입니다. 나중에 UPDATE로 다른 값을 넣는 것은 막지 못합니다. 값을 제한하는 것은 화면 7의 CHECK입니다.

DEFAULT가 더 중요해지는 경우가 하나 있습니다. 이미 행이 들어 있는 표에 NOT NULL 열을 새로 더할 때, 기존 행들은 그 열에 넣을 값이 없으므로 DEFAULT가 있어야 합니다. 화면 6에서 실제로 그렇게 합니다. 운영 중인 표에서 이 작업을 안전하게 하는 방법은 9장의 주제입니다. 9장에서 다시 본다

UNIQUE 가 못 막는 것 세 가지

UNIQUE 는 "글자가 완전히 같은가"만 봅니다

  • 표기 차이. '아메리카노 '(끝 공백)는 '아메리카노'와 다른 값이라 통과합니다. 1장이 본 "끝 공백" 문제 그대로입니다. 영문 메뉴라면 'Americano'와 'americano'도 다른 값입니다. 해결은 화면 7의 CHECK로 공백을 막는 것입니다.
  • NULL. NULL은 여러 개 넣을 수 있으므로, UNIQUE 열은 대개 NOT NULL과 함께 씁니다. (PostgreSQL 15부터는 UNIQUE NULLS NOT DISTINCT로 NULL끼리도 중복으로 보게 할 수 있습니다.)
  • 내린 메뉴의 이름. 화면 6에서 다룰 판매중지(메뉴를 지우지 않고 "팔지 않음" 표시만 하는 방식)에서는 행이 남아 있으니 그 이름은 다른 새 메뉴가 쓸 수 없습니다. "판매중지가 아닌 메뉴끼리만 겹치지 않게" 하는 방법도 있지만(조건부 UNIQUE 색인) 이 교재에서는 다루지 않습니다.

전화번호: UNIQUE 를 우회하는 표기

2장의 member.phone 규칙은 "같은 번호로 두 번 가입할 수 없다"였습니다. 그런데 010-1111-2222와 01011112222는 글자가 달라서 둘 다 들어갑니다. UNIQUE가 의미를 가지려면 표기가 하나여야 합니다. 해법은 두 가지이고 둘 다 씁니다.

  • 앱이 정규화: 사용자가 어떻게 입력하든 하이픈 형식으로 바꿔서 저장합니다. 사용자 친화적인 쪽은 앱입니다.
  • DB가 형식을 강제: 형식에 맞지 않으면 저장하지 않습니다(화면 7의 CHECK). 스크립트나 직접 수정이 형식을 깨는 것을 막는 최후 방어선입니다.

이 교재는 phone을 010-1111-2222 같은 하이픈 형식으로 통일합니다. 그 CHECK는 화면 7에서 씁니다.

CHECK — 수량은 1 이상이다 (C2)

화면 1의 입력 중 수량·가격·이름 표기·결제수단·전화번호 형식은 모두 "한 행의 값이 지켜야 할 조건"에 관한 규칙이었습니다. 이런 규칙을 선언하는 것이 CHECK입니다. 한 행의 값이 조건식을 만족해야 저장하고, 만족하지 않으면 그 INSERT나 UPDATE를 거부합니다.

-- C2: 수량은 1 이상quantity  INTEGER NOT NULL CHECK (quantity >= 1)

INSERT INTO order_line (order_id, menu_id, quantity) VALUES (101, 2, 0);
-- ERROR:  new row for relation "order_line" violates check constraint
--         "order_line_quantity_check"
-- DETAIL:  Failing row contains (101, 2, 0).

경계값은 업무가 정합니다. 0장 퀴즈가 말한 "이상"의 경계입니다. v3의 CHECK를 모아 봅니다.

열조건경계를 이렇게 정한 이유
order_line.quantity>= 1수량 0인 라인은 "주문하지 않았다"는 뜻이라 저장할 이유가 없다
menu.price>= 00을 허용한다. 무료 메뉴가 생길 수 있고, 5장에서 가격 0원 옵션이 나온다. > 0이라 썼다면 그때 제약을 고쳐야 한다
menu.name<> '' 이고 = btrim(name)0장이 미룬 빈 글자와 1장의 끝 공백을 막는다(아래)
member.phone정규식 형식화면 5의 표기 문제(아래)
-- 글자 열의 CHECK 두 가지CHECK (name <> '' AND name = btrim(name))
CHECK (phone ~ '^01[0-9]-[0-9]{3,4}-[0-9]{4}$')
  • 1행 btrim(name)은 글자 양끝의 공백을 없앤 결과를 돌려주는 함수입니다(탭·줄바꿈은 지우지 않습니다). 원래 값과 같다는 것은 양끝에 공백이 없다는 뜻이고, <> ''와 함께면 "빈 글자"와 "공백만 있는 글자"도 막힙니다(공백만 있는 글자는 btrim 결과가 ''라서 원래 값과 달라집니다).
  • 2행 ~는 정규식에 맞는지 묻는 연산자입니다. 정규식 ^01[0-9]-[0-9]{3,4}-[0-9]{4}$는 "01과 숫자 한 자리, 하이픈, 숫자 3~4자리, 하이픈, 숫자 4자리"가 글자 전체라는 뜻입니다. 010-1111-2222는 통과하고 01011112222는 거부됩니다. 읽기만 하면 충분하고, 이 교재가 정규식을 가르치지는 않습니다.
  • 한계도 있습니다. 유선 번호나 해외 번호는 이 형식으로 받을 수 없습니다. 요구가 바뀌면 제약을 바꿔야 합니다. 그것이 DB 제약의 가격입니다(화면 1의 반대 의견).

CHECK 는 조건이 NULL이면 통과합니다

화면 2의 3값 논리를 떠올리세요. quantity가 NULL이면 NULL >= 1은 알 수 없음이고, CHECK는 "거짓인 행"만 거부하므로 통과합니다. 그래서 CHECK가 있는 열은 NOT NULL과 짝으로 써야 합니다. order_line.quantity에 이미 NOT NULL이 있었던 이유입니다.

CHECK 가 못 하는 것

  • 같은 행의 열만 볼 수 있습니다. 다른 행이나 다른 표를 조회(서브쿼리)하는 조건은 쓸 수 없습니다. "이 주문의 라인이 몇 개인가"를 CHECK로 쓰지 못하는 이유이고, 화면 9에서 다룹니다.
  • 이전 값을 모릅니다. UPDATE에서 CHECK가 보는 것은 새 값뿐이라 "접수에서 곧바로 픽업으로"처럼 값이 바뀌는 순서는 막지 못합니다(화면 8).
  • 이미 행이 들어 있는 표에 CHECK를 더하면 기존 행 전체가 검사됩니다. 위반 행이 있으면 제약을 더할 수 없습니다(9장의 마이그레이션).

글자로 고르는 열 — 결제수단과 주문 상태 (C7)

결제수단(orders.payment)은 '카드', '현금' 중 하나입니다. 화면 1의 5번이 보여 준 것처럼 글자로 적는 열은 'card', '카드 ' 같은 표기 흔들림이 생깁니다. 이처럼 값이 정해진 목록 중 하나인 열을 지키는 방법은 셋입니다.

여기에 주문 상태가 더해집니다. 0장의 흐름(주문 → 제조 → 픽업)을 지호가 주문마다 기록하려면 orders에 상태를 담을 열이 필요합니다. C7의 규칙은 이렇습니다. 접수 → 제조중 → 완료 → 픽업 순으로만 가고, 접수와 제조중에서만 취소할 수 있다.

v3의 결정: status와 payment 모두 CHECK로 합니다. 이유는 값의 수가 적고(다섯 개, 두 개) 바뀌는 일이 드물며, 값 목록이 앱 코드와 같은 문장으로 DDL에 그대로 드러나기 때문입니다. 값이 자주 늘거나 값에 속성이 붙으면 별도 표로 옮깁니다. (결제수단에 간편결제가 들어와 종류마다 수수료율이 붙는다면 별도 표가 맞습니다.) 값은 한글 그대로 쓰지만, 실무에서는 'RECEIVED' 같은 영문 코드를 쓰는 조직도 많습니다.

-- v3 의 orders.payment 와 statuspayment  TEXT  NOT NULL CHECK (payment IN ('카드', '현금')),
barista  TEXT  NOT NULL,
status   TEXT  NOT NULL DEFAULT '접수'
         CHECK (status IN ('접수', '제조중', '완료', '픽업', '취소'))

새 주문은 status를 적지 않으면 DEFAULT에 따라 '접수'로 시작합니다. CHECK는 '제조 중'(띄어쓰기)이나 'cooking' 같은 목록 밖의 값을 막습니다.

전이 순서는 앱의 일

그런데 CHECK가 막지 못하는 것이 있습니다. 화면 7에서 말했듯 CHECK는 새 값만 보기 때문에 '접수'에서 곧바로 '픽업'으로 바꾸는 UPDATE도 목록 안의 값이라 통과합니다. 허용되는 전이는 다음과 같습니다.

이 표는 앱이 지킵니다. 그런데 "현재 상태를 읽고 → 가능한지 판단하고 → 쓴다"를 따로 하면 그 사이에 다른 요청이 끼어들 수 있으니, 현재 상태를 조건에 넣은 UPDATE로 씁니다.

-- 앱이 전이를 지키는 방법: 이전 상태를 조건에 넣는다UPDATE orders SET status = '제조중'
WHERE  order_id = 106 AND status = '접수';            -- 갱신된 행 수가 1 이면 성공

UPDATE orders SET status = '취소'
WHERE  order_id = 106 AND status IN ('접수', '제조중'); -- 0 이면 이미 지나간 주문
  • 갱신된 행이 1이면 "접수였던 주문이 제조중이 되었다"이고, 0이면 그 주문이 이미 다른 상태였다는 뜻입니다. 앱은 갱신된 행 수를 확인해 "이미 제조가 시작되어 취소할 수 없습니다" 같은 안내를 합니다.
  • 이 습관이 8장에서 동시에 들어오는 요청을 막는 조건부 UPDATE의 출발점입니다. 8장에서 다시 본다
  • PostgreSQL에는 트리거(특정 변경이 일어날 때 자동으로 실행되는 DB 안의 프로그램)로 전이를 DB 안에서 지키는 방법도 있지만, 이것은 선언이 아니라 프로그램 코드이고 DB마다 다릅니다. 이 교재는 앱에 둡니다.

그래서 나중에 무슨 문제가 되는가

status 열은 지금 상태만 담습니다. "몇 시에 제조중이 되었는가"는 알 수 없습니다. 상태가 바뀐 시각과 이력이 필요해지면 그것을 담는 표를 따로 설계해야 합니다. 또 취소된 주문은 지워지지 않고 남으므로, 매출을 셀 때는 status를 조건에 넣는 것을 잊으면 안 됩니다.

DB로 못 막는 규칙 — 주문은 라인이 1개 이상이다 (C1)

C1을 DB에 맡겨 봅시다. 먼저 화면 1의 7번이 왜 저장되는지 확인합니다.

-- 라인 없는 주문이 저장된다INSERT INTO orders (order_id, member_id, payment, barista)
VALUES (107, 1, '카드', '지호');
-- 성공. order_line 에는 107 이 없다.

-- 이런 주문을 찾아내는 점검 조회
SELECT o.order_id
FROM   orders AS o
LEFT JOIN order_line AS ol ON ol.order_id = o.order_id
WHERE  ol.order_id IS NULL;      -- 107
  • 1~2행의 INSERT는 성공합니다. 어떤 제약도 "이 주문에 라인이 있는가"를 묻지 않기 때문입니다.
  • 점검 조회의 LEFT JOIN은 짝이 없는 왼쪽 행도 남기고 오른쪽 열을 NULL로 채우는 JOIN입니다. 그래서 화면 2에서 배운 IS NULL로 "라인이 없는 주문"을 골라낼 수 있습니다.

DB에 맡기려는 시도는 세 가지가 있고, 모두 막힙니다.

시도왜 안 되는가
orders에 CHECK로 "라인 수 >= 1"화면 7: CHECK는 그 행의 열만 봅니다. 다른 표의 행 수를 세는 서브쿼리는 쓸 수 없습니다
orders가 첫 라인을 NOT NULL 외래키로 가리키게닭과 달걀입니다. 주문이 있으려면 라인이 먼저 있어야 하고, 라인은 주문을 가리키므로 주문이 먼저 있어야 합니다
"저장 순간마다 라인이 1개 이상"으로 강제주문을 저장하고 그 다음에 라인을 넣는 것이 자연스러운 순서입니다. 그 사이의 순간에는 라인이 0개인 주문이 있어야 합니다. 규칙은 "매 순간"이 아니라 "한 묶음이 끝났을 때"의 상태에 대한 것입니다

세 번째가 본질입니다. 이 규칙은 행 하나가 아니라 "여러 행이 모인 결과"에 대한 것이고, "언제 검사하는가"가 저장 한 번이 아니라 여러 저장의 묶음 단위입니다. CHECK, 외래키, UNIQUE 같은 선언만으로는 표현할 수 없습니다.

"DB로는 절대 못 한다"는 아닙니다

PostgreSQL에는 묶음이 끝나는 시점까지 검사를 미루는 제약 트리거(CONSTRAINT TRIGGER, 검사를 미룰 수 있는 트리거)가 있어서 비슷하게 만들 수는 있습니다. 하지만 그것은 선언이 아니라 DB 안에 넣는 프로그램 코드입니다. DB마다 다르고, 테스트하고 관리할 대상이 늘어납니다. 이 교재는 이 규칙을 앱이 지킨다고 정리합니다.

앱이 지킨다는 것은 구체적으로 이렇습니다.

  1. 주문을 만드는 코드가 라인 목록이 비어 있지 않은지 먼저 확인합니다.
  2. 주문 한 건과 그 라인들을 하나의 트랜잭션(0장에서 본 "전부 성공 아니면 전부 취소"의 묶음)으로 저장합니다. 중간에 실패하면 주문도 취소됩니다.
  3. 라인을 지우는 코드도 마지막 라인을 지우면 그 주문의 라인이 0개가 되는지 확인합니다(반대편 구멍입니다).
  4. 위의 점검 조회를 주기적으로 돌려 구멍이 없는지 봅니다.

이 트랜잭션을 동시에 여러 요청이 들어와도 안전하게 만드는 방법이 8장의 주제이고, D5(C1의 빚)를 그때 갚습니다. 8장에서 다시 본다

DB에 못 맡기는 규칙의 모양

C1만의 문제가 아닙니다. 다음 모양의 규칙은 선언만으로는 안 됩니다.

  • 여러 행을 세거나 합산하는 규칙(라인이 1개 이상, 재고 합계, 포인트 잔액)
  • 다른 표의 상태에 따라 달라지는 규칙(판매중지 메뉴는 새 주문에 못 담는다)
  • 값이 바뀌는 순서에 대한 규칙(주문 상태 전이)

이런 규칙은 뒤의 장에서 계속 만납니다. 그때마다 "이것은 선언할 수 있는가, 아니면 앱과 트랜잭션의 몫인가"를 먼저 묻는 습관이 이 장의 결론입니다.

스키마 v3 — 제약조건 표 정리

이 장에서 고른 것을 한 번에 모으면 스키마 v3입니다. 표 네 개와 관계는 v2와 같고, 제약과 새 열 둘(menu.is_active, orders.status)이 달라졌습니다.

-- 스키마 v3: v2 + 제약 (C2, C4, C6, C7 과 v3 자체 규칙)-- 메뉴 한 종류
CREATE TABLE menu (
    menu_id    INTEGER PRIMARY KEY,
    name       TEXT    NOT NULL UNIQUE
               CHECK (name <> '' AND name = btrim(name)),
    price      INTEGER NOT NULL CHECK (price >= 0),
    is_active  BOOLEAN NOT NULL DEFAULT TRUE
);

-- 회원 한 명
CREATE TABLE member (
    member_id  INTEGER PRIMARY KEY,
    name       TEXT    NOT NULL,
    phone      TEXT    NOT NULL UNIQUE
               CHECK (phone ~ '^01[0-9]-[0-9]{3,4}-[0-9]{4}$')
);

-- 주문 한 건 (비회원 주문이면 member_id 는 NULL)
CREATE TABLE orders (
    order_id    INTEGER     PRIMARY KEY,
    member_id   INTEGER     REFERENCES member (member_id),
    ordered_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    payment     TEXT        NOT NULL CHECK (payment IN ('카드', '현금')),
    barista     TEXT        NOT NULL,
    status      TEXT        NOT NULL DEFAULT '접수'
                CHECK (status IN ('접수', '제조중', '완료', '픽업', '취소'))
);

-- 주문 안의 메뉴 한 줄
CREATE TABLE order_line (
    order_id  INTEGER NOT NULL REFERENCES orders (order_id),
    menu_id   INTEGER NOT NULL REFERENCES menu (menu_id) ON DELETE RESTRICT,
    quantity  INTEGER NOT NULL CHECK (quantity >= 1),
    PRIMARY KEY (order_id, menu_id)
);
  1. 2~8행 menu: 4행 UNIQUE가 C4이고, 5행 CHECK가 빈 글자와 끝 공백을 막습니다(화면 7). 6행 price >= 0은 0을 허용합니다. 7행 is_active는 새 열이고 DEFAULT TRUE 덕분에 기존 메뉴는 모두 판매 중이 됩니다(화면 6).
  2. 14~15행 member.phone: UNIQUE에 더해 하이픈 형식을 강제합니다. 표기가 하나여야 UNIQUE가 의미가 있기 때문입니다(화면 5).
  3. 21행 member_id는 이 스키마에서 유일하게 NULL을 허용하는 열입니다(비회원 주문, 화면 4).
  4. 22행 ordered_at: 시각은 TIMESTAMPTZ, 적지 않으면 DB가 지금 시각을 넣습니다(화면 3, 4).
  5. 23행 payment: 글자 목록 CHECK입니다(화면 8).
  6. 25~26행 status: 새 열입니다. 적지 않으면 '접수'로 시작하고(25행), 목록 밖의 값은 거부됩니다(26행). 전이 순서는 이 제약이 아니라 앱이 지킵니다(C7).
  7. 32행 ON DELETE RESTRICT가 C6입니다. 메뉴를 지우려 하면 거부되고, 판매중지 플래그로 대신합니다.
  8. 33행 CHECK (quantity >= 1)이 C2입니다. 31행의 order_id는 삭제 정책을 적지 않은 기본값입니다(주문은 지우지 않고 '취소'로 남김).
  9. 34행 기본키 (order_id, menu_id)는 v1에서 바뀌지 않았습니다. 이것이 C3의 v1 형태입니다.

같은 메뉴는 한 주문에 한 줄이라는 C3이 이 기본키로 표현됩니다. 같은 주문 안에 같은 메뉴가 두 줄 들어갈 수 없다는 뜻입니다. 지금은 문제가 없지만, 같은 메뉴를 다른 방식으로 두 번 주문할 수 있게 되는 순간 이 규칙이 무너집니다. 5장에서 다시 본다

4장 마무리

핵심 요약

  1. 규칙은 앱이 지키거나 DB가 지킵니다. DB 제약은 입력 경로를 가리지 않는 최후 방어선이고, 앱 검증은 친절을 위한 것이라 둘 다 둡니다.
  2. NULL은 0도 빈 글자도 아닌 "모른다"이고, 비교하면 참이 아니라 알 수 없음이 됩니다. = NULL 대신 IS NULL을 쓰고, NOT NULL이 기본이며 NULL 허용은 이유를 댈 수 있는 열만 합니다.
  3. 타입도 설계입니다. 금액은 정수(원 단위) 또는 NUMERIC, 시각은 TIMESTAMPTZ, 전화번호는 TEXT입니다.
  4. UNIQUE(C4), 외래키와 ON DELETE RESTRICT(C5, C6), CHECK(C2, C7의 값 목록)가 DB에 맡기는 규칙이고, CHECK는 NULL이면 통과하며 한 행만 봅니다.
  5. 여러 행을 세는 규칙(C1)과 값이 바뀌는 순서(C7 전이)는 선언으로 못 막아 앱과 트랜잭션이 지킵니다. 결과가 스키마 v3이고 D1~D5는 그대로 남았습니다.

orders에 member_id가 각각 1, 2, NULL인 주문 101, 102, 106이 있습니다. SELECT order_id FROM orders WHERE member_id <> 1;의 결과는?

  1. 102와 106
  2. 102만
  3. 0행

비회원을 포함하려면 member_id IS NULL OR member_id <> 1로 쓰거나 member_id IS DISTINCT FROM 1(NULL도 "다르다"로 셈)을 씁니다. 이런 버그는 테스트 데이터에 NULL이 없으면 발견되지 않습니다. NULL을 허용하는 열을 만들었다면, 그 열을 쓰는 모든 조회에 NULL 행을 넣어 시험해 보세요.

order_line.menu_id의 외래키를 ON DELETE CASCADE로 선언했다면, 치즈케이크(3번)를 DELETE할 때 무슨 일이 일어날까요?

  1. 라인의 menu_id가 NULL로 바뀌고 라인은 남는다
  2. 그 메뉴가 들어간 라인이 함께 지워져 과거 주문 금액이 줄어든다
  3. 삭제가 거부된다

CASCADE가 틀린 선택이라는 뜻은 아닙니다. 부모가 사라지면 자식이 의미를 잃는 관계, 예를 들어 주문 전의 임시 장바구니와 그 항목에는 맞는 선택입니다. 삭제 정책은 "부모를 지울 때 자식의 사실이 여전히 의미가 있는가"라는 업무 질문의 답입니다. 매출 기록은 지워서는 안 되는 사실이라 RESTRICT입니다.

CHECK (status IN ('접수', '제조중', '완료', '픽업', '취소'))가 막아 주는 것은 무엇일까요?

  1. '접수'에서 곧바로 '픽업'으로 건너뛰는 갱신
  2. '제조 중'(띄어쓰기) 같은 목록에 없는 값
  3. 같은 주문을 두 사람이 동시에 갱신하는 충돌

그래서 전이는 UPDATE ... WHERE status = '접수'처럼 이전 상태를 조건에 넣고 갱신된 행 수를 확인하는 방식으로 앱이 지킵니다. 한 가지 더, 이 CHECK에는 NULL이 통과한다는 구멍이 있습니다. status에 NOT NULL이 함께 있어야 "상태가 없는 주문"이 막힙니다.

"주문은 라인이 1개 이상이다"(C1)를 CHECK·외래키·UNIQUE 같은 선언만으로 지킬 수 없는 가장 근본적인 이유는?

  1. 규칙이 한 행이 아니라 여러 행(라인)의 개수에 대한 것이고, 검사 시점도 저장 한 번이 아니라 묶음이 끝났을 때이기 때문이다
  2. 라인이 너무 많으면 검사가 느려지기 때문이다
  3. 제약조건은 숫자 열에만 쓸 수 있기 때문이다

4장의 이해도 체크포인트가 이 질문입니다. 답은 두 줄이면 됩니다. "DB는 한 행 단위의 선언만 한다. C1은 여러 행의 묶음이므로 앱이 트랜잭션 안에서 지킨다." 그 뒤에 PostgreSQL의 지연 제약 트리거가 있다는 것까지 덧붙이면 정확합니다.

3장의 원두 판매 장부 설계를 기억하시나요? 3NF까지 나눈 결과의 열은 다음과 같았습니다.

  • bean(bean_id, name, origin, price_per_100g) — 원두 한 종류
  • sale(sale_id, sold_on, member_id) — 판매 한 건(회원에게만 판매, 스키마 v3의 member 사용)
  • sale_line(sale_id, bean_id, quantity) — 판매 안의 원두 한 줄
  1. 각 열의 타입과 NOT NULL/UNIQUE/CHECK를 정해 CREATE TABLE로 쓰세요. (price_per_100g의 경계값도 정하세요.)
  2. 세 외래키의 삭제 정책을 정하고 이유를 한 줄씩 쓰세요.
  3. 이 설계에서 DB 제약으로 지키지 못하는 규칙을 하나 들고, 누가 지킬지 쓰세요.
모범답안 — 그리고 흔한 오답이 왜 틀리는지 
-- 모범답안 (member 는 v3 의 표를 그대로 사용)CREATE TABLE bean (
    bean_id         INTEGER PRIMARY KEY,
    name            TEXT    NOT NULL UNIQUE CHECK (name <> '' AND name = btrim(name)),
    origin          TEXT    NOT NULL,
    price_per_100g  INTEGER NOT NULL CHECK (price_per_100g >= 0)
);
CREATE TABLE sale (
    sale_id    INTEGER PRIMARY KEY,
    sold_on    DATE    NOT NULL,
    member_id  INTEGER NOT NULL REFERENCES member (member_id)
);
CREATE TABLE sale_line (
    sale_id   INTEGER NOT NULL REFERENCES sale (sale_id),
    bean_id   INTEGER NOT NULL REFERENCES bean (bean_id) ON DELETE RESTRICT,
    quantity  INTEGER NOT NULL CHECK (quantity >= 1),
    PRIMARY KEY (sale_id, bean_id)
);

1. 단가는 원 단위 정수, 판매일은 날짜만 의미가 있으므로 DATE입니다. 3장에서 원두(이름)가 원산지와 단가를 정한다고 했으므로 원두 이름이 겹치면 안 되어 UNIQUE입니다. 단가의 경계는 업무가 정합니다. 위는 샘플 증정을 0원으로 기록할 수 있게 >= 0으로 썼고, 공짜 판매를 받지 않는다면 > 0이어도 틀린 답이 아닙니다. sale.member_id는 회원에게만 판매한다고 했으므로 NULL을 허용하지 않습니다(비회원에게도 판다면 NULL을 허용하고 그 이유를 적어야 합니다).

2. sale_line.bean_id는 RESTRICT(과거 판매 기록을 지키려고). sale_line.sale_id와 sale.member_id는 기본값(판매는 지우지 않는다는 원칙이고, 회원 삭제 정책은 별도 결정).

3. "판매는 라인이 1개 이상"(C1과 같은 모양)입니다. 여러 행의 개수에 대한 규칙이라 선언으로는 못 지키고, 앱이 한 트랜잭션 안에서 판매와 라인을 함께 저장하며 지킵니다.

흔한 오답 1 — price_per_100g를 FLOAT로 둔다. 100g당 단가가 정수 원이라면 정수로 충분하고, FLOAT는 합계 오차를 만듭니다. 소수 단가가 필요할 때는 NUMERIC입니다.

흔한 오답 2 — sale_line.bean_id를 ON DELETE CASCADE로 한다("단종된 원두를 지우기 편하게"). 원두를 지우는 순간 과거 판매 라인이 사라져 매출이 줄어듭니다. 원두에 판매중지 열을 두는 쪽이 맞습니다.

흔한 오답 3 — "판매는 라인 1개 이상"을 CHECK로 쓰려 한다. CHECK는 다른 표의 행을 셀 수 없습니다(화면 7, 9).
