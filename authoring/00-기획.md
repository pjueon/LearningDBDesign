# DB 설계 학습 교재 제작 기획서

> 제작용 문서는 `authoring/`, 산출물은 `docs/` 에 둔다(스킬 기본값은 `docs/00-기획.md` 이지만
> 제작 문서와 산출물을 분리한다). 호스팅 여부와 방식은 저자가 나중에 결정한다.

## 1. 목적과 대상 독자

**목적**: 관계형 DB 설계의 기본 이론(엔터티·키·관계 모델링, 정규화, 제약조건)을 배우고,
"요구사항이 바뀌어도 버틸 스키마를 어떻게 고르는가"를 판단할 수 있게 만드는 HTML 교재.
SQL 문법 교재가 아니다. 블로그 글 모음이 아니라 **한 권의 책** — 앞장에서 만든 스키마가
뒷장에서 요구사항을 만나 깨지고 고쳐지는 구조.

**대상 독자 (저자 본인)**
- C++ 개발자. Python 도 어느 정도 읽는다. 구조체·클래스·`std::map`·포인터 감각이 있다.
- 웹·네트워크 경험이 적다. **DB 를 다뤄본 경험이 거의 없다.**
- SQL 은 책으로 기초 문법을 한 번 훑은 정도.

**전제하지 않아도 되는 것**: 정규화·함수 종속·키 종류, ER 다이어그램, 인덱스와 B-tree, 트랜잭션·락·격리 수준,
`JOIN`/`GROUP BY` 능숙도, 마이그레이션, 카페 운영 업무 용어.  
**전제해도 되는 것**: 프로그래밍 일반(자료구조, 참조/포인터, 시간복잡도 감각),
관계형 DB 가 "표 여러 장"이라는 정도의 이미지, `SELECT`/`INSERT`/`UPDATE` 가 존재한다는 것.
SQL 은 0장에서 **읽는 데 필요한 최소분**만 설명하고 그 뒤로는 나오는 자리에서 설명한다.
PK/FK/UNIQUE/CHECK/인덱스/트랜잭션 같은 핵심 용어는 0장의 **DB 개념 지도**에서 한 줄씩 이름을 붙이고, 각 장에서 처음 깊게 다루는 자리에서 정식으로 설명한다.

## 2. 학습 목표 (다 읽은 뒤 할 수 있어야 하는 것)

1. 표 하나짜리 설계에서 갱신·삽입·삭제 이상현상을 찾아내고, 왜 생기는지 설명할 수 있다.
2. 요구사항 문장에서 엔터티·속성·관계(1:1, 1:N, N:M)를 뽑아 ER 모델을 그리고 테이블로 옮길 수 있다.
3. 함수 종속을 찾아 1NF~3NF(BCNF 맛보기)로 정규화하고, 그 결과를 검증할 수 있다.
4. 규칙 하나하나를 PK/FK/UNIQUE/CHECK 로 DB 에 맡길지, 앱이 지킬지 근거와 함께 정할 수 있다.
5. 옵션·세트·가격 변경·쿠폰·다점포 같은 실무 요구사항을 스냅샷·이력·원장·연결 테이블로 모델링할 수 있다.
6. 조회 패턴에서 인덱스를 고르고, 데이터가 커졌을 때 조회가 느려지는 이유(풀스캔·페이지네이션·대용량)와 대응을 설명하며, 동시 요청에서 깨지는 규칙(재고·쿠폰·예약)을 트랜잭션과 제약으로 막을 수 있다.
7. 운영 중인 DB 의 스키마를 데이터를 보존하며 바꾸는 순서를 설명할 수 있다.
8. **정규화를 일부러 깨야 할 때와 관계형 DB 를 쓰지 말아야 할 때를 판단할 수 있다.** (이게 빠지면 교재가 실패다)

## 3. 관통 시나리오 — "동백커피"

모든 장이 **하나의 가상 회사**를 계속 파고든다. 장마다 소재가 바뀌면 앞장의 스키마가
뒷장에서 버려지고 독자는 매번 새 맥락을 이해하는 데 힘을 쓴다.

### 3.1 회사 개요

**동백커피**: 동네 카페 1호점. 처음에는 서연 사장 혼자 종이 전표와 엑셀로 주문·매출을 관리한다.
키오스크와 앱 주문을 붙이면서 DB 가 필요해지고, 교재 후반에 가맹점이 늘어난다.
바리스타 지호가 실제로 주문을 처리하고, 후반에 본사 기획자 하윤이 프로모션과 매출 리포트를 요구한다.
(인물은 요구사항이 어디서 오는지 보이기 위한 장치다. 이름만 쓰고 성별 대명사는 쓰지 않는다.)

이 설정을 고른 이유: 메뉴·옵션·세트, 가격 인상, 쿠폰·멤버십, 다점포, 재고(완제품과 원재료), 픽업 시간 예약처럼
**정규화·이력·동시성 문제가 자연스럽게 발생**하고, 독자가 업무를 이미 알아서 도메인 설명에 힘을 덜 쓴다.

### 3.2 스키마 진화 로드맵과 요구사항 배치

초반(0~4장)의 요구사항은 단순하다. 아래 새 요구사항이 **정해진 장에서 들어와** 기존 설계를 깬다.
새 요구는 그 장의 첫 화면에서 서연/지호/하윤의 말로 등장한다. 그 전 장에서 미리 언급하지 않는다.

| 스키마 버전 | 시점 | 담긴 것 | 이 장에서 들어오는 요구 → 깨지는 것 |
|---|---|---|---|
| (엑셀) | 1장 | 주문 한 줄에 모든 것이 든 표 | 전화번호 수정·메뉴 등록·주문 삭제 → 이상현상 3종 |
| v1 | 2장 후 | `menu`, `member`, `orders`, `order_line` | — (ER 모델링의 결과물) |
| v2 | 3장 후 | v1 을 정규화·파생값 제거한 결과 | — (검증 결과) |
| v3 | 4장 후 | v2 + 제약조건 표 C1~C7 | — |
| v4 | 5장 후 | + 옵션 그룹·옵션(가격 0원 포함)·세트 | **요구1: 샷 추가·시럽 빼기·얼음 적게(0원)·휘핑·우유 추가, 세트 메뉴** → 라인 PK 충돌(C3), 메뉴 종류 폭발 |
| v5 | 6장 후 | + 가격 이력, 주문 스냅샷, 쿠폰, 멤버십 등급, 포인트 원장 | **요구2: 가격 인상, 쿠폰, 멤버십** → 과거 주문 금액이 바뀜 |
| v6 | 8장 후 | + 재고 품목(완제품·원재료), 레시피(메뉴·옵션별 소요량), 픽업 슬롯, 일 매출 요약(7장) | **요구3: 케이크·쿠키 완제품 재고, 원두·우유·시럽 원재료 재고, 재료가 부족한 메뉴·옵션은 키오스크에서 주문 차단, 픽업 예약** → 동시 요청에서 규칙이 깨짐 |
| v7 | 9장 후 | + 매장, 매장별 메뉴·가격 | **요구4: 가맹점 확대** → "매장 1개" 가정이 스키마 곳곳에 박혀 있음 |

**7장(인덱스)에서 들어오는 문제**는 요구사항이 아니라 **데이터량**이다. 주문이 수백만 건이 되고
하윤의 일 매출 리포트가 느려진다 → 인덱스 → 그래도 부족 → 의도적 비정규화(요약 테이블).

### 3.3 의도적으로 미뤄두는 빚과 갚는 장

앞 장에서 표시(`.later`)만 하고, 갚는 장에서 반드시 갚는다.

| # | 빚 | 생기는 장 | 갚는 장 |
|---|---|---|---|
| D1 | `order_line` 이 단가를 갖지 않고 `menu.price` 만 참조한다. **정규화 관점에서는 맞다**(단가는 메뉴에 종속). 그러나 가격이 바뀌면 과거 주문 금액이 바뀐다 | 2~3장 | 6장 (스냅샷: 값이 같아도 **의미가 다른 사실은 중복이 아니다**) |
| D2 | 모든 테이블이 **매장 1개**를 가정한다(`store_id` 없음, 메뉴 가격 전역) | 2장 | 9장 |
| D3 | `order_line` 의 PK 가 `(order_id, menu_id)` — 같은 메뉴를 다른 옵션으로 두 줄 시킬 수 없다 | 2장 | 5장 (라인 번호/대리키) |
| D4 | 주문 총액을 **저장하지 않고** 라인에서 계산한다(3장 결정, 파생값이라서) | 3장 | 7장 (조회가 느려져 요약 테이블로 의도적으로 되돌림) |
| D5 | C1("주문은 라인 1개 이상")은 DB 제약으로 표현할 수 없어 4장에서 "앱이 지킨다"로 남긴다 | 4장 | 8장 (트랜잭션으로 지킨다) |

3~4장을 쓸 때 위 다섯 가지를 유지하고 해당 화면에 "N장에서 다시 볼 문제" 표시를 남긴다.
**"정규화했으니 끝이 아니다"를 독자가 D1 로 겪는 것이 이 교재의 뼈대 중 하나다.**

### 3.4 제약조건 표 (교재 전체의 기준선)

각 장은 이 표의 규칙을 스키마로 만들어 간다. 규칙마다 **누가 지키는가**가 핵심 학습 대상이다.

| # | 규칙 | 강제 수단 | 처음 등장 → 완성 |
|---|---|---|---|
| C1 | 주문은 라인이 1개 이상이다 | DB 로 표현 불가 → 앱 + 트랜잭션 | 4장(한계 인식) → 8장 |
| C2 | 라인 수량은 1 이상이다 | `CHECK` | 4장 |
| C3 | 한 주문에서 같은 (메뉴 + 옵션 조합) 은 한 줄로 합친다 | v1 은 `PK(order_id, menu_id)` → 5장에서 깨짐 | 2장 → 5장 |
| C4 | 메뉴 이름은 겹치지 않는다 | `UNIQUE` | 4장 |
| C5 | 없는 메뉴·회원·주문을 참조할 수 없다 | `FOREIGN KEY` | 2장, 4장 |
| C6 | 메뉴를 내려도 과거 주문은 남는다 | `FK ... ON DELETE RESTRICT` + 판매중지 플래그 | 4장 → 6장 |
| C7 | 주문 상태는 접수→제조중→완료→픽업 순으로만 간다(접수·제조중에서만 취소) | `CHECK`(값 목록) + 앱(전이 순서) | 4장 → 8장 |
| C8 | 주문 시점의 메뉴명·단가·옵션가는 스냅샷으로 복사한다 | 컬럼 복사(D1 상환) | 6장 |
| C9 | 옵션 그룹마다 선택 개수 범위가 있다(샷 0~3, 시럽 0~1) | 앱 (DB 로는 일부만) | 5장 |
| C10 | 세트는 구성 슬롯을 모두 채워야 한다(음료 1 + 디저트 1, 디저트는 케이크류 중 택1) | 앱 + 구성 테이블 | 5장 |
| C11 | 쿠폰은 회원당 1회만 쓸 수 있다 | `UNIQUE(coupon_id, member_id)` → 동시 사용은 8장 | 6장 → 8장 |
| C12 | 포인트 잔액은 음수가 될 수 없다 | 원장 합계 검증 + 락 | 6장 → 8장 |
| C13 | 재고(완제품 케이크·쿠키, 원재료 원두·우유·시럽)는 음수가 될 수 없다 | `CHECK(qty >= 0)` + 조건부 `UPDATE` | 8장 |
| C14 | 픽업 슬롯 정원을 넘길 수 없다 | 카운터 + `CHECK` 또는 락 | 8장 |
| C15 | 매장마다 판매 메뉴·가격이 다를 수 있다 | `PK(store_id, menu_id)` | 9장 |
| C16 | 스키마를 바꿔도 과거 데이터는 보존된다 | 마이그레이션 절차 (확장→이전→축소) | 9장 |
| C17 | 재료가 부족한 메뉴·옵션은 주문할 수 없다(키오스크 품절 표시, 주문 확정 시 재검사) | 조회 계산 + 주문 트랜잭션에서 재고 차감으로 최종 확인(앱 + 트랜잭션) | 8장 |

### 3.5 용어표 (초안 — 장이 진행되며 `glossary.html` 로 확장)

세 번째 칸이 핵심이다. 독자가 자주 혼동하는 쌍을 미리 정한다.

| 용어 | 뜻 | 무엇과 다른가 |
|---|---|---|
| 테이블(릴레이션) | 같은 모양의 행을 모은 표 | 엑셀 시트와 다르다: 행 순서가 없고, 열마다 타입이 있고, 제약이 붙는다 |
| 기본키(PK) | 행 하나를 유일하게 가리키는 열(들) | 후보키 중 **대표로 뽑은 것**. 후보키는 유일성만 만족하는 모든 후보 |
| 자연키 / 대리키 | 업무에 원래 있는 식별자 / 시스템이 붙인 번호 | 자연키는 "안 바뀔 줄 알았는데 바뀐다"가 문제, 대리키는 의미가 없다는 것이 문제 |
| 외래키(FK) | 다른 테이블 행을 가리키는 열 | C++ 포인터와 닮았지만 **댕글링을 DB 가 막아준다** |
| 함수 종속 | A 값이 정해지면 B 값이 하나로 정해진다(A→B) | "A 가 B 를 결정한다"는 업무 규칙. 데이터에서 우연히 그런 것과 다르다 |
| 이상현상 | 중복 때문에 생기는 갱신·삽입·삭제 오류 | 버그가 아니라 **설계 결함** |
| 정규화 / 비정규화 | 중복을 없애도록 쪼갬 / 성능 등을 위해 일부러 합침 | 비정규화는 "정규화를 안 한 것"이 아니라 **한 뒤에 되돌린 것** |
| 논리 모델 / 물리 모델 | 무엇을 저장하나 / 어떻게 저장하나(타입·인덱스) | ER 다이어그램은 논리, `CREATE TABLE` 은 물리에 가깝다 |
| 제약조건 / 인덱스 | 데이터가 지켜야 할 규칙 / 찾기를 빠르게 하는 구조 | `UNIQUE` 는 둘을 겸한다. 목적은 다르다 |
| `NULL` | 값이 없다 / 알 수 없다 | 0·빈 문자열과 다르다. `NULL = NULL` 은 참이 아니다 |
| 카디널리티 | ER 에서는 관계의 대응 수(1:N), 인덱스에서는 열이 가진 서로 다른 값의 수 | **같은 낱말이 두 뜻이다.** 문맥으로 구분한다 |
| ACID | 트랜잭션이 지켜야 할 네 성질(원자성·일관성·격리성·지속성) | 격리성은 완벽하지 않고 수준을 고를 수 있다. 일관성은 "제약을 지킨다"이지 "업무적으로 옳다"가 아니다 |
| 스냅샷 / 이력 | 주문 시점 값을 복사해 둠 / 값의 변경 내역을 쌓음 | 스냅샷은 "그때 얼마였나", 이력은 "언제 무엇으로 바뀌었나" |
| 원장(ledger) | 증감 내역을 쌓기만 하는 표. 잔액은 합계 | 잔액 컬럼 하나를 덮어쓰는 방식과 다르다 |
| 트랜잭션 / 락 | 전부 성공하거나 전부 취소되는 묶음 / 동시 접근을 막는 장치 | 트랜잭션만으로 동시성이 자동 해결되지는 않는다 |
| 옵션 / 세트 | 메뉴에 붙는 선택지(샷 추가) / 여러 메뉴를 묶은 상품 | 옵션은 메뉴를 **바꾸고**, 세트는 메뉴를 **묶는다** |
| 프로모션 / 쿠폰 / 멤버십 등급 | 기간 이벤트 / 회원이 가진 1회성 혜택 / 회원에게 붙은 상시 자격 | 셋 다 할인이지만 **누가 어떤 조건으로 갖는지**가 달라 테이블이 다르다 |

## 4. 교재의 형태 — 결정 사항

- **장 = HTML 파일 1개, 장 안은 화면(`section.screen`) 단위**, 화면당 10~12분. (스킬 R1. 다시 논의하지 않는다)
- **`file://` 로 열린다.** `fetch()`·`type="module"`·CDN·외부 폰트를 쓰지 않고 본문은 인라인. 진도는
  `localStorage` + try/catch, 키 접두어는 **`dbdesign-book:`**.
- **파일 구조**:

```
authoring/                 제작용
  00-기획.md  01-커리큘럼.md  02-스키마-정본.md  03-집필-절차.md  _smoke.html
docs/                      산출물
  index.html  ch00.html … ch10.html  glossary.html
  assets/book.css  assets/book.js
```

- **`_smoke.html` 은 `authoring/` 에 둔다**(스킬 기본은 `docs/`. 산출물에 점검 파일을 섞지 않으려는 결정).
  `03-집필-절차.md` 는 이 교재 전용 집필·점검 절차(경로, probe 사용법)를 적는 파일로, 골격 세우기 단계에서 만든다.
- **예제 코드 언어: SQL(PostgreSQL 방언)이 주 언어.** Python 은 쓰지 않는다(앱 코드는 "앱이 지킨다"는 문장과
  의사코드로 충분하다). 방언 차이가 학습에 영향을 주는 곳은 "다른 DB 에서는" 접힌 상자로 알린다.
- **코드 하이라이터**: 동봉 `book.js` 는 주석이 `#` 전용이고 키워드가 **대소문자를 구분**한다. 그래서
  ① SQL 키워드는 **대문자로 쓴다**(`SELECT`, `CREATE TABLE`, `PRIMARY KEY`), 식별자는 소문자 snake_case,
  ② `book.js` 의 `[교재별 5/5]` 블록에서 `PY_RE` 의 주석 그룹에 `--` 를 추가하고 `PY_KW` 에 SQL 키워드(대문자)를
  합집합으로 넣는다. Python 토큰은 지우지 않는다 — `_smoke.html` 의 하이라이터 단정이 Python 코드를 쓰기 때문이다.
  변경 뒤 `_smoke` 를 반드시 다시 돌린다.
- **식별자 표기**: 테이블·컬럼은 영문 snake_case(`orders`, `order_line`; `order` 는 예약어라 쓰지 않는다).
  한글 용어와의 대응은 용어표와 각 장 첫 등장 자리에서 밝힌다.
- **`examples/`(실행 가능한 실습 파일)는 이번 범위에 넣지 않는다.** 이유: 본문은 PostgreSQL 기준인데
  sqlite 는 FK 를 기본으로 강제하지 않고 타입이 느슨하며 `SELECT ... FOR UPDATE` 가 없어, 독자가 본문 DDL 을
  sqlite 에 붙이면 "제약이 안 막아 준다"는 잘못된 교훈을 얻는다. 직접 돌려보고 싶으면 PostgreSQL 에 복사한다.
  필요해지면 교재 완성 후 차이표와 함께 따로 추가한다.
- **넣을 인터랙티브 요소**: 화면 넘김·진도·퀴즈(`data-why`)·용어 툴팁·Before/After 탭·접힌 모범답안,
  그리고 위젯 3개(스킬 R6, 글로 충분한 곳에는 넣지 않는다).
  ① **이상현상 시뮬레이터**(1장): 엑셀 표에서 가격을 고치면 어느 행이 안 바뀌는지 눌러서 확인.
  ② **B-tree 탐색 스텝퍼**(7장): 인덱스 유무에 따라 몇 행을 읽는지 단계로 비교.
  ③ **동시성 타임라인**(8장): 두 트랜잭션의 실행 순서를 바꿔가며 재고가 음수가 되는 순서를 찾기.
  ER 다이어그램과 스키마 그림은 인라인 SVG. **넣지 않을 것**: 브라우저 SQL 실행, 서버 기능, 검색.

## 5. 서술 방침

- **개념 → 이름 순서.** 문제 상황과 표를 먼저 보이고 이름은 나중에.
  (함수 종속도 "가격은 메뉴 이름이 정한다"는 사실을 먼저 보이고 이름을 붙인다.)
- **1장은 나쁜 설계로 시작한다.** 엑셀 한 장짜리 주문표의 이상현상 3종을 손으로 겪은 뒤 해법을 배운다.
- **정규화는 ER 모델링 뒤에 온다.** 2장에서 요구사항 문장으로 엔터티를 뽑아 설계하고, 3장에서 정규화를
  "그 설계를 검증·교정하는 도구"로 쓴다. 이론 순서(정규화 먼저)를 일부러 뒤집는 이유는 실무가 그렇게 흐르기 때문이다.
- **구조를 DDL 보다 먼저**: 테이블 목록 + 관계 그림 + "한 행이 무엇을 뜻하는가"를 보이고 코드를 보인다.
- **C++ 개발자에게 통하는 비유는 쓰되 한계도 적는다**: 테이블 ≈ 구조체 배열, 인덱스 ≈ 정렬된 `std::map`,
  FK ≈ 댕글링을 막는 포인터, 트랜잭션 ≈ 롤백되는 `std::lock_guard` + 임시 사본. 비유가 깨지는 지점을 반드시 밝힌다.
- **매 장 끝**: 핵심 요약 3~5줄 + 퀴즈(모든 선택지에 `data-why`) + 직접 해보기 1개(접힌 모범답안 + "흔히 이렇게 풀지만 안 되는 이유").
- **원전 표기**: Codd(1970) 관계 모델 논문, William Kent 「A Simple Guide to Five Normal Forms」(정규형 직관),
  C. J. Date 『Database Design and Relational Theory』, Bill Karwin 『SQL Antipatterns』(EAV·쿠폰 등 반례),
  Markus Winand 『Use The Index, Luke』(인덱스), Martin Kleppmann 『Designing Data-Intensive Applications』(다음 단계).
  출처를 밝히되 인용은 짧게, 내용은 이 교재의 예제로 다시 쓴다.
- **반대 의견도 쓴다**: "정규화는 3NF 까지"가 언제 틀리는지, 대리키 vs 자연키 논쟁, DB 제약 vs 앱 검증 논쟁,
  EAV 가 정당한 드문 경우, 관계형이 안 맞는 경우.
- **DB 제품 중립성**: 개념은 제품과 무관하게, 문법·동작은 PostgreSQL 기준으로 쓰고 그 사실을 0장에서 밝힌다.

### 5.1 코드 해설 원칙

독자의 SQL 지식을 얕게 가정한다. 던져놓고 "보면 안다"고 넘어가지 않는다.

1. **20줄이 넘는 코드에는 `ol.notes` 해설**: 몇 행 + 무엇을 + 왜 그렇게. 행 번호는 실제 코드와 대조한다
   (가장 자주 틀리는 부분이다).
2. **SQL 관용구는 처음 나오는 자리에서 설명한다**: `PRIMARY KEY`, `REFERENCES`, `CHECK`, `JOIN ... ON`,
   `GROUP BY`, `BEGIN/COMMIT`, `SELECT ... FOR UPDATE`, `ALTER TABLE ... ADD COLUMN` 등.
3. **카페 업무 용어는 코드보다 먼저** 화면이나 상자로 소개한다(샷, 시럽, 세트 구성, 픽업 슬롯).
4. **해설은 기술 설명으로 끝내지 않는다.** 항목 끝에 "그래서 나중에 무슨 문제가 되는가"를 붙여 다음 장의 예고로 만든다.

## 6. 분량 목표

- **11장(0~10장) + 용어집 부록**, 장당 7~16화면, 전체 약 **132화면**.

- 성격별 비중: 설계 이론(1~6, 9장 일부) 약 75%, **설계와 맞닿은 운영**(7~9장) 약 25%.
  운영 장은 "앞에서 설계한 스키마가 운영에서 어떻게 깨지는가"로 시작한다.
