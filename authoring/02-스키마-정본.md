# 스키마 정본

본문의 DDL 은 이 문서를 따른다. 본문에 다른 DDL 을 쓰려면 **이 문서를 먼저 고치고** 변경 이력에 한 줄 남긴다.
이미 쓴 장에 영향이 있으면 그 장도 고친다. 표기 규약은 `03-집필-절차.md` §2(키워드 대문자, 식별자 소문자 snake_case).

## 예시 데이터 (1장·2장 공통, 바꾸지 않는다)

`member`: (1, 민준, 010-1111-2222) (2, 소라, 010-3333-4444) (3, 도윤, 010-5555-6666)
`orders`: (101, 회원 1, 3/4 09:10, 카드, 지호) (102, 2, 3/4 09:25, 현금, 지호) (103, 1, 3/4 10:02, 카드, 서연) (104, 2, 3/5 08:55, 현금, 지호) (105, 3, 3/5 09:40, 카드, 서연)
`order_line`: (101,1,2) (101,3,1) (102,2,1) (103,1,1) (104,1,1) (105,2,2)

**v3 에서 새 열의 값**(4장부터): `menu.is_active` 는 세 메뉴 모두 TRUE. `orders.status` 는 101~105 모두 '픽업'(3/4·3/5 주문은 모두 끝난 주문).
4장 본문이 보여 주는 가정 행(정본 데이터 밖, 설명용): 비회원 주문 106(`member_id` NULL, 카드, 지호).

## v1 (2장 후)

```sql
-- 메뉴 한 종류 (0장과 같은 표)
CREATE TABLE menu (
    menu_id  INTEGER PRIMARY KEY,
    name     TEXT    NOT NULL,
    price    INTEGER NOT NULL
);

-- 회원 한 명
CREATE TABLE member (
    member_id  INTEGER PRIMARY KEY,
    name       TEXT    NOT NULL,
    phone      TEXT    NOT NULL UNIQUE
);

-- 주문 한 건 (비회원 주문이면 member_id 는 NULL)
CREATE TABLE orders (
    order_id    INTEGER     PRIMARY KEY,
    member_id   INTEGER     REFERENCES member (member_id),
    ordered_at  TIMESTAMPTZ NOT NULL,
    payment     TEXT        NOT NULL,
    barista     TEXT        NOT NULL
);

-- 주문 안의 메뉴 한 줄
CREATE TABLE order_line (
    order_id  INTEGER NOT NULL REFERENCES orders (order_id),
    menu_id   INTEGER NOT NULL REFERENCES menu (menu_id),
    quantity  INTEGER NOT NULL,
    PRIMARY KEY (order_id, menu_id)
);
```

- 번호(`*_id`)는 본문 간결을 위해 `INTEGER PRIMARY KEY` 로 쓴다. 자동 부여(`GENERATED ALWAYS AS IDENTITY`)는
  2장 화면 5 의 접힌 상자에서만 소개하고 정본 DDL 에는 넣지 않는다(0장 `menu` 와 같은 모양을 유지).
- 관계: `member` 1 — N `orders`(선택적), `orders` 1 — N `order_line`, `menu` 1 — N `order_line`.
  `order_line` 이 `orders` ↔ `menu` 의 N:M 연결 테이블이다.
- 2장 본문에서 정본 밖 **설명용 표**: `menu_nutrition`(화면 8, 1:1 예시), `bean_class`·`enrollment`(직접 해보기). 스키마 v1 에 포함하지 않는다.
- 요구사항 화면 1 에 "같은 전화번호로 두 번 가입할 수 없다", "비회원의 정보는 받지 않는다"가 들어 있다(전화번호 UNIQUE 의 근거).
- 1장 시트의 "고객"은 2장부터 "회원"(`member`)이다. 열 순서는 1장 직관 초안과 다를 수 있다.
- 규칙: 2장에서 실제로 DB 에 적힌 것은 C5(없는 것을 참조할 수 없다)와 C3 의 v1 형태(`PK(order_id, menu_id)`),
  그리고 회원 전화번호 중복 불가(`UNIQUE`, 후보키)다. 전화번호 UNIQUE 는 C 번호가 없는 v1 자체 규칙이며 4장에서 되짚는다.
- 아직 없는 것: `quantity >= 1`(C2, 4장), 메뉴 이름 UNIQUE(C4, 4장), 삭제 정책(C6, 4장), 주문 상태(C7, 4장), 총액 열(3장이 결정).

### v1 이 남긴 빚과 3장 점검 후보

- **D1**: `order_line` 에 단가가 없다. 가격은 `menu.price` 만 본다 → 6장.
- **D2**: 어느 표에도 매장이 없다 → 9장.
- **D3**: `order_line` PK 가 `(order_id, menu_id)` → 5장.
- 3장이 v1 을 검증할 때 볼 후보: `orders.barista`(직원이라는 다른 종류의 사실이 문자열로 들어 있음, 1장 화면 9 에서 예외로 둔 것),
  `orders.payment`(글자로 적는 열, 표기 문제는 4장), 총액 열이 없다는 사실(파생값, D4 는 3장이 결정).

## v2 (3장 후)

v1 과 **표·열·제약이 같다.** 3장이 한 일은 표를 바꾸는 것이 아니라 v1 이 정규형을 만족함을 확인하고
"주문 총액 열을 두지 않는다"는 결정을 기록한 것이다. 각 표의 후보키와 결과:

| 표 | 후보키 | 정규형 |
|---|---|---|
| `menu` | `menu_id` | 3NF, BCNF |
| `member` | `member_id`, `phone` | 3NF, BCNF |
| `orders` | `order_id` | 3NF, BCNF |
| `order_line` | `(order_id, menu_id)` | 3NF, BCNF |

- 3장 본문의 설명용 표(정본 밖): `member_phone`(1NF 실습), 변형 초안(2NF·3NF 위반 예시), 강사·클래스 배정(BCNF 예시), 원두 판매 장부(과제).
- D4: 총액은 `SUM(m.price * ol.quantity)` 로 계산한다 → 7장에서 요약 테이블로 되돌린다.

## v3 (4장 후)

```sql
-- 메뉴 한 종류
CREATE TABLE menu (
    menu_id    INTEGER PRIMARY KEY,
    name       TEXT    NOT NULL UNIQUE
               CHECK (name <> '' AND name = btrim(name)),
    price      INTEGER NOT NULL CHECK (price >= 0),
    is_active  BOOLEAN NOT NULL DEFAULT TRUE
);

-- 회원 한 명
CREATE TABLE member (
    member_id  INTEGER PRIMARY KEY,
    name       TEXT    NOT NULL,
    phone      TEXT    NOT NULL UNIQUE
               CHECK (phone ~ '^01[0-9]-[0-9]{3,4}-[0-9]{4}$')
);

-- 주문 한 건 (비회원 주문이면 member_id 는 NULL)
CREATE TABLE orders (
    order_id    INTEGER     PRIMARY KEY,
    member_id   INTEGER     REFERENCES member (member_id),
    ordered_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    payment     TEXT        NOT NULL CHECK (payment IN ('카드', '현금')),
    barista     TEXT        NOT NULL,
    status      TEXT        NOT NULL DEFAULT '접수'
                CHECK (status IN ('접수', '제조중', '완료', '픽업', '취소'))
);

-- 주문 안의 메뉴 한 줄
CREATE TABLE order_line (
    order_id  INTEGER NOT NULL REFERENCES orders (order_id),
    menu_id   INTEGER NOT NULL REFERENCES menu (menu_id) ON DELETE RESTRICT,
    quantity  INTEGER NOT NULL CHECK (quantity >= 1),
    PRIMARY KEY (order_id, menu_id)
);
```

v2 와 달라진 것은 **제약과 새 열 둘**이다(표 4개, 관계는 그대로). 본문 DDL 은 위와 한 글자도 다르지 않아야 한다.

| 규칙 | 수단 | 위치 |
|---|---|---|
| C2 수량은 1 이상 | `CHECK (quantity >= 1)` (+ 기존 `NOT NULL`: CHECK 는 NULL 을 통과시키므로 짝이 필요) | `order_line.quantity` |
| C3 같은 (메뉴+옵션) 은 한 줄 | v1 형태 그대로 `PRIMARY KEY (order_id, menu_id)`. **5장에서 깨진다**(D3) | `order_line` |
| C4 메뉴 이름은 겹치지 않는다 | `UNIQUE` | `menu.name` |
| C5 없는 것을 참조할 수 없다 | `REFERENCES` (2장에서 이미) | 세 FK |
| C6 메뉴를 내려도 과거 주문은 남는다 | `ON DELETE RESTRICT` + `is_active` 플래그(삭제 대신 판매중지). 새 주문에 판매중지 메뉴를 못 담게 하는 것은 앱. 6장에서 완성 | `order_line.menu_id`, `menu.is_active` |
| C7 주문 상태 | `CHECK` 값 목록(접수·제조중·완료·픽업·취소). **전이 순서는 앱**(`UPDATE ... WHERE status = 이전 상태`) | `orders.status` |
| C1 주문은 라인 1개 이상 | **보통의 선언으로는 표현되지 않음**(지연 가능 외래키로 표현은 되지만 중복 열·동기화 부담 때문에 쓰지 않음) **→ 앱 + 트랜잭션**(D5, 8장) | 없음 |

### v3 자체 규칙 (C 번호 없음, 4장 결정)

- `menu.price >= 0` — **0 을 허용**한다. 5장의 0원 옵션(얼음 적게)과 충돌하지 않게 하려는 것이다. 금액 열은 앞으로도 `>= 0`.
- `menu.name`: `CHECK (name <> '' AND name = btrim(name))` — 0장 화면 4 가 미룬 빈 문자열, 1장이 본 끝 공백 표기 문제. 회원 이름은 동명이인·외국 이름 등 형식 규칙이 마땅치 않아 `NOT NULL` 까지만 둔다.
- `member.phone` 형식 `CHECK`: v1 의 `UNIQUE` 는 글자가 같아야 중복으로 잡으므로 `01011112222` 와 `010-1111-2222` 가 둘 다 들어간다. **근거: UNIQUE 가 의미를 가지려면 표기가 하나여야 한다.** 휴대전화 `01X-XXX(X)-XXXX` 하이픈 형식만 허용하고, 앱은 입력을 이 형식으로 바꿔서 넣는다(둘 다). 한계: 유선·국제번호는 못 받는다 → 요구가 바뀌면 제약을 교체.
- `orders.payment`: `CHECK (payment IN ('카드', '현금'))`. **근거: 값이 둘이고 바뀌는 일이 드물다.** 별도 표(lookup)·ENUM 보다 DDL 만 보고 값을 알 수 있다. 결제수단이 늘거나 속성(표시명·정렬)이 붙으면 lookup 표로 옮긴다.
- `orders.status`: 값은 한글 그대로('접수', '제조중', '완료', '픽업', '취소'). 실무에서는 영문 코드를 쓰는 조직도 많으나 교재 가독성을 택했다.
- `orders.ordered_at DEFAULT NOW()`: 앱이 시각을 채우지 않아도 DB 서버 시각이 들어간다.
- 타입: 금액 `INTEGER`(원 단위 정수, 소수가 필요하면 `NUMERIC`), 시각 `TIMESTAMPTZ`, 글자 `TEXT`, 플래그 `BOOLEAN`.
- 삭제 정책: `order_line.menu_id` 만 `RESTRICT` 를 **명시**한다. `order_line.order_id`, `orders.member_id` 는 기본(`NO ACTION`)이다. 주문은 지우지 않고 `'취소'` 상태로 남기는 것이 원칙(C6 과 C7 이 연결)이라 연쇄 삭제(`CASCADE`)는 채택하지 않았다. 회원 삭제 정책(탈퇴)은 4장에서 다루지 않는다.
- `is_active` 는 `menu` 에만 있다. 이름·가격을 바꾸면 과거 주문 조회 결과도 바뀌는 문제(D1)는 그대로이고 6장이 갚는다.

### v3 이 남긴 것

- **D1~D5 는 그대로**: D1(6장), D2(9장), D3(5장, C3 의 깨짐), D4(7장), D5(C1, 8장).
- C6 완성(판매중지 메뉴를 새 주문에 못 담게 하는 것, 이름·가격 변경 이력)은 6장.
- C7 전이 순서를 동시 요청에서도 지키는 문제는 8장.

## v4 (5장 후)

요구1(옵션·0원 옵션·세트)이 들어와 v3 의 `order_line` 기본키 `(order_id, menu_id)` 가 깨진다(D3, C3).
**표 11개**: v3 의 세 표(`menu`, `member`, `orders`)는 글자까지 같고, `order_line` 이 바뀌고, 새 표 일곱이 생긴다.
본문 DDL 은 아래와 한 글자도 다르지 않아야 한다(표 단위로 나눠 싣는다). 5장 화면 12 의 접힌 상자 "v4 전체 DDL 한눈에 보기"에는 아래 블록 전체가 한 번 더 실린다(표 단위 비교 스크립트는 같은 표가 두 번 나와도 둘 다 정본과 같으면 통과로 본다).

```sql
-- 메뉴 한 종류
CREATE TABLE menu (
    menu_id    INTEGER PRIMARY KEY,
    name       TEXT    NOT NULL UNIQUE
               CHECK (name <> '' AND name = btrim(name)),
    price      INTEGER NOT NULL CHECK (price >= 0),
    is_active  BOOLEAN NOT NULL DEFAULT TRUE
);

-- 회원 한 명
CREATE TABLE member (
    member_id  INTEGER PRIMARY KEY,
    name       TEXT    NOT NULL,
    phone      TEXT    NOT NULL UNIQUE
               CHECK (phone ~ '^01[0-9]-[0-9]{3,4}-[0-9]{4}$')
);

-- 주문 한 건 (비회원 주문이면 member_id 는 NULL)
CREATE TABLE orders (
    order_id    INTEGER     PRIMARY KEY,
    member_id   INTEGER     REFERENCES member (member_id),
    ordered_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    payment     TEXT        NOT NULL CHECK (payment IN ('카드', '현금')),
    barista     TEXT        NOT NULL,
    status      TEXT        NOT NULL DEFAULT '접수'
                CHECK (status IN ('접수', '제조중', '완료', '픽업', '취소'))
);

-- 옵션 그룹 한 종류 (샷, 시럽, 얼음 ...)와 고를 수 있는 개수 범위
CREATE TABLE option_group (
    group_id    INTEGER PRIMARY KEY,
    name        TEXT    NOT NULL UNIQUE
                CHECK (name <> '' AND name = btrim(name)),
    min_select  INTEGER NOT NULL DEFAULT 0 CHECK (min_select >= 0),
    max_select  INTEGER NOT NULL CHECK (max_select >= 1),
    CHECK (max_select >= min_select)
);

-- 옵션 한 가지 (샷 추가, 얼음 적게 ...)와 그 가격. 0원 옵션은 0 으로 적는다
CREATE TABLE option_item (
    option_id  INTEGER PRIMARY KEY,
    group_id   INTEGER NOT NULL REFERENCES option_group (group_id),
    name       TEXT    NOT NULL
               CHECK (name <> '' AND name = btrim(name)),
    price      INTEGER NOT NULL CHECK (price >= 0),
    is_active  BOOLEAN NOT NULL DEFAULT TRUE,
    UNIQUE (group_id, name)
);

-- 이 메뉴에서 이 옵션 그룹을 고를 수 있다 (메뉴와 옵션 그룹의 N:M 연결)
CREATE TABLE menu_option_group (
    menu_id   INTEGER NOT NULL REFERENCES menu (menu_id),
    group_id  INTEGER NOT NULL REFERENCES option_group (group_id),
    PRIMARY KEY (menu_id, group_id)
);

-- 주문 안의 한 줄 (같은 메뉴여도 옵션이 다르면 다른 라인이다)
CREATE TABLE order_line (
    order_id  INTEGER NOT NULL REFERENCES orders (order_id),
    line_no   INTEGER NOT NULL CHECK (line_no >= 1),
    menu_id   INTEGER NOT NULL REFERENCES menu (menu_id) ON DELETE RESTRICT,
    quantity  INTEGER NOT NULL CHECK (quantity >= 1),
    PRIMARY KEY (order_id, line_no)
);

-- 라인에 붙은 옵션 한 가지와 그 횟수 (같은 옵션은 한 라인에 한 번만 적는다)
CREATE TABLE order_line_option (
    order_id    INTEGER NOT NULL,
    line_no     INTEGER NOT NULL,
    option_id   INTEGER NOT NULL REFERENCES option_item (option_id) ON DELETE RESTRICT,
    option_qty  INTEGER NOT NULL DEFAULT 1 CHECK (option_qty >= 1),
    PRIMARY KEY (order_id, line_no, option_id),
    FOREIGN KEY (order_id, line_no) REFERENCES order_line (order_id, line_no)
);

-- 세트의 구성 슬롯 (케이크 세트의 '음료', '디저트')
CREATE TABLE set_slot (
    slot_id      INTEGER PRIMARY KEY,
    set_menu_id  INTEGER NOT NULL REFERENCES menu (menu_id),
    name         TEXT    NOT NULL
                 CHECK (name <> '' AND name = btrim(name)),
    UNIQUE (set_menu_id, name)
);

-- 슬롯에 들어갈 수 있는 메뉴 (후보)
CREATE TABLE set_slot_menu (
    slot_id  INTEGER NOT NULL REFERENCES set_slot (slot_id),
    menu_id  INTEGER NOT NULL REFERENCES menu (menu_id),
    PRIMARY KEY (slot_id, menu_id)
);

-- 세트 라인이 슬롯마다 고른 메뉴
CREATE TABLE order_line_pick (
    order_id  INTEGER NOT NULL,
    line_no   INTEGER NOT NULL,
    slot_id   INTEGER NOT NULL,
    menu_id   INTEGER NOT NULL,
    PRIMARY KEY (order_id, line_no, slot_id),
    FOREIGN KEY (order_id, line_no) REFERENCES order_line (order_id, line_no),
    FOREIGN KEY (slot_id, menu_id)  REFERENCES set_slot_menu (slot_id, menu_id)
                                    ON DELETE RESTRICT
);
```

- 생성 순서: 가리켜지는 표가 먼저다. `menu`, `member`, `orders`, `option_group`, `option_item`, `menu_option_group`, `order_line`, `order_line_option`, `set_slot`, `set_slot_menu`, `order_line_pick`.
- 관계: `option_group` 1 — N `option_item`. `menu` N — M `option_group`(연결 `menu_option_group`). `orders` 1 — N `order_line`. `order_line` 1 — N `order_line_option`, `order_line_option` N — 1 `option_item`. `menu`(세트 행) 1 — N `set_slot`, `set_slot` N — M `menu`(후보, 연결 `set_slot_menu`), `order_line` 1 — N `order_line_pick`, `order_line_pick` N — 1 `set_slot_menu`(복합 외래키 `(slot_id, menu_id)`).
- 자동 생성 제약 이름(PGlite 0.5.8 = PostgreSQL 18.3 에서 확인): `order_line_pkey`(이전 전후 같은 이름), `order_line_line_no_check`, `order_line_option_pkey`, `order_line_option_option_id_fkey`, `order_line_option_order_id_line_no_fkey`, `order_line_option_option_qty_check`, `option_group_check`(표 수준 CHECK), `option_group_max_select_check`, `option_item_price_check`, `option_item_group_id_name_key`, `order_line_pick_pkey`, `order_line_pick_slot_id_menu_id_fkey`, `set_slot_menu_menu_id_fkey`, `menu_category_parent_id_fkey`(설명용 표).

### v3 → v4 이전 스크립트 (기존 데이터 6행 보존, PGlite 로 검증)

새 표 일곱은 위 DDL 그대로 만들고(단 `order_line_option`, `order_line_pick` 은 `order_line` 의 새 기본키를 가리키므로 아래 이전 **뒤에** 만든다), `order_line` 만 다음 순서로 바꾼다. `line_no` 는 주문 안에서 `menu_id` 순으로 1, 2, … 를 매긴다.
이전 뒤 `line_no` 열은 표의 **맨 끝**에 놓인다(새로 만든 v4 와 열 순서만 다르다. 의미·제약은 같다).

```sql
BEGIN;
ALTER TABLE order_line ADD COLUMN line_no INTEGER;
UPDATE order_line AS ol
SET    line_no = t.rn
FROM  (SELECT order_id, menu_id,
              ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY menu_id) AS rn
       FROM   order_line) AS t
WHERE  ol.order_id = t.order_id AND ol.menu_id = t.menu_id;
ALTER TABLE order_line ALTER COLUMN line_no SET NOT NULL;
ALTER TABLE order_line ADD CHECK (line_no >= 1);
ALTER TABLE order_line DROP CONSTRAINT order_line_pkey;
ALTER TABLE order_line ADD PRIMARY KEY (order_id, line_no);
COMMIT;
```

### v4 설계 결정과 한계 (근거는 본문 화면 번호)

- **줄 식별: `(order_id, line_no)`**(화면 6). 대리키(`line_id ... GENERATED ALWAYS AS IDENTITY`)도 가능하지만 자식 표의 외래키가 한 열로 줄고 번호를 DB 가 매기는 대신 줄 번호라는 업무 의미가 사라진다. 그래서 줄 번호를 택했고 번호는 앱이 1부터 매긴다. 정본 DDL 에는 `IDENTITY` 를 넣지 않는다(v1 정본의 방침 유지, 본문 접힌 상자에서만 소개).
- **옵션 횟수: `order_line_option.option_qty`**(화면 6). 샷 0~3 을 "샷 추가 × 횟수"로 센다. 한 줄의 `quantity`(잔 수)와 구별한다: 금액 = `quantity × (menu.price + Σ option.price × option_qty)`.
- **옵션 가격은 참조만**(`option_item.price`). 주문 시점 복사(스냅샷)는 하지 않는다 → D1 이 옵션 가격까지 넓어진다(6장).
- **세트 = `menu` 의 한 행**(화면 8). `is_set` 열은 두지 않는다: "슬롯을 가진 메뉴"가 세트이며 파생 가능한 사실이라 저장하면 어긋날 수 있다(D4 와 같은 질문). 세트 가격(9500)은 구성 메뉴 가격의 합(예: 아메리카노 4500 + 치즈케이크 6500 = 11000)과 **다른 사실**이라 중복이 아니다. 세트 줄은 **수량이 여럿이면 같은 구성 n 세트**를 뜻한다(다른 구성은 다른 줄).
- **슬롯 후보는 메뉴를 열거**(`set_slot_menu`). 분류("케이크류") 지정 방식은 선택 화면(화면 10)의 설명용이고 v4 에 넣지 않는다.
- **한계(본문 화면 8·9 에 명시)**: ① 세트 안의 구성 메뉴에는 옵션을 붙일 수 없다(옵션은 줄에 붙는다. 필요하면 세트를 자식 줄로 푸는 모델이 필요하고 이 교재 범위 밖). ② 세트 구성에 따른 추가금은 없다(필요하면 `set_slot_menu` 에 금액 열을 더한다). ③ 구성품별 판매 집계는 `order_line` 과 `order_line_pick` 을 합쳐야 한다. ④ 세트가 자기 자신을 후보로 삼는 것, 슬롯이 다른 세트 소속인 것, `min_select` 가 1 이상인 그룹의 미선택은 DB 가 막지 않는다.
- `menu_category`(자기 참조)·`line_attr`(EAV)는 선택 화면의 설명용이며 v4 가 아니다. 이후 장은 이 둘에 의존하지 않는다.

### v4 가 남긴 것

- **D3 상환**(5장 화면 6). C3 는 DB 규칙에서 앱 규칙으로 바뀌었다.
- **D1 은 더 넓어졌다**: 옵션 가격(`option_item.price`)과 세트 가격을 바꾸면 과거 주문 금액이 바뀐다 → 6장(스냅샷).
- **D4**: 줄 금액 계산이 네 표 조인(`order_line`, `menu`, `order_line_option`, `option_item`)으로 무거워졌다 → 7장.
- **D5 와 같은 모양의 규칙이 둘 더**: C9 합계 범위, C10 슬롯 충족 → 8장(트랜잭션).
- D2 는 그대로(매장 없음, 9장). `order_line_option.option_id` 등 새 외래키 열에는 자동 색인이 없다 → 7장.

## v5 (6장 후)

요구2(가격 인상·쿠폰·등급 할인·포인트)가 들어와 v4 의 D1 이 터진다. **표 17개**: v4 의 11개 중 6개가 바뀌고(`menu`, `member`, `orders`, `order_line`, `order_line_option`, `order_line_pick`), 새 표 6개가 생기고, 5개(`option_group`, `option_item`, `menu_option_group`, `set_slot`, `set_slot_menu`)는 v4 와 글자까지 같다.
**v4 까지 "글자까지 같다"던 `menu`·`member`·`orders` 세 표가 모두 바뀐다**(`menu` 는 `price` 열 삭제, `member`·`orders` 는 열 추가).
본문 DDL 은 아래와 한 글자도 다르지 않아야 한다(표 단위 스크립트 비교, `CREATE EXTENSION` 블록 포함). 표 단위로는 바뀐 표와 새 표만 각 화면에 싣고, 6장 화면 11 의 접힌 상자 "v5 전체 DDL 한눈에 보기"에 아래 블록 전체(변경 없는 5개 표 포함)를 한 번 더 싣는다.

```sql
-- 겹침 방지(EXCLUDE)에서 정수와 구간을 함께 비교하려면 필요한 확장
CREATE EXTENSION btree_gist;

-- 회원 등급과 등급별 할인율
CREATE TABLE membership_grade (
    grade         TEXT    PRIMARY KEY
                  CHECK (grade <> '' AND grade = btrim(grade)),
    discount_pct  INTEGER NOT NULL CHECK (discount_pct BETWEEN 0 AND 100)
);

-- 메뉴 한 종류 (가격은 menu_price 로 옮겨 갔다)
CREATE TABLE menu (
    menu_id    INTEGER PRIMARY KEY,
    name       TEXT    NOT NULL UNIQUE
               CHECK (name <> '' AND name = btrim(name)),
    is_active  BOOLEAN NOT NULL DEFAULT TRUE
);

-- 회원 한 명 (grade 는 지금 등급)
CREATE TABLE member (
    member_id  INTEGER PRIMARY KEY,
    name       TEXT    NOT NULL,
    phone      TEXT    NOT NULL UNIQUE
               CHECK (phone ~ '^01[0-9]-[0-9]{3,4}-[0-9]{4}$'),
    grade      TEXT    NOT NULL DEFAULT '일반' REFERENCES membership_grade (grade)
);

-- 주문 한 건 (비회원 주문이면 member_id 가 NULL, member_grade 는 주문한 그때의 등급)
CREATE TABLE orders (
    order_id      INTEGER     PRIMARY KEY,
    member_id     INTEGER     REFERENCES member (member_id),
    ordered_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    payment       TEXT        NOT NULL CHECK (payment IN ('카드', '현금')),
    barista       TEXT        NOT NULL,
    status        TEXT        NOT NULL DEFAULT '접수'
                  CHECK (status IN ('접수', '제조중', '완료', '픽업', '취소')),
    member_grade  TEXT        REFERENCES membership_grade (grade),
    CHECK (member_id IS NOT NULL OR member_grade IS NULL)
);

-- 메뉴 가격의 유효 기간 (valid_to 가 NULL 이면 끝나는 때가 정해지지 않은 행이다)
CREATE TABLE menu_price (
    menu_id     INTEGER     NOT NULL REFERENCES menu (menu_id),
    valid_from  TIMESTAMPTZ NOT NULL,
    valid_to    TIMESTAMPTZ,
    price       INTEGER     NOT NULL CHECK (price >= 0),
    PRIMARY KEY (menu_id, valid_from),
    CHECK (valid_to IS NULL OR valid_to > valid_from),
    EXCLUDE USING gist (menu_id WITH =, tstzrange(valid_from, valid_to) WITH &&)
);

-- 옵션 그룹 한 종류 (샷, 시럽, 얼음 ...)와 고를 수 있는 개수 범위
CREATE TABLE option_group (
    group_id    INTEGER PRIMARY KEY,
    name        TEXT    NOT NULL UNIQUE
                CHECK (name <> '' AND name = btrim(name)),
    min_select  INTEGER NOT NULL DEFAULT 0 CHECK (min_select >= 0),
    max_select  INTEGER NOT NULL CHECK (max_select >= 1),
    CHECK (max_select >= min_select)
);

-- 옵션 한 가지 (샷 추가, 얼음 적게 ...)와 그 가격. 0원 옵션은 0 으로 적는다
CREATE TABLE option_item (
    option_id  INTEGER PRIMARY KEY,
    group_id   INTEGER NOT NULL REFERENCES option_group (group_id),
    name       TEXT    NOT NULL
               CHECK (name <> '' AND name = btrim(name)),
    price      INTEGER NOT NULL CHECK (price >= 0),
    is_active  BOOLEAN NOT NULL DEFAULT TRUE,
    UNIQUE (group_id, name)
);

-- 이 메뉴에서 이 옵션 그룹을 고를 수 있다 (메뉴와 옵션 그룹의 N:M 연결)
CREATE TABLE menu_option_group (
    menu_id   INTEGER NOT NULL REFERENCES menu (menu_id),
    group_id  INTEGER NOT NULL REFERENCES option_group (group_id),
    PRIMARY KEY (menu_id, group_id)
);

-- 주문 안의 한 줄 (menu_name, unit_price 는 주문한 그때의 값을 복사한 것)
CREATE TABLE order_line (
    order_id    INTEGER NOT NULL REFERENCES orders (order_id),
    line_no     INTEGER NOT NULL CHECK (line_no >= 1),
    menu_id     INTEGER NOT NULL REFERENCES menu (menu_id) ON DELETE RESTRICT,
    quantity    INTEGER NOT NULL CHECK (quantity >= 1),
    menu_name   TEXT    NOT NULL CHECK (menu_name <> ''),
    unit_price  INTEGER NOT NULL CHECK (unit_price >= 0),
    PRIMARY KEY (order_id, line_no)
);

-- 라인에 붙은 옵션 한 가지와 그 횟수 (option_name, unit_price 도 그때의 값)
CREATE TABLE order_line_option (
    order_id     INTEGER NOT NULL,
    line_no      INTEGER NOT NULL,
    option_id    INTEGER NOT NULL REFERENCES option_item (option_id) ON DELETE RESTRICT,
    option_qty   INTEGER NOT NULL DEFAULT 1 CHECK (option_qty >= 1),
    option_name  TEXT    NOT NULL CHECK (option_name <> ''),
    unit_price   INTEGER NOT NULL CHECK (unit_price >= 0),
    PRIMARY KEY (order_id, line_no, option_id),
    FOREIGN KEY (order_id, line_no) REFERENCES order_line (order_id, line_no)
);

-- 세트의 구성 슬롯 (케이크 세트의 '음료', '디저트')
CREATE TABLE set_slot (
    slot_id      INTEGER PRIMARY KEY,
    set_menu_id  INTEGER NOT NULL REFERENCES menu (menu_id),
    name         TEXT    NOT NULL
                 CHECK (name <> '' AND name = btrim(name)),
    UNIQUE (set_menu_id, name)
);

-- 슬롯에 들어갈 수 있는 메뉴 (후보)
CREATE TABLE set_slot_menu (
    slot_id  INTEGER NOT NULL REFERENCES set_slot (slot_id),
    menu_id  INTEGER NOT NULL REFERENCES menu (menu_id),
    PRIMARY KEY (slot_id, menu_id)
);

-- 세트 라인이 슬롯마다 고른 메뉴 (menu_name 은 그때의 이름)
CREATE TABLE order_line_pick (
    order_id   INTEGER NOT NULL,
    line_no    INTEGER NOT NULL,
    slot_id    INTEGER NOT NULL,
    menu_id    INTEGER NOT NULL,
    menu_name  TEXT    NOT NULL CHECK (menu_name <> ''),
    PRIMARY KEY (order_id, line_no, slot_id),
    FOREIGN KEY (order_id, line_no) REFERENCES order_line (order_id, line_no),
    FOREIGN KEY (slot_id, menu_id)  REFERENCES set_slot_menu (slot_id, menu_id)
                                    ON DELETE RESTRICT
);

-- 쿠폰 한 종류 (정액 할인)
CREATE TABLE coupon (
    coupon_id   INTEGER     PRIMARY KEY,
    name        TEXT        NOT NULL UNIQUE
                CHECK (name <> '' AND name = btrim(name)),
    amount      INTEGER     NOT NULL CHECK (amount > 0),
    valid_from  TIMESTAMPTZ NOT NULL,
    valid_to    TIMESTAMPTZ NOT NULL,
    CHECK (valid_to > valid_from)
);

-- 쿠폰 발급: 이 회원이 이 쿠폰을 받았다 (같은 쿠폰은 회원당 한 번만 받는다)
CREATE TABLE coupon_issue (
    issue_id   INTEGER     PRIMARY KEY,
    coupon_id  INTEGER     NOT NULL REFERENCES coupon (coupon_id),
    member_id  INTEGER     NOT NULL REFERENCES member (member_id),
    issued_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (coupon_id, member_id)
);

-- 주문에 적용된 할인 한 건 (amount 는 그때 계산된 할인액)
CREATE TABLE order_discount (
    order_id     INTEGER NOT NULL REFERENCES orders (order_id),
    discount_no  INTEGER NOT NULL CHECK (discount_no >= 1),
    kind         TEXT    NOT NULL CHECK (kind IN ('쿠폰', '등급')),
    issue_id     INTEGER UNIQUE REFERENCES coupon_issue (issue_id),
    amount       INTEGER NOT NULL CHECK (amount > 0),
    PRIMARY KEY (order_id, discount_no),
    CHECK ((kind = '쿠폰') = (issue_id IS NOT NULL))
);

-- 한 주문에 등급 할인은 한 번만
CREATE UNIQUE INDEX order_discount_grade_once
    ON order_discount (order_id) WHERE kind = '등급';

-- 포인트 원장: 늘고 주는 내역을 쌓기만 한다 (잔액은 delta 의 합)
CREATE TABLE point_ledger (
    entry_id    INTEGER     PRIMARY KEY,
    member_id   INTEGER     NOT NULL REFERENCES member (member_id),
    reason      TEXT        NOT NULL CHECK (reason IN ('적립', '사용', '조정')),
    delta       INTEGER     NOT NULL,
    order_id    INTEGER     REFERENCES orders (order_id),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CHECK ((reason = '적립' AND delta > 0)
        OR (reason = '사용' AND delta < 0)
        OR (reason = '조정' AND delta <> 0)),
    CHECK (reason = '조정' OR order_id IS NOT NULL)
);

-- 한 주문에 적립도 사용도 한 번씩만
CREATE UNIQUE INDEX point_ledger_once
    ON point_ledger (order_id, reason) WHERE reason IN ('적립', '사용');
```

- 생성 순서(위 블록 순서): `btree_gist` 확장, `membership_grade`, `menu`, `member`, `orders`, `menu_price`, `option_group`, `option_item`, `menu_option_group`, `order_line`, `order_line_option`, `set_slot`, `set_slot_menu`, `order_line_pick`, `coupon`, `coupon_issue`, `order_discount`(+부분 인덱스), `point_ledger`(+부분 인덱스).
- 관계: `membership_grade` 1 — N `member`, `membership_grade` 1 — N `orders`(`member_grade`, 선택적), `menu` 1 — N `menu_price`, `coupon` 1 — N `coupon_issue`, `member` 1 — N `coupon_issue`, `orders` 1 — N `order_discount`, `coupon_issue` 1 — 0..1 `order_discount`(`issue_id UNIQUE`), `member` 1 — N `point_ledger`, `orders` 1 — N `point_ledger`(`order_id`, 선택적). 나머지는 v4 와 같다.
- 자동 생성 제약·색인 이름(PGlite 0.5.8 = PostgreSQL 18.3 에서 확인): `menu_price_pkey`, `menu_price_menu_id_tstzrange_excl`(EXCLUDE), `menu_price_check`(표 수준 CHECK), `coupon_issue_coupon_id_member_id_key`, `order_discount_issue_id_key`, `order_discount_check`(종류·발급 일치), `order_discount_amount_check`, `order_discount_grade_once`(부분 UNIQUE 인덱스), `orders_check`(표 수준 CHECK), `orders_member_grade_fkey`, `member_grade_fkey`, `point_ledger_check`(부호), `point_ledger_check1`(적립·사용은 주문 필수), `point_ledger_once`(부분 UNIQUE 인덱스), `menu_name_key`(v4 와 같다).
  **이전본과의 차이 하나**: 이전본에서는 `menu_price` 의 표 수준 CHECK 이름이 `menu_price_check1` 이다(이전 시점에 `menu.price` 의 CHECK 가 이미 `menu_price_check` 를 쓰고 있었기 때문). 본문은 이 이름을 인용하지 않는다.

### v4 → v5 이전 스크립트 (기존 데이터 보존, PGlite 로 검증)

순서는 **확장 → 이전 → 축소**다. ① `CREATE EXTENSION btree_gist;` 와 새 표 여섯(`membership_grade`, `menu_price`, `coupon`, `coupon_issue`, `order_discount`+인덱스, `point_ledger`+인덱스)을 위 DDL 그대로 만든다(`menu_price` 는 `menu` 가 있으면 되므로 이전 **앞**에서 만든다). ② 아래 스크립트로 기존 표를 바꾼다. **가격을 올리기 전에** 실행해야 한다.

```sql
BEGIN;
-- ① 스냅샷 열: NULL 을 허용해 더하고, 지금 값으로 채운 뒤 NOT NULL 을 건다
ALTER TABLE order_line
    ADD COLUMN menu_name TEXT, ADD COLUMN unit_price INTEGER;
ALTER TABLE order_line_option
    ADD COLUMN option_name TEXT, ADD COLUMN unit_price INTEGER;
ALTER TABLE order_line_pick ADD COLUMN menu_name TEXT;

UPDATE order_line AS ol
SET    menu_name = m.name, unit_price = m.price
FROM   menu AS m WHERE m.menu_id = ol.menu_id;
UPDATE order_line_option AS o
SET    option_name = i.name, unit_price = i.price
FROM   option_item AS i WHERE i.option_id = o.option_id;
UPDATE order_line_pick AS p
SET    menu_name = m.name
FROM   menu AS m WHERE m.menu_id = p.menu_id;

ALTER TABLE order_line
    ALTER COLUMN menu_name SET NOT NULL, ALTER COLUMN unit_price SET NOT NULL,
    ADD CHECK (menu_name <> ''), ADD CHECK (unit_price >= 0);
ALTER TABLE order_line_option
    ALTER COLUMN option_name SET NOT NULL, ALTER COLUMN unit_price SET NOT NULL,
    ADD CHECK (option_name <> ''), ADD CHECK (unit_price >= 0);
ALTER TABLE order_line_pick
    ALTER COLUMN menu_name SET NOT NULL, ADD CHECK (menu_name <> '');

-- ② 등급: 회원은 '일반'으로 시작하고, 옛 주문의 등급은 모르니 NULL 로 둔다
INSERT INTO membership_grade VALUES ('일반', 0), ('실버', 5), ('골드', 10);
ALTER TABLE member
    ADD COLUMN grade TEXT NOT NULL DEFAULT '일반' REFERENCES membership_grade (grade);
ALTER TABLE orders ADD COLUMN member_grade TEXT REFERENCES membership_grade (grade);
ALTER TABLE orders ADD CHECK (member_id IS NOT NULL OR member_grade IS NULL);

-- ③ 가격: 지금 가격을 이력의 첫 행으로 옮기고 menu.price 를 없앤다
INSERT INTO menu_price (menu_id, valid_from, price)
SELECT menu_id, '-infinity', price FROM menu;
ALTER TABLE menu DROP COLUMN price;
COMMIT;
```

- 검증(`cmp.mjs`): v4 DB(+5장 데이터)에 위 순서로 이전한 DB 와 처음부터 v5 로 만든 DB 를 비교했다. 열(73개, **열 순서 포함**)과 제약(150개)·색인(28개)이 같고, **차이는 `menu_price_check1` 이름 하나뿐**이다(위 "이전본과의 차이"). 열 순서가 같은 것은 v5 DDL 이 스냅샷 열·`grade`·`member_grade` 를 각 표의 **끝**에 놓았기 때문이다(v4 때 `line_no` 와 달리 열 순서 차이가 없다).
- **backfill 의 한계**: 스냅샷 열은 **현재 `menu.price`·`option_item.price`·이름**으로 채운다. "이전 전에 가격이 바뀐 적이 없다"는 가정 위에서만 정확하므로 **가격 인상 전에** 실행한다. 이미 올린 뒤라면 옛 가격을 아는 다른 기록이 있어야 한다(모르면 채우지 않고 조사). 이력의 첫 행은 시작을 `'-infinity'` 로 적는다(언제부터였는지 모르므로 지어낸 날짜를 쓰지 않는다). `orders.member_grade` 는 채우지 않고 NULL(등급제 이전 주문의 그때 등급은 기록 없음). `member.grade` 는 `DEFAULT '일반'`(지금 등급이 일반이라는 현재의 사실).
- `DROP COLUMN price` 는 **축소** 단계다. `menu.price` 를 읽던 앱·조회가 이 순간 깨지므로 현실에서는 앱을 먼저 `menu_price` 로 바꿔 배포한 뒤 마지막에 실행한다 → 9장(확장→이전→축소).
- 수백만 행 표에서 `UPDATE` 한 번이 서비스를 막는 문제 → 9장.

### v5 의 규칙과 누가 지키는가

### v5 설계 결정과 한계 (근거는 본문 화면 번호)

- **`menu.price` 를 지우고 `menu_price` 로 옮긴다**(화면 4). 이력의 "열린 행"과 `menu.price` 는 **같은 의미의 같은 사실**(진짜 중복)이라 집을 한 곳으로 정했다. 지금 가격은 저장하지 않고 조회로 계산한다(D4 와 같은 원칙). 대가: ① `menu.price` 를 읽던 앱·조회가 이전 순간 깨짐(축소 단계, 9장), ② 지금 가격 조회가 시간 조건 조인, ③ "판매 중인 모든 메뉴에 열린 가격 행이 있다"는 규칙은 DB 가 못 막음(점검 조회).
  **다른 장에 주는 영향(후속 집필자 주의)**: **7장** 줄 금액 계산은 이제 `order_line` + `order_line_option` **두 표 조인**이라 D4 의 조인 부담이 줄었고, 과거 주문의 합계는 스냅샷 덕에 바뀌지 않으므로 요약 테이블이 어긋날 위험이 작다. 지금 가격 조회(`menu_price`)·원장 합계·할인 내역 합계의 색인이 7장 후보다(`menu_price` 는 PK `(menu_id, valid_from)` 과 gist 색인이 이미 있다). **9장** `menu → menu + store_menu` 분리 실습의 "가격" 은 이미 `menu_price` 에 있으므로, 매장별 가격은 `menu_price` 에 `store_id` 를 더하고 EXCLUDE 를 `(store_id WITH =, menu_id WITH =, 기간 WITH &&)` 로 넓히는 일이 된다(`store_menu` 는 매장별 판매 여부·진열 쪽이 중심). 커리큘럼 9장의 "테이블 분리 실습" 문구는 이에 맞게 조정이 필요하다. **8장** 재고·레시피는 `menu`·`option_item` 키를 그대로 쓰며 가격과 무관하다.
- **옵션 가격에는 이력이 없다**(화면 4). `option_item.price` 는 "지금 가격"이고 과거 금액은 스냅샷이 지킨다. 하윤이 예약을 요구한 것은 메뉴 가격뿐이다. **정확성은 스냅샷이, 이력은 예약·분석이라는 별개 요구가 있을 때만**(화면 12 이력 과잉). 필요해지면 같은 모양의 표를 하나 더 둔다.
- **스냅샷 범위**(화면 2): `order_line`(`menu_name`, `unit_price`), `order_line_option`(`option_name`, `unit_price`), `order_line_pick`(`menu_name` 만 — 세트 구성품은 가격 없음, 세트 가격은 세트 줄의 `unit_price`). `menu_id`/`option_id` 는 남긴다(이름이 바뀌어도 같은 메뉴를 셈). `is_active` 등 "지금 상태"는 복사하지 않는다(복사하면 진짜 중복). 논증: `(order_id, line_no) → unit_price` 는 성립하고 `menu_id → unit_price` 는 반례(3월 4500, 4월 4800)가 있어 성립하지 않는다 → 이행 종속 아님 → 3NF 위반 아님. 이름도 업무가 "이름은 바뀔 수 있고 영수증엔 그때 이름"이라 하므로 종속 아님(업무가 "고정"이라 하면 위반).
- **총액·결제금액은 저장하지 않는다**(화면 9, **D4 결정 유지**). 세 금액을 구별한다: **소계**(줄 금액 합), **할인 후 금액**(소계 − 할인 합), **청구액**(할인 후 금액 − 사용 포인트). 모두 **그 주문 자신의 행**(스냅샷이 붙은 줄·옵션, `order_discount`, `point_ledger`)만으로 계산되고 저장하지 않는다. 저장하는 것은 "그때 계산된 **사실**"(줄 단가, 할인액, 적립·사용 행)이고 합계는 그 사실들의 **파생값**이다(3장 화면 9 와 모순 없음). 스냅샷 덕에 계산이 틀어질 원인(가격 변경)이 사라졌고, 끝난 주문 행은 고치지 않으므로(앱 규칙) 합계는 영원히 같다 → **7장 요약 테이블(D4 상환)을 얹어도 어긋날 위험이 작다.** 카드 승인 금액처럼 외부 시스템이 확정하는 "결제 사실"을 저장하는 설계는 결제 내역 표가 필요하며 이 교재 범위 밖이다(`orders.payment` 는 '카드'·'현금' 둘뿐이라 전액 포인트 결제·혼합 결제는 표현 불가).
- **프로모션은 새 표를 만들지 않는다**(화면 6). "기간을 가진 가격"이라 `menu_price` 의 기간 행으로 담는다(EXCLUDE 때문에 기존 행을 행사 시작에서 닫고 행사 행·복귀 행을 넣는다). 영수증에 할인 줄로 보여야 한다는 요구가 생기면 `order_discount.kind` 에 종류를 더하는 것을 검토한다. 할인 정책: 등급 할인 = 쿠폰 적용 **전** 소계 × 할인율(원 미만 절사), 쿠폰 = 정액, **중복 허용**, 할인의 합은 소계 이하(앱). 정책은 저장하지 않고 앱이 계산, **결과만** `order_discount` 에 저장.
- **쿠폰**(화면 7, 9): 정액·회원당 1회까지. 정률·메뉴 한정·N회 쿠폰은 범위 밖. **주문이 '취소'되어도 할인 행은 남으므로 쿠폰은 복원되지 않는다**(정책). 복원하려면 `voided_at` + 부분 UNIQUE 로 바꾼다(6장 직접 해보기 모범답안, 실행 확인).
- **등급**(화면 8): `grade` 를 자연키(텍스트)로 쓴다(이름이 거의 안 바뀜; 새 등급을 더하는 식으로 운영, 삭제·개명은 하지 않는다). 할인율은 `membership_grade` 에 둔다(`member_id → grade → discount_pct` 이행 종속 회피). `orders.member_grade` = 주문 시점 등급 스냅샷. **NULL 은 두 의미**(비회원 = 해당 없음, 회원인데 NULL = 등급제 이전 주문이라 기록 없음). `CHECK (member_id IS NOT NULL OR member_grade IS NULL)` 는 "비회원 주문에 등급 금지"만 DB 가 지킨다. **"회원 주문은 등급 필수"는 앱 규칙**으로 둔다: `(member_id IS NULL) = (member_grade IS NULL)` 를 `NOT VALID` 로 걸면 **옛 행을 어느 열이든 UPDATE 하는 순간 거부**되어(실측 오류 원문은 본문 화면 8 접힌 상자) 9장의 `ALTER TABLE orders ADD COLUMN store_id; UPDATE orders SET store_id = 1;` 같은 전체 행 갱신이 막히므로 채택하지 않았다. 등급 변경 이력 표는 만들지 않는다(주문이 그때 등급을 들고 있다, 화면 12).
- **포인트**(화면 10): **포인트는 할인이 아니라 결제수단**이라 `order_discount` 에 넣지 않고 원장에만 둔다(같은 사실을 두 표에 두면 진짜 중복). 적립 규칙: **청구액의 1%, 원 미만 절사**(401: 13490 → 134, 402: 청구액 2500 → 25). 원장은 쌓기만 한다(정정은 '조정' 행, UPDATE·DELETE 차단은 권한 관리라 범위 밖 = 앱 규칙). 부분 UNIQUE 로 주문당 적립·사용 1회(재시도 방어). 포인트 유효기간·소멸은 '조정' 행으로 흉내만 낸다.
- **가격 이력 표기**(화면 4): 기간은 `[valid_from, valid_to)` 반열림, `valid_to NULL` = 끝이 정해지지 않음(예약 인상이 있으면 열린 행이 미래에 시작할 수 있으므로 "지금 유효한 행"은 `valid_from <= NOW() AND (valid_to IS NULL OR NOW() < valid_to)` 로 고른다), 쿠폰 기간도 같은 반열림. 두 열 + `EXCLUDE ... tstzrange(valid_from, valid_to) WITH &&`(PostgreSQL). 다른 DB 는 앱·트랜잭션. PostgreSQL 18 의 `PRIMARY KEY (menu_id, valid_at WITHOUT OVERLAPS)`(기간 열 하나) 는 본문 접힌 상자에서 소개(PGlite 에서 실행 확인, 이 경우에도 `btree_gist` 필요). 빈틈은 `EXCLUDE` 가 못 막아 점검 조회(`LEAD`)를 둔다.
- **`btree_gist`**: PGlite 0.5.8 에서 `import { btree_gist } from '@electric-sql/pglite/contrib/btree_gist'` + `new PGlite({ extensions: { btree_gist } })` + `CREATE EXTENSION btree_gist;` 로 **로드된다**(EXCLUDE 오류 원문·겹침 거부·경계 맞닿음 통과 모두 실행 확인).

본문 DDL 은 아래와 한 글자도 다르지 않아야 한다(덩어리 단위 스크립트 비교, 빈 줄로 덩어리를 나눈다).

```sql
-- 일 매출 요약: 한 행 = 그 날(서울 시각) 들어온 취소 아닌 주문 전체의 합
CREATE TABLE daily_sales (
    sales_date    DATE        PRIMARY KEY,
    order_count   INTEGER     NOT NULL CHECK (order_count >= 0),
    subtotal      BIGINT      NOT NULL CHECK (subtotal >= 0),
    discount      BIGINT      NOT NULL CHECK (discount >= 0),
    refreshed_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CHECK (discount <= subtotal)
);
```

```sql
-- 기간으로 주문을 고른다 (일 매출 집계, 기간 조회)
```

- 생성 순서: `daily_sales` → 인덱스 5개(순서 무관). v5 → v5.1 은 **확장만** 있고 이전·축소 단계가 없다: 위 DDL 을 실행하고 요약을 채운다.
- 요약 채우기(본문 화면 8, 하루치. 과거 전체를 한 번에 채울 때는 기간의 시작 조건을 빼고 끝 조건만 "오늘 0시"로 둔다):

```sql
INSERT INTO daily_sales (sales_date, order_count, subtotal, discount)
WITH o AS (
    SELECT order_id, (ordered_at AT TIME ZONE 'Asia/Seoul')::date AS sales_date
    FROM   orders
    WHERE  status <> '취소'
      AND  ordered_at >= TIMESTAMPTZ '2026-09-30 00:00+09'
      AND  ordered_at <  TIMESTAMPTZ '2026-10-01 00:00+09'
)
SELECT o.sales_date,
       COUNT(*)                                            AS order_count,
       SUM(COALESCE(l.amount, 0) + COALESCE(x.amount, 0))  AS subtotal,
       SUM(COALESCE(d.amount, 0))                          AS discount
FROM   o
LEFT JOIN (SELECT ol.order_id, SUM(ol.quantity * ol.unit_price) AS amount
           FROM   order_line AS ol JOIN o ON o.order_id = ol.order_id
           GROUP BY ol.order_id) AS l ON l.order_id = o.order_id
LEFT JOIN (SELECT ol.order_id,
                  SUM(ol.quantity * ox.unit_price * ox.option_qty) AS amount
           FROM   order_line_option AS ox
           JOIN   order_line AS ol
                  ON ol.order_id = ox.order_id AND ol.line_no = ox.line_no
           JOIN   o ON o.order_id = ol.order_id
           GROUP BY ol.order_id) AS x ON x.order_id = o.order_id
LEFT JOIN (SELECT di.order_id, SUM(di.amount) AS amount
           FROM   order_discount AS di JOIN o ON o.order_id = di.order_id
           GROUP BY di.order_id) AS d ON d.order_id = o.order_id
GROUP BY o.sales_date;
```

- **갱신 방법(본문 화면 9, 이 교재의 선택 = 배치)**: 그날 행을 `DELETE` 한 뒤 위 `INSERT ... SELECT` 를 같은 트랜잭션에서 실행한다(`BEGIN; DELETE FROM daily_sales WHERE sales_date = DATE '2026-09-30'; INSERT ...; COMMIT;`). 몇 번 실행해도 결과가 같고(멱등), 그날 주문이 전부 취소되어 조회 결과에 날짜가 없는 경우에도 옛 행이 남지 않는다(`ON CONFLICT DO UPDATE` 만 쓰면 옛 행이 남는 것을 실행 확인). 최근 며칠을 다시 계산해 마감 뒤 취소·과거 주문 수정에 대비한다. 증분 방식(트리거·앱)은 `INSERT ... ON CONFLICT (sales_date) DO UPDATE SET order_count = daily_sales.order_count + EXCLUDED.order_count, ...` 모양이고 **멱등이 아니다**(재시도로 두 번 실행하면 그날 주문 수 1 → 3, 실행 확인).
- **점검 조회**: `WITH raw AS (<위 SELECT, 마감된 날 전체>) SELECT ... FROM raw AS r FULL JOIN daily_sales AS s USING (sales_date) WHERE r.order_count IS DISTINCT FROM s.order_count OR ...` 비어 있어야 정상. 일부러 한 행을 고쳐 보면 그날이 나오는 것을 실행 확인.

### v5.1 설계 결정과 한계 (근거는 본문 화면 번호)

- **요약 표의 입도는 하루**(화면 8). 한 행 = "그 날(서울 시각)에 들어온 취소 아닌 주문 전체의 합". 날짜는 `(ordered_at AT TIME ZONE 'Asia/Seoul')::date` 로 만들되, 조회의 `WHERE` 는 `ordered_at` 범위 그대로 둔다(열에 함수를 씌우면 인덱스를 못 쓴다: 실측 22쪽 vs 9,141쪽). `status <> '취소'` 이므로 접수·제조중 주문도 집계에 들어간다. 배치는 마감 뒤에 돌고 안 끝난 주문이 남으면 그 날을 다시 계산한다(멱등).
- **`orders` 에 `total` 열을 두지 않는다**(D4 결정 유지). 요약은 읽는 단위(하루)에 맞춘 파생 표이고, 주문 단위 총액 열은 1년치에서 여전히 47만 행을 더해야 해서 해법이 아니다.
- **표 안에서도 파생값은 저장하지 않는다.** 할인 후 금액(매출)은 `subtotal - discount` 로 읽을 때 뺀다. 청구액(포인트 차감)은 열이 없다(필요해지면 열을 더하되 원장에서 주문별로 먼저 합해야 곱해지지 않는다).
- **금액 계산 쿼리의 모양**: 줄·옵션·할인 세 자식 표를 각각 **주문별 합으로 먼저 줄인 뒤** 주문에 붙인다(화면 8). 조인 부풀림(6장 화면 9)을 피하는 것이 정확성의 핵심이다.
- **인덱스 5개와 FK 판정**(화면 5, 7): v5 의 외래키 22개 중 11개는 복합 PK·UNIQUE 의 **선두 열**이라 이미 덮여 있다. 만든 것 3개(`orders.member_id` 는 복합 `(member_id, ordered_at)` 가 겸함, `point_ledger.member_id`, `coupon_issue.member_id`). **일부러 만들지 않은 것 8개**: `order_line.menu_id`·`order_line_option.option_id`(큰 표이지만 조회가 이 열로 들어오지 않고 값 하나가 표의 12~20% 라 이득이 없거나 작음. 부모를 지우지 않음(C6), `menu_price` FK 가 먼저 막음, 삭제 검사 183ms 가 한 번), `member.grade`·`orders.member_grade`(값 3종), `menu_option_group.group_id`·`set_slot_menu.menu_id`·`order_line_pick (slot_id, menu_id)`(부모가 작고 안 지움), `point_ledger.order_id`(`point_ledger_once` 가 부분 인덱스라 `reason` 조건 없이는 못 씀. 청구액 계산은 `reason = '사용'` 을 붙인다). 이 판단은 "조회와 삭제 빈도가 바뀌면 다시 본다"이다. 2·4·5장의 "외래키 색인은 7장에서" 약속은 이 표로 갚았다.
- **인덱스 비용**(화면 7): 같은 열의 표 셋에 같은 10만 건을 번갈아 6번 넣은 중앙값이 PK 만 1.0, +3개 2.7배, +7개 4.4배(인덱스 크기 19·51·74MB, 표 60MB). 실제 `orders` 에서는 외래키·CHECK 비용이 섞여 1.1~2.3배로 흔들렸다.
- **포인트 잔액 캐시는 만들지 않는다**(화면 9). `point_ledger(member_id)` 인덱스로 6,142쪽 → 180쪽이라 속도 이유가 없고, 잔액 열을 두는 이유는 `CHECK (point_balance >= 0)` 로 C12 를 되살리는 것인데 그것은 원장과 같은 트랜잭션 갱신이라는 원자성 문제다 → 8장.
- **요약 표 대신 머티리얼라이즈드 뷰**(화면 9, 반대 의견): 전체 재계산(하루만 불가)이 약점이고 `REFRESH ... CONCURRENTLY` 는 UNIQUE 인덱스가 필요하다(`cannot refresh materialized view ... concurrently` 실행 확인).
- **판매중지 메뉴 행 정리는 하지 않는다**(화면 11, 6장 빚): `menu` 는 수십 행이고 쌓이는 곳은 주문 쪽이다. 아카이브 표에는 외래키를 걸지 않는다(스냅샷 열이 이름·단가를 들고 있어 `menu` 없이 읽힌다).
- **파티셔닝은 설명 수준**(화면 11): PK 에 분할 열이 들어가야 하고(`unique constraint on partitioned table must include all partitioning columns`), 그러면 `order_line` 등 자식의 외래키가 `orders (order_id)` 를 가리킬 수 없다(`there is no unique constraint matching given keys for referenced table`). 자식 표도 분할 열을 들고 다니도록 바꾸는 스키마 변경이라 이 장에서 하지 않고 9장으로 넘긴다. 아카이브는 자식 먼저 옮기고, 포인트 원장은 잔액이 전체 합이라 대상에서 빼거나 '조정' 행으로 이월해야 하며, 원본을 지운 날은 요약이 유일한 기록이 된다.

### 8장이 이어받는 것

- **v6 = v5.1 + 재고 품목·레시피·픽업 슬롯**(8장 요구3). 8장의 새 표는 `menu`·`option_item` 키를 그대로 쓰며 `daily_sales`·인덱스 5개는 건드리지 않는다. 기획서 §3.2 의 v6 열에 적힌 "일 매출 요약(7장)"은 이 v5.1 이 이미 도입한 것이다.
- **요약 갱신의 동시성**: 증분(트리거·앱) 방식은 모든 주문이 "오늘 행" 하나에 쓰기를 몰고(줄 서기) 재시도에 멱등이 아니다. 배치 방식도 재계산 도중 들어오는 주문과 어떻게 만나는지(격리 수준) → 8장 `.later`.
- **포인트 잔액 캐시**: 원장과 잔액 열을 한 트랜잭션에서 갱신하는 원자성 + `CHECK (point_balance >= 0)` → 8장 `.later`.
- **C1·C11·C12 와 주문 생성 한 묶음**(D5): 변함없이 8장. 8장의 "주문 생성 트랜잭션"은 요약을 건드리지 않는다(요약은 배치가 만든다).

### 9장 영향 (후속 집필자 주의)

- `daily_sales` 의 PK 는 `(store_id, sales_date)` 로, `orders` 의 인덱스는 `store_id` 를 앞 열로 넓힌다(`orders_ordered_at_idx` → `(store_id, ordered_at)` 등). 요약의 "서울 시각" 날짜는 매장별 시간대가 필요해지면 다시 본다.
- 운영 중인 큰 표에 `CREATE INDEX` 는 쓰기를 막으므로 `CREATE INDEX CONCURRENTLY`(트랜잭션 안에서 못 씀)가 확장→이전→축소 흐름과 만난다(본문 화면 7 `.later`).
- 파티셔닝(화면 11 `.later`)을 하려면 `orders` PK 를 `(order_id, ordered_at)` 로 바꾸고 자식 표의 외래키 열을 늘려야 한다. 전 행 변경이므로 9장의 PK 바꾸기 실습과 같은 종류다.

### v5.1 이 남긴 것

- **D4 상환**(7장 화면 8·9): 소계·할인 후 금액을 주문 단위로 저장하지 않는 결정은 유지하고, 읽는 단위(일)의 파생 표를 얹어 되돌렸다. "비정규화는 정규화를 안 한 것이 아니라 한 뒤에 되돌린 것"(3장)의 재회수.
- **앞 장 `.later` 중 7장 몫 전부 상환**: 앞 장 위치 → 갚은 7장 화면(본문 화면 11 표와 같다): ch00 화면 3·6, ch01 화면 10·11, ch02 화면 5·6·9·11, ch03 화면 9·14·16, ch04 화면 5·6·10, ch05 화면 6(네 표 조인 → 화면 8, 옵션 FK → 화면 5)·12, ch06 화면 3(→5)·5(→11)·9(→9)·10(→9)·11(→8)·13(→9).
- **D2**: 그대로(매장 1개) → 9장. **D5 와 같은 모양**(C1, C9, C10, C12, 주문 생성 한 묶음) → 8장.
- 8장: 요약 갱신 동시성, 포인트 잔액 캐시. 9장: 요약 PK·인덱스에 `store_id`, `CREATE INDEX CONCURRENTLY`, 파티셔닝을 위한 PK 변경.

## v6 (8장 후)

요구3(재고·재료 부족 메뉴 주문 차단·픽업 시간 예약)이 들어와, 지금까지의 "한 요청이 규칙을 지키면 끝"이 **동시 요청에서 깨진다**. **표 22개**: v5.1 의 18개 중 17개는 **하나도 바뀌지 않고**(열·제약·인덱스 모두), `orders` 에 **열 하나**(`pickup_start`)가 더해지며, 새 표 4개(`stock_item`, `menu_recipe`, `option_recipe`, `pickup_slot`)가 생긴다. `daily_sales` 와 인덱스 5개는 건드리지 않는다.
본문 DDL 은 아래와 한 글자도 다르지 않아야 한다(덩어리 단위 스크립트 비교, 빈 줄로 덩어리를 나눈다). 본문은 앞 세 덩어리를 화면 2 에서, 뒤 두 덩어리를 화면 11 에서 보인다.

```sql
-- 재고 품목 한 가지 (완제품: 케이크·쿠키, 원재료: 원두·우유·시럽). qty 는 지금 남은 양
CREATE TABLE stock_item (
    item_id  INTEGER PRIMARY KEY,
    name     TEXT    NOT NULL UNIQUE
             CHECK (name <> '' AND name = btrim(name)),
    kind     TEXT    NOT NULL CHECK (kind IN ('완제품', '원재료')),
    unit     TEXT    NOT NULL CHECK (unit <> ''),
    qty      INTEGER NOT NULL CHECK (qty >= 0)
);

-- 메뉴 1개를 만들 때 이 품목을 amount 만큼 쓴다 (완제품은 소요량 1)
CREATE TABLE menu_recipe (
    menu_id  INTEGER NOT NULL REFERENCES menu (menu_id),
    item_id  INTEGER NOT NULL REFERENCES stock_item (item_id),
    amount   INTEGER NOT NULL CHECK (amount > 0),
    PRIMARY KEY (menu_id, item_id)
);

-- 옵션을 1회 고를 때마다 이 품목을 amount 만큼 더 쓴다
CREATE TABLE option_recipe (
    option_id  INTEGER NOT NULL REFERENCES option_item (option_id),
    item_id    INTEGER NOT NULL REFERENCES stock_item (item_id),
    amount     INTEGER NOT NULL CHECK (amount > 0),
    PRIMARY KEY (option_id, item_id)
);

-- 픽업 시간대(픽업 슬롯) 하나: 정원과 지금까지 받은 주문 수 (주문 1건이 정원 1을 쓴다)
CREATE TABLE pickup_slot (
    slot_start  TIMESTAMPTZ PRIMARY KEY,
    capacity    INTEGER     NOT NULL CHECK (capacity >= 0),
    reserved    INTEGER     NOT NULL DEFAULT 0 CHECK (reserved >= 0),
    CHECK (reserved <= capacity)
);

-- 주문 한 건 (v5 와 다른 곳은 pickup_start 한 줄: 픽업 시간을 예약한 주문이면 그 슬롯)
CREATE TABLE orders (
    order_id      INTEGER     PRIMARY KEY,
    member_id     INTEGER     REFERENCES member (member_id),
    ordered_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    payment       TEXT        NOT NULL CHECK (payment IN ('카드', '현금')),
    barista       TEXT        NOT NULL,
    status        TEXT        NOT NULL DEFAULT '접수'
                  CHECK (status IN ('접수', '제조중', '완료', '픽업', '취소')),
    member_grade  TEXT        REFERENCES membership_grade (grade),
    pickup_start  TIMESTAMPTZ REFERENCES pickup_slot (slot_start),
    CHECK (member_id IS NOT NULL OR member_grade IS NULL)
);
```

- 생성 순서: `stock_item` → `menu_recipe`·`option_recipe`(v5 의 `menu`·`option_item` 이 있어야 한다) → `pickup_slot` → `orders`. **처음부터 v6 을 만들 때**는 v5 DDL 의 `orders` 를 위 `orders` 로 바꾸고 `pickup_slot` 을 그 앞에 둔다.
- 관계: `menu` 1 — N `menu_recipe` N — 1 `stock_item`, `option_item` 1 — N `option_recipe` N — 1 `stock_item`(메뉴·옵션과 재고 품목의 **N:M 연결 둘**, 연결의 속성이 `amount`), `pickup_slot` 1 — N `orders`(`pickup_start`, 선택적).
- 자동 생성 제약 이름(PostgreSQL 18.4 에서 확인): `stock_item_pkey`, `stock_item_name_key`, `stock_item_name_check`, `stock_item_kind_check`, `stock_item_unit_check`, `stock_item_qty_check`, `menu_recipe_pkey`, `menu_recipe_menu_id_fkey`, `menu_recipe_item_id_fkey`, `menu_recipe_amount_check`, `option_recipe_pkey`, `option_recipe_option_id_fkey`, `option_recipe_item_id_fkey`, `option_recipe_amount_check`, `pickup_slot_pkey`, `pickup_slot_capacity_check`, `pickup_slot_reserved_check`, **`pickup_slot_check`**(표 수준 `reserved <= capacity`, 앱이 오류를 번역할 때 이 이름으로 구분), `orders_pickup_start_fkey`. `qty >= 0` 위반 오류는 `stock_item_qty_check`.

### v5.1 → v6 이전 스크립트 (기존 데이터 보존, PostgreSQL 18.4 로 검증)

순서는 **확장**뿐이다(이전·축소 단계 없음). 새 표 넷을 위 DDL 그대로 만들고(`pickup_slot` 이 `orders` 변경보다 먼저), 아래를 실행한다. 기존 주문 행은 `pickup_start` 가 NULL 이다(현장 주문).

```sql
BEGIN;
-- (새 표 넷을 위 DDL 로 먼저 만든다: stock_item, menu_recipe, option_recipe, pickup_slot)
ALTER TABLE orders ADD COLUMN pickup_start TIMESTAMPTZ
    REFERENCES pickup_slot (slot_start);
COMMIT;
```

- 검증(`cmp6.mjs`): v5.1 DB 에 위 순서로 이전한 DB 와 **처음부터 v6 로 만든 DB** 의 열(순서 포함)·제약(정의 포함)·색인을 비교했다. 열 순서가 같은 것은 `pickup_start` 를 `orders` 의 **끝**에 놓았기 때문이다.
- 이 한 줄이 운영 중인 큰 `orders` 표에서 하는 일(락, FK 검증 비용)은 9장.

### v6 예시 데이터 (정본)

### v6 의 규칙과 누가 지키는가

| 규칙 | 수단 | 위치 |
|---|---|---|
| C2~C6, C8, C9(범위 저장 부분), C10(구성 부분) | v5 와 같다 | DB / 앱 |
| **C13** 재고는 음수가 될 수 없다 | `stock_item.qty CHECK (qty >= 0)`(마지막 방어선) + **조건부 `UPDATE ... SET qty = qty - n WHERE item_id = ? AND qty >= n`** + 영향 행 수 확인(0이면 전체 취소). 락은 `UPDATE` 가 건다 | DB + 앱(0행 처리) |
| **C14** 픽업 슬롯 정원 | `pickup_slot` 카운터 `reserved` + `CHECK (reserved <= capacity)`(마지막 방어선) + 조건부 `UPDATE ... SET reserved = reserved + 1 WHERE ... AND reserved < capacity`. 카운터와 주문의 일치(파생값)는 점검 조회 + 취소 시 같은 트랜잭션에서 −1 | DB + 앱 |
| **C17** 재료 부족 메뉴·옵션은 주문할 수 없다 | 키오스크 표시 = **조회로 계산**(저장 안 함, 개별 메뉴·옵션 단독 판정, 참고용) + **주문 확정 트랜잭션의 조건부 차감**이 최종 판정 | 앱 + 트랜잭션 |
| **C1 (상환, D5)** 주문은 라인 1개 이상 | 여전히 **보통의 선언으로는 표현되지 않음**(지연 가능 외래키 우회는 쓰지 않음, 4장). 주문 생성 한 트랜잭션 안에서 앱이 `COUNT` 를 확인하고 `COMMIT`. 한 주문의 행들은 커밋 전에 남에게 보이지 않으므로 중간 상태가 새지 않는다 | **앱 + 트랜잭션** |
| **C7 (완성)** 상태 전이 순서 | `UPDATE orders SET status = 새 상태 WHERE order_id = ? AND status IN (이전 상태들)` 의 영향 행 수. 동시 요청에서는 락 대기 뒤 **새 상태로 `WHERE` 를 다시 평가**해 한쪽이 0행. '조회 후 저장'(무조건 `UPDATE`)은 한쪽 결과를 덮어쓴다 | 앱(조건부 `UPDATE`) |
| **C9·C10 (완성)** 옵션 합계 범위·세트 슬롯 충족 | 한 주문 안의 규칙이라 **주문 생성 트랜잭션에서 `COMMIT` 직전에** 5장의 점검 조회를 그 주문 번호로 실행(0행이어야). 그 주문은 커밋 전에 남에게 안 보이므로 별도 락이 필요 없다. 남은 틈: 옵션 그룹의 범위를 관리자가 바꾸는 순간과의 경쟁(드묾, 허용) | 앱 + 트랜잭션 |
| **C11 (완성)** 쿠폰 회원당 1회 | v5 의 `UNIQUE` 두 개가 동시 사용도 막는다(나중 트랜잭션은 앞 트랜잭션의 커밋·롤백을 기다린 뒤 커밋이면 `23505`, 롤백이면 통과). 그 **오류가 주문 전체 롤백이 되게 하는 것**이 트랜잭션. "N회 쿠폰"은 `UNIQUE` 로 불가 → 발급 행을 잠그고 센다(C12 와 같은 모양) | DB + 트랜잭션 |
| **C12 (완성)** 포인트 잔액 ≥ 0 | 선언 불가. **`member` 행을 `FOR UPDATE` 로 잠근 뒤** 원장 합계 확인 → 사용 행 삽입. 한 회원의 동시 주문이 한 줄로 선다. 잔액 열(캐시)은 **만들지 않는다**(결정 아래) | 앱 + 트랜잭션 |
| 요약 갱신(7장 `.later`) | 주문 생성 트랜잭션은 `daily_sales` 를 건드리지 않는다(배치가 만든다). 배치 두 개가 같은 날을 동시에 돌리면 한쪽이 `daily_sales_pkey` 위반(`23505`)으로 실패 → 배치는 한 번에 하나 | 앱(배치 운영) |
| **락 순서 규칙** | 모든 주문 트랜잭션은 **회원 → 주문 행 → 재고 품목(번호 오름차순) → 픽업 슬롯 → 할인·포인트 행 삽입** 순서로 자원을 잡는다(주문 생성에서는 주문 행이 새로 넣는 행이라 남과 맞물리지 않는다). 순서가 같으면 서로 기다리다 맞물리는 교착(40P01)이 안 생긴다. 데드락·직렬화 실패(40001)가 나면 앱이 **트랜잭션 전체를 재시도** | 앱 |
| v6 자체 규칙(C 번호 없음) | `stock_item.kind` 값 목록, `unit <> ''`, 이름 공백 금지, 소요량 `amount > 0`, `capacity >= 0`, `reserved >= 0` | DB |

### v6 설계 결정과 한계 (근거는 본문 화면 번호)

- **수량은 정수, 기본 단위로 저장**(화면 2). 원두 g, 우유·시럽 ml, 완제품 개. 소수·단위 변환(1kg 팩 → g)은 입고 입력의 일이고 이 표는 기본 단위만 안다.
- **완제품도 레시피(소요량 1 행)로 통일**(화면 2). 대안: `menu.stock_item_id` 같은 직접 열(완제품 전용 경로). 통일한 이유는 **차감 경로가 하나**(메뉴 → 레시피 → 품목)라 주문 트랜잭션에 `kind` 분기가 없기 때문이다. 대가: 완제품의 소요량 1 행이 군더더기처럼 보이고, `kind` 는 **동작을 바꾸지 않는 분류**(목록·발주 구분용)가 된다. 케이크 한 판을 8조각으로 파는 경우는 조각 단위를 품목으로 삼아 입고 때 조각 수로 입력한다(이 교재의 선택. 소요량이 정수여야 하므로 "1/8 판"을 쓰지 않는다).
- **세트 메뉴 자체에는 레시피를 두지 않는다**(화면 2·3·8). 세트 줄이 쓰는 재고는 고른 구성 메뉴(`order_line_pick.menu_id`)의 `menu_recipe` × 줄 `quantity` 다. 주문 생성 트랜잭션의 필요량 조회에 `order_line_pick` 을 잇는 세 번째 `UNION ALL` 가지가 더 필요하고(실행 확인: 주문 202 → 원두 18, 티라미수 1), 본문 화면 8·12 는 단품 줄만 보인다. **키오스크 품절 조회는 세트를 항상 주문 가능으로 본다**(한계, 화면 3): 세트의 품절은 "슬롯마다 후보 하나라도 팔 수 있다"라 한 겹 더 안쪽 `NOT EXISTS` 가 된다.
- **'덜 쓰는' 옵션은 표현하지 않는다**(화면 2). `amount > 0` 이라 "시럽 빼기" 같은 감소 옵션은 `option_recipe` 에 행이 없고, 기본 레시피(카페라떼의 시럽 10ml)가 그대로 차감된다 = **안전한 쪽(과다 차감)으로 틀린다**. 대안은 `amount <> 0` 로 음수를 허용하는 것인데, 그러면 "메뉴 + 옵션 합이 0 이상" 이라는 또 하나의 여러 행 규칙이 생겨 채택하지 않았다.
- **재고 변동 원장은 두지 않는다**(화면 2·14). `qty` 열이 C13 의 `CHECK` 대상이자 **락을 걸 행**이다. 6장의 포인트는 정정·감사가 핵심이라 원장을 택했지만, 재고는 "지금 몇 개 남았나"와 "음수 금지"가 중심이다. 입고·폐기·실사·취소 복원의 이력이 필요해지면 `stock_movement`(증감 행)를 **더하고 `qty` 는 그 합의 캐시**로 두되 두 표를 같은 트랜잭션에서 고친다(화면 10 의 포인트 잔액 캐시와 같은 모양). **취소 복원이 정확하려면 "그 주문이 실제로 얼마를 차감했는가"가 있어야** 한다 — 레시피가 그 뒤에 바뀌었으면 재계산 값이 어긋난다(6장 스냅샷과 같은 논리). v6 은 이 기록을 두지 않고 한계로 둔다.
- **포인트 잔액 캐시(`member.point_balance`)를 만들지 않는다**(화면 10, 7장 `.later` 판단). 속도 이유는 없고(7장), C12 는 `member` 행 락으로 지킬 수 있다. 캐시를 두면 `CHECK (point_balance >= 0)` 로 음수 금지를 선언으로 되살릴 수 있고(실행 확인: 동시 사용 시 나중 쪽이 `member_point_balance_check` 위반 `23514`), 대가는 원장과 잔액을 **한 트랜잭션에서 같이 고쳐야 하는 규율**과 어긋남 위험이다. 판단 기준: 잔액 조회·차감이 아주 잦아 합계가 병목이거나 DB 제약으로 마지막 방어선을 세우고 싶으면 캐시를 둔다.
- **픽업 슬롯: 시작 시각이 PK, 주문 1건이 정원 1**(화면 11). 슬롯 길이는 저장하지 않는다(모두 같다는 앱의 약속, 달라지면 `slot_end` 열). 정원 단위가 "주문 수"이므로 잔 수·메뉴 종류는 무관하다. **`reserved` 는 `orders` 로 센 수와 같아야 하는 파생값이라 같은 사실의 중복**(D4·7장 요약 표와 같은 질문)이다. 채택 이유: ① `CHECK (reserved <= capacity)` 가 **마지막 방어선**으로 선언된다, ② 락 대상(행)이 있다. 대가: 취소·변경 때 같은 트랜잭션에서 −1 해야 하고 점검 조회가 필요하다. 반대 의견: 카운터 없이 슬롯 행만 `FOR UPDATE` 로 잠그고 `COUNT` 하면 중복이 없다(대신 선언적 방어선이 없다).
- **`orders.pickup_start` 는 NULL 허용**: 현장 주문은 슬롯이 없다. "그 슬롯이 아직 안 지났는가, 지금 시각 + 준비 시간 이후인가"는 앱.
- **인덱스 판단(7장 기준 적용)**: `orders.pickup_start` FK 에는 인덱스를 만들지 않는다(슬롯 삭제를 하지 않고, 슬롯별 주문 수 점검은 최근 기간 `ordered_at` 범위로 한정). `menu_recipe.item_id`·`option_recipe.item_id` 도 표가 작고 품목을 지우지 않아 만들지 않는다.
- **취소**(화면 14): 같은 트랜잭션에서 **회원 행 잠금 → 조건부 `UPDATE`(상태) → (접수 상태였으면) 재고 복원(번호 순) → 슬롯 −1**(락 순서 규칙과 같은 순서: 회원 → 주문 행 → 재고 → 슬롯. 슬롯을 먼저 잡으면 생성 트랜잭션과 교착이 난다, 실행 확인). 조건부라서 두 번 취소해도 두 번째는 0행이라 이중 복원이 없다. 쿠폰·포인트는 6장 정책(쿠폰 비복원, 원장은 '조정' 행으로 정정)을 따른다.
- **교재의 동시성 검증 환경**: 진짜 PostgreSQL 18.4(Windows, `embedded-postgres`) 서버에 연결 둘 이상으로 실행하고, 락 대기는 `pg_stat_activity` 의 `wait_event_type = 'Lock'` 으로 확인했다. 위젯의 규칙 모델은 가능한 모든 실행 순서(112개)를 같은 서버에서 재생해 대조했다.

### v6 이 남긴 것

- **D5 상환**(8장 화면 12): C1 은 여전히 보통의 선언으로 지키지 않고, **한 트랜잭션 + 앱의 확인**으로 지킨다. C9·C10 도 같은 자리에서 점검한다.
- **앞 장 `.later` 중 8장 몫 12개 전부 상환**(본문 화면 13 표, 앞 장 화면 번호는 실제 `.later` 위치): ch00 화면 7(트랜잭션 맛보기 → 화면 4·5), ch04 화면 1(조회 후 저장 → 화면 6·10)·화면 8(C7 → 화면 6)·화면 9(D5 → 화면 12), ch05 화면 7(C9 → 화면 12)·화면 9(C10 → 화면 12), ch06 화면 2(복사 → 화면 12)·화면 7(N회 쿠폰 → 화면 10)·화면 9(쿠폰 오류 전체 취소 → 화면 10)·화면 10(포인트 잠금 → 화면 10), ch07 화면 9(트리거 줄 서기 → 화면 9, 잔액 캐시 → 화면 10).
- **D2**: 그대로 → 9장. 다만 **재고 품목과 픽업 슬롯도 매장마다 달라진다**(D2 가 재고·슬롯까지 넓어짐): 9장에서 `stock_item`·`pickup_slot` 의 키에 `store_id` 가 들어가고, 재고 락의 범위(매장별)가 달라진다.
- 9장: `ALTER TABLE orders ADD COLUMN ... REFERENCES` 의 락과 검증, `orders` 에 `store_id` 를 더할 때의 슬롯 키 변경.
- 없는 것(한계로 본문에 명시): 재고 변동 이력, 차감 기록(취소 복원의 정확성), 세트 품절 조회, 감소 옵션, 장바구니 재고 예약(담아 둔 동안 재고 잡아 두기), 재고 부족 시 대체 메뉴 제안.

## v7 (9장 후)

요구4(가맹점 확대)가 들어와 2장이 남긴 D2("매장은 하나뿐이다")가 청구된다. **표 25개**: v6 의 22개 중 5개가 바뀌고(`orders`, `menu_price`, `pickup_slot`, `daily_sales`, `stock_item`) 17개는 **하나도 바뀌지 않으며**(열·제약 모두 v6 와 글자까지 같다), 새 표 3개(`store`, `store_menu`, `store_stock`)가 생긴다.
본문 DDL 은 아래와 한 글자도 다르지 않아야 한다(덩어리 단위 스크립트 비교, 빈 줄로 덩어리를 나눈다). 본문은 화면 3 에서 `store`·`store_menu`·`menu_price` 덩어리를, 화면 12 의 접힌 상자 "v7 변경 DDL 한눈에 보기"에서 바뀐 표 전부(`stock_item`, `store`·`store_menu`·`store_stock`, `menu_price`, `orders`·`pickup_slot`·`daily_sales`, 바뀐 색인 둘)를 다시 보이고(`store_stock` 은 화면 6 의 1단계 스크립트에도 들어 있다) 나머지 17개 표는 v6 DDL 그대로다. **처음부터 v7 을 만들 때**는 아래 네 블록을 순서대로 실행한다(영역: ① 브랜드 공통 ② 매장 ③ 주문 ④ 요약·색인).

**영역 ① 브랜드 공통(14개 표, `btree_gist` 확장 포함) — 13개는 v6 와 같고 `stock_item` 만 `qty` 가 빠졌다**

```sql
-- 겹침 방지(EXCLUDE)에서 정수와 구간을 함께 비교하려면 필요한 확장
CREATE EXTENSION btree_gist;

-- 회원 등급과 등급별 할인율
CREATE TABLE membership_grade (
    grade         TEXT    PRIMARY KEY
                  CHECK (grade <> '' AND grade = btrim(grade)),
    discount_pct  INTEGER NOT NULL CHECK (discount_pct BETWEEN 0 AND 100)
);

-- 메뉴 한 종류 (가격은 menu_price 로 옮겨 갔다)
CREATE TABLE menu (
    menu_id    INTEGER PRIMARY KEY,
    name       TEXT    NOT NULL UNIQUE
               CHECK (name <> '' AND name = btrim(name)),
    is_active  BOOLEAN NOT NULL DEFAULT TRUE
);

-- 회원 한 명 (grade 는 지금 등급)
CREATE TABLE member (
    member_id  INTEGER PRIMARY KEY,
    name       TEXT    NOT NULL,
    phone      TEXT    NOT NULL UNIQUE
               CHECK (phone ~ '^01[0-9]-[0-9]{3,4}-[0-9]{4}$'),
    grade      TEXT    NOT NULL DEFAULT '일반' REFERENCES membership_grade (grade)
);

-- 옵션 그룹 한 종류 (샷, 시럽, 얼음 ...)와 고를 수 있는 개수 범위
CREATE TABLE option_group (
    group_id    INTEGER PRIMARY KEY,
    name        TEXT    NOT NULL UNIQUE
                CHECK (name <> '' AND name = btrim(name)),
    min_select  INTEGER NOT NULL DEFAULT 0 CHECK (min_select >= 0),
    max_select  INTEGER NOT NULL CHECK (max_select >= 1),
    CHECK (max_select >= min_select)
);

-- 옵션 한 가지 (샷 추가, 얼음 적게 ...)와 그 가격. 0원 옵션은 0 으로 적는다
CREATE TABLE option_item (
    option_id  INTEGER PRIMARY KEY,
    group_id   INTEGER NOT NULL REFERENCES option_group (group_id),
    name       TEXT    NOT NULL
               CHECK (name <> '' AND name = btrim(name)),
    price      INTEGER NOT NULL CHECK (price >= 0),
    is_active  BOOLEAN NOT NULL DEFAULT TRUE,
    UNIQUE (group_id, name)
);

-- 이 메뉴에서 이 옵션 그룹을 고를 수 있다 (메뉴와 옵션 그룹의 N:M 연결)
CREATE TABLE menu_option_group (
    menu_id   INTEGER NOT NULL REFERENCES menu (menu_id),
    group_id  INTEGER NOT NULL REFERENCES option_group (group_id),
    PRIMARY KEY (menu_id, group_id)
);

-- 세트의 구성 슬롯 (케이크 세트의 '음료', '디저트')
CREATE TABLE set_slot (
    slot_id      INTEGER PRIMARY KEY,
    set_menu_id  INTEGER NOT NULL REFERENCES menu (menu_id),
    name         TEXT    NOT NULL
                 CHECK (name <> '' AND name = btrim(name)),
    UNIQUE (set_menu_id, name)
);

-- 슬롯에 들어갈 수 있는 메뉴 (후보)
CREATE TABLE set_slot_menu (
    slot_id  INTEGER NOT NULL REFERENCES set_slot (slot_id),
    menu_id  INTEGER NOT NULL REFERENCES menu (menu_id),
    PRIMARY KEY (slot_id, menu_id)
);

-- 쿠폰 한 종류 (정액 할인)
CREATE TABLE coupon (
    coupon_id   INTEGER     PRIMARY KEY,
    name        TEXT        NOT NULL UNIQUE
                CHECK (name <> '' AND name = btrim(name)),
    amount      INTEGER     NOT NULL CHECK (amount > 0),
    valid_from  TIMESTAMPTZ NOT NULL,
    valid_to    TIMESTAMPTZ NOT NULL,
    CHECK (valid_to > valid_from)
);

-- 쿠폰 발급: 이 회원이 이 쿠폰을 받았다 (같은 쿠폰은 회원당 한 번만 받는다)
CREATE TABLE coupon_issue (
    issue_id   INTEGER     PRIMARY KEY,
    coupon_id  INTEGER     NOT NULL REFERENCES coupon (coupon_id),
    member_id  INTEGER     NOT NULL REFERENCES member (member_id),
    issued_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (coupon_id, member_id)
);

-- 재고 품목 한 가지의 정의 (완제품: 케이크·쿠키, 원재료: 원두·우유·시럽). 남은 양은 store_stock
CREATE TABLE stock_item (
    item_id  INTEGER PRIMARY KEY,
    name     TEXT    NOT NULL UNIQUE
             CHECK (name <> '' AND name = btrim(name)),
    kind     TEXT    NOT NULL CHECK (kind IN ('완제품', '원재료')),
    unit     TEXT    NOT NULL CHECK (unit <> '')
);

-- 메뉴 1개를 만들 때 이 품목을 amount 만큼 쓴다 (완제품은 소요량 1)
CREATE TABLE menu_recipe (
    menu_id  INTEGER NOT NULL REFERENCES menu (menu_id),
    item_id  INTEGER NOT NULL REFERENCES stock_item (item_id),
    amount   INTEGER NOT NULL CHECK (amount > 0),
    PRIMARY KEY (menu_id, item_id)
);

-- 옵션을 1회 고를 때마다 이 품목을 amount 만큼 더 쓴다
CREATE TABLE option_recipe (
    option_id  INTEGER NOT NULL REFERENCES option_item (option_id),
    item_id    INTEGER NOT NULL REFERENCES stock_item (item_id),
    amount     INTEGER NOT NULL CHECK (amount > 0),
    PRIMARY KEY (option_id, item_id)
);
```

**영역 ② 매장(5개 표) — `store`, `store_menu`, `store_stock` 은 새 표, `pickup_slot`, `menu_price` 는 키가 바뀐 표**

```sql
-- 매장 한 곳 (1호점도 가맹점도 한 행). 번호는 대리키
CREATE TABLE store (
    store_id  INTEGER PRIMARY KEY,
    name      TEXT    NOT NULL UNIQUE
              CHECK (name <> '' AND name = btrim(name))
);

-- 이 매장 메뉴판에 오른 메뉴. is_active 는 지금 이 매장에서 파는가
CREATE TABLE store_menu (
    store_id   INTEGER NOT NULL REFERENCES store (store_id),
    menu_id    INTEGER NOT NULL REFERENCES menu (menu_id),
    is_active  BOOLEAN NOT NULL DEFAULT TRUE,
    PRIMARY KEY (store_id, menu_id)
);

-- 매장별 재고: 이 매장에 이 품목이 qty 만큼 남았다
CREATE TABLE store_stock (
    store_id  INTEGER NOT NULL REFERENCES store (store_id),
    item_id   INTEGER NOT NULL REFERENCES stock_item (item_id),
    qty       INTEGER NOT NULL CHECK (qty >= 0),
    PRIMARY KEY (store_id, item_id)
);

-- 픽업 시간대(슬롯) 하나: 매장마다 따로 정원과 받은 주문 수 (주문 1건이 정원 1)
CREATE TABLE pickup_slot (
    slot_start  TIMESTAMPTZ NOT NULL,
    capacity    INTEGER     NOT NULL CHECK (capacity >= 0),
    reserved    INTEGER     NOT NULL DEFAULT 0 CHECK (reserved >= 0),
    store_id    INTEGER     NOT NULL REFERENCES store (store_id),
    PRIMARY KEY (store_id, slot_start),
    CHECK (reserved <= capacity)
);

-- 매장별 메뉴 가격의 유효 기간 (valid_to 가 NULL 이면 끝나는 때가 정해지지 않은 행이다)
CREATE TABLE menu_price (
    menu_id     INTEGER     NOT NULL,
    valid_from  TIMESTAMPTZ NOT NULL,
    valid_to    TIMESTAMPTZ,
    price       INTEGER     NOT NULL CHECK (price >= 0),
    store_id    INTEGER     NOT NULL,
    PRIMARY KEY (store_id, menu_id, valid_from),
    FOREIGN KEY (store_id, menu_id) REFERENCES store_menu (store_id, menu_id),
    CHECK (valid_to IS NULL OR valid_to > valid_from),
    EXCLUDE USING gist (store_id WITH =, menu_id WITH =,
                        tstzrange(valid_from, valid_to) WITH &&)
);
```

**영역 ③ 주문(5개 표) — `orders` 만 바뀌고 줄·옵션·픽·할인·포인트 원장 표는 v6 와 같다**

```sql
-- 주문 한 건: 어느 매장의 주문인가(store_id). 픽업 슬롯은 같은 매장의 슬롯이어야 한다
CREATE TABLE orders (
    order_id      INTEGER     PRIMARY KEY,
    member_id     INTEGER     REFERENCES member (member_id),
    ordered_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    payment       TEXT        NOT NULL CHECK (payment IN ('카드', '현금')),
    barista       TEXT        NOT NULL,
    status        TEXT        NOT NULL DEFAULT '접수'
                  CHECK (status IN ('접수', '제조중', '완료', '픽업', '취소')),
    member_grade  TEXT        REFERENCES membership_grade (grade),
    pickup_start  TIMESTAMPTZ,
    store_id      INTEGER     NOT NULL REFERENCES store (store_id),
    CHECK (member_id IS NOT NULL OR member_grade IS NULL),
    FOREIGN KEY (store_id, pickup_start) REFERENCES pickup_slot (store_id, slot_start)
);

-- 주문 안의 한 줄 (menu_name, unit_price 는 주문한 그때의 값을 복사한 것)
CREATE TABLE order_line (
    order_id    INTEGER NOT NULL REFERENCES orders (order_id),
    line_no     INTEGER NOT NULL CHECK (line_no >= 1),
    menu_id     INTEGER NOT NULL REFERENCES menu (menu_id) ON DELETE RESTRICT,
    quantity    INTEGER NOT NULL CHECK (quantity >= 1),
    menu_name   TEXT    NOT NULL CHECK (menu_name <> ''),
    unit_price  INTEGER NOT NULL CHECK (unit_price >= 0),
    PRIMARY KEY (order_id, line_no)
);

-- 라인에 붙은 옵션 한 가지와 그 횟수 (option_name, unit_price 도 그때의 값)
CREATE TABLE order_line_option (
    order_id     INTEGER NOT NULL,
    line_no      INTEGER NOT NULL,
    option_id    INTEGER NOT NULL REFERENCES option_item (option_id) ON DELETE RESTRICT,
    option_qty   INTEGER NOT NULL DEFAULT 1 CHECK (option_qty >= 1),
    option_name  TEXT    NOT NULL CHECK (option_name <> ''),
    unit_price   INTEGER NOT NULL CHECK (unit_price >= 0),
    PRIMARY KEY (order_id, line_no, option_id),
    FOREIGN KEY (order_id, line_no) REFERENCES order_line (order_id, line_no)
);

-- 세트 라인이 슬롯마다 고른 메뉴 (menu_name 은 그때의 이름)
CREATE TABLE order_line_pick (
    order_id   INTEGER NOT NULL,
    line_no    INTEGER NOT NULL,
    slot_id    INTEGER NOT NULL,
    menu_id    INTEGER NOT NULL,
    menu_name  TEXT    NOT NULL CHECK (menu_name <> ''),
    PRIMARY KEY (order_id, line_no, slot_id),
    FOREIGN KEY (order_id, line_no) REFERENCES order_line (order_id, line_no),
    FOREIGN KEY (slot_id, menu_id)  REFERENCES set_slot_menu (slot_id, menu_id)
                                    ON DELETE RESTRICT
);

-- 주문에 적용된 할인 한 건 (amount 는 그때 계산된 할인액)
CREATE TABLE order_discount (
    order_id     INTEGER NOT NULL REFERENCES orders (order_id),
    discount_no  INTEGER NOT NULL CHECK (discount_no >= 1),
    kind         TEXT    NOT NULL CHECK (kind IN ('쿠폰', '등급')),
    issue_id     INTEGER UNIQUE REFERENCES coupon_issue (issue_id),
    amount       INTEGER NOT NULL CHECK (amount > 0),
    PRIMARY KEY (order_id, discount_no),
    CHECK ((kind = '쿠폰') = (issue_id IS NOT NULL))
);

-- 한 주문에 등급 할인은 한 번만
CREATE UNIQUE INDEX order_discount_grade_once
    ON order_discount (order_id) WHERE kind = '등급';

-- 포인트 원장: 늘고 주는 내역을 쌓기만 한다 (잔액은 delta 의 합)
CREATE TABLE point_ledger (
    entry_id    INTEGER     PRIMARY KEY,
    member_id   INTEGER     NOT NULL REFERENCES member (member_id),
    reason      TEXT        NOT NULL CHECK (reason IN ('적립', '사용', '조정')),
    delta       INTEGER     NOT NULL,
    order_id    INTEGER     REFERENCES orders (order_id),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CHECK ((reason = '적립' AND delta > 0)
        OR (reason = '사용' AND delta < 0)
        OR (reason = '조정' AND delta <> 0)),
    CHECK (reason = '조정' OR order_id IS NOT NULL)
);

-- 한 주문에 적립도 사용도 한 번씩만
CREATE UNIQUE INDEX point_ledger_once
    ON point_ledger (order_id, reason) WHERE reason IN ('적립', '사용');
```

**영역 ④ 요약과 색인 — `daily_sales` 가 바뀌고 색인 5개 중 둘이 재정의된다**

```sql
-- 일 매출 요약: 한 행 = 그 매장에 그 날(서울 시각) 들어온 취소 아닌 주문 전체의 합
CREATE TABLE daily_sales (
    sales_date    DATE        NOT NULL,
    order_count   INTEGER     NOT NULL CHECK (order_count >= 0),
    subtotal      BIGINT      NOT NULL CHECK (subtotal >= 0),
    discount      BIGINT      NOT NULL CHECK (discount >= 0),
    refreshed_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    store_id      INTEGER     NOT NULL REFERENCES store (store_id),
    PRIMARY KEY (store_id, sales_date),
    CHECK (discount <= subtotal)
);

-- 매장의 기간별 주문 (일 매출 집계, 기간 조회)
CREATE INDEX orders_store_ordered_idx ON orders (store_id, ordered_at);

-- 회원의 최근 주문 (orders.member_id 외래키의 인덱스를 겸한다)
CREATE INDEX orders_member_ordered_idx ON orders (member_id, ordered_at);

-- 매장의 처리 중인 주문만 (주방 화면)
CREATE INDEX orders_open_idx ON orders (store_id, ordered_at)
    WHERE status IN ('접수', '제조중');

-- 회원의 포인트 잔액 (point_ledger.member_id 외래키)
CREATE INDEX point_ledger_member_idx ON point_ledger (member_id);

-- 회원의 쿠폰함 (coupon_issue.member_id 외래키)
CREATE INDEX coupon_issue_member_idx ON coupon_issue (member_id);
```

- 생성 순서(네 블록 순서): ① 브랜드 공통(`stock_item` 은 `menu_recipe`·`option_recipe` 보다 앞) → ② `store` → `store_menu`·`store_stock` → `pickup_slot` → `menu_price`(`store_menu` 필요) → ③ `orders`(`pickup_slot` 필요) → 줄·옵션·픽·할인·원장 → ④ `daily_sales`(`store` 필요) → 색인.
- **열 순서 약속**: 기존 표에 더한 `store_id` 는 모두 **열 목록의 끝**에 둔다(`ADD COLUMN` 이 끝에 붙이므로 이전본과 처음부터 만든 표의 열 순서가 같다). 키에서의 순서(`PRIMARY KEY (store_id, ...)`)는 별개다.
- 관계: `store` 1 — N `store_menu` N — 1 `menu`, `store_menu` 1 — N `menu_price`(복합 외래키 `(store_id, menu_id)`), `store` 1 — N `store_stock` N — 1 `stock_item`, `store` 1 — N `pickup_slot`, `pickup_slot` 1 — N `orders`(복합 외래키 `(store_id, pickup_start)`, 선택적 — `pickup_start` 가 NULL 이면 검사하지 않으므로 `orders.store_id → store` 외래키가 **따로** 있다), `store` 1 — N `orders`, `store` 1 — N `daily_sales`. 나머지는 v6 와 같다. `menu_price` 의 `menu_id → menu` 외래키는 `store_menu` 를 거치는 복합 외래키가 대신해 사라졌다.
- 자동 생성 제약·색인 이름(PostgreSQL 18.4 에서 확인): `store_pkey`, `store_name_key`, `store_name_check`, `store_menu_pkey`, `store_menu_store_id_fkey`, `store_menu_menu_id_fkey`, `store_stock_pkey`, `store_stock_store_id_fkey`, `store_stock_item_id_fkey`, `store_stock_qty_check`(재고 음수 오류 이름이 `stock_item_qty_check` 에서 바뀐다), `pickup_slot_pkey`, `pickup_slot_store_id_fkey`, `pickup_slot_check`(그대로), `menu_price_pkey`, `menu_price_store_id_menu_id_fkey`, **`menu_price_store_id_menu_id_tstzrange_excl`**(EXCLUDE; 겹침 오류 이름이 `menu_price_menu_id_tstzrange_excl` 에서 바뀐다), `menu_price_check`(그대로), `orders_store_id_fkey`, **`orders_store_id_pickup_start_fkey`**(복합; 옛 `orders_pickup_start_fkey` 는 사라진다), `daily_sales_pkey`, `daily_sales_store_id_fkey`.
- 색인 이름: `orders_store_ordered_idx`(새), `orders_open_idx`(`(store_id, ordered_at)` 로 재정의, 이름 유지), `orders_member_ordered_idx`·`point_ledger_member_idx`·`coupon_issue_member_idx`(그대로), `orders_ordered_at_idx`(삭제).

### v6 → v7 이전 스크립트 (기존 데이터 보존, 확장 → 이전 → 축소, PostgreSQL 18.4 로 검증)

단계마다 **옛 앱(v6)과 새 앱(v7)이 모두 동작**해야 한다. 실행 순서는 1단계 → 2단계(새 앱 배포 뒤) → 3단계 → 4단계이고, **`CREATE INDEX CONCURRENTLY` 와 `DROP INDEX CONCURRENTLY` 는 트랜잭션 블록 밖에서 한 문장씩 실행**한다(그래서 한 파일을 통째로 `BEGIN ... COMMIT` 에 넣지 못한다). 2호점 데이터는 **4단계의 기본키 교체가 끝난 뒤에만** 넣을 수 있다(옛 기본키·옛 `EXCLUDE` 가 2호점 행을 거부한다). 기존 행은 모두 1호점이 된다.

**1단계 확장** — 더하기만 한다. 옛 앱은 그대로 동작한다.

```sql
BEGIN;
-- 새 표 셋은 v7 DDL 그대로 만든다 (store, store_menu, store_stock)
-- 매장 한 곳 (1호점도 가맹점도 한 행). 번호는 대리키
CREATE TABLE store (
    store_id  INTEGER PRIMARY KEY,
    name      TEXT    NOT NULL UNIQUE
              CHECK (name <> '' AND name = btrim(name))
);
INSERT INTO store (store_id, name) VALUES (1, '동백커피 1호점');

-- 이 매장 메뉴판에 오른 메뉴. is_active 는 지금 이 매장에서 파는가
CREATE TABLE store_menu (
    store_id   INTEGER NOT NULL REFERENCES store (store_id),
    menu_id    INTEGER NOT NULL REFERENCES menu (menu_id),
    is_active  BOOLEAN NOT NULL DEFAULT TRUE,
    PRIMARY KEY (store_id, menu_id)
);
INSERT INTO store_menu (store_id, menu_id, is_active)
SELECT 1, menu_id, is_active FROM menu;

-- 매장별 재고: 이 매장에 이 품목이 qty 만큼 남았다
CREATE TABLE store_stock (
    store_id  INTEGER NOT NULL REFERENCES store (store_id),
    item_id   INTEGER NOT NULL REFERENCES stock_item (item_id),
    qty       INTEGER NOT NULL CHECK (qty >= 0),
    PRIMARY KEY (store_id, item_id)
);

-- 새 열: 옛 앱이 몰라도 동작하게 (orders 는 NULL 허용, 작은 표는 상수 기본값)
ALTER TABLE orders ADD COLUMN store_id INTEGER;
ALTER TABLE pickup_slot
```

**2단계 이전 ②** — 점검 시간: 주문 접수를 멈추고 → 재고 수량을 1호점 몫으로 복사하고 → 재고 경로를 `store_stock` 으로 전환하고 → 주문을 다시 받는다. **2단계 ①에서 배포한 새 앱도 이 전환 전까지는 재고를 `stock_item.qty` 로 다룬다**(`store_stock` 은 비어 있다). `LOCK` 은 복사하는 동안의 쓰기만 막고, 복사와 전환 사이의 틈은 주문 중지가 덮는다(무중단 대안은 이중 쓰기).

```sql
-- 점검 시간: 주문 접수를 멈춘 상태에서 재고 수량을 1호점 몫으로 복사한다
-- (LOCK 은 복사하는 동안의 쓰기만 막는다. 복사 뒤 재고 경로를 store_stock 으로
--  전환하고 주문을 다시 받는다)
BEGIN;
LOCK TABLE stock_item IN SHARE ROW EXCLUSIVE MODE;
INSERT INTO store_stock (store_id, item_id, qty)
SELECT 1, item_id, qty FROM stock_item;
COMMIT;
```

**3단계 조이기 ①** — `NOT NULL`(CHECK → NOT VALID → VALIDATE → SET NOT NULL, PostgreSQL 12 부터 스캔 생략), 외래키, 이전용 기본값 거두기. **채우기가 끝난 뒤에** 건다.

```sql
-- NOT NULL: CHECK 를 NOT VALID 로 걸고, 검증하고, SET NOT NULL 뒤 CHECK 를 지운다
ALTER TABLE orders
    ADD CONSTRAINT orders_store_id_nn CHECK (store_id IS NOT NULL) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_store_id_nn;
ALTER TABLE orders ALTER COLUMN store_id SET NOT NULL;
ALTER TABLE orders DROP CONSTRAINT orders_store_id_nn;
-- 외래키도 NOT VALID 로 걸고 나중에 검증한다
ALTER TABLE orders ADD CONSTRAINT orders_store_id_fkey
    FOREIGN KEY (store_id) REFERENCES store (store_id) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_store_id_fkey;
-- 이전용 기본값은 거둔다: 앞으로 store_id 를 빠뜨리면 오류가 나야 한다
ALTER TABLE pickup_slot ALTER COLUMN store_id DROP DEFAULT;
ALTER TABLE menu_price ALTER COLUMN store_id DROP DEFAULT;
ALTER TABLE daily_sales ALTER COLUMN store_id DROP DEFAULT;
```

**3단계 조이기 ②** — 새 유일 인덱스와 조회 인덱스를 `CONCURRENTLY` 로(BEGIN 밖, 한 문장씩).

### v7 설계 결정과 한계 (근거는 본문 화면 번호)

- **표의 매장 범위**(화면 2): 세 질문으로 가른다 — 값이 매장마다 달라지거나 한 매장의 사건이면 **매장 소유**, 부모를 따라가면 매장을 알면 **상속**, 나머지는 **브랜드 공통**. 매장 소유: `orders`, `menu_price`, `pickup_slot`, `daily_sales`, 재고 수량(`store_stock`), 새 표 `store_menu`. 상속: `order_line`, `order_line_option`, `order_line_pick`, `order_discount`. 브랜드 공통: 나머지 14개(`stock_item` 의 정의 부분 포함). 애매한 `point_ledger`(주체는 회원), `menu_recipe`·`option_recipe`(메뉴의 성질), `option_item`(가격 이력 없음, 매장 공통)은 브랜드 공통.
- **자식 표에 `store_id` 를 넣지 않는다**(화면 2): `order_id → store_id` 이므로 줄 표에 넣으면 기본키 `(order_id, line_no)` 의 일부에만 종속하는 열(부분 종속, 3장). 대안(대각선 외래키: `orders UNIQUE (order_id, store_id)` + 줄 표 `(order_id, store_id)`·`(store_id, menu_id)` 복합 외래키)은 서버에서 동작을 확인했고(잘못된 매장 줄 거부 `line_x_order_id_store_id_fkey`, 취급하지 않는 메뉴 거부 `line_x_store_id_menu_id_fkey`) 접힌 상자로 소개만 한다. 매장 일치는 앱(주문 생성 트랜잭션)이 지킨다.
- **C15 의 재해석(커리큘럼 문구와 달라진 점)**(화면 3): 커리큘럼은 "`menu` → `menu` + `store_menu` 분리 실습"이었으나 6장이 `menu.price` 를 `menu_price`(이력)로 옮겼으므로 쪼갤 가격 열이 `menu` 에 없다. 가격의 집이 `menu_price` 한 곳이라는 6장 결정을 지키려고 **`menu_price` 에 `store_id` 를 넣어 매장별 가격 이력**으로 풀고, `store_menu` 는 "이 매장 메뉴판에 있고 지금 파는가"(가격 아닌 사실)를 담는다. 기각한 대안: `store_menu.price` 열(이력 상실, 6장이 지운 중복이 부활), 본사 기본가 + 매장 예외(기본키 열은 NULL 불가, 조회가 "예외 없으면 기본" 이중화). **브랜드 일괄 가격은 NULL `store_id` 가 아니라 매장마다 명시한 행**이며 본사 일괄 인상은 `INSERT ... SELECT FROM store_menu` 한 문장(실행 확인, 겹침 방지가 매장별로 동작: 한 매장 인상이 다른 매장에 영향 없음). `menu.is_active` 는 브랜드 단종으로 남기고 `store_menu.is_active` 가 매장 판매 여부(이전 시 1호점 값은 `menu.is_active` 복사).
- **진짜 표 분리는 `stock_item`**(화면 10): `item_id → name, kind, unit` 과 `(store_id, item_id) → qty` 가 섞여 있어(키에 매장이 들어오면 부분 종속) `stock_item`(정의, 브랜드) + `store_stock`(수량, 매장)으로 쪼갠다. 대안 `stock_item PK (store_id, item_id)` 는 이름·단위가 매장마다 복사되고 레시피가 가리킬 유일 키가 사라져 기각. **수량은 계속 변하는 값이라** 복사와 새 앱 전환 사이의 차감이 새 표에 없다 → 이 교재는 **짧은 점검 시간**(주문 접수 중지 → `LOCK TABLE ... SHARE ROW EXCLUSIVE MODE` 아래에서 복사 → 재고 경로를 `store_stock` 으로 전환 → 재개)을 택하고 무중단 대안(이중 쓰기·트리거)은 설명만 한다. 2단계 ①에서 배포한 새 앱도 전환 전까지 재고는 `stock_item.qty` 로 다룬다. `LOCK` 은 복사하는 동안 다른 연결의 `UPDATE` 를 대기시키고 `SELECT` 는 통과시킨다(실행 확인)는 것뿐이고, 복사와 전환 사이의 틈은 주문 중지가 덮는다. `DROP COLUMN qty` 가 이전의 유일한 **비가역** 단계.
- **회원은 브랜드 전체**(화면 4): 근거 ① 포인트 원장(잔액 = 회원의 합)·등급·쿠폰 발급이 이미 회원 단위(하윤의 "어느 매장에서든 포인트") ② 한 사람 한 행(전화번호 `UNIQUE` 유지, 매장 소속이면 같은 사람이 매장 수만큼 행) ③ 되돌리기 쉬움(주 이용 매장 열은 나중에 더하면 된다). 대가: 8장의 회원 락이 **같은 회원이 두 매장에서 동시에 주문하면 서로 기다린다**(실행 확인, 의도한 직렬화). 쿠폰·포인트·등급·옵션 가격의 매장 범위는 브랜드 전체. 매장 한정 쿠폰(`coupon_store` 연결 표), 매장 간 포인트 정산, 매장별 옵션 가격은 **만들지 않았고 한계**다. 멀티테넌시 대안(매장별 DB·스키마)은 접힌 상자(반대 의견).
- **주문·줄의 기본키는 바꾸지 않는다**(화면 9): `order_id` 가 이미 전체에서 유일한 대리키다. `(store_id, order_id)` 로 가면 `order_line`, `order_line_option`, `order_line_pick`, `order_discount`, `point_ledger.order_id` 모두에 `store_id` 열과 복합 외래키가 연쇄한다. 영수증의 매장별 번호가 필요해지면 `orders.store_no` + `UNIQUE (store_id, store_no)`(만들지 않음).
- **파티셔닝은 하지 않기로 결정**(화면 9, 7장 `.later` 상환): 기본키에 분할 열이 들어가야 하고(`unique constraint on partitioned table must include all partitioning columns`, 실행 확인) 자식 외래키가 막히는(`there is no unique constraint matching given keys for referenced table`) 변경이라 자식 5개 표를 건드리는 위 "기본키 안 바꾸는 이유"와 같은 연쇄다. 수백만~수천만 행은 7장 인덱스·요약으로 충분하고 보관 정책이 아직 없으며, 필요해지면 화면 9 의 5걸음을 반복하되 파티션 표로의 이전은 새 표를 만들어 옮기는 별도 작업.
- **기본키 교체 순서**(화면 9): `store_id` 열 → 새 유일 인덱스 `CONCURRENTLY` → **새 외래키를 옛 것과 나란히 `NOT VALID` → `VALIDATE`**(외래키는 유일 인덱스만 있으면 걸린다, 실행 확인) → `DROP CONSTRAINT 옛_pkey, ADD CONSTRAINT 옛_pkey PRIMARY KEY USING INDEX 새_인덱스` 한 문장(키 없는 순간 없음, 인덱스 이름이 제약 이름으로 바뀜) → 옛 외래키·옛 `EXCLUDE` 삭제. 의존 외래키가 있는 기본키를 그냥 지우면 `ERROR: cannot drop constraint pickup_slot_pkey on table pickup_slot because other objects depend on it`(실행 확인). **`EXCLUDE` 는 예외**: `NOT VALID` 불가(`ERROR: EXCLUDE constraints cannot be marked NOT VALID`)·`CONCURRENTLY` 없음 → 표 락을 쥐고 만든다. `menu_price` 는 수십 행이라 그냥 건다(수백만 행이면 점검 창).
- **열 추가·채우기**(화면 7): PostgreSQL 11 부터 **상수** `DEFAULT` 는 재작성이 없다(실측 2ms, 파일 번호 불변), 휘발성 기본값(`random()`)은 재작성(4,601ms, 130→178MB). 전 행 `UPDATE` 는 200만 행에서 16.3초, 표 130→291MB·인덱스 146→292MB. 10만 행씩 21번 + 사이마다 `VACUUM` 은 합 19.3초, 한 번 최대 0.92초, 최종 168MB. `orders` 는 일부러 일반 경로(NULL 허용 열 → 채우기 → 조이기)를 쓴다: 값이 행마다 다른 경우의 표준 경로이고, `DEFAULT 1` 을 달고 배포하면 새 앱의 `store_id` 누락이 조용히 1호점 매출이 되는 것을 피한다. 작은 표 셋은 상수 `DEFAULT` 지름길 + 3단계에서 `DROP DEFAULT`.
- **`NOT NULL` 은 CHECK 를 거쳐서**(화면 7): `CHECK (col IS NOT NULL) NOT VALID`(순간) → `VALIDATE CONSTRAINT`(2M 행 1,784ms, 락 `SHARE UPDATE EXCLUSIVE` 라 쓰기 통과) → `SET NOT NULL`(1ms, `debug1` 알림 `existing constraints on column "orders.store_id" are sufficient to prove that it does not contain nulls`, PostgreSQL 12 부터). 증거 CHECK 없이 곧장 `SET NOT NULL` 은 1,547ms 스캔(`verifying table "orders"`) 동안 `ACCESS EXCLUSIVE`. 함정: **채우기 전에** `NOT VALID` CHECK 를 걸면 옛 행의 아무 열 `UPDATE` 가 `23514`(`new row for relation "orders" violates check constraint "orders_store_id_nn"`)로 거부되어(6장 화면 8 의 경고가 실제가 됨) 순서는 확장 → 새 앱 → 채우기 → 제약. (PostgreSQL 18 에는 `ADD CONSTRAINT ... NOT NULL col NOT VALID` 문법이 있음을 실행 확인했지만 교재는 12 이상에서 되는 CHECK 경유를 쓴다.)
- **`lock_timeout`**: 이전 스크립트는 단계마다 `SET lock_timeout = '2s'` 를 건 세션에서 실행하는 것을 전제로 한다(스크립트 파일에는 넣지 않았다. 화면 6 본문이 이 전제를 적는다).
- **락 거동**(화면 5·7·8, 200만 행·연결 셋): 연결 A 가 읽기 트랜잭션을 연 채 B 가 `ALTER TABLE orders ADD COLUMN` 하면 B 는 `AccessExclusiveLock` 대기, **뒤에 온 C 의 단순 `SELECT` 도 `AccessShareLock` 대기**(`pg_locks.granted = false`). `SET lock_timeout = '2s'` 면 2.0초 뒤 `ERROR 55P03: canceling statement due to lock timeout` 이고 C 가 풀린다. 락 모드 실측: `ADD COLUMN`·`ADD CONSTRAINT CHECK ... NOT VALID` 는 `ACCESS EXCLUSIVE`(순간, 스캔 없음), FK `NOT VALID` 는 `SHARE ROW EXCLUSIVE`(양 표), `CREATE INDEX` 는 `SHARE`(쓰기 대기), `CREATE INDEX CONCURRENTLY` 는 `SHARE UPDATE EXCLUSIVE`, `VALIDATE`(CHECK·FK)는 `SHARE UPDATE EXCLUSIVE`. 8장 `ALTER TABLE orders ADD COLUMN pickup_start TIMESTAMPTZ REFERENCES pickup_slot (slot_start)` 는 2ms 에 끝나지만 `orders` `ACCESS EXCLUSIVE` + `SHARE ROW EXCLUSIVE`, `pickup_slot` `SHARE ROW EXCLUSIVE` 를 잡는다(8장 `.later` 상환).
- **인덱스**(화면 8): `CREATE INDEX` 840ms(그동안 `INSERT` 대기 약 540ms) vs `CONCURRENTLY` 940ms(대기 없음). `BEGIN` 안에서는 `ERROR 25001: CREATE INDEX CONCURRENTLY cannot run inside a transaction block`. 실패하면 무효 인덱스가 남는다(`could not create unique index "orders_dup_idx"`, `pg_index.indisvalid = false`, 직접 `DROP`). 교체는 새 이름으로 만들고 옛 것을 지우고 `RENAME`. `orders_ordered_at_idx` 를 지운 뒤에도 PostgreSQL 18 의 **skip scan** 으로 `store_id` 조건 없는 기간 조회가 `orders_store_ordered_idx` 를 쓴다(`Index Searches: 4`; 17 이하는 재어 보지 않음). FK 인덱스 판단(7장 기준): 새 표들은 기본키 선두 열이 `store_id` 라 덮여 있고 `store_stock.item_id` 는 만들지 않는다(품목을 지우지 않는다).
- **되돌리기**(화면 11): 1단계는 down 스크립트로 완전히 되돌아간다(실행 확인: 열·제약이 v6 와 같음). 2·3단계도 가역(단, `store_stock` 을 비워 되돌리는 것은 재고 경로 전환 전까지, 기본키 교체를 거꾸로 하는 것은 2호점 행이 들어오기 전까지), **4단계 `DROP COLUMN qty` 만 비가역**(`RENAME COLUMN` 으로 늦추는 길). 기록표 `schema_migration(version PK, applied_at)` 의 기본키가 중복 적용을 막는다(`schema_migration_pkey` 위반 실행 확인). 도구는 파일을 트랜잭션으로 감싸므로 `CONCURRENTLY` 는 트랜잭션 밖 설정이 필요.
- **교재의 검증 환경**: 진짜 PostgreSQL 18.4(Windows, `embedded-postgres`), 연결 셋 이상, 락 대기는 `pg_stat_activity`·`pg_locks`, 200만 행 합성 `orders` 로 시간 측정(1회 측정이라 절대값보다 자릿수를 본다). 못 한 것: PostgreSQL 17 이하 비교(skip scan 부재), 수천만 행 이상, 실제 앱과의 옛·새 공존 시나리오(서버 두 대), `pg_upgrade`·복제 환경.

### 8장 주문 생성 트랜잭션이 v7 에서도 성립하는가

성립한다(화면 10). 골격(회원 `FOR UPDATE` → 주문·줄·옵션 → C1 줄 수 확인 → 재고 조건부 차감 → 슬롯 → 할인 → 포인트)과 **락 순서(회원 → 주문 행 → 재고 번호 순 → 슬롯)는 그대로**. 바뀌는 곳은 ② `orders` 에 `store_id`·가격 조회에 `p.store_id = ?`(그 매장에 가격이 없는 메뉴는 줄이 안 만들어져 C1 확인에서 취소), ④ `store_stock ... WHERE store_id = ? AND item_id = ? AND qty >= n`, ⑤ `pickup_slot ... WHERE store_id = ? AND slot_start = ?`. 필요량 조회(레시피)·할인·포인트는 그대로. 취소 트랜잭션(8장 화면 14)도 같은 곳에 `store_id`. 서버 실험: 같은 매장의 마지막 케이크를 두 주문이 동시에 줄이면 둘째가 락 대기 뒤 영향 행 0(C13), 다른 매장의 같은 품목은 서로 기다리지 않고, 같은 회원은 매장을 가로질러 회원 락에서 줄을 선다. 8장 본문의 `stock_item`·`slot_start` 조건 문장은 v6 시점의 것으로 두고 9장이 바뀐 곳을 보인다(8장은 고치지 않는다).
