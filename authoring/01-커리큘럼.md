# DB 설계 학습 교재 커리큘럼 · 학습 스케줄

전제: `00-기획.md` 의 시나리오("동백커피"), 스키마 버전(v1~v7), 빚(D1~D5), 제약조건 표(C1~C17)를 따른다.
화면 수와 시간은 집필의 계약이다. 마지막 화면은 항상 요약·퀴즈·직접 해보기이며 화면 수에 포함한다.

## 1. 장 구성 원칙 — 설계 판단을 먼저, 운영은 설계를 흔드는 만큼만

일반적인 DB 책은 정규화 이론을 먼저 세우고 예제를 붙인다. 이 교재는 **고통 → 모델링 → 검증 → 강제 → 확장**
순서로 간다. 정규화 용어를 몰라도 엑셀 표의 이상현상은 누구나 겪을 수 있고,
ER 모델링으로 한번 설계해 본 사람만 정규화가 "검증 도구"라는 것을 체감하기 때문이다.

```
엑셀 한 장의 고통 (1장)
  → 요구사항에서 테이블 뽑기: 엔터티·키·관계 (2장)            v1
  → 정규화로 검증·교정 (3장)                                   v2
  → 규칙을 DB 제약으로 강제, 못 하는 것 구분 (4장)            v3
  ↑ 여기까지 "기본 이론" — 요구사항이 단순한 1호점
  ↓ 여기부터 "요구사항이 바뀔 때" — 새 요구가 설계를 깬다
  → 옵션·세트: 변형이 폭발할 때 (5장)                          v4  요구1
  → 가격 변경·쿠폰·멤버십: 과거를 지키기 (6장)                 v5  요구2
  ↓ 여기부터 "운영에서 설계가 깨진다"
  → 데이터가 커질 때: 인덱스와 의도적 비정규화 (7장)
  → 동시에 들어올 때: 트랜잭션과 제약 (8장)                    v6  요구3
  → 가게가 늘어날 때: 스키마를 데이터째 바꾸기 (9장)          v7  요구4
  → 언제 깨고, 언제 쓰지 말까 (10장)
```

**이 순서의 대가**: 2~4장의 스키마는 정규화·제약 관점에서 옳지만 요구사항을 못 담는 채로 남는다(D1~D5).
독자는 "규칙대로 했는데 왜 깨지지?"를 겪는다. 각 장에 "N장에서 다시 볼 문제" 표시를 남기고
5·6·7·8·9장이 그 빚을 실제로 갚는다.

## 2. 장별 상세

각 장의 형식은 같다: **문제 상황 → 겪기 → 개념과 이름 → 설계·수정 → 한계와 반대의견 → 요약 → 퀴즈 → 직접 해보기.**

### 0장 — 이 교재를 읽는 방법과 동백커피 이야기
- 교재 사용법(화면 넘김, 접힌 상자, 퀴즈), 이 교재가 SQL 교재가 아니라는 것, PostgreSQL 기준이라는 것
- 동백커피와 서연·지호·하윤, 초기 업무 흐름(주문 → 제조 → 픽업 → 정산)
- **DB 개념 지도**: DB·DBMS·스키마·테이블·행/열·키·제약·인덱스·트랜잭션이 각각 무엇인지 한 줄씩, 그리고 어느 장에서 깊게 다루는지 (이름표만 붙이는 화면. 깊은 설명은 각 장)
- 표(테이블)를 읽는 법: 행·열·타입, 엑셀 시트와의 차이
- 최소 SQL ① `CREATE TABLE`·타입·`PRIMARY KEY` 읽기
- 최소 SQL ② `SELECT`·`WHERE`·`JOIN` 읽기 (쓰는 법이 아니라 **읽는** 법)
- 최소 SQL ③ `INSERT`/`UPDATE`/`DELETE`, 트랜잭션이 있다는 것만
- 요약 · 퀴즈(SQL 읽기) · 학습 트랙 고르기

### 1장 — 엑셀 한 장의 고통: 나쁜 설계와 이상현상
- 서연의 엑셀 주문표 실물(주문일시·고객·전화·메뉴·가격·수량·합계·결제수단·바리스타가 한 줄)
- 서연이 원하는 "메뉴별 매출" 뽑기가 왜 아픈가(하윤은 후반 등장)
- 갱신 이상: 고객 전화번호를 고쳤더니 어떤 행은 그대로(단가 정정도 같은 구조. 가격 *인상* 이력 문제는 6장의 몫이라 여기서 다루지 않는다)
- 삽입 이상: 아직 안 팔린 신메뉴를 등록할 자리가 없다
- 삭제 이상: 마지막 주문을 지웠더니 메뉴 정보까지 사라진다
- **위젯 — 이상현상 시뮬레이터**: 표에서 눌러 가며 세 가지를 직접 재현
- 표기 흔들림: "아메리카노 / 아메 / 끝 공백 / 오타" (무결성 문제. 온도 같은 옵션은 5장 요구라 여기서 쓰지 않는다)
- 원인: 한 표에 **여러 종류의 사실**이 섞였다
- 사실별로 쪼개 보기(직관으로 표 4개) · 쪼갠 표를 키로 다시 잇기(`JOIN` 의 필요)
- 한계: 엑셀이 더 나은 경우, 쪼개기가 늘 옳은 것은 아니다

### 2장 — 테이블 나누기: 엔터티·키·관계
- 요구사항 문장에서 명사·동사 뽑기
- 엔터티와 속성 후보, 무엇이 엔터티인가(속성과 엔터티의 경계)
- 후보키와 기본키 · 자연키 vs 대리키(주민번호·전화번호는 왜 키로 위험한가). PK·UNIQUE 는 DB 가 인덱스를 자동으로 만든다는 사실을 한 줄로 알리고 "인덱스는 7장에서" 예고
- 관계와 카디널리티: 1:N
- N:M 과 연결 테이블(주문 ↔ 메뉴)
- 1:1 과 선택적 관계
- 외래키와 참조 무결성 (C++ 포인터 비유와 그 한계). FK 컬럼은 자동으로 인덱스가 생기지 않는다는 것을 예고(7장)

### 3장 — 정규화: 나눈 설계를 검증하는 도구 ← 이 교재의 허리
- v1 에 1장의 세 사고를 다시 시도해 통과하는 것을 보고, 직관 검증의 한계에서 엄밀한 기준으로 넘어간다
- 함수 종속: 뜻 먼저("가격은 메뉴가 정한다"), 이름은 나중에
- 함수 종속 찾는 법: 업무 규칙과 우연의 구별
- 함수 종속으로 후보키 다시 찾기
- 1NF: 원자값(전화번호 목록, "아메리카노 2, 치즈케이크 1" 같은 메뉴 목록 칸). 옵션 문자열은 5장의 요구이므로 여기서 쓰지 않는다
- 1NF 위반 고치기 실습
- 2NF: 부분 종속(복합키의 일부에만 종속). 소재는 1장 시트에 주문번호를 붙인 것
- 3NF: 이행 종속. 분리하면 v1 의 네 표가 되고, 2장이 남긴 `orders.barista` 를 판정한다(주문에 직접 종속이라 위반 아님)
- 파생값을 저장할까: 주문 총액 (**D4**: 저장하지 않기로 결정)
- BCNF 맛보기: 3NF 로 못 잡는 드문 경우 *(선택)*
- 정규화 전 과정 다시 훑기: 1장 시트가 1NF→2NF→3NF 를 거쳐 v1 이 되는 과정
- **정규형 요약표**(정규형 | 규칙 | 위반 신호 | 고치는 법)와 **이상현상 대응표**(1장의 갱신·삽입·삭제 이상이 어느 규칙 위반에서 생기고 어느 단계가 막아 주는가)
- 무손실 분해와 종속 보존의 직관 *(선택)*
- 정규화의 비용(`JOIN`)과 반대 의견: 언제 3NF 에서 멈추는가, 4NF·5NF 는 존재만
- v2 스키마 정본(**표는 v1 과 같다**: 검증 통과 + 총액 미저장 결정) · **"정규화했는데 왜 과거 주문 금액이 위험한가"** (D1 예고)
- 요약 · 퀴즈 · 직접 해보기

### 4장 — 제약조건: 규칙을 DB 에 맡기기
- 규칙은 누가 지키는가: 앱 vs DB, 왜 둘 다 필요한가(앱이 여러 개가 되는 순간)
- **`NULL` 이란 무엇인가**: "값 없음/알 수 없음" ≠ 0 ≠ 빈 문자열, `= NULL` 이 안 통하는 이유, 언제 허용할까
- **데이터 타입 선택도 설계다**: 금액을 `float` 으로 두면 안 되는 이유(`NUMERIC`/정수 원 단위), 시각과 시간대(`timestamptz`), 문자열 길이, 상태값 타입
- `NOT NULL` · `DEFAULT`
- `PRIMARY KEY` · `UNIQUE` (C4)
- `FOREIGN KEY` 와 `ON DELETE` 선택지 (C5, C6)
- `CHECK` (C2)
- 상태값을 어떻게 표현하나: `CHECK` vs 별도 테이블 vs `ENUM` (C7)
- **DB 로 못 막는 규칙**: C1 은 왜 표현할 수 없는가 (**D5**)
- 제약조건 표 정리 (**v3**)

### 5장 — 옵션과 세트: 변형이 폭발하는 메뉴 (요구1)
- 서연의 요구: "샷 추가, 시럽 빼기, 얼음 적게, 휘핑크림, 우유 추가, 그리고 음료+케이크 세트" (v3 가 못 담는다). 옵션마다 가격이 있고 **얼음 적게처럼 가격이 0원인 옵션**도 있으며, 메뉴마다 고를 수 있는 옵션이 다르다
- 옵션이란 무엇인가(업무 용어 먼저)
- 첫 시도: 컬럼 늘리기 → 옵션마다 컬럼, 실패하는 이유
- 두 번째 시도: 옵션 문자열 → 1NF 위반, 집계 불가
- 옵션 그룹 · 옵션 · 메뉴-옵션그룹 연결 모델 (옵션 가격 열. **0원 옵션은 0으로 저장하고 NULL 과 구분한다** — 4장 NULL 화면과 연결)

- 선택 개수 규칙 C9 — DB 로는 어디까지 되나

### 7장 — 데이터가 커질 때: 인덱스와 의도적 비정규화
- 문제: 주문 수백만 건, 하윤의 일 매출 리포트가 20초
- **인덱스란 무엇인가**: DB 는 어떻게 찾는가 — 풀스캔 (C++ `std::vector` 선형 탐색 비유), 책의 색인 비유, 앞장의 PK·UNIQUE 가 인덱스를 겸했다는 회수
- **위젯 — B-tree 탐색 스텝퍼**: 인덱스가 있을 때와 없을 때 읽는 행 수 비교
- 인덱스 종류와 복합 인덱스의 컬럼 순서
- 조회 패턴에서 인덱스 고르기 (리포트·주문 조회·회원 조회). **FK 컬럼 인덱스**(자동으로 안 생긴다)와 **카디널리티(선택도)**: 값 종류가 적은 컬럼에 인덱스가 왜 잘 안 듣는가
- 실행 계획(`EXPLAIN`) 읽는 최소한 *(선택)*
- 인덱스의 비용: 쓰기 느려짐, 공간
- 그래도 느릴 때: **요약 테이블 = 의도적 비정규화**(D4 상환)
